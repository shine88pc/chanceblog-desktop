# 설치 파일·자동 업데이트·릴리스

> **장래 설계(미구현) — 이 문서의 설치 파일(Setup)·자동 업데이트·서명 매니페스트·롤백은 아직 코드로 만들어지지 않았다.**
> 지금의 배포 경로는 [`PACKAGE.md`](PACKAGE.md) 의 개인 PC 제한 시험용 Package(미서명 압축 폴더 — 새 버전은 새로 풀어서 쓴다)와 시험지 [`PERSONAL_PC_TEST.md`](PERSONAL_PC_TEST.md) 뿐이다.

> 2026-10-30 조사(조사 에이전트가 공식 문서·릴리스 API 를 읽은 보고, `chanceblog` 의 `docs/analysis/2026-10-30_desktop-release-update.md`)를 이 저장소에 맞춰 줄인 것이다. **세부 수치는 요약 도구를 거친 것이라 시행 전에 원문과 대조한다.** 결정은 [`DECISIONS.md`](DECISIONS.md) D-04·D-05.

## 방식

**PyInstaller(`--onedir`) + Velopack(파이썬 SDK) + GitHub Releases 초안.** `vpk` 한 번으로 설치 파일(`Setup.exe`)·휴대용 ZIP·차등 업데이트·채널이 나온다. 직접 얹는 것은 둘: **Ed25519 서명 매니페스트**(업데이트 무결성)와 **앱 안의 백업·마이그레이션·롤백**(Velopack 문서에 자동 롤백이 없다). 2순위는 Inno Setup(사용자 단위) + tufup.

## 공개되는 파일(릴리스마다)

`BlogPublisher-Setup-x.y.z.exe` · `BlogPublisher-Portable-x.y.z.zip` · full/delta 패키지 · 채널 매니페스트 · `SHA256SUMS.txt`(+서명) · `CHANGELOG.md` · `MIGRATION_NOTES.md`. 채널은 Stable·Beta·Dev(태그 `vX.Y.Z`, `vX.Y.Z-beta.N`, `vX.Y.Z-dev.N`).

## 릴리스 절차

1. **버전 올리기(AI)**: PR 로 `VERSION`·`CHANGELOG.md`·이관 노트·DB 마이그레이션 갱신 → 시험·CI 통과 → 운영자 병합 → 태그(운영자 승인 뒤에만 만든다. 릴리스 태그는 T3).
2. **Actions 빌드**(`windows-latest`): 시험 → PyInstaller → 자가 점검(`--selftest`) → `vpk pack --channel` → SHA256SUMS + Ed25519 서명 → **초안 릴리스**로 업로드(`--publish` 를 쓰지 않는다).
3. **운영자 공개**: 텔레그램 요청의 안내대로 'Publish release' 한 번. 저장소 설정에서 **불변 릴리스(Enable release immutability)** 를 켜 두면 공개 뒤 자산·태그를 바꿀 수 없다(운영자 설정, T3).
4. **앱의 확인**: 채널별로 확인, 서명 매니페스트의 서명·version·seq·expires 를 검증, 다운그레이드 거부.
5. **다운로드·검증**: Velopack 의 크기·해시 검증 + 서명된 해시 대조. 불일치하면 폐기.
6. **백업 → 적용 → 마이그레이션 → 점검**: SQLite backup API 로 스냅샷 → `apply_updates_and_restart` → 첫 실행에서 `PRAGMA user_version` 순방향 마이그레이션 → 자체 점검 통과 시 '정상' 표식.
7. **롤백**: 점검 실패나 연속 기동 실패 2회면 백업 복원 + 이전 릴리스 재설치(직접 구현·시험). 다운그레이드는 복구 모드에서만.
8. **업데이트 시험**: Actions 에서 (n-1) 설치 → (n) 업데이트 → 롤백 시뮬레이션.

## 워크플로 규칙

기본 권한 전부 차단(`permissions: {}`), 시험 잡은 `contents: read`, 빌드 잡은 환경 시크릿(`environment: release`, 필수 검토자)과 `contents: write`(초안 업로드)만. 액션은 전체 SHA 로 고정, `pip --require-hashes`, `vpk` 버전 = 파이썬 SDK 버전. 시크릿은 자동 `GITHUB_TOKEN` 과 `UPDATE_SIGNING_KEY`(Ed25519 개인키)뿐이다. **업데이트·서명·워크플로·공개키를 바꾸는 PR 은 T3 로 표시하고 승인 전에 병합하지 않는다.**

## 코드 서명

지금은 **무서명으로 시작**한다(유료 인증서는 사지 않는다). 앱이 받은 업데이트 파일에는 '인터넷에서 받음' 표식이 붙지 않아 SmartScreen 창이 뜨지 않고, 경고는 **첫 설치에만** 나온다. **Smart App Control(SAC)이 켜져 있으면 무서명 프로그램이 차단된다** — 먼저 개인 PC 에서 Windows 보안 → 앱 및 브라우저 컨트롤 → 스마트 앱 컨트롤 상태를 확인한다(끄거나 서명 도입). 서명이 필요해지면 SignPath(무료, OSI 라이선스·공개 저장소 등 조건 충족 시, 라이선스는 D-13) → 사업자등록이 있으면 Azure Artifact Signing(월 $9.99) → 인증서 구매 순. 서명해도 SmartScreen 평판은 수 주 걸리므로 1인 도구에서 서명의 실익은 주로 SAC 통과다. 서명하려면 번들 안 모든 PE(.exe/.dll/.pyd)와 제거기까지 서명해야 한다.

## 운영자만 하는 일 / AI 가 하는 일

- **운영자**: GitHub 패스키·2FA, 저장소 설정(불변 릴리스·Environment `release`·태그 보호·Actions 권한), 시크릿 값 입력(`UPDATE_SIGNING_KEY` — 키 생성 스크립트는 AI 가 쓰되 개인키 값은 운영자만 보관), 서명 계정 가입·결제, PC 점검(SAC), 최초 설치(경고 클릭), 릴리스마다 Publish.
- **AI**: 앱·시험·워크플로 PR, 업데이트 클라이언트·서명 검증·백업·마이그레이션·롤백, 릴리스·이관 노트·복구 안내, 의존성 잠금·점검.

## 확인하지 못한 것

Velopack 의 롤백·서명 검증은 '문서에 없음'일 뿐 코드는 미확인(정적 `latest/download` URL 방식 시험 필요), 파이썬 SDK 레퍼런스가 얇음, 설치기 한국어 지원, 토스트 알림용 앱 식별자, PyInstaller 오탐 빈도, 설치 크기·빌드 시간 실측, 서명 서비스의 한국 개인 자격. 점검 시점: 2026-11 말(서명 서비스 지역·자격), 2026-12(Velopack 1.3 정식·파이썬 SDK).

**설치 시험 항목(화면, D-32)**: 설치 파일에 PySide6 와 함께 **JPG·PNG·WebP 를 읽는 Qt 이미지 형식 플러그인**(`PySide6/plugins/imageformats` 의 `qjpeg`·`qwebp`)이 들어갔는지, 설치된 환경에서 `QImageReader.supportedImageFormats()` 에 `jpeg`·`png`·`webp` 가 있는지, 실제 윈도 125%·150% 화면·한글 입력기·화면 읽기 프로그램에서 홈 화면이 잘리지 않는지 확인한다([`UI_IMAGES.md`](UI_IMAGES.md) §4, [`UI_VISUAL_QA.md`](UI_VISUAL_QA.md) §6).

**라이선스 확인(화면, D-32)**: **PySide6(Qt for Python)는 LGPL 이다.** 개발·시험에 쓰는 것은 문제없지만 PySide6 를 설치 파일에 넣어 배포하기 전에는 ① 고지(저작권·라이선스 문구·LGPL 전문·소스를 얻는 방법을 설치 파일·앱 안 '정보' 에 싣기) ② 재배포 조건(사용자가 PySide6·Qt 라이브러리를 바꿔 끼울 수 있게 동적 링크 상태로 두는 것 — 단일 파일로 합치거나 정적으로 묶는 방식은 조건을 따져 봐야 한다) 을 검토해야 한다. 앱 자체의 라이선스가 미정(D-13)이라 그 결정과 함께 정한다.

## 릴리스 노트 규칙 — CHANGELOG 의 새 절과 Release 본문을 같은 글로 (1.0 준비 설계, 2026-11-24 덧붙임)

> **이 절은 설계다 — 아직 아무것도 구현하지 않았다.** 위 배너대로 이 문서의 나머지도 장래 설계이고, 이 절은 v1.0 완료 기준 12번(버전·변경 이력이 화면과 Release 에서 일치)을 채우려는 규칙을 먼저 정해 두는 것이다. 구현(생성 스크립트·워크플로 단계·점검)은 릴리스 갈래와 종합 검증 갈래의 몫이고, `.github` 변경은 T3 라서 운영자 승인 뒤에만 한다. 외부 도구(GitHub·`gh`)에 대한 사실은 이 저장소에서 확인하지 못한 것을 **'확인 필요'** 로 표시했다. 낡은 문장 목록은 [`V1_RELEASE_CHECKLIST.md`](V1_RELEASE_CHECKLIST.md), 사용자 데이터 이관 안내의 틀은 [`MIGRATION_NOTES_TEMPLATE.md`](MIGRATION_NOTES_TEMPLATE.md) 에 있다.

### 1. 어느 쪽이 정본인가 — `CHANGELOG.md` 의 그 버전 절

- **정본은 `CHANGELOG.md` 의 `## [X.Y.Z] — 날짜` 절이다.** Release 본문은 그 절에서 **만들어 내는 글**이고 GitHub 화면에서 손으로 쓰거나 고치지 않는다.
- 이유(위임 규칙의 우선순위로): CHANGELOG 는 저장소 안에 있어 PR 검토·시험·병합 기록이 남고 `VERSION` 과 이미 시험으로 묶여 있다(`test_repo_layout` 의 VersionTest 가 맨 위 절 이름 = `VERSION`). Release 는 저장소 밖(GitHub 서버)이라 검토 없이 고쳐질 수 있고, 불변 릴리스를 켜면 공개한 뒤에는 고칠 수도 없다(위 '릴리스 절차' 3번 — 원문 대조 필요). 그래서 **공개 전에 본문이 맞는지 이쪽에서 확인**해야 한다.
- GitHub 의 '릴리스 노트 자동 생성' 기능은 쓰지 않는다(바깥 서비스가 만든 요약이라 정본과 어긋난다 — 쓸 수 있는지·결과는 확인 필요).

### 2. 1.0.0 부터 CHANGELOG 절의 모양

지금의 CHANGELOG 는 한 줄이 수천 자인 개발 일지다(전체 약 220KB). **그대로는 Release 본문이 될 수 없다**(읽을 사람이 사용자이고 본문 길이 한도도 있다 — GitHub 본문 한도는 확인 필요). 그래서 `1.0.0` 부터 새 절은 **사용자용 릴리스 노트**로 쓰고, 개발 일지 수준의 자세한 내용은 결정 기록(`DECISIONS.md` 의 D 번호)에 둔다. 옛 절(`0.1.0-preview.1`·`0.0.0`)은 지우거나 고치지 않고 그대로 아래에 남긴다.

```text
## [1.0.0] — 2026-MM-DD

### 요약
- 쉬운 한국어 한 줄에 한 가지. 3–10줄. 영문 약어는 풀어 쓴다.

### 자세히
- 사용자에게 보이는 변화를 항목별로(필요한 만큼). 개발 내용은 D 번호로 가리킨다.

### 이관 노트
- 이 버전으로 올릴 때 내 데이터에서 달라지는 것 — 없으면 '달라지는 것 없음'. 있으면 MIGRATION_NOTES 의 같은 버전 절을 가리킨다.
```

- 머리 줄은 정확히 `## [버전] — YYYY-MM-DD` 꼴이다(버전 뒤에 괄호 설명을 붙이지 않는다 — 옛 절은 붙였지만 새 절은 생성 스크립트가 읽기 쉽게 고정한다). 버전은 `VERSION` 파일과 글자 그대로 같다(`1.0.0`, 시험판은 `1.0.0-rc.1` 꼴).
- 한 절의 길이는 **20,000자 이하**를 앱 쪽 한도로 삼는다(GitHub 한도보다 훨씬 작게 — 확인 필요). 물결표·웹 주소·이중 중괄호는 쓰지 않는다(문서 규칙).

### 3. Release 본문을 만드는 방법(생성)

1. **절 고르기**: `CHANGELOG.md` 에서 머리 줄이 `## [X.Y.Z] — YYYY-MM-DD` 인 줄이 **정확히 하나**여야 한다(없거나 둘이면 실패). 절은 그 줄부터 다음 `## [` 줄 앞까지(없으면 파일 끝까지).
2. **본문**: 절의 첫 줄(머리 줄)을 뺀 나머지에서 앞뒤 빈 줄을 지운 글 — 줄 끝은 LF. **이 글이 Release 본문과 글자 그대로 같아야 한다.** 제목은 머리 줄에서 읽은 `ChanceBlog Desktop X.Y.Z`, 태그는 `vX.Y.Z`(태그 규칙은 확인 C 가 정한다 — 추천값).
3. **스크립트**: 위 규칙을 한 곳에 둔 작은 표준 라이브러리 스크립트(예: `scripts/release_notes.py` — **아직 없다**)가 `--version X.Y.Z` 로 본문을 파일에 써 준다. 릴리스 워크플로는 이 파일만 본문으로 쓴다(워크플로 안에 본문 글을 직접 적지 않는다). 파일을 본문으로 넘기는 도구의 옵션(예: GitHub CLI 의 `--notes-file`)과 초안 릴리스의 태그 생성 시점은 확인 필요.
4. **초안으로만**: 위 '릴리스 절차' 2번대로 초안 릴리스로 올리고 운영자가 `Publish release` 를 누른다(`--publish` 를 쓰지 않는다). 운영자는 공개 전에 본문을 읽을 수 있고, **고칠 것이 있으면 Release 화면이 아니라 CHANGELOG 를 고친 새 커밋으로** 다시 만든다.

### 4. 같아야 하는 것들 — 누가 지키나

| 같아야 하는 것 | 지키는 곳 | 지금 있나 |
|---|---|---|
| `VERSION` = `CHANGELOG.md` 맨 위 절의 버전 | `tests/test_repo_layout.py` VersionTest | 있음 |
| `VERSION` = 화면 '정보' 카드의 버전 | `ui/core/version.py` 가 `VERSION` 을 읽는다. 묶음에서는 `--selftest` 의 `version_file` 이 정보 파일과 견준다 | 있음(읽기와 자가 점검) |
| `VERSION` = 묶음 정보(`PACKAGE_INFO.json`)·압축 파일 이름의 버전 | 빌드가 `VERSION` 에서 만들고 시험이 이름을 견준다 | 있음 |
| `VERSION` = 태그 이름(`v` + 버전) | 릴리스 워크플로가 태그를 `VERSION` 에서 만들거나 견준다 | **없음** — 릴리스 갈래 |
| CHANGELOG 절 = Release 본문 | 생성 스크립트가 만들고 점검이 다시 견준다 | **없음** — 릴리스·종합 검증 갈래 |
| 후보 빌드의 위 값이 모두 같다 | 종합 검증의 점검 스크립트(예: `scripts/release_check.py`)가 한 번에 견준다 | **일부 있음** — `scripts/release_check.py`(결정 D-670–D-675)가 `VERSION` 과 `CHANGELOG.md` 맨 위 절을 견준다. 태그·산출물 이름까지의 견주기는 릴리스 갈래 몫 |

### 5. 시험 아이디어(구현은 릴리스·종합 검증 갈래)

1. **절 고르기 단위 시험**: 가짜 CHANGELOG 로 마지막 절·중간 절·없는 버전·같은 버전이 둘·시험판 접미사(`1.0.0-rc.1`)·날짜 없는 머리 줄이 각각 옳게(또는 거절로) 나오는지.
2. **모양 검사**: `### 요약` 이 있고 3–10줄이며 비어 있지 않은지, `### 이관 노트` 가 있는지, 길이 한도(20,000자)를 넘지 않는지, 물결표·웹 주소·이중 중괄호가 없는지.
3. **같은 글 시험**: 생성한 본문 파일 = 절의 본문(줄 끝만 통일)인지 — 한 글자만 바꾼 변이를 일부러 넣어 시험이 빨개지는지 확인한다.
4. **워크플로 구조 시험**(`test_workflow_*` 와 같은 방식): 릴리스 워크플로가 본문을 생성 스크립트의 출력에서만 가져오는지, 태그를 `VERSION` 에서 만드는지, 공개하는 호출(`--publish`·`gh release edit`)이 없는지.
5. **종합 점검(후보 빌드)**: `VERSION`·CHANGELOG 맨 위·`PACKAGE_INFO` 의 버전·압축 파일 이름·태그(만들어진 뒤)가 모두 같은지 한 번에 견준다. 값 하나만 틀리게 한 사본에서 이 점검이 빨개지는지 변이로 확인한다.
6. **공개 뒤 사후 확인(읽기 전용)**: 공개된 Release 의 본문을 읽어 CHANGELOG 절과 같은지 견준다 — 바깥 서버를 읽는 새 접속이라 NET 갈래의 틀과 운영자 승인이 먼저다(확인 필요).

### 6. 정해지지 않은 것(확인 C)과 이 절이 가정한 것

- 태그 규칙(`vX.Y.Z` 대 `desktop-vX.Y.Z`)·채널 수(추천: Stable 하나)·산출물 이름(`BlogPublisher-…` 대 `ChanceBlogDesktop-…` — 위 '공개되는 파일' 의 이름은 정정 대상)은 확인 C 의 결정을 기다린다. 이 절은 **추천값을 가정**했고 결정이 다르면 숫자·이름만 바꾸면 된다.
- 본문 길이 한도·본문을 파일로 넘기는 옵션·초안 릴리스의 태그 생성 시점·불변 릴리스의 동작은 이 저장소에서 확인하지 못했다(**확인 필요** — 워크플로를 만드는 갈래가 원문과 대조한다).

# 구조 — 데스크톱 작업대와 클라우드 파이프라인 (기술 구조의 단일 기준 문서)

> 이 문서는 설계다. 구현이 따라가며 바뀌면 같은 PR 에서 이 문서를 고친다. 결정과 근거는 [`DECISIONS.md`](DECISIONS.md). 어느 AI 코딩 도구든 이 문서와 `AGENTS.md` 만으로 같은 구조·규칙으로 일할 수 있어야 한다.

## 1. 무엇을 만드나

개인용 Windows PC 에서 **하나의 원본 글**을 쓰고(직접 쓰거나 기존 원고를 불러와서), 검사하고, 플랫폼별로 **변환·미리보기·승인**한 뒤 내보내는 프로그램이다. **AI 없이 모든 핵심 기능이 동작한다**(§8). 무료 AI 는 몇 가지 선택 보조 기능에 한정하고 기본값은 꺼짐이다(§7).

| 플랫폼 | 내보내는 방식 | 사람이 하는 일 |
|---|---|---|
| GitHub Pages(Chance 블로그) | **연결해 둔 기존 `chanceblog` 로컬 저장소**에 글·이미지를 만들고, 승인 뒤 commit·push → **기존 자동 배포 흐름**(`pages.yml`)이 사이트를 배포 | 미리보기에서 승인 |
| Google Blogger(영문·한글) | 공식 API 로 **초안 저장·수정**(자동 공개 없음) | Blogger 화면에서 발행 |
| 네이버 블로그 A·B | **복사 패키지**(제목·본문·이미지 위치·태그) 제공, 글쓰기 페이지 열기 | 에디터에 붙여넣고 발행, 발행 주소 입력 |
| 티스토리 | **제외·격리**(D-01) | — |

## 2. 큰 그림 — 두 저장소

```text
[클라우드 — chanceblog(별도 저장소), PC 가 꺼져 있어도 AI 없이 돈다]
  GitHub Actions 정기 실행 → pipeline(생성·게이트·발행) → GitHub Pages 자동 · Blogger 초안 · 초안 이슈(네이버)
  감시: 발행 중단 감시 · 확인 필요 모음 · 배포 확인 · 요청 알림(텔레그램)  ← 운영자 호출은 여기로만
        ▲ 이 저장소가 기존 chanceblog 로컬 저장소를 '연결'해 글·이미지를 넣고 push → 기존 자동 배포
[개인 PC — chanceblog-desktop(이 저장소)]
  원고(직접/불러오기) → 검사 → 플랫폼별 변환 → 미리보기·승인 → 내보내기 → 상태·이력
  설치·업데이트: GitHub Releases(초안 → 운영자 공개) → 앱이 확인·백업·검증·적용·롤백
```

원칙: ① 클라우드 자동 발행·감시·알림은 앱이 없어도 **지금 구조 그대로** 계속된다 ② 앱은 사람이 검수하는 경로를 편하게 하는 도구다 ③ 승인(T0~T3)·독립 검증·텔레그램 요청 규칙은 `chanceblog` 의 것을 따른다 ④ 로그인·쿠키·탐지 회피 자동화 없음 ⑤ 유료 호출 없음 ⑥ 오류 안내는 AI 가 아니라 **규칙(오류 코드 + 안내 문구)** 으로 한다([`TROUBLESHOOTING.md`](TROUBLESHOOTING.md)).

## 3. GitHub Pages — 기존 `chanceblog` 로컬 저장소 연결

앱은 설정에 **로컬 `chanceblog` 저장소 경로**를 가진다. 연결할 때 확인한다: 폴더가 git 저장소인가, `origin` 이 `shine88pc/chanceblog` 인가, 작업 트리가 깨끗한가, push 자격(Git 로그인)이 있는가(`git push --dry-run` — `connect` 는 폴더·origin·main·변경 없음까지만 확인하고 push 자격은 `doctor --online` 이 점검한다). 실패하면 이유와 하실 일을 보인다(`PAGES_LOCAL_REPO_INVALID` 등).
- **구현(연결 확인)**: `src/chanceblog_desktop/publish/gitrepo.py` — `inspect_repo`(폴더·`origin`·`main` 브랜치·저장하지 않은 변경 확인, 새 파일은 변경으로 보지 않음)·`sync_latest`(원격 `main` 을 받아 빨리감기로만 맞춤 — 로컬이 앞서거나 갈라져 있으면 건드리지 않고 `PAGES_LOCAL_REPO_DIVERGED`)·`check_push_access`(`git push --dry-run`, 실제로는 올리지 않음). 앱은 사용자의 커밋·변경을 지우거나 되돌리지 않고 브랜치를 바꾸지 않으며, git 이 대화창을 띄우지 않게(`GIT_TERMINAL_PROMPT=0`·입력 장치를 막아 둔다) 영어 메시지로 실행하고(사용자 PC 의 `GIT_DIR` 같은 다른 저장소 설정은 지우되, 사용자의 ssh·자격 증명 설정은 건드리지 않는다), 시간(기본 90초)이 넘으면 git 과 그 손자 프로세스까지 끄고 `NETWORK_TIMEOUT` 으로 알린다(출력은 파이프가 아닌 임시 파일로 받아, 끝난 git 의 손자가 연결을 붙잡고 있어도 기다리며 매달리지 않는다)(받기 뒤 git 이 정리(gc)를 시작하지 않게 `gc.auto=0`). 실패는 출력 문구로 오류 코드(`GIT_PUSH_AUTH`·`GIT_PUSH_NETWORK`·`GIT_PUSH_REJECTED`·`FILE_WRITE_FAILED`·`DISK_FULL` 등)로 나누고, 세부(detail)는 끝 400자만 남기되 자르기 전에 `security/mask.py` 로 가린다. `origin` 은 받는 주소와 올리는 주소(`pushurl` 포함)를 **모두** 확인한다. `sync_latest` 는 원격 main 을 명시한 refspec 으로 받고, 받을 파일과 겹치는 내 파일(추적하지 않는 새 파일·무시(`.gitignore`)한 파일)이 있으면 병합을 시도하지 않고 `PAGES_LOCAL_FILE_IN_THE_WAY`(겹치는 파일 이름을 보여 준다)로 멈추며, git 이 내 변경·내 파일을 지키려고 병합을 거절하면(`PAGES_LOCAL_REPO_DIRTY`·`PAGES_LOCAL_FILE_IN_THE_WAY`) 아무것도 되돌리지 않고, 병합이 파일을 쓰다 멈추면(다른 프로그램이 쓰는 중·디스크 가득·시간 초과) **병합이 쓴 것만**(내용이 원격 main 과 똑같은 파일·그 색인 항목·원격이 지웠거나 이름을 바꾼 파일) 병합 전으로 되돌리고 내가 고친 파일은 건드리지 않는다(원격이 정한 파일 이름이 저장소 밖을 가리키면 무시하고, 경로 인자는 글자 그대로 읽는다 — `GIT_LITERAL_PATHSPECS`). 받기·올리기에서 사용자가 ssh 명령을 따로 정하지 않았으면 `ssh -o BatchMode=yes` 로 질문을 입력 없이 기다리며 멈추는 일을 막는다. `check_push_access` 는 사용자의 `pre-push` 훅을 돌리지 않는다(`--no-verify`).
- **글**: `chanceblog` 의 Chance 글과 같은 형식으로 만든다(2026-10-30 실제 글·생성기 `generator.py` 확인) — 파일 `_posts/<분야 폴더>/YYYY-MM-DD-KR|EN-HHMMSS.md`(한국 시각; 날짜는 파일 이름에서, 주소는 사이트 설정의 `permalink` 가 만든다), 머리말은 한 줄 한 키로 `layout: post`·`title`·`category`·`tags`·`lang`(ko|en)·`image`(필수)와 `description`·`source_name`·`source_url`·`source_domain`(있을 때) 순서이고 값은 한 줄 JSON, 본문에는 대표 이미지 줄(`![Thumbnail]` 에 이미지 주소를 괄호로 붙인 것)이 한 번은 있다. **구현**: `src/chanceblog_desktop/render/pages.py` 의 `render_pages_post`(순수 함수 — 원고(ContentProject)와 분야·언어·대표 이미지·태그·설명·출처 → 경로와 파일 내용, 파일은 쓰지 않는다)와 머리말 검사 `front_matter_problems`. 시험이 `tests/fixtures/` 의 **실제 글 두 편(영어·한글)을 글자 단위로 되살리고** 설명 자동 추출도 같은지 확인한다. 폴더 이름은 생성기의 `safe_category_dir` 규칙에 Windows 에서 만들 수 없는 글자(`<>:"|?*`)와 끝의 점·공백 정리를 더했다. `chanceblog` 쪽 규칙(`generator.py`)이 바뀌면 이쪽도 같은 PR 에서 맞춘다.
- **이미지**: 지금 Chance 는 외부 이미지 주소(Unsplash)를 `image:` 에 쓴다. 앱은 같은 방식과 함께 사용자가 고른 이미지 파일을 저장소 안 정해진 폴더에 두는 방식을 지원한다(폴더·크기 규칙은 첫 구현에서 정한다, 사이트 설정 `_config.yml` 은 건드리지 않는다).
- **발행**(구현: `publish/pages.py`): 미리보기에서 승인하면 앱이 **항상 최신 `main` 을 먼저 가져온 뒤**(봇이 같은 `main` 에 직접 커밋한다) 파일을 만들고 commit·push 한다. 세 단계로 나뉜다 — `commit_post`(글 검사 → 최신 받기 → 같은 주소(분야가 달라도, 확장자가 달라도 날짜·언어·시각이 같으면 Jekyll 주소가 같다)의 글이 있는지 → 파일 쓰기 → **그 파일만** commit. 실패하면 쓴 것을 치우고, 못 치운 것은 오류 세부에 이름으로 알리며(다음 시도는 그 파일이 내가 쓰던 것과 같으면 이어서 쓰고, 지난번 실패가 남긴 '이 글 하나만 스테이징된' 상태도 알아보고 치운다) = 상태 `COMMITTED`)와 `push_commit`(올리지 않은 것이 '이 글 하나'인지·아직 `main` 인지 확인 → **검사한 그 커밋 번호로** push(그 뒤에 사용자가 `main` 에 커밋을 더해도 같이 올라가지 않는다. 올리기 직전에 한 번 더 확인한다), 봇이 먼저 올려 막히면 최신 위로 그 커밋만 옮겨 다시 최대 3번, 같은 주소의 글을 봇이 먼저 올렸으면 되돌리고 `DUPLICATE_SLUG` = 상태 `PUSHED`), 끝내 올리지 못한 글 커밋(같은 주소의 글이 먼저 올라가 있어 멈춤 등)은 `discard_commit` 이 되돌린다(원격을 먼저 받아 아직 올라가지 않은 이 글의 커밋만 — 이미 올라갔거나 다른 변경이 섞였거나 앱이 만든 커밋이 아니면 건드리지 않는다). 이미 올라가 있으면 아무것도 안 하고 성공으로 끝나므로(올리다 연결이 끊겨도) 같은 글이 두 번 올라가지 않는다. 강제 push·브랜치 변경·사용자의 훅·서명 대화창은 쓰지 않고, 올리지 않은 다른 커밋이 있으면 `PAGES_LOCAL_REPO_DIVERGED` 로 멈춘다. 글이나 commit 제목에 키 모양 문자열이 있으면 `SECRET_IN_TEXT_BLOCKED` 로 막는다. 알려 둔 한계: `git rebase` 프로세스가 뜨는 바로 그 몇 밀리초 사이에 사용자가 다른 브랜치로 바꾸면 그 브랜치가 옮겨질 수 있다(원격에는 잘못 올라가지 않는다) · 원격 `main` 의 이력을 다시 쓰는(비밀 제거 등) 동안에는 앱으로 발행하지 않는다 — 올리기 직전 몇 밀리초 사이에 되감기면 지운 커밋이 되살아날 수 있다(강제 push 계열을 쓰지 않는 대신 받아들인 한계). 배포 확인(공개 주소가 열리는지 — chanceblog 의 `scripts/verify_pages_deploy.py` 로직을 가져다 쓴다)은 다음 묶음이다. 이후는 기존 흐름이다: `main` push → `pages.yml` 이 Jekyll 빌드·배포 → 배포 확인. 앱은 Actions 실행 상태를 읽어 성공·실패를 보이고(§6 오류 안내), 발행 주소를 기록한다.
- **배포 확인**(구현: `publish/deploy.py`): push 뒤 글이 공개 주소에서 실제로 열리는지 본다. chanceblog 의 배포 워크플로가 쓰는 확인 코드(`scripts/verify_pages_deploy.py`)를 `vendor/scripts/` 에 원본 그대로 가져와(§4) 쓴다 — 공개 CDN 이 '없음(404)' 도 최대 18분쯤 보관해 같은 주소를 반복 요청하면 계속 404 를 받으므로 시도마다 요청 모양을 바꾸고, `published: false`·미래 날짜·Jekyll permalink 계산도 같은 코드가 한다. 이 모듈은 '내가 올린 글 하나'만 확인하도록 임시 사이트 폴더(`_config.yml` + 그 글)를 만들어 건네며 연결한 저장소는 건드리지 않는다. `expected_url` 은 네트워크 없이 공개 주소를 계산하고(상태 `PUBLISHED` 에 기록할 주소), `check_deployed` 는 열릴 때까지(기본 최대 12분, 대기 10초에서 2배씩) 기다리다 끝내 안 열리면 `PAGES_DEPLOY_NOT_VISIBLE` 을 낸다. 기다리는 동안 멈춰 있으므로 화면과 다른 작업 줄에서 부른다.
- **클라우드 자동 발행과의 관계**: 클라우드는 하루 **2슬롯**(한국 시각 9시·18시 이후 첫 실행, 하루 최대 2편 — `chanceblog` 설정 `slots_kst [9, 18]`·`max_posts_per_day 2`)으로 올린다. 데스크톱은 **같은 주소(slug) 중복**(같은 초의 파일 이름 충돌)과 **내용이 똑같은 글이 이미 있는지**만 확인한다. 같은 날 자동 글 수·`history.json`(자동 발행 이력)·제목 유사도는 **구현하지 않았다** — 일일 상한은 클라우드가 `history.json` 으로 세므로 데스크톱 글은 그 상한에 잡히지 않는다(규칙이 구체적으로 정해지면 따로 더한다). 이 한 곳이 이 문제의 설명이다(§5 는 이 줄을 가리킨다).

## 4. 핵심 코드 재사용 — '정해진 버전으로 가져다 쓴다'

`chanceblog` 의 `pipeline/` 에는 이미 시험 4,000여 개로 고정된 코드(검사 `gates.py`, 비밀 패턴 `secret_patterns.py`, 상태 `state.py`, 실패 분류·마스킹 `llm.py` 의 일부, Blogger 어댑터 `publishers/blogger.py`, 복사 패키지 `publishers/issue_package.py`)가 있다. 파이썬 그대로 가져다 쓰면 다시 시험하지 않아도 된다.
- 방식: `vendor/pipeline/` 에 **원본과 한 글자도 다르지 않게** 복사하고 `vendor/VENDOR.json` 에 가져온 저장소·커밋 SHA(40자리)·파일별 SHA-256 을 적는다. 앱은 시작할 때 `chanceblog_desktop.core.use_vendored_core()` 로 `vendor/` 를 `sys.path` 맨 앞에 올려(이미 있어도 맨 앞으로 옮기고, 같은 이름의 다른 `pipeline` 이 먼저 불려 와 있으면 멈춘다) `from pipeline import gates` 처럼 쓴다. 갱신은 `python scripts/sync_core.py --source <chanceblog 를 받아 둔 폴더> --ref <커밋·태그·브랜치>`(먼저 원본 폴더의 `origin` 이 chanceblog 이고 가져올 커밋이 `origin/main` 에 병합된 것이며 대상이 일반 파일(링크·하위 모듈·폴더 아님)인지 확인하고, 원본 커밋의 바이트를 그대로 쓰며, 읽기에 실패하면 아무것도 쓰지 않는다). `--check` 와 시험이 `vendor/` 해시와 `VENDOR.json` 이 같은지, `vendor/` **전체**에 목록 밖 파일이 없는지(컴파일 캐시 `.pyc` 도 포함 — `vendor/` 는 import 경로 맨 앞이라 어느 자리의 파일이든 앱이 불러올 수 있고, 소스와 수정 시각·크기만 맞춘 `.pyc` 는 소스 대신 실행된다. 앱은 컴파일 캐시를 사용자 폴더(`sys.pycache_prefix`)에 두므로 `vendor/` 안에는 없어야 한다). 목록의 파일 자리에 링크·하드 링크가 있으면 `--check` 가 알리고 가져오기는 쓰기 전에 멈춘다(링크 너머를 덮어쓰지 않게) 확인한다. `.gitattributes` 의 `vendor/** -text` 가 줄바꿈 변환(Windows autocrlf 포함)을 막는다. 코어를 고칠 일이 생기면 `chanceblog` 에서 고쳐 병합한 뒤 다시 가져온다(이 저장소에서 `vendor/` 를 고치지 않는다).
- 지금 가져오는 파일(앱이 쓰는 것만, 목록은 `scripts/sync_core.py` 의 `FILES`): `pipeline/__init__.py`·`console.py`·`gates.py`(발행 전 검사)·`secret_patterns.py`(비밀 모양 검사)·`scripts/verify_pages_deploy.py`(배포 뒤 공개 주소 확인 — `chanceblog_desktop.core.load_vendored_script("verify_pages_deploy")` 로 파일 경로로 불러와 `scripts` 라는 패키지 이름을 만들지 않는다). 모두 표준 라이브러리만 쓴다. Blogger 어댑터·복사 패키지·상태 등은 그 기능을 만드는 묶음에서 목록에 더한다.
- 서브모듈·패키지 설치 방식은 비개발자 운영과 PC 이관에 부담이라 쓰지 않는다.

**`service/` 구현 범위와 한계**(명령줄은 README 의 '명령줄로 써 보기'):
- **GitHub Pages 올리기**(`pages_flow.py`, 변경 등급 T2): `publish-pages` 는 **기본이 미리 보기(dry run)** — 승인·검사·연결한 저장소·같은 주소(slug)·같은 내용의 글 확인과 공개 주소 계산까지만 하고 아무것도 쓰지 않는다(읽기 전용 git 명령뿐 — 잠금 파일도 만들지 않는다). `--yes` 가 있어야 commit → push → 공개 확인을 하고, 확인 표시가 없으면 commit 도 push 도 점검도 하지 않는다(AGENTS.md 규칙 7). 올라가는 내용은 다시 만든 것이 아니라 **승인한 렌더링 그대로**이고, 파일 이름의 시각만 올리는 순간의 한국 시각이다.
  상태는 사실을 따라 단계마다 바로 저장한다: `APPROVED` → `COMMITTED` → `PUSHED` → `PUBLISHED`. 공개 주소가 아직 안 열리면(`PAGES_DEPLOY_NOT_VISIBLE`) 상태를 `PUSHED`(올림·공개 확인 대기)로 두고 `check-deploy` 로 마친다. push 가 막히면 `COMMITTED` 로 남아 같은 명령이 push 만 이어서 하고(다시 commit 하지 않는다), `--cancel --yes` 는 `discard_commit` 이 허락할 때만 글 기록을 되돌려 `PUBLISH_FAILED`(`PUBLISH_CANCELLED`)로 남긴다. 같은 주소의 글이 먼저 올라가 있으면(`DUPLICATE_SLUG`) 글 기록을 되돌리고 `PUBLISH_FAILED` 로 남긴다. commit 뒤 상태를 저장하지 못하면 방금 만든 commit 을 되돌린다. **잠금**(`lock.py`·`liveness.py`): 올리기·`--cancel`·`check-deploy` 는 점검보다 먼저 그 글의 잠금 파일(`publish/<글번호>.lock` — `O_EXCL` 로 만들고 프로세스 번호·시작 시각·실행 번호·PC 이름을 적는다)을 잡고, 못 잡으면 아무것도 바꾸지 않고 `PUBLISH_IN_PROGRESS` 로 멈춘다(다른 창에서 같은 글을 올리는 중). 정상·실패·Ctrl+C 모두 풀고 **자기 실행 번호인 잠금만** 지운다. 작업이 죽어 남은 잠금은 ① 그 프로세스가 같은 PC 에서 이미 끝났으면(Windows 는 상태를 읽는 `OpenProcess` 로 — 프로세스를 끝내는 `os.kill(pid, 0)` 은 쓰지 않는다. 번호가 재사용됐으면 시작 시각으로 가려낸다) 바로, ② 알 수 없으면 시작한 지 30분(오래 기다리겠다고 한 작업은 그 시간 + 15분)이 지난 뒤에 넘겨받고 그 사실을 알린다. 실패 경로가 발행 기록을 지울 때는 **이 실행이 쓴 기록과 똑같을 때만** 지운다. **저장소 잠금**: 글 잠금은 글마다라서 서로 다른 두 글을 거의 동시에 올리면 둘 다 '최신 받기 → commit' 을 같은 저장소에서 하다가 둘 다 commit 만 하고 올리지 못했다(올리지 않은 commit 이 둘). 그래서 commit·push·되돌리기 구간은 연결한 저장소마다 한 번에 한 작업만 돈다 — 잠금 파일은 **그 저장소의 `.git` 안**(`.git/chanceblog-desktop-publish.lock`, git 이 추적하지 않는 파일; `.git` 이 `gitdir:` 연결 파일이면 가리키는 폴더)에 있어서 같은 저장소면 경로 표기·링크·대소문자가 달라도 같고 **`--data-dir` 을 다르게 준 앱끼리도 서로를 안다**(데이터 폴더에 두면 서로 몰랐다). `.git` 에 잠금 파일을 못 만들면(권한·읽기 전용·디스크 가득) 데이터 폴더의 잠금으로 물러서지 않고 올리지 않는다(`FILE_WRITE_FAILED`·`DISK_FULL` — fail closed, 아무것도 바뀌지 않는다). `.git` 이 아예 없는 폴더는 잠글 것이 없어 이어지는 저장소 확인이 평소의 오류로 멈춘다. **글 잠금을 먼저, 저장소 잠금을 그다음에** 잡는 순서가 고정이라 서로 기다리며 멈추지 않고(같은 글은 기다리지 않고 바로 `PUBLISH_IN_PROGRESS`), 다른 글이 쥐고 있으면 `Context.lock_wait`(기본 120초) 동안 기다리다 `PUBLISH_REPO_BUSY` 로 아무것도 바꾸지 않고 물러난다(같은 명령을 다시 실행하면 된다). 글 파일 이름의 초(날짜·언어·시각)가 이미 쓰였으면(바로 앞 글이 같은 초에 올라간 경우 — 기다린 글이든 아니든) 점검 단계에서 다음 초의 이름으로 정한다(읽기만 하며 최대 5번 — 이름의 시각이 '올리는 순간' 보다 몇 초 늦을 수 있다). 공개 확인을 기다리는 동안에는 저장소 잠금을 풀어 다른 글이 올라갈 수 있고, 미리 보기·`check-deploy` 는 저장소 잠금이 필요 없다. 두 잠금 모두 죽은 프로세스의 것은 바로 넘겨받고 알린다(같은 멈춤의 흔적이면 한 번만). **올리지 않은 commit 이 이미 있으면** 새 글을 올리지 않고(미리 보기 포함) 상황별로 정확한 안내 한 가지를 낸다 — 앱이 올리다 멈춘 글 하나면 그 글의 같은 명령이 이어서 올리거나 `--cancel --yes`, 그런 글이 겹쳤으면 **가장 나중에 기록한 글부터** `--cancel --yes` 로 되돌린 뒤 남은 글을 올리고(되돌린 글은 `review` 로 다시 만들어 승인), 앱이 만든 것이 아닌 commit 은 사람이 확인한다(`unpushed.py`, `doctor` 도 같은 말). **올리고 나서(올림 기록을 마치기 전에) 멈춘 글**은 올리지 않은 commit 이 아니다 — `--cancel` 은 `PUBLISH_ALREADY_PUSHED` 로 거절하고 `--cancel` 없는 같은 명령이 올림 기록과 공개 확인을 마친다. 공개된 글에 남은 발행 기록(지우기 직전에 멈춘 흔적)은 다음 `check-deploy`·`publish-pages` 가 그 글의 기록만 정리하고 `doctor` 가 알린다. **올림(PUSHED)인데 발행 기록이 없는 글**(글을 지웠다가 백업으로 되살리거나 오래된 백업으로 되돌릴 때 생긴다 — 발행 기록은 백업에 들어 있지 않고, 올라간 글의 파일 이름(올린 순간의 시각)은 기록에만 있다)은 `check-deploy`·`publish-pages`·`--cancel` 어느 것도 이을 수 없다. 그래서 ① 발행 기록이 있는 올림 글은 `delete` 가 거절한다(먼저 `check-deploy` 로 마친다 — 데이터를 만들어 내지 않는 쪽) ② 이미 기록 없는 올림 글은 네 명령·`doctor` 가 모두 `delete 글번호 --yes` 한 가지 출구만 말하고(서로를 가리키지 않는다) 그 글은 지울 수 있다(올라간 글은 저장소에 그대로 있고 이 앱은 올라간 글을 지우지 않는다). 읽을 수 없는 기록은 '없다' 로 보지 않고 `SETTINGS_INVALID` 로 알린다. **commit 직후에 멈춘 경우**(commit 은 했는데 발행 기록·COMMITTED 를 저장하기 전에 프로세스가 죽음 = 승인됨 + 올리지 않은 commit 하나 + 기록 없음): 그 commit 이 **이 글의 승인한 렌더링을 그대로 더한 앱의 commit 하나뿐**이면(경로는 이 글의 분야·언어로 앱이 만드는 모양, 내용은 한 글자도 다르지 않음, 제목은 앱의 것) 같은 명령이 그것을 이어받아(기록을 만들고 COMMITTED 로 이어서 push) 올리고, `--cancel --yes` 는 `discard_commit` 의 조건 안에서 되돌린다. 조금이라도 다르면 아무것도 하지 않고 `PAGES_LOCAL_REPO_DIVERGED`·`DUPLICATE_SLUG` 로 멈춘다. `doctor` 가 그런 글을 이름과 함께 알려 준다. **commit 뒤 원고를 고치면**: push 직전에 승인한 판과 지금 원고의 판을 다시 비교해 다르면 올리지 않고 `PUBLISH_CONTENT_CHANGED`(`--cancel --yes` 로 되돌린 뒤 다시 승인).
  어디까지 했는지(글 파일 경로·커밋 번호)는 사용자 데이터 폴더의 `publish/<글번호>.json` 에 적는다(저장소 상대 경로와 커밋 번호뿐 — 이 PC 의 절대경로는 적지 않는다). 이 기록이 틀려도 push 는 안전하다(`push_commit` 이 올릴 것이 이 글 하나인지 다시 확인한다).
- **검사(`gate.py`)는 기본값이다**: chanceblog 의 Chance 블로그에는 `gates.check_post` 용 프로필이 없어, chanceblog 생성기가 글을 받을 때 쓰는 최소 본문 분량(출처 목록·링크 표시·Markdown 기호·공백을 뺀 글자 수가 한글 1000자·영문 1500자 이상 — 생성기와 **같은 계산**에 눈에 안 보이는 글자는 세지 않는다는 규칙을 더했다)·언어 비율·AI 가 흘린 문구·키 모양 문자열만이 아니라, **올라가는 Markdown 원문**을 본다: 원시 HTML 태그(`<script>`·`<ins>`·`<iframe>`·`<img onerror>` …)·`javascript:`/`data:`/`vbscript:` 주소(엔티티·공백으로 숨긴 것 포함)·`{% %}`/`{{ }}`/`{# #}` 템플릿 표기·`{: }` 속성 붙이기·광고 스크립트(`adsbygoogle`·`googlesyndication`) — 저장소에 올라가는 것은 원문이고 사이트(Jekyll)는 원시 HTML 을 그대로 내보내며 Liquid 를 글을 만들 때 실행하기 때문이다(코드 블록 안이어도 막는다. 이 앱은 Markdown 글만 올린다). **머리말 값 전부**(제목·분야·태그·대표 이미지 주소·설명·출처 이름·주소·도메인)에도 같은 HTML·템플릿·위험한 주소·광고 스크립트 검사를 하고 줄바꿈·제어 문자·너무 긴 값·https 가 아닌 이미지 주소·따옴표/꺾쇠/공백이 든 주소·모르는 머리말 키(`published`·`permalink` 같은 글의 공개·주소를 바꾸는 키)·어긋난 출처 세 줄도 막는다(`HEADER_VALUE`) — 머리말 값은 사이트의 글 목록(`posts.json`)·카드·`<title>` 에 들어가고 첫 화면 카드는 제목·분야·태그·이미지 주소를 이스케이프 없이 HTML 에 넣는 곳이 있어서다. 렌더링(`render/pages.py`)은 값을 한 줄 JSON 으로 이스케이프하고 줄바꿈을 거절하므로 제목에 따옴표·콜론·`---`·`#` 가 있어도 머리말 구조는 깨지지 않고 다른 키가 끼어들지 못하며(시험으로 확인), 게이트는 저장된 글이 어떻게든 바뀌어 있어도 같은 값을 다시 본다. 글을 만들거나 고칠 때의 제목과 `review`·`preview` 로 준 값도 같은 사유로 그 자리에서 막는다. 따옴표는 막지 않는다(실제 Chance 글에도 있다 — 첫 화면 카드의 속성 이스케이프는 `chanceblog` 쪽 일이다). 눈에 안 보이는 글자(폭 없는 공백·채움 글자·점자 빈칸)가 50개를 넘거나 본문의 5% 를 넘어도 막고(이모지의 ZWJ·변형 선택자는 뺀다), 글자가 화면에 보이는 방향·순서를 바꾸는 제어 문자(U+202A–202E·U+2066–2069)는 본문·머리말 값(제목 포함) 어디에 한 개만 있어도 막고(`INVISIBLE` — U+200E·U+200F 같은 방향 '표시' 는 제외), 이 PC 의 폴더 경로는 `C:\Users\…`·`\\서버\공유`(UNC)·`file:`·8.3 짧은 이름·WSL 경로·대소문자·슬래시만 다른 저장소 경로까지 막는다. 정규식은 이상한 입력에서도 선형 시간에 끝난다 — 대부분은 길이 상한을 두지만, **주소 앞의 공백에는 상한을 두지 않는다**(CommonMark 에서 링크 목적지 앞 공백은 길이 제한이 없어, 상한을 두면 공백을 길게 넣은 `javascript:` 링크가 검사를 빠져나간다). 대신 공백을 나누는 방법이 하나뿐인 꼴(`\s*(?:<\s*)?`)로 써서 공백이 아무리 길어도 선형이다(예전 꼴은 6만 개에 88초). 금지 낱말·주제 같은 **정책은 새로 만들지 않았다**(정책·톤은 T3 — 운영자 결정 필요). chanceblog 생성기의 '검증된 원문 링크 인용' 검사는 하지 않는다.
- **주제 후보 명령줄**(`service/candidates.py`·`cli.py`, 변경 등급 T1 — 값을 정한 것은 D-23·D-24): `candidates list·show·add·import-csv·select·hold·reject·review·restore·delete·link·unlink`. 후보 번호(uuid)는 사람이 쓰기 어려워 화면에는 **순번**(만든 시각 순, 전체 목록 기준)과 **번호 앞 8자**를 함께 보이고(`list` 는 늘, 보류·제외·선택·연결·지움의 결과 줄과 겹침 안내에도), 순번(1~999)이나 번호의 **앞 4자 이상**(번호 전체가 먼저, 대소문자 무시)으로 고른다. 숫자만 4~7자인데 맞는 번호가 없으면(`list` 에서 본 1000번 이상 순번을 친 것) '1000번 이상은 순번으로 고를 수 없습니다 — 번호 앞 8자로 고르세요' 로 이유를 알리고, 앞부분이 둘 이상과 맞으면 `CANDIDATE_AMBIGUOUS` 가 순번·주제·번호 앞 8자 목록(8개까지)을 오류 세부에 보인다. 순번은 새 후보가 뒤에 붙어도 앞의 것이 안 바뀌지만(같은 초에 연달아 만들거나 시계가 뒤로 갔어도 새 후보의 만든 시각은 이미 있는 후보 중 가장 늦은 것의 1초 뒤로 적어 무작위 번호가 순서를 뒤섞지 못하게 한다) **지우면 뒤가 당겨지므로 지우기는 순번으로 받지 않는다** — `delete` 는 번호 앞 8자(또는 더 긴 앞부분·번호 전체)와 `--yes` 가 있어야 지우고, 순번이나 짧은 앞부분과 `--yes` 를 함께 주면 아무것도 지우지 않고 `CANDIDATE_DELETE_NEEDS_NUMBER` 로 지울 명령(`candidates delete <번호 앞 8자> --yes`)을 후보 제목과 함께 알린다(전에는 같은 `delete 3 --yes` 를 되풀이하면 다른 후보가 차례로 지워졌다 — 독립 검증). `--yes` 없는 미리 보기는 순번도 받고 같은 명령을 보여 주며, 같은 번호를 두 번 지우면 둘째는 `CANDIDATE_NOT_FOUND` 다. 화면의 영문 상태 코드·번호 전체는 `--json`·`--verbose` 에서만 나온다. 화면의 시각과 재선택 경고의 '며칠 전' 은 **한국 시간(KST) 달력** 기준이고 저장은 UTC 그대로다. **`list`·`show` 는 읽기 전용으로 연다**(`ctx.reading_only()` → `Store.open(migrate=False)`) — 보관함 파일이 없거나 옛 구조(판 1)여서 후보 표가 없으면 파일을 만들지도 올리지도 않고 한 바이트도 바꾸지 않은 채 '아직 후보가 없습니다(쓰는 명령을 처음 실행하면 보관함이 올라갑니다)' 로 알린다(점검과 같은 이유 — 읽기만 하는 명령이 사용자 데이터 파일과 사본을 몰래 만들면 안 된다). 앱이 쓰다 꺼져 끝내지 못한 저장이 남았으면 읽기 전용 명령은 `STORE_RECOVERY_PENDING` 으로 멈추고, 안내대로 `list`(글 목록)나 `candidates add …` 처럼 보관함을 여는 명령을 한 번 실행하면 정리된다. 쓰는 명령은 열면서 옛 구조를 올린다. 상태 이동은 `Store.set_candidate_status`(읽고 바꾸고 쓰는 `Candidate.new` 로 만든다 — 지표가 있는 줄은 조회일(열 또는 `--data-date`)이 있어야 하고(조회일은 오늘(UTC)보다 하루 뒤까지만 받는다), 결과를 약속하는 표현 같은 후보 규칙은 그대로 줄 단위로 거절한다. 읽기 도구의 칸 크기 한도(기본 128KB)는 이 파일 안에서 파일 크기까지 올려 읽고 되돌린다(한도에서 읽기가 끊기면 큰따옴표 속 여러 줄이 새 후보로 읽히는 유령 줄이 생겼다). 잘못된 줄은 줄 번호와 이유로 그 줄만 거절하고 같은 핵심 키워드·주제·블로그가 이미 있는 줄은 건너뛰므로(**다시 가져와도 겹치지 않는다**) `N개 추가·M개 건너뜀·K개 거절` 이 결과이고, 거절한 줄이 있으면 종료 코드 1 이다(나머지는 저장됐다). **'이미 있나 확인 → 저장' 은 보관함의 한 쓰기 트랜잭션**(`Store.add_candidates(plan)` — 쓰기 잠금을 잡은 **뒤** 지금 있는 후보를 읽어 계획을 세우고 모두 저장한다)에서 하므로 같은 파일을 두 프로세스가 동시에 가져와도 겹치지 않고, 가져오다 멈추면 아무것도 저장되지 않는다(같은 명령을 다시 실행하면 된다). `add` 도 같은 방법이라 같은 후보를 동시에 더해도 하나만 들어간다. 한 번에 가져온 후보는 같은 시각에 만들어도 파일의 줄 순서대로 순번이 매겨진다(번호를 오름차순으로 나눠 준다). `safe_cell`(엑셀이 수식으로 읽을 `=`·`+`·`-`·`@`·탭·줄 처음으로 시작하는 글 앞에 `'` 를 붙인다)은 이 앱이 CSV 를 쓰지 않아 호출처가 아직 없고, 내보내기를 만들 때 쓰도록 규칙만 시험으로 고정해 두었다(숫자 칸에는 쓰지 않는다). 알려 둔 한계: 네이버 데이터 수집(키 필요)·초안·화면은 없다(프로필로 먼저 제안하는 일은 아래 항목) · 시각 표시는 한국 시간(+9) 고정이다.

  항목은 용도마다 **3개까지**(`MAX_ENTRIES_PER_PURPOSE` — 키를 하나만 두는 용도인 NAVER API HUB 는 `Purpose.max_entries = 1`), 이름·소속 프로젝트·순서·상태(사용·예비·꺼짐)를 가진다. 같은 앱(앱을 가리키는 칸이 있는 용도는 그 칸의 같은 값 — NAVER API HUB·Blogger 는 클라이언트 ID, 검색광고는 고객 ID — 그 밖은 같은 소속 프로젝트 이름 — 비워 두면 '미지정' 하나)의 항목은 한 **한도 묶음**이라 한도를 함께 쓴다. 둘째 키부터는 약관 확인 표시(`--i-understand-terms`)가 있어야 하고 확인한 시각이 그 항목에 적힌다. **한도 안전장치(`QuotaGuard`)**: `acquire(용도, calls, priority)` → `Lease`/`Denied`, `report(lease, 결과, …)` → 전환·재시도·멈춤. 예산은 우선순위별로 남겨 둘 몫이 다르다(일괄 갱신 30%·새 후보 20%·선택된 후보 10%·필수 호출 0% — 마지막 10% 는 필수 호출 전용 = 절약 모드). 다만 단계표가 있는 NAVER API HUB 는 이 몫 규칙을 쓰지 않고 아래의 단계를 쓴다(하루 100회 창에도 쓰지 않는다 — 구현 쪽 기본값, 알려 둔 한계 ⑮). 결과는 10종이고 **전환할 수 있는 것은 정확히 네 가지**(`rate_limited`·`quota_exhausted`·`transient_error`·`timeout`)이며, 나머지(`auth_failed`·`bad_request`·`policy_blocked`·`content_blocked`·`other_error`)는 어떤 정책에서도 다른 항목을 시도하지 않고 쉬운 한국어 조치 안내만 한다. 전환 대상은 같은 용도·제공자의 사용·예비 항목(순서대로)과 레지스트리 `fallback_providers`(운영자가 켠 것 — 기본은 비어 있다)뿐이고, 한 요청에서 같은 항목을 두 번 시도하지 않으며(한 바퀴), 한도 오류 뒤에는 같은 묶음으로 넘어가지 않고(5xx·시간 초과는 허용), 요청이 성공하면 다음 요청은 늘 첫 항목부터 시작한다(순환 상태를 저장하지 않는다). `rate_limited` 는 `Retry-After`(정수 초·소수 초·HTTP-date 세 꼴을 읽고 최대 48시간 — 값이 있는데 읽을 수 없으면 0 으로 보지 않고 1분 이상 쉰다)를 지키고 5초에서 두 배씩(상한 1시간, 난수 없음) 쉬며, `quota_exhausted` 는 초기화 시각(한국 시간 0시)까지 막고 '이어 하기' 시각을 알린다. 잠금을 못 잡거나 상태가 깨져도 호출을 열어 두지 않는다(`Denied`, 깨진 상태는 오늘 한도의 절반을 쓴 것으로 가정 — Fail-Closed 인 NAVER API HUB 는 가정하지 않고 멈춘다). `Denied` 의 `degraded` 는 오류가 아니다 — 호출하는 쪽은 '데이터 없음'(또는 저장해 둔 값)으로 계속한다.

5종**(`content/post_types.py`)의 단계 이름과 순서는 요구서 그대로이고, 소제목 수는 프로필 범위에 맞춘다 — 단계가 많으면 이웃한 단계를 한 소제목으로 묶고(말씨 0 은 가운데부터, 1 은 뒤에서부터), 적으면 사실을 단정하지 않는 구조용 단락(자주 묻는 질문·용어 풀이·점검표)을 마무리 앞에 더한다. 제외할 말(프로필의 제외 주제·사용자의 제외할 내용)이 든 단계·소제목·핵심 내용은 빠지고(안전 주의사항은 빼지 않는다) 후보의 주제·키워드 자체에 있으면 제목에는 그대로 두고 확인 권장으로 알린다. 제목 후보는 사용자가 정한 제목 방향·결론으로 고른 틀 제목까지 모두 한 관문(제외할 말·금지 표현·'지어내지 않기')을 지나고, 제외할 말이 든 보조 키워드는 핵심 내용·태그에서도 선택 기준 정리(둘 다 제품·서비스 소개형), 경험형 후기→정보형 안내 글(글 유형은 그대로)로 바꾸고 제목·소제목·태그에서 후기·체험 낱말을 걷으며 바꿨다는 사실을 확인 권장에 적는다(후기를 '쓴' 글이 아니라 후기에 '대한' 글 — '후기 쓰는 법'·'가짜 리뷰 구별' — 은 바꾸지 않되 헷갈리면 후기로 본다: 사진·순위·점수 같은 흔한 명사는 '사진 검사**(`check/claims.py`): 직접 사용·방문·구매·수익·효과를 체감했다는 주장·실제 대화나 댓글·실제로 있었다는 사람이나 사례는 **위반**, 가격·날짜·시각·통계는 **확인 권장**이다(경험을 입력했으면 사용자가 입력한 문장과 정규화한 글이 똑같은 문장만 위반에서 빼고 — 계획이 입력을 되풀이하는 `이름(입력): 내용` 줄은 내용만 견준다 1천만 건에서 0 이 되는 로그 눈금이라 많을수록 낮음, 관심도 20 — 상승 100·보합 50·하락 0, 없는 하위 점수는 빼고 다시 나눔) 없으면 그 요인을 **빼고 나머지 가중치를 다시 나눈다** — '데이터 없음' 을 0점으로 치지 않는다. 외부 지표는 보관함의 같은 키워드 후보(CSV 로 가져온 값)에서 키워드로 찾아 쓴다(블로그와 상관없이 같은 값). 조회일은 오늘 기준 며칠 지났는지로 보이고 30일을 넘으면(정확히 30일은 아직 아니다) '오래된 데이터' 라고, 오늘보다 이틀 이상 앞선 날짜면 '날짜를 확인하라' 고 알린다(점수는 깎지 않는다). 이번 제안은 '계산일' 과 '외부 데이터 없음' 을 나눠 보인다. ⑤ **다양성**: 점수 순(같으면 조합 순서)으로 훑으며 같은 키워드·낱말 집합이 0.7 이상 겹치는 키워드는 건너뛰고, 한 씨앗·한 틀·한 글 유형이 요청 개수의 40%·20%·40%(올림)를 넘지 않게 한 뒤 모자라면 상한만 풀어 채운다. ⑥ **보관함 후보에 같은 계산**: `candidates list --priority`·`show` 가 `suggest.assess` 로 우선도·적합도·이유를 지금 계산해 덧붙여 보인다(저장된 값은 바뀌지 않고 읽기만 한다 — 사람이 적거나 CSV 로 가져온 우선도·적합도·기회도 칸은 `show` 에서 '이전에 적어 둔 값' 으로 따로 밝히고 계산에는 쓰지 않는다 · 자기 자신의 제목·이어진 글의 제목은 기존 글과 견주지 않는다). **`suggest` 는 읽기만 한다**(`ctx.reading_only()` — 보관함이 없으면 만들지 않고 옛 구조(판 1)도 올리지 않으며 데이터 폴더의 모든 파일이 그대로다). 기존 글 제목은 보관함의 원고 제목과 '선택됨' 후보의 주제에서만 읽는다 — 연결한 chanceblog 저장소의 `_posts` 머리말 제목은 읽지 않는다(`publish/` 에 제목만 안전하게 읽는 함수가 아직 없어 이번에는 하지 않았다 — **알려 둔 한계**). **`--add 번호|범위|all|키워드 [--yes]`**: `--yes` 없이는 넣을 목록만 보이고, `--yes` 로는 보관함의 한 쓰기 트랜잭션(`Store.add_candidates`) 안에서 같은 키워드·같은 블로그의 후보가 이미 있는지 **키워드로 다시 확인**해 있으면 건너뛰고 새 후보(상태 새 후보, 출처 표시는 추천 이유 앞의 '프로필 제안 —', 계산한 점수·적합도는 저장하지 않는다 — 후보 모델·보관함 스키마는 그대로)로 넣는다. `all` 은 처음 보이던 번호 1~개수라 되풀이해도 다음 제안이 딸려 들어가지 않는다. 키워드로는 보여 준 개수 밖의 제안(`Report.more` — 관문을 통과했지만 개수나 다양성 때문에 목록에 오르지 못한 것, JSON 에는 싣지 않는다)에서도 찾는다. 화면의 '넣으려면' 안내는 번호를 바꾸는 `--count`·`--month`·`--type` 도 적어 준다. 없는 번호·키워드는 `SUGGESTION_NOT_FOUND`(아무것도 넣지 않고, 오류 문구에 사용자가 친 값을 싣지 않는다). 알려 둔 한계: 계절표·글 틀은 **일반적인 시기 주제와 틀일 뿐 검색 수요를 보증하지 않는다** · 월간 검색 수요 같은 외부 지표를 모으는 일(네이버 API·키)은 없다 · 프로필(주제)을 저장하는 곳은 네이버 A·B 뿐이라 다른 블로그는 제안하지 않는다 · 시각 표시·최근 선택의 '며칠' 은 한국 시간(+9) 달력이다 · **위험 낱말·경험 단정 거르기는 한국어 낱말 규칙이라 놓치거나 잘못 걸러 낸다** — 독립 검증 2차가 새 예문으로 잰 값은 겪은 일 주장 30%·결과 보장 약속 46%·돌려 쓴 표현 88% 를 놓치고, 일부러 어렵게 고른 정상 주제 62%·일반 주제 7% 를 잘못 걸렀다(D-29 ⑫). 제안은 사람이 고르는 후보일 뿐이라 어색하거나 겪지 않은 일을 전제하면 `--add` 하지 않고 넘긴다.
- **하지 않는 것**(이 `service/` 층 — 화면은 `ui/` 가 맡는다, §5.1): Blogger·예약 작업·자동 업데이트·설치 파일·보조 AI(`assist/`)·네이버 로그인·브라우저 자동화(AGENTS.md 규칙 6). 같은 날 자동 글 수 확인·`history.json` 기록·제목 유사도는 §3 마지막 줄에 적은 이유로 하지 않는다 — **같은 주소(slug)** 와 **같은 내용의 글** 중복만 확인한다(백업으로 되돌려 이미 올린 글이 다시 '승인됨' 이 되어도 `DUPLICATE_CONTENT` 로 막는다 — 내용이 한 글자라도 다른 글은 새 글로 본다). Pages 글의 대표 이미지는 https 주소만 쓴다(내 이미지 파일을 저장소에 두는 방식은 아직 없다).
- 알려 둔 한계: 저장소 잠금은 저장소의 `.git` 안에 있어 데이터 폴더가 달라도 서로를 알지만, 이 보강 전에 `--data-dir` 이 다른 두 앱이 동시에 올려 쌓인 commit 의 흔적은 남아 있을 수 있다 — `doctor`·올리기 안내가 '이 데이터 폴더에 기록이 없는데 앱이 만든 모양(제목이 '글 올리기(데스크톱 앱):')인 commit' 을 직접 만든 commit 과 구분해 말하고(그 앱에서 맨 위 commit 의 글부터 `--cancel --yes`), 이 데이터 폴더의 글이 맨 위 commit 이면 올릴 수는 없어도 되돌릴 수는 있다고 말한다 · 저장소 잠금의 위치가 데이터 폴더에서 `.git` 으로 바뀐 앞뒤 두 버전의 앱을 동시에 실행하면 서로의 잠금을 모른다(업데이트할 때는 앱을 모두 닫고 한다) · 공개 확인(`check-deploy`)은 저장소 잠금 없이 저장소의 `_config.yml` 을 읽으므로 다른 글이 받아 오는 바로 그 순간과 겹치면 드물게 한 번 실패할 수 있다(같은 명령을 다시) · 잠금 파일을 남긴 프로세스가 **다른 PC** 의 것이거나 살아 있는지 확인할 수 없으면 30분(기다리는 시간이 길면 그 + 15분)을 기다린다 · 프로세스 번호가 재사용된 경우 POSIX 에서는 가려내지 못한다(Windows 는 시작 시각으로 가려낸다) · 공개 확인을 기다리는 동안 명령이 멈춰 있고(기본 최대 12분, `--wait` 최대 6시간) 기다릴 때마다 표준 오류로 진행을 알린다(`--no-wait` 로 건너뛰고 나중에 `check-deploy`) · commit 직후에 멈춘 뒤 **원고를 고쳐 다시 승인한 경우**는 이어받을 수 없다(내용이 달라서) — 앱이 정리하지 못하고 `doctor` 도 알려 주지 못하니 사람이 `git log` 로 확인한다 · `--yes`·`approve` 를 사람이 직접 입력했는지는 앱이 알 수 없다(터미널 확인이 없다) — 승인은 운영자의 채팅 승인 규칙(AGENTS.md 규칙 9)이 유일한 통제다 · 정상 코드 글의 오탐(`Map<String, List<Integer>>`·`x<y 이고 y>z`·`{:.2f}`·`{#anchor}` 가 `RAW_HTML`·`KRAMDOWN`·`LIQUID` 로 막힌다 — 코드 블록 안이어도 막는 설계)은 **미완료(설계 메모)**: 코드 블록 안의 HTML 태그 검사만 건너뛰려면 kramdown 의 코드 블록 규칙(닫힌 펜스만·줄 맨 앞·`~~~` 변형·인라인 코드·문단 바로 뒤의 펜스는 코드가 아님 등)을 실제 Jekyll 빌드로 확인해 '코드로 확실한 곳만' 보수적으로 구현해야 하는데 아직 확인하지 못했다(잘못 건너뛰면 `<script>` 가 통과한다). `{% %}`·`{{ }}`·`{: }` 는 코드 블록 안에서도 사이트가 처리하므로 어떤 경우에도 계속 막는다.

### 5.1 화면(GUI) 층 — `ui/` (PySide6, D-32)

화면 도구는 운영자가 PySide6 로 정했다(2026-11-03, D-04 의 '또는' 을 닫는 결정이 D-32). **PySide6 는 선택 의존성이다** — 명령줄·서비스 층은 PySide6 없이 동작하고, `ui/core/`·`ui/adapters.py`·`ui/launcher.py` 는 PySide6 를 불러오지 않는다(시험이 소스를 훑어 지킨다).
`python -m chanceblog_desktop gui` 는 PySide6 가 없으면 쉬운 한국어로 설치 방법을 안내하고 끝난다(종료 코드 1). 새 의존성은 PySide6 하나뿐이고 `ci.yml`·CI 의존성은 이 묶음에서 바꾸지 않았다 — Qt 시험은 PySide6 가 없으면 건너뛰므로 **CI 는 `ui/qt/` 를 검증하지 않는다**(CI 에 Qt 칸을 넣는 일은 `ci.yml` 변경이라 병합 뒤 별도 묶음으로 한다 — D-32).

```text
View(ui/qt/screens·shell·components)  →  AppState(ui/core/app_state.py: 뷰모델·화면 동작)  →  HomeProvider(ui/core/services.py)  ┬ FakeHomeProvider(가짜 — '예시 데이터')
        ▲ 시그널(작업 스레드 → 화면 스레드)                                  JobRunner(ui/core/jobs.py: 작업 스레드)             └ ServiceHomeProvider(ui/adapters.py → service/ 읽기 전용)
```

- **값은 한 곳**(`ui/core/tokens.py`): Theme Token(색 — 밝은 테마만, 사용자 화면에 테마 선택 없음, 나중에 어두운 테마를 같은 키로 더할 수 있음)·**Text Token 5개**(`Text/Strong #0B1736`·`Text/Primary #14213D`·`Text/Secondary #5F6B7A`·`Text/Muted #8491A3`·`Text/Disabled #AAB4C3` — 순수 검정을 글자색으로 쓰지 않는다)·Typography Token(크기·굵기·행간)·간격·모서리·그림자·크기·움직임. Qt 스타일시트(`qt/theme.py` 의 `build_qss`)는 이 값으로만 만들고, 화면 코드에는 색 값·인라인 스타일·글꼴 이름이 없다(시험이 막는다).
- **글꼴**: 특정 글꼴 이름을 두지 않고 `QFontDatabase.systemFont()`(일반 `GeneralFont`, 로그·경로·진단 정보만 `FixedFont`)의 Family 를 따르며 크기·굵기는 Typography Token 이 정한다. **화면 배율**: Qt6 High DPI 자동 처리를 그대로 쓰고 배율을 곱하거나 고정하지 않는다(논리 px 만 쓴다). 아이콘은 SVG 를 그릴 때마다 그린다(`SvgIconEngine`).
- **부품 규칙**: 화면(`screens.py`·`shell.py`)은 Qt 기본 위젯(`QPushButton`·`QLabel` …)을 직접 만들지 않고 `components.py` 의 부품만 쓴다. 누르는 칸은 36px 이상·중요 단추 40~44px, 아이콘 단독 단추는 접근 이름+툴팁(키보드 포커스에도 보임)이 필수, 눌리는 모든 것은 Tab·Enter·Space 로 쓸 수 있고 포커스 링이 보이며 Esc 로 대화상자·서랍을 닫는다(열려 있는 동안 Tab 은 그 안에서만 돈다). 고정 폭·높이는 쓰지 않고 `QLayout`·`QSizePolicy` 로 배치하며(그림 칸 제외) 가로 스크롤 막대는 끄고 배치를 바꿔 맞춘다(보장은 아니다 — 아주 긴 한 낱말·큰 글자에서는 글이 잘릴 수 있다, [`UI_DESIGN_SPEC.md`](UI_DESIGN_SPEC.md) §3) — 폭에 따라 요약 카드 4→2→1열, 오른쪽 패널 옆→아래, 추천 행의 지표 칸 접기로 바뀐다. 자세한 목록은 [`UI_COMPONENTS.md`](UI_COMPONENTS.md), 값은 [`UI_DESIGN_SPEC.md`](UI_DESIGN_SPEC.md).
- **서비스 연결**: 화면은 서비스 층을 직접 부르지 않는다. `HomeProvider.load_home(progress, cancelled)` 는 **작업 스레드에서** 불리고(화면 스레드를 막지 않는다 — 이 구현의 실측: 1.2초짜리 일 동안 화면이 멈춘 가장 긴 틈이 작업 스레드 176ms(끝날 때 화면을 다시 그리는 시간 포함) 대 화면 스레드에서 직접 기다리면 1,236ms, [`UI_VISUAL_QA.md`](UI_VISUAL_QA.md) §4), 가짜 공급자는 `sample=True` 라 화면에 '예시 데이터' 표시가 붙는다. 실제 어댑터는 `candidates list` 와 같은 함수(`service/candidates.list_candidates`)와 글 목록(`service/projects.list_projects`, 읽기 전용)만 읽어 화면용 값으로 바꾼다 — 가져올 수 없는 값은 `None`(보이지 않음 또는 '데이터 없음')이고 서비스 오류는 쉬운 문장 + 오류 코드(진단 정보에만)로 바뀐다. 작성 완료·발행 완료 수는 글의 플랫폼별 상태에서 센다(`DONE_STATES`·`status.is_published`). 화면에 나갈 글은 **가린 뒤에 자른다** — 블로그 이름(30자)은 뷰모델과 같은 `shown`(가리기 → 자르기)으로, 오류 문구의 값 자리(오류 층이 160자에서 자른다)는 어댑터가 자르기 전에 먼저 가려서 넘긴다(자르기가 먼저면 키가 반쪽이 되어 가림 규칙이 못 알아본다). 직접 정한 `--data-dir` 가 없거나 파일이면 빈 화면 대신 쉬운 안내가 나오고, 읽기만 하는 화면에서는 '저장하지 못했습니다' 류 오류 문구를 '읽지 못했어요' 로 바꾼다(코드는 진단 정보에 그대로). 어댑터는 단계 사이마다 취소를 확인한다.
- **화면 표와 설정 화면(P4a, D-90~D-97)**: `ui/qt/screens.py` 의 `SCREEN_BUILDERS`(메뉴 → 화면 만드는 함수 표 — `app_state.NAV` 의 여섯 열쇠마다 한 줄)가 어느 메뉴가 어느 화면인지 정하고 `AppShell.render()` 는 이 표 한 곳만 거친다. 홈과 설정만 화면이 있고 나머지 넷은 같은 자리표시다. 화면마다 공급자를 두는 틀을 따라 설정 화면은 `ConnectionsProvider`(`ui/core/services.py` — 가짜 `FakeConnectionsProvider`, 실제 `ui/adapters.py::ServiceConnectionsProvider`)를 읽는다: 홈 공급자가 `connections_provider()` 로 짝을 돌려주어 `--sample`·`--data-dir` 선택이 설정에도 같게 적용된다. 뷰모델은 `ui/core/settings_view.py`(순수)이고 상태는 `AppState.conn_*`(홈과 따로, 작업 이름 `settings-load`)다. 어댑터는 `service/connections.py`(`load`·`listed_purposes`·`secret_present`·`purpose_status`)와 `service/quota.py`(`QuotaGuard.usage`) 읽기 함수만 부르고 **키 값을 꺼내지 않는다**(보관소에는 '있나' 만 묻는다 — `keystore.get`·끝 4자 없음, 쓰기 호출 없음). 자세한 값·상태는 [`UI_DESIGN_SPEC.md`](UI_DESIGN_SPEC.md) §4-2·[`UI_STATES.md`](UI_STATES.md) §5.
- **작업 스레드**(`ui/core/jobs.py`): 같은 이름의 작업은 하나만 돈다(중복 클릭은 거절하고 안내), 취소는 협조적이고(취소를 눌렀으면 늦게 온 결과도 버리고, 화면을 먼저 풀고 안내했으면 늦게 끝난 일의 취소 신호는 무시한다), 실패해도 입력(payload)은 그대로 돌려주며, 기술 문구를 그대로 내보내지 않는다. 콜백은 작업 스레드에서 불리고 Qt 쪽은 시그널(`ui/qt/workers.py`)로 화면 스레드에 넘긴다. 작업이 `SystemExit` 로 끝나도 '실패' 로 알려 영원히 running 으로 남지 않는다. 화면 스레드의 결과 슬롯(`AppShell._on_loaded` 등) 안에서 난 예외는 `_guarded` 가 잡아 '불러오는 중' 에 멈추지 않고 오류 상태(쉬운 문장 + 예외 이름만 진단 정보에)로 바꾸며 원인을 한 줄로 표준 오류에 남기고(콘솔 실행 기준 — `pythonw`·창 없는 exe 처럼 표준 오류가 없으면 남지 않는다, 로그 파일은 설치 파일 묶음), 그 밖에 처리하지 못한 예외는 `sys.excepthook`(`ui/qt/app.py` 의 `make_excepthook`)이 **한 줄**(예외 이름 + 비밀을 가리고 경로를 지운 글)만 표준 오류에 남기고 쉬운 안내(토스트)를 보인다. 창을 닫을 때는 창을 먼저 숨기고 끝나지 않은 작업을 최대 1초 기다린다.
- **알려 둔 한계**: 홈과 설정 외의 화면(주제 후보 목록·초안·발행 기록·블로그 관리)은 '아직 만들고 있어요' 안내 화면이다(다음 묶음). 윈도의 '텍스트 크기' 접근성 설정은 반영하지 않는다(글자 크기는 토큰이 정하고 화면 배율만 Qt 가 처리). 실제 윈도 125·150% 렌더·한글 입력기·화면 읽기 프로그램(Narrator 등) 동작·개인 PC 확인은 운영자 PC 검증으로 남는다([`UI_VISUAL_QA.md`](UI_VISUAL_QA.md)). **PySide6 는 LGPL 이다** — 설치 파일에 넣어 배포하기 전에 고지·재배포 조건을 검토한다(D-32, [`RELEASE.md`](RELEASE.md)). 독립 검증이 지적한 그 밖의 한계(명세와 다른 모양·좁은 곳·가리기 규칙의 빈틈 등)는 [`UI_DESIGN_SPEC.md`](UI_DESIGN_SPEC.md) §9 에 모았다.
- **사진·검수 도구**(`scripts/ui_capture.py`·`ui_image_check.py`·`ui_offscreen.py`): 창을 띄우지 않고(offscreen) 환경별 사진·글자 잘림·누르는 칸·가로 스크롤을 점검하고 내 사진 형식별 로딩표를 만든다. 화면 없는 환경은 운영체제 글꼴을 몰라 점검 도구만 윈도가 알려 준 시스템 글꼴을 대신 건넨다(앱 코드는 쓰지 않는다).

## 6. 오류 안내 — 규칙 기반이 먼저다

실패는 AI 가 아니라 **오류 코드 → 플랫폼별 안내 문구**로 설명한다. 예: Blogger HTTP 401 → `BLOGGER_AUTH_EXPIRED`(인증 만료·다시 로그인 안내), Git push 실패 → `GIT_PUSH_AUTH`/`GIT_PUSH_NETWORK`/`GIT_PUSH_REJECTED`(저장소 인증·네트워크·최신 상태 확인), Actions 실패 → `ACTIONS_RUN_FAILED`(실패한 워크플로·잡 이름과 링크 표시), 파일 생성 실패 → `FILE_WRITE_FAILED`(저장 경로·권한 확인), API 호출 제한 → `API_RATE_LIMITED`(재시도 가능 시간 표시). 코드 목록과 문구는 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) 가 정본이고, `errors/catalog.py` 는 그 표에서 `scripts/sync_errors.py` 가 **만든 파일**이며 **시험이 둘이 같은지 확인**한다(표만 고치고 다시 만들지 않으면 실패). 표에 없는 코드는 `UNEXPECTED_ERROR` 로 안내해 오류 안내가 또 실패하지 않게 한다. 로그와 오류 보고서에는 키·토큰을 쓰지 않는다.

## 7. 선택 보조 AI — 기본 꺼짐, 최소 인터페이스

범위(필요성이 확인됐을 때만 추가): ① 감시 결과 한 줄 요약 ② 긴 오류 로그의 간단한 설명 ③ 사용자가 확인할 조치 추천 ④ 주간 운영 결과 요약.
- `assist/` 는 작은 인터페이스(`is_configured()`·`summarize(text, task)`)와 아무 일도 하지 않는 기본 구현(`NullAssistant`)만 둔다. **`assist/` 에는 여러 공급자를 두거나 한도 소진 시 자동 전환하는 구조(AI Router)를 두지 않는다**(D-15). 운영자가 2026-11-03 에 정한 좁은 범위의 키 전환(D-31)은 `service/quota.py` 가 맡는다. 새 공급자가 필요해지면 그때 새 결정으로 연다.
- **AI 가 없어도 모든 핵심 기능이 동작한다.** AI 연결 실패·키 없음·시간 초과는 그 보조 기능만 건너뛰고(`ASSIST_UNAVAILABLE`) 프로그램 전체 오류로 번지지 않는다. 입력은 소독·마스킹하고 비공개 원고는 보내지 않는다. 출력은 '보조 의견(미검증)'으로 표시하고 어떤 결정·게시에도 직접 쓰지 않는다.
- 기존 Gemini 기능(`chanceblog` 클라우드 파이프라인)은 그대로 두고, 이 앱에서는 선택 기능으로만 연결한다.

- API 키 원문은 데이터베이스·프로젝트 파일·로그에 저장하지 않는다.
- **작성 기반**(`DraftPlan` — 제목 후보·목차·핵심 내용·태그·확인 권장)은 저장하지 않는다. 후보·블로그 프로필·선택 입력(`DraftOptions`)에서 그때그때 계산해 보여 줄 뿐이라 보관함 구조(판 2)는 그대로이고 사용자가 입력한 값도 보관함에 남기지 않는다(초안을 저장하게 되면 그때 정한다).
- **상태 흐름**(코드 `content/status.py` 의 `FLOWS` 가 이 표와 같고 시험이 확인한다. 굵게 쓴 공개 상태는 되돌리지 않는다 — 공개 취소는 사람이 플랫폼에서 한다):
  - GitHub Pages: `NOT_STARTED` → `DRAFT_GENERATED` → `REVIEW_REQUIRED` → `APPROVED` → `COMMITTED` → `PUSHED` → **`PUBLISHED`**
  - Blogger(영문·한글): `NOT_STARTED` → `DRAFT_GENERATED` → `REVIEW_REQUIRED` → `APPROVED` → `DRAFT_SAVED` → **`PUBLISHED_MANUAL`** (공개는 운영자가 Blogger 에서)
  - 네이버 A·B: `NOT_STARTED` → `DRAFT_GENERATED` → `REVIEW_REQUIRED` → `READY_TO_COPY` → `COPY_COMPLETED` → **`PUBLISHED_MANUAL`**
  - 어느 플랫폼이든 승인 단계에서 `REVIEW_REQUIRED` 로, 검토 단계에서 `DRAFT_GENERATED` 로 물러설 수 있고, 올리는 중에 실패하면 `PUBLISH_FAILED`(오류 코드 필수)로 갔다가 `REVIEW_REQUIRED` 나 `DRAFT_GENERATED` 로 돌아가 다시 한다.
- **상태 규칙**: ① 원고를 고치면(판 번호 `revision` 이 오른다) 검토·승인·초안 저장·복사 중이던 변형은 `DRAFT_GENERATED` 로 돌아가 처음부터 다시 검토한다 — 이미 올라간 `COMMITTED`·`PUSHED`·공개 상태는 과거의 사실이라 그대로 둔다. ② 승인(`APPROVED`·`READY_TO_COPY`)은 **현재 판으로 만든 렌더링**에만 줄 수 있다. ③ 공개 상태로 바꿀 때는 **발행 주소**(https, 로그인 정보 없음, 네이버는 `blog.naver.com` 주소)가 있어야 한다. ④ `PUBLISH_FAILED` 로 바꿀 때는 **오류 코드**가 있어야 한다. 규칙을 어기면 오류 코드(`STATUS_TRANSITION_INVALID`·`PUBLISHED_URL_REQUIRED`·`PUBLISHED_URL_INVALID`·`NAVER_PUBLISH_URL_INVALID`·`CONTENT_INVALID`)로 거절하고 아무것도 바꾸지 않는다.
- 네이버: 두 네이버 블로그는 같은 주제여도 **제목·도입부·문단 구성·태그를 각자 프로필에 맞게 변환하고 각각 검수**하며, 유사도가 기준을 넘으면 경고하고 운영자가 명시 승인해야 `READY_TO_COPY` 가 된다. 같은 원고를 그대로 복제하는 기능은 기본값으로 두지 않는다. 네이버 A·B 는 표시명·URL·주제·대상 독자·말투·카테고리 매핑·기본 태그·금지 표현·이미지 규격·글 길이·발행 주기·발행 이력을 **각자 독립 프로필**로 관리한다.
- **주제 후보**(코드 `content/candidates.py`, 보관함 `candidates` 표): 후보 하나는 추천 포스팅 주제·핵심 키워드·보조 키워드·추천 대상 블로그(다섯 플랫폼 중 하나 이상)·추천 글 유형(정보형·비교형·문제 해결형·제품·서비스 소개형·장소·업체 정보형)과 **선택 지표**(월간 검색 수요·관련 블로그 검색 결과 수·최근 관심도 변화·모바일 비중·계절성·기존 글 중복 여부·블로그 프로필 적합도·콘텐츠 작성 우선도·키워드 기회도), 추천 이유·데이터 조회일·연결한 글 번호를 가진다. 지표는 모두 비워 둘 수 있고('데이터 없음') 값이 하나라도 있으면 조회일도 있어야 한다. 후보를 모으는 일(네이버 자료 수집)과 초안 문장 만들기는 이 자료의 일이 아니다 — 프로필로 먼저 제안하는 규칙과 우선도·기회도 계산 틀은 `content/suggest*.py` 에 따로 있고(§5) 후보 자료의 칸(`priority`·`profile_fit`·`keyword_opportunity`)은 사람이 적거나 CSV 로 가져온 값을 담을 뿐이라 제안은 그 칸을 쓰지도 채우지도 않는다.
  - **상태**(코드 `TRANSITIONS` 가 이 줄과 같고 시험이 확인한다): `NEW` → `REVIEW`·`SELECTED`·`HOLD`·`REJECTED` / `REVIEW` → `SELECTED`·`HOLD`·`REJECTED` / `HOLD` → `REVIEW`·`SELECTED`·`REJECTED` / `REJECTED` → `REVIEW` / `SELECTED` → `HOLD`·`REVIEW`. 화면에는 새 후보·검토 중·선택됨·보류·제외로 보인다. 초안 이후의 상태는 후보에 새로 만들지 않고 글의 네이버 흐름 상태에 대응시킨다(요구서의 DRAFTING·DRAFT_READY·COPIED·PUBLISHED 는 각각 `DRAFT_GENERATED`·`READY_TO_COPY`·`COPY_COMPLETED`·`PUBLISHED_MANUAL` 에 대응하고, 화면에는 초안 작성 중·초안 완료·복사 완료·발행 완료로 보인다).
  - **규칙**: ① '선택'은 블로그마다 따로 기록한다(`selections` — 이미 '선택됨'인 후보에 블로그를 더 고르는 것은 상태 이동이 아니라 선택 기록을 더하는 일이다. 보류·검토 중으로 물렸다가 다시 고르면 그때 고른 블로그만 기록에 남는다 — 물리기 전에 고른 것은 취소된 것이라 재선택 경고에 되살아나지 않는다) — 같은 주제를 두 블로그에서 쓸 수 있고, 같은 핵심 키워드(띄어쓰기와 덜 중요한 기호는 무시하되 `+`·`#`·숫자 사이의 소수점은 구별한다 — C++ 와 C# 은 다르고 1.5 와 15 도 다르다)를 **같은 블로그용으로** 그 블로그 프로필의 `topic_reuse_days`(기본 90일) 안에 이미 고른 '선택됨' 후보가 있으면 `Store.recent_selections` 가 알려 준다(경고용이고 막지 않는다). ② 후보는 바꿀 수 없는 값이라 바꿀 때마다 판 번호가 오르고, 저장은 **내가 불러온 판에서 바뀐 것**일 때만 된다(`save_candidate` 의 `expected_revision` — 주지 않으면 판 바로 앞이고, 저장된 판이 다르면 `STORE_CONFLICT` 다. 한 번에 한 판씩만 오르므로 낡은 복사본이 판 번호가 높다는 이유로 다른 쪽의 변경을 덮어쓰지 못한다. 여러 번 고친 복사본은 불러온 판을 `expected_revision` 으로 준다). 상태도 저장될 때 저장된 상태에서 위 표에 있는 곳으로만 바뀐다(`dataclasses.replace` 로 만든 후보도 같다 — 표에 없으면 `CANDIDATE_TRANSITION_INVALID`). ③ '상위노출 보장'·'노출 확률'·'검색 1위 가능성'·'수익 보장' 같은 결과를 약속하는 표현은 주제·키워드·보조 키워드·추천 이유에 쓸 수 없다(영어 'guaranteed #1 ranking'·'guaranteed income' 과 한자 섞기도 같다). 낱말이 바로 이어질 때만 걸리고, '보장하지 않습니다'·'보장할 수 없다' 같은 부정이나 '상위노출 보장 업체 피하는 법' 같은 경계하는 글은 지나간다('광고 노출 확률 높이는 법' 처럼 표현 자체를 쓴 글은 걸리니 말을 바꿔 쓴다). 위험한 HTML 태그·이벤트 속성·스크립트 주소·템플릿 표기도 쓸 수 없지만 `Map<String, List<Integer>>`·`JavaScript: 비동기` 같은 글은 지나간다. 지표는 정해진 이름(키워드 기회도·콘텐츠 작성 우선도·블로그 프로필 적합도·최근 관심도 변화·관련 블로그 검색 결과 수 …)으로만 부른다. ④ 후보를 지울 때는 확인이 있어야 하고(`CANDIDATE_CONFIRM_REQUIRED` — 문구에 후보의 주제와 짧은 번호가 보인다. 명령줄 `candidates delete` 는 서비스 층의 `CONFIRMATION_REQUIRED` 로 먼저 막으므로 사용자에게는 그 코드가 보이고 이 코드는 저장소를 직접 쓰는 쪽의 이중 방어다) 연결한 글은 남는다 — 연결한 글을 지우면 후보는 남고 연결만 끊긴다. ⑤ 판 번호는 1~10억, 고친 시각은 만든 시각보다 앞설 수 없고, 새 후보에는 선택 기록이 있을 수 없으며, `blogs`·`sub_keywords` 는 list·tuple 만 받는다. 깨진 후보 한 행은 그 후보만 막고(`CANDIDATE_CORRUPT` — 목록 조회는 멈추지만 그 후보만 `delete_candidate` 로 지울 수 있다) 원고와 다른 후보는 그대로다. 오류 코드: `CANDIDATE_INVALID`(칸 값 — 어느 칸이 왜 안 되는지 문구에 담긴다)·`CANDIDATE_NOT_FOUND`·`CANDIDATE_TRANSITION_INVALID`·`CANDIDATE_CONFIRM_REQUIRED`·`CANDIDATE_CORRUPT`, 명령줄에서 더해진 `CANDIDATE_AMBIGUOUS`(번호 앞부분이 여러 후보와 맞음)·`CANDIDATE_CSV_INVALID`(CSV 파일 전체를 가져올 수 없음).

## 10. 로컬 데이터와 백업

사용자 데이터는 `%LOCALAPPDATA%\ChanceblogDesktop\`(설정·SQLite·이미지·백업·로그)에 둔다. **구현(`service/context.py`)**: 글 저장소 `chanceblog.db`·설정 `settings.json`(연결한 chanceblog 폴더·네이버 프로필 — 키·토큰 없음)·백업 `backups/`·올리는 중인 글 기록 `publish/`·연결 설정 `connections.json`(키 항목의 이름·상태 같은 메타데이터뿐 — 키 값은 없고 키는 Windows 자격 증명 관리자에만 있다)·사용량 기록 `quota_state.json`·잠금 파일 `locks/`. 폴더는 `--data-dir`·환경 변수 `CHANCEBLOG_DESKTOP_DATA` 로 바꿀 수 있지만 git 저장소 안은 거절한다. 설치 폴더 밖이라 업데이트가 `current` 만 교체해도 데이터가 남는다. 업데이트 전에 SQLite backup API 로 스냅샷하고 최근 N개를 보관하며, 스키마는 `PRAGMA user_version` 으로 순방향 마이그레이션, 실패하면 백업 복원.

**구현**: `src/chanceblog_desktop/content/store.py`(`Store`) — 파일 하나에 `projects`·`revisions`(원고의 판 기록, 프로젝트마다 기본 50개)·`drafts`(자동 저장 초안)·`candidates`(주제 후보, 스키마 판 2 — 판 1 의 파일은 열 때 사본 `.v1.bak` 을 두고 이 표만 더한다) 네 표. 열 때 `application_id`(이 프로그램의 파일인가)·`user_version`(더 새로운 버전이 만든 것은 아닌가, 0·음수는 이 프로그램이 만든 적이 없다)·`quick_check`(깨지지 않았나)·표와 열이 그 판에 맞는가를 보고, 아니면 **파일을 한 바이트도 바꾸지 않고**(사본도 만들지 않고) `STORE_CORRUPT`·`STORE_VERSION_UNSUPPORTED` 로 멈춘다. 옛 구조는 **쓰기 잠금을 잡은 뒤** 판 번호를 다시 읽어(그 사이 다른 창이 이미 올렸으면 아무것도 안 하고 성공으로 이어 간다 — 여러 창이 동시에 열어도 한 곳만 올린다) 사본(`<파일>.v<번호>.bak`)을 두고 한 트랜잭션으로 올리며, 판 번호도 같은 트랜잭션 안·COMMIT 앞에서 올라가므로 어느 순간에 죽어도 '옛 판 그대로' 아니면 '새 판 전체' 다. 이미 있는 사본은 덮어쓰지 않는다 — 똑같은 내용이면 그것을 쓰고, 다르거나 못 읽는 것이면 건드리지 않고 `.v1.2.bak` 처럼 다른 이름으로 새로 만든다(사본은 임시 이름으로 만들어 점검한 뒤 이름을 바꾼다). 올리는 DDL 은 판마다 상수로 고정돼 있고(판 2 의 `_V2_CANDIDATES` — 시험이 해시로 지킨다, 나중에 표를 바꾸면 판 3 단계를 따로 만든다) 다시 돌려도 안전하며(`IF NOT EXISTS` + 만든 것이 정해 둔 모양인지 확인), 올리다 난 오류는 잠김 `STORE_LOCKED`('잠시 뒤 다시')·디스크 가득·읽기 전용·경로가 너무 김·사본을 못 두는 폴더 `MIGRATION_BLOCKED`(파일은 바뀌지 않았다고 알린다)·그 밖 `MIGRATION_FAILED` 로 나뉜다. **읽기만 하는 도구(점검 같은 것)는 `Store.open(경로, migrate=False)` 로 연다** — 파일을 만들지도 올리지도 않고 한 바이트(수정 시각까지)도 바꾸지 않으며(옛 판 파일은 `needs_migration`·`schema_version` 으로 알려 줄 뿐이다) 쓰는 일은 모두 거절한다 — 단 보관함 파일을 바꾸지 않고 다른 폴더에 사본만 만드는 `backup()` 은 허용한다(쓰다가 갑자기 꺼져 정리 못 한 저장 — `-journal` 파일 — 이 남은 파일은 읽기 전용으로 정리할 수 없어 `STORE_RECOVERY_PENDING` 으로 알리고 그대로 둔다. 일반 열기가 정리한다). 읽기 전용 열기의 SQLite 주소(`mode=ro`)는 `_read_only_uri` 가 직접 만든다 — 네트워크(UNC) 경로는 `file:////서버/공유/…`, 확장 경로(`\\?\C:\…`)는 접두사를 걷은 주소라 매핑한 네트워크 드라이브·UNC 위의 데이터 폴더에서도 열린다(`Path.as_uri()` 가 만든 `file://서버/공유/…` 는 SQLite 가 `invalid uri authority` 로 거절했다. 보통 경로로 열어 `PRAGMA query_only` 를 거는 방법은 연결이 쓰기 가능이라 옛 저널을 되돌려 파일을 바꿀 수 있어 쓰지 않았다). 쓰는 일은 모두 한 트랜잭션이고 저장된 판보다 낮은 판으로는 덮어쓰지 않는다(`STORE_CONFLICT`). 읽을 때 `ContentProject.from_dict` 의 엄격한 검사를 다시 거치고, 여러 스레드가 함께 써도 한 번에 하나씩 실행한다. `backup()` 은 SQLite backup API 로 점검한 사본(`<이름>-YYYYMMDD-HHMMSS.db`)을 만들고 최근 10개만 남기며, `restore_from()` 은 이 프로그램의 온전한 백업이 아니면 아무것도 바꾸지 않는다(원하면 바꾸기 직전 상태를 먼저 따로 백업한다). 주제 후보를 여럿 새로 더하는 일은 `add_candidates(plan)` 이다 — 쓰기 잠금을 잡은 **뒤** 지금 있는 후보를 읽어 `plan` 에 넘기고 그것이 돌려준 후보를 한 트랜잭션으로 저장하므로(하나라도 안 되면 하나도 저장되지 않는다) 같은 후보를 두 프로세스가 동시에 더해도 겹치지 않는다. `candidate_ids()` 는 자료를 읽지 않고 번호만 오름차순으로 준다(깨져서 목록을 막는 후보를 번호 앞부분으로 찾아 지울 때).

**주제 엔진(P3)**: 사용자 데이터 폴더 아래 `topic_engine\` 에 보관함 `topic_engine.db`(자체 `application_id`·`user_version` — 글 보관함 `chanceblog.db` 와 서로 모른다)와 설정 파일 셋 `channel_profiles.json`·`seeds.json`·`calendar.json`을 둔다 (파일마다 `schema` 숫자와 정확한 칸 집합, 모르는 칸 거절, 없으면 기본값으로 읽고 **만들지 않는다** — 만드는 것은 `topics init --yes` 뿐이다). 백업·복원은 `backups/topic_engine/` 에 따로 둔다(기존 `backup` 은 그대로 `chanceblog.db` 만 다룬다). API 키·자격 증명은 어느 파일에도 없고 백업에도 없다(백업은 키·토큰 모양이 보이면 만들지 않는다).

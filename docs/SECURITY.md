# 보안

이 저장소는 **공개**이고 앱은 운영자의 개인 PC 에서 키를 다룬다. 규칙의 정본은 `chanceblog` 의 `docs/SECURITY_GUARDRAILS.md`(G-S 비밀·G-L 호출·G-C 채널)이고, 여기에는 앱 고유의 것만 적는다.

## 1. 키와 비밀

| 비밀 | 어디에 | 이 저장소에 |
|---|---|---|
| 선택 보조 AI 키(Gemini 등 — 기본은 없음)·네이버·이미지 공급자 키 | **Windows 자격 증명 관리자**(OS 보안 저장소) — `keys add` 의 숨김 입력으로만 넣는다(§7). 키가 없어도 모든 핵심 기능이 동작한다 | 없음 |
| Blogger OAuth 토큰·클라이언트 비밀 | 같은 곳(앱이 브라우저 loopback 로그인으로 받음) | 없음 |
| 업데이트 서명 개인키 | GitHub Environment 시크릿 `UPDATE_SIGNING_KEY` + 운영자의 오프라인 백업 2곳 | 없음(공개키는 앱에 내장·저장소에 있음) |
| GitHub 토큰 | 앱에 내장하지 않는다. Pages 발행은 PC 의 Git 로그인(자격 증명 관리자)을 쓴다 | 없음 |

- 키는 소스·로그·설정 내보내기·DB 에 쓰지 않는다. 설정 내보내기 파일에는 키가 없다. 키가 없어도 앱은 수동 모드로 실행된다.
- 선택 보조 AI 키를 만들게 되면 자동 발행(Actions)에 쓰는 키와 **분리**한다(한도를 나눠 쓰지 않고, 유출 범위를 줄인다). 보조 AI 연결 실패는 해당 기능만 건너뛰고 프로그램 오류로 번지지 않는다(`ASSIST_UNAVAILABLE`).
- 실제 키가 든 `.env` 는 GitHub 에 올리지 않는다(`.gitignore`). **`.env.example` 에는 변수 이름만** 적는다. 클라우드(Actions)에서 필요한 키는 GitHub Secrets 에만 둔다.
- 유출이 의심되면 즉시 폐기·재발급한다. 저장소에서 문자열만 지워도 이력에 남는다.

## 2. 로그

요청 헤더·키·토큰·개인정보를 출력하지 않는다. 로그·오류 보고서에 나가는 글은 `src/chanceblog_desktop/security/mask.py` 의 `mask`·`safe_detail`(이를 쓰는 `AppError.log_line()` 포함)을 거친다. 규칙은 ① `chanceblog` 의 비밀 패턴 `pipeline/secret_patterns.py` 14종(`vendor/` 에 원본 그대로 — 패턴이 늘면 시험이 새 표본을 요구한다) ② 주소 속 `사용자:토큰@`(비밀번호에 `@` 가 있어도) ③ 주소의 `?access_token=`·`code=`·`session=` 같은 인자 ④ `Bearer`·`Basic` 토큰·JWT·Slack 웹훅 주소·npm 토큰·`aws_secret_access_key=`·따옴표 없는 `password: 값`·개인 키 블록 전체 ⑤ 눈에 안 보이는 글자(폭 없는 글자·방향 제어 등)로 쪼갠 토큰(그 글자를 먼저 지운다) ⑥ 정본의 `sk-` 패턴(영숫자만)이 못 알아보는 붙임표·밑줄이 든 새 키 모양 — OpenAI 프로젝트 키(`sk-proj-…`)·Anthropic 키(`sk-ant-api03-…`)·OpenRouter 키(`sk-or-v1-…`)와 그 밖의 `sk-` 긴 모양(꼬리 40자 이상에 앞 60자 안의 대문자·숫자)이다. 정본은 고치지 않고 `mask.py` 에서 더했고 `shape.py` 의 자기 검사는 이미 이 모양들을 키로 본다(시험이 둘의 일치를 지킨다). 다만 이 '가린다' 는 화면·기록 쪽이다 — 발행 직전의 비밀 차단(`publish/pages.py`)은 이 새 모양 4가지(`sk-proj-`·`sk-ant-api03-`·`sk-or-v1-`·`sk-` 일반형)를 아직 모른다(c3 이전부터의 한계이고 같은 모양 판정을 쓰게 하는 일은 후속이다). `sk-` 일반형은 대문자·숫자가 든 40자 이상 붙임표 슬러그(`sk-Hynix-Q3-2026-…`·`sk-proj-weekly-…`)도 키로 보고 가린다(오탐 — 정상 글이 가려질 수 있다). 어떤 입력에도 예외를 내지 않고, 이미 가린 글을 다시 가려도 같다(입력이 20만 자 이하일 때 — 그보다 긴 글은 비밀이 반쪽으로 잘리지 않게 공백에서 잘라 앞부분만 가리고 나머지는 내보내지 않는다). `AppError.detail` 은 화면에 내지 않고 `log_line()` 으로만 기록하며, git 의 출력은 끝 400자만 남기되 **자르기 전에** 가린다. 로그를 내보내기 전에 한 번 더 가린다. 이 규칙은 **알려진 모양**만 가린다 — 같은 종류의 토큰이 공백 없이 이어 붙은 것이나 낱말 경계로 시작하는 패턴이 앞 글자에 붙은 것(`키는ghp_…`), 줄바꿈으로 쪼갠 토큰이나 무작위 40자 문자열(AWS 비밀 키처럼 git 해시와 구분할 수 없는 것)은 못 가리므로, 비밀을 애초에 로그에 넣지 않는 것(§1)이 먼저다.

명령줄(`service/cli.py`)은 화면에 나가는 모든 글 — 일반 출력·오류·`--json` 값 — 을 같은 `mask` 로 가린다(원고·제목·git 의 오류 세부에 키 모양 문자열이 있어도 출력에는 없다). 환경 변수는 데이터 폴더·저장소 폴더 위치(`CHANCEBLOG_DESKTOP_DATA`·`CHANCEBLOG_LOCAL_REPO`)만 읽고 키·토큰은 읽지 않으며(시험 전용 가짜 보관소를 여는 `CHANCEBLOG_KEYSTORE` 는 §7 의 안전장치를 모두 통과할 때만 열린다 — `Context.get_keystore()` 가 받은 환경 변수 모음을 보관소 모듈(`security/keystore.py`)에 그대로 넘기고 그 값을 읽는 곳은 그 모듈 한 곳이다), 사용자 데이터는 저장소(git) 안에 둘 수 없다(`DATA_DIR_UNSAFE`). 시험(`tests/test_service_safety.py`)이 이 규칙들을 소스에서 직접 확인한다. 여러 줄에 걸친 비밀(개인 키 블록 — `-----BEGIN … PRIVATE KEY-----` 부터 END 까지·다음 줄에 이어지는 값)이 줄 단위 가리기를 빠져나가지 않도록 **출력 전체를 통째로** 가린다(`cli.mask_block` — 글이 아주 길면 줄 경계에서 나눠 가리되 열린 개인 키 블록 안에서는 끊지 않는다).

## 5. 올라가는 글과 승인

- **올라가는 것은 Markdown 원문이다.** 발행 전 검사(`service/gate.py`)는 그 원문에서 원시 HTML 태그·`javascript:`/`data:`/`vbscript:` 주소·`{% %}`/`{{ }}` 템플릿 표기·`{: }` 속성 붙이기·광고 스크립트를 막는다 — 공개 사이트(Jekyll)가 원시 HTML 을 그대로 내보내고 Liquid 를 글을 만들 때 실행하기 때문이다([`ARCHITECTURE.md`](ARCHITECTURE.md) §5).
- **승인 통제는 채팅 승인 규칙 하나다.** 앱은 `--yes`·`approve` 를 사람이 직접 입력했는지 알 수 없다(터미널 확인이 없다). 그래서 AI 코딩 도구가 운영자의 승인 없이 대신 입력하는 것은 [`AGENTS.md`](../AGENTS.md) 규칙 7·9 로 막는다 — 앱이 막을 수 있는 것은 확인 표시 없이 실행하지 않는 것까지다.
- **머리말 값도 같다.** 제목·분야·태그·대표 이미지 주소·설명·출처의 HTML 태그·`{% %}`/`{{ }}`·`javascript:` 같은 주소·광고 스크립트와 줄바꿈·제어 문자·따옴표/꺾쇠가 든 주소·모르는 머리말 키(`published`·`permalink` 등)를 막는다(`HEADER_VALUE`·`RAW_HTML` …). 머리말 값은 사이트의 글 목록·카드에 들어가고 일부는 이스케이프 없이 HTML 에 들어간다. 렌더링은 한 줄 JSON 으로 이스케이프해 제목의 따옴표·콜론·`---`·`#` 가 머리말 구조를 깨거나 다른 키를 끼워 넣지 못하고(시험), 게이트는 저장된 글이 바뀌어 있어도 다시 본다. 글을 만들거나 고칠 때의 제목도 같은 검사를 거친다. 알려 둔 한계: 제목의 큰따옴표는 막지 않는다(실제 Chance 글에도 있다) — 첫 화면 카드가 속성 안에 제목을 이스케이프 없이 넣는 것은 `chanceblog` 쪽에서 고칠 일이다.
- 같은 글을 두 곳에서 동시에 올리지 못하도록 글마다 잠금을 잡고(`PUBLISH_IN_PROGRESS`), **서로 다른 두 글이 같은 저장소에 동시에 commit·push 하지 못하도록** 저장소마다 잠금을 한 번 더 잡는다(`PUBLISH_REPO_BUSY` — 글 잠금 먼저·저장소 잠금 나중의 고정 순서, 죽은 프로세스의 잠금은 바로 넘겨받음). 저장소 잠금 파일은 **연결한 저장소의 `.git` 안**(`.git/chanceblog-desktop-publish.lock`)에 만든다 — 서비스 층(`service/`)이 연결한 저장소에 직접 쓰는 파일은 이 잠금 파일 하나뿐이고(글 파일은 `publish/pages.py` 가 쓴다) 잠금 파일은 git 이 추적하지 않는다. 데이터 폴더(`--data-dir`)가 다른 앱끼리도 서로를 알게 하려는 것이고, `.git` 에 만들 수 없으면 데이터 폴더로 물러서지 않고 올리지 않는다(fail closed). 이 PC 의 폴더 경로·눈에 안 보이는 글자로 길이를 채운 글·글자의 표시 방향을 바꾸는 제어 문자(U+202A–202E·U+2066–2069 — 글을 다르게 보이게 위장할 수 있다)가 든 글도 막는다.
- **작성 기반 명령줄**(`draft plan`)은 읽기만 하고 아무것도 저장하지 않는다. 사용자가 준 참고 URL 은 https 공개 주소만(로그인 정보·`javascript:`·IP 주소·토큰 인자 거절) 글자로 받고 **앱이 열지도 가져오지도 않는다** — 자동 검색·네트워크가 없어 요청 위조·토큰 유출 면이 없다. 계획의 문장은 경험·가격·날짜·통계를 지어내지 않도록 `check/claims.py` 로 확인한다(한국어 낱말 규칙이라 놓치거나 잘못 걸 수 있다 — 독립 검증자의 새 예문 기준 경험 단정 놓침 14~30%·평범한 문장 오탐 5→7%였고 c2-fix 가 기준선이 막던 문장을 못 막는 것 122→0개로 되돌렸으나 그 예문 안에서만 맞은 값이었고, 서술 끝말을 바꾼 탐침의 구멍은 2차에서 구조 규칙으로 다시 고쳤다 — 새 끝말 맹검 예문에서도 기준선이 걸던 것의 7%(46/618)는 못 건다. 개발용 예문 수치는 증거가 아니다. **이 검사는 발행을 막는 방벽이 아니라 확인을 권하는 안내이고** `draft plan` 의 문장 거름·경고와 후보 제안의 위험 표시에만 쓰이므로, 발행 관문으로 쓰기 전에 한계를 먼저 닫아야 한다. 수치와 남은 한계는 D-26 ⑤·D-33 ⑪·⑫·⑬). 주소의 비밀 인자 이름은 token·secret·password·passphrase·auth_code·code_verifier·rlkey·share_key·download_key 를 품거나 sid·ticket·code·reset·magic·invite 와 같을 때 보고 퍼센트는 세 겹까지 풀며, 후보 CSV 가 모르는 블로그 이름을 되풀이할 때 키 앞머리 조각이나 password·token·secret 낱말이 든 글은 숨긴다. 비밀번호·키·토큰처럼 보이는 글은 칸 값으로 받지 않고(거절) 모양 없는 긴 무작위 영숫자(영숫자만 24자 이상·`\uXXXX` 이스케이프를 여섯 번 넘게 이은 글·무작위로 보이는 40자 이상 base64 덩어리)도 글칸 아홉 곳에서는 거절하며(**주소 칸(`--url`)은 이 규칙 밖이다** — 무작위 40자가 든 주소가 통과해 화면에 그대로 나오고 실제 비밀 주소 18모양 중 8개(Discord 웹훅 등)를 받는다. 같은 검사를 주소 칸에도 적용하는 것은 후속이다. 새로 쓴 정상 입력 202개 중 32·40자 해시를 적은 2개만 잘못 거절했지만 키와 비슷한 정상 입력(전체 해시·CamelCase 해시태그·24자 이상 주문번호·구글 문서 주소)은 46개 중 34개를 거절한다. 반대로 네이버 키(client_id 20자·secret 10자)와 8~23자 키·공백·붙임표·점으로 나눠 적은 키·전각 숫자·`\x41`·`%41` 로 적은 키·28~32자 base64(41~48% 통과)는 모양만으로 구분하지 못해 받고, 막히는 것은 Unsplash 43자 같은 긴 키뿐이다. D-34), 어떤 오류 문구·세부·`--json`·`--verbose` 에도 입력한 글이나 그 일부(앞 몇 글자)를 적지 않는다 — 가리기 규칙은 전체 모양만 알아보므로 잘린 조각은 못 막기 때문이다. 가리기 규칙(`security/mask.py`)의 키 모양 경계는 정본(`vendor/`)의 단어 경계가 한글 바로 옆의 키(`키는AKIA…를`)를 놓쳐서, 같은 패턴의 ASCII 영숫자 기준 앞뒤 확인 판을 하나 더 돌린다(정본은 고치지 않았다. 일반 글의 출력은 그대로이고 `…_api_key = "…"`·`키는api_key = "…"` 꼴만 가림 표지가 `[가림: 값]` 에서 `[가림: 키/토큰 할당]` 로 바뀐다(비밀은 둘 다 가려지고 비교한 글의 0.6%). 영문·숫자에 바로 붙은 `abcAKIA…` 와 밑줄·하이픈 앞의 JWT 는 정본처럼 알아보지 못한다).
- `restore`(백업으로 글 저장소를 통째로 바꾸는 일)와 `delete` 는 `--yes` 가 있어야 하고, 바꾸기 직전 상태를 먼저 따로 백업한다. 올렸지만 공개 확인이 끝나지 않은 글(`PUSHED`)은 발행 기록이 있는 동안 `delete` 가 거절한다(지우면 기록도 지워져 공개 확인을 이어갈 수 없다 — 먼저 `check-deploy`).

로그인·쿠키·세션 자동화, 탐지 회피, CAPTCHA 우회, 무료 한도 우회용 다계정·키 회전, 유료 호출, 키를 저장소·로그에 기록, 한도 오류 무한 재시도.

## 7. 키 보관(연결 설정) — 설계 D-30·D-31

앱의 연결 설정(`keys` 명령 — 용도별로 키를 넣고, 같은 용도에 여러 개를 둘 수 있고, 한도에 막혀 일이 멈추지 않게 하는 안전장치)은 **키를 Windows 자격 증명 관리자(OS 보안 저장소)에만** 둔다. 화면에 키 원문을 보이는 기능은 없다 — 보이는 것은 다섯 가지 상태 문구(연결 안 됨, 연결됨, 인증 정보 오류, 연결 확인 필요, 요청 한도 도달)와 이름뿐이고, 값이 16자 이상일 때만 끝 4자(`****abcd`)를 목록에 보인다. 키를 다시 보여 주는 기능은 만들지 않는다(잃어버리면 서비스 쪽에서 폐기하고 새로 받아 넣는다).

**어디에 무엇이 있나.**

| 대상 | 두는 곳 | 비고 |
|---|---|---|
| 키 값(필드 묶음) | 자격 증명 관리자의 항목 `ChanceBlogDesktop:<용도>:<항목번호>`(범용 자격 증명, `CRED_PERSIST_LOCAL_MACHINE` — 재부팅 뒤에도 남고 이 PC 에서만 쓰인다) | 필드들을 JSON 한 덩어리로 묶어 UTF-16 으로 적는다. 값 한도 2,560바이트 — 넘으면 `KEY_TOO_LONG` |
| 이름·소속 프로젝트·순서·상태·확인 시각·한도 묶음 이름·약관 확인 시각 | 데이터 폴더의 `connections.json`(임시 파일에 쓰고 `fsync` 한 뒤 이름을 바꾸는 쓰기·구조 버전·낯선 칸 거절·직전의 올바른 사본 `.bak`) | **비밀이 아니다.** 이 파일에는 **비밀 칸의 값에서 만든 것(해시·지문·끝 글자)이 하나도 없다** — 약한 값은 해시만으로도 대입해 알아낼 수 있어서 지문을 두지 않고, 같은 값을 두 번 넣는지는 보관소의 값을 직접 비교해 막는다. 한도 묶음 이름의 해시는 클라이언트 ID·고객 ID 같은 비밀이 아닌 칸에서만 만든다 |
| 사용량·막힘 해제 시각·전환 기록 | 데이터 폴더의 `quota_state.json`(원자적 쓰기·잠금·깨지면 보수적으로 오늘 한도의 절반을 쓴 것으로 가정) | 키 값 없음 |

**하지 않는 것**: 키를 파일·환경 변수·설정 JSON·`.env`·로그·저장소·명령 인자로 받거나 쓰지 않는다. 앱은 환경 변수로 키를 읽지 않는다(시험이 지킨다 — 그래서 `.env.example` 에 키 칸을 더하지 않는다). 키는 **명령 인자로 받지 않고** 터미널의 숨김 입력(`getpass`)이나 `--stdin`(JSON 한 줄)으로만 받으며, 입력은 화면에 되풀이하지 않는다. 터미널이 아니고 `--stdin` 도 없으면 묻지 않고 멈춘다. **`--stdin` 은 자동 시험·스크립트용이다** — 키를 명령줄에 직접 쳐서(예: `echo '{…}' | …`) 넘기면 그 줄이 셸 기록에 남으니 사람이 넣을 때는 숨김 입력을 쓴다. 키를 받는 자리(`keys add`)에서는 화면·오류·`--json`·`--verbose`·`repr`·예외 문구 어디에도 입력한 값은 없고(모양 검사는 이유만 알린다), 키를 인자 자리에 잘못 쳤을 때의 사용법 오류도 입력한 값을 되풀이하지 않는다 — 모든 명령의 사용법 오류는 argparse 의 문구 대신 값 없는 고정 문장(틀린 옵션 이름·종류·고를 수 있는 값만)이고, 값 검사 문구 속 '받은 값'·「값」 도 지운다(`--옵션=값`·`-h값` 꼴 포함 — 시험이 26가지 명령 모양×값 3가지와 진짜 프로세스 24곳으로 확인). 후보·글 번호 자리와 `restore` 의 백업 파일 자리(번호를 받는 명령 22개 — 후보 9·`draft plan`·글 11·`restore`)에 키를 잘못 쳐도 오류 문구·`--json`·`--verbose` 의 기록용 한 줄은 친 글을 **번호 모양일 때만** 되풀이하고(16진수 8자 이하 — 순번과 화면에 보이는 짧은 번호, 백업은 앱이 만드는 `chanceblog-날짜-시각.db` 이름 하나) 아니면 `(입력한 번호)`·`(입력한 파일)` 로 바꾼다. 판정은 `echo.py` 한 곳이고 오류를 만드는 곳(`AppError` 의 칸 값)에서 바꾸므로 화면·`--json`·기록이 같으며 오류 코드·종료 코드·하실 일은 그대로다(D-34). 시험이 파서에서 번호 자리 27곳(위 22개 명령과 `candidates link` 의 둘째 자리·`keys` 4개)을 모아 가짜 키 28종을 넣어 출력(화면·`--json`·`--verbose`·`--yes`)과 데이터 폴더를 확인하고, 진짜 프로세스(cp949 콘솔·셸 인용 포함)로도 본다. **알려 둔 한계**: 번호 모양(16진수 8자 이하)은 그대로 되풀이한다 · 경로 자리는 어느 폴더가 문제인지 알려야 해서 경로를 적는다(`--data-dir` 의 폴더는 `doctor` 출력에 그대로 나온다) · 제목·주제·키워드·원고처럼 사용자가 쓴 글은 화면에 나가고 저장된다(마스크가 아는 모양만 가린다) · `restore` **성공** 문구('백업으로 되돌렸습니다: …')와 `connect` 의 폴더 경로도 친 경로를 그대로 적는다 · 표 시험은 위치 인자 번호 자리만 모은다(옵션 값 자리는 독립 검증이 전수로 확인했다) · 안전 시험은 `os.truncate`·`shutil.move`·`sqlite3.connect` 같은 쓰기 호출 32가지를 못 거른다(c3 이전부터). 그 밖의 오류 문구는 마지막 관문 `mask` 가 가린다(마스크가 모르는 일반 영숫자 키는 못 가린다 — 그래서 입력이 문구에 들어가는 곳을 따로 막았다). 마지막 관문으로 모든 출력은 `security.mask` 를 거친다. 이름·소속 프로젝트에 키 모양의 글이나 키 값이 그대로 들어 있으면 파일에 남기기 전에 거절한다(`security/shape.py` — 한글·괄호·따옴표·줄바꿈 바로 옆에 붙은 것도 찾는다).

**막는 것(위협 모델).** 저장소·`connections.json`·`quota_state.json`·로그·오류 보고서·백업(`backup` 은 글 저장소만 담는다)·설정 내보내기·진단 정보·화면·스크린샷·클립보드에 키가 남는 것을 막는다. 진단 요약(`connections.diagnostic_summary`)에는 용도별 항목 수뿐이고 이름·번호·끝 4자도 싣지 않는다. **막지 못하는 것**: 같은 Windows 사용자로 도는 악성 프로그램(자격 증명 관리자는 같은 사용자의 프로그램을 구분하지 않아 값을 읽을 수 있다)·PC 를 가진 관리자·메모리 덤프. 파이썬 문자열은 바꿀 수 없어 읽은 값을 메모리에서 완전히 지우지 못한다 — 앱은 자격 증명 관리자가 돌려준 원본 메모리와 보관소로 넘긴 사본을 바로 0 으로 덮고, 읽은 값을 필요한 순간에만 꺼내 쓰고 버리지만 파이썬 쪽 사본은 가비지 수집 때까지 남을 수 있다. 그래서 **키는 언제든 폐기·재발급할 수 있는 것만** 넣는다.

**키 노출이 의심될 때**: ① 그 서비스의 콘솔에서 키를 바로 폐기하고 새로 만든다(저장소에서 문자열만 지워도 이력에 남는다) ② `keys remove 번호 --yes` 로 보관소의 값을 지우고 `keys add` 로 새 키를 넣는다 ③ 그 키를 같이 쓰던 곳(클라우드 자동 발행의 GitHub Actions 시크릿 등)이 있으면 거기서도 바꾼다. 데스크톱용 키와 GitHub Actions 용 시크릿은 **같은 값을 쓰지 않는다**(이 앱은 Actions 시크릿을 읽지 않고 클라우드는 이 PC 의 키를 쓰지 않는다 — 같은 값이면 유출 범위와 한도가 함께 묶인다. Unsplash 는 데스크톱용으로 따로 앱을 등록해 한도도 따로 쓴다).

**시험 전용 가짜 보관소.** 명령줄을 진짜 프로세스로 시험할 때만 환경 변수 `CHANCEBLOG_KEYSTORE=memory-file` 이 임시 폴더의 가짜 JSON 파일 보관소를 연다. 이 값이 **정확히** 맞고, 폴더(`CHANCEBLOG_KEYSTORE_DIR`)가 운영체제 임시 폴더 안·이름이 `chanceblog-fake-keystore-` 로 시작·표시 파일이 있을 때만이며, 설치본(`sys.frozen`)에서는 환경 변수를 아예 무시한다. 환경 변수가 없으면 프로그램의 기본 경로는 언제나 진짜 자격 증명 관리자다(Windows 가 아니면 `KEY_STORE_UNAVAILABLE`). 이 가짜 보관소를 쓰는 중이면 화면에 경고가 나온다.

**한도 안전장치의 근거(확인한 사실).** Gemini API: 한도는 키가 아니라 **프로젝트** 단위다(같은 프로젝트에서 키를 더 만들어도 늘지 않는다). 네이버 검색 API: 앱(클라이언트 ID)마다 하루 약 25,000회(제3자 문서 — 공식 문서와 대조 필요). Unsplash: 데모 앱은 시간당 50회, 승인된 앱은 시간당 1,000회이고 `api.unsplash.com` 요청만 센다. 여러 프로젝트·계정으로 무료 한도를 나눠 쓰는 것은 서비스 약관과 공정 사용 규칙에 어긋날 수 있다. 그래서 한도 단위는 키가 아니라 한도 묶음(같은 앱·프로젝트)이고, 한도 오류 뒤에는 같은 묶음의 다른 키로 넘어가지 않으며, 용도마다 키는 3개까지이고, 둘째 키를 넣을 때 약관 경고를 보이고 확인(`--i-understand-terms`)을 받아 항목에 기록하며, Unsplash 는 어떤 오류에도 자동으로 다른 키로 넘어가지 않는다. 전환할 수 있는 결과는 429·기간 한도·일시 5xx(500·502·503·504)·시간 초과 네 가지뿐이고 401·403·400·422·정책 차단·콘텐츠 차단은 숨기지 않고 조치 안내만 한다. 기본 안전장치는 전환이 아니라 **절약**이다(예산의 마지막 10% 는 필수 호출 전용·저장해 둔 값 우선·`Denied(degraded)` — 호출하는 쪽은 '데이터 없음' 으로 계속한다).

# 보안

이 저장소는 **공개**이고 앱은 운영자의 개인 PC 에서 키를 다룬다. 규칙의 정본은 `chanceblog` 의 `docs/SECURITY_GUARDRAILS.md`(G-S 비밀·G-L 호출·G-C 채널)이고, 여기에는 앱 고유의 것만 적는다.

## 1. 키와 비밀

| 비밀 | 어디에 | 이 저장소에 |
|---|---|---|
| 선택 보조 AI 키(Gemini 등 — 기본은 없음)·네이버·이미지 공급자 키 | **Windows 자격 증명 관리자**(OS 보안 저장소) — `keys add` 의 숨김 입력으로만 넣는다(§7). 키가 없어도 모든 핵심 기능이 동작한다 | 없음 |
| Blogger OAuth 토큰·클라이언트 비밀 | 같은 곳(앱이 브라우저 loopback 로그인으로 받음) — **이 시험 버전은 입력 칸이 없고 서비스·명령줄도 받지 않는다**(`BLOGGER_OAUTH_INPUT = False`, 아래 PCSEC1 절) | 없음 |
| 업데이트 서명 개인키 | GitHub Environment 시크릿 `UPDATE_SIGNING_KEY` + 운영자의 오프라인 백업 2곳 | 없음(공개키는 앱에 내장·저장소에 있음) |
| GitHub 토큰 | 앱에 내장하지 않는다. Pages 발행은 PC 의 Git 로그인(자격 증명 관리자)을 쓴다 — **이 시험 버전은 외부 게시가 소스 상수로 꺼져 있어 그 로그인도 쓰지 않는다**(아래 PCSEC1 절) | 없음 |

- 키는 소스·로그·설정 내보내기·DB 에 쓰지 않는다. 설정 내보내기 파일에는 키가 없다. 키가 없어도 앱은 수동 모드로 실행된다.
- 선택 보조 AI 키를 만들게 되면 자동 발행(Actions)에 쓰는 키와 **분리**한다(한도를 나눠 쓰지 않고, 유출 범위를 줄인다). 보조 AI 연결 실패는 해당 기능만 건너뛰고 프로그램 오류로 번지지 않는다(`ASSIST_UNAVAILABLE`).
- 실제 키가 든 `.env` 는 GitHub 에 올리지 않는다(`.gitignore`). **`.env.example` 에는 변수 이름만** 적는다. 클라우드(Actions)에서 필요한 키는 GitHub Secrets 에만 둔다.
- 유출이 의심되면 즉시 폐기·재발급한다. 저장소에서 문자열만 지워도 이력에 남는다.

## 2. 로그

요청 헤더·키·토큰·개인정보를 출력하지 않는다. 로그·오류 보고서에 나가는 글은 `src/chanceblog_desktop/security/mask.py` 의 `mask`·`safe_detail`(이를 쓰는 `AppError.log_line()` 포함)을 거친다. 규칙은 ① `chanceblog` 의 비밀 패턴 `pipeline/secret_patterns.py` 14종(`vendor/` 에 원본 그대로 — 패턴이 늘면 시험이 새 표본을 요구한다) ② 주소 속 `사용자:토큰@`(비밀번호에 `@` 가 있어도) ③ 주소의 `?access_token=`·`code=`·`session=` 같은 인자 ④ `Bearer`·`Basic` 토큰·JWT·Slack 웹훅 주소·npm 토큰·`aws_secret_access_key=`·따옴표 없는 `password: 값`·개인 키 블록 전체 ⑤ 눈에 안 보이는 글자(폭 없는 글자·방향 제어 등)로 쪼갠 토큰(그 글자를 먼저 지운다) ⑥ 정본의 `sk-` 패턴(영숫자만)이 못 알아보는 붙임표·밑줄이 든 새 키 모양 — OpenAI 프로젝트 키(`sk-proj-…`)·Anthropic 키(`sk-ant-api03-…`)·OpenRouter 키(`sk-or-v1-…`)와 그 밖의 `sk-` 긴 모양(꼬리 40자 이상에 앞 60자 안의 대문자·숫자)이다. 정본은 고치지 않고 `mask.py` 에서 더했고 `shape.py` 의 자기 검사는 이미 이 모양들을 키로 본다(시험이 둘의 일치를 지킨다). 다만 이 '가린다' 는 화면·기록 쪽이다 — 발행 직전의 비밀 차단(`publish/pages.py`)은 이 새 모양 4가지(`sk-proj-`·`sk-ant-api03-`·`sk-or-v1-`·`sk-` 일반형)를 아직 모른다(c3 이전부터의 한계이고 같은 모양 판정을 쓰게 하는 일은 후속이다). `sk-` 일반형은 대문자·숫자가 든 40자 이상 붙임표 슬러그(`sk-Hynix-Q3-2026-…`·`sk-proj-weekly-…`)도 키로 보고 가린다(오탐 — 정상 글이 가려질 수 있다). 어떤 입력에도 예외를 내지 않고, 이미 가린 글을 다시 가려도 같다(입력이 20만 자 이하일 때 — 그보다 긴 글은 비밀이 반쪽으로 잘리지 않게 공백에서 잘라 앞부분만 가리고 나머지는 내보내지 않는다). `AppError.detail` 은 화면에 내지 않고 `log_line()` 으로만 기록하며, git 의 출력은 끝 400자만 남기되 **자르기 전에** 가린다. 로그 파일과 내보내기 기능은 아직 없다(만든다면 기록이 만들어질 때 이미 가려져 있다 — 아래 PCSEC1 절 '공통 경계'). 이 규칙은 **알려진 모양**만 가린다 — 같은 종류의 토큰이 공백 없이 이어 붙은 것이나 낱말 경계로 시작하는 패턴이 앞 글자에 붙은 것(`키는ghp_…`), 이름 표지 없이 줄바꿈으로 쪼갠 토큰이나 무작위 40자 문자열(AWS 비밀 키처럼 git 해시와 구분할 수 없는 것)은 못 가리므로, 비밀을 애초에 로그에 넣지 않는 것(§1)이 먼저다. 가리기 규칙의 강화(이름 목록 확장·헤더 줄·눈속임 풀이)와 한계는 아래 PCSEC1 절이 정본이다.

명령줄(`service/cli.py`)은 화면에 나가는 모든 글 — 일반 출력·오류·`--json` 값 — 을 같은 `mask` 로 가린다(원고·제목·git 의 오류 세부에 키 모양 문자열이 있어도 출력에는 없다 — 가리는 함수 `mask_block`·`mask_deep` 은 공통 경계 `security/boundary.py` 에 있고 `cli` 는 같은 이름을 쓴다). 환경 변수는 데이터 폴더·저장소 폴더 위치(`CHANCEBLOG_DESKTOP_DATA`·`CHANCEBLOG_LOCAL_REPO`)만 읽고 키·토큰은 읽지 않으며(시험 전용 가짜 보관소를 여는 `CHANCEBLOG_KEYSTORE` 는 §7 의 안전장치를 모두 통과할 때만 열린다 — `Context.get_keystore()` 가 받은 환경 변수 모음을 보관소 모듈(`security/keystore.py`)에 그대로 넘기고 그 값을 읽는 곳은 그 모듈 한 곳이다), 사용자 데이터는 저장소(git) 안에 둘 수 없다(`DATA_DIR_UNSAFE`). 시험(`tests/test_service_safety.py`)이 이 규칙들을 소스에서 직접 확인한다. 여러 줄에 걸친 비밀(개인 키 블록 — `-----BEGIN … PRIVATE KEY-----` 부터 END 까지·다음 줄에 이어지는 값)이 줄 단위 가리기를 빠져나가지 않도록 **출력 전체를 통째로** 가린다(`cli.mask_block` — 글이 아주 길면 줄 경계에서 나눠 가리되 열린 개인 키 블록 안에서는 끊지 않는다).

## 3. 업데이트 보안

[`RELEASE.md`](RELEASE.md) 의 서명 매니페스트·해시 검증·다운그레이드 거부·불변 릴리스·백업/롤백이 핵심이다. 업데이트 경로는 HTTPS 와 고정 저장소 주소만 쓰고, 서명이 없거나 어긋나면 업데이트를 거부한다.

## 4. 공급망

액션은 전체 커밋 SHA 로 고정한다(`.github/workflows/`, 시험이 지킨다 — 갱신은 AI 가 같은 메이저 안의 최신 태그를 확인해 PR 로 올린다. Dependabot 은 알림·PR 이 늘어 기본은 켜지 않는다). 의존성은 생기면 해시 잠금, `pip-audit` 은 릴리스 전에 돌린다. 외부 AI 응답은 데이터이므로 HTML 은 허용 태그만 남기고(소독) 링크·스크립트를 제거한다.

`auto-pr.yml`(병합 부탁 PR 자동 만들기, D-175)은 **PR 만 만들고 병합하지 않는다.** 트리거는 병합 가지(`ai/claude/M###-*`)의 push 하나, 권한은 contents 읽기·pull-requests 쓰기·actions 읽기 셋뿐이고, `uses:`·시크릿·체크아웃이 없이 러너의 `gh` 로 정해진 API 여섯 가지만 부른다(병합·승인·라벨·코멘트·가지 삭제·설정 변경 호출 없음). 가지 이름·커밋 제목·본문은 AI 가 쓴 글이라 env 로만 넘기고 `run:` 에 표현식을 끼우지 않으며 정규식으로 거른 뒤 파일·따옴표 친 변수로만 다룬다(`pull_request_target`·`workflow_run`·`issue_comment`·`schedule` 은 쓰지 않는다). 시험 `tests/test_auto_pr_workflow.py` 가 모양을 고정하고, 이 파일을 바꾸는 변경은 T3 로 다룬다(워크플로는 `AGENTS.md` 3 표의 T2 인데 PR 만들기 권한과 저장소 설정 한 줄에 닿는 보안 영역이라 운영자 승인 병합으로 올린다). 커밋 제목·본문은 PR 로 그대로 공개되므로 비밀·키·`@이름` 멘션을 쓰지 않고, 포크에서 올라오는 PR 에는 돌지 않는다. 저장소 설정 `Allow GitHub Actions to create and approve pull requests` 는 운영자만 켠다(워크플로의 PR '승인'도 허용하는 설정이므로 승인 호출을 넣는 변경은 받지 않는다).

## 5. 올라가는 글과 승인

- **올라가는 것은 Markdown 원문이다.** 발행 전 검사(`service/gate.py`)는 그 원문에서 원시 HTML 태그·`javascript:`/`data:`/`vbscript:` 주소·`{% %}`/`{{ }}` 템플릿 표기·`{: }` 속성 붙이기·광고 스크립트를 막는다 — 공개 사이트(Jekyll)가 원시 HTML 을 그대로 내보내고 Liquid 를 글을 만들 때 실행하기 때문이다([`ARCHITECTURE.md`](ARCHITECTURE.md) §5).
- **승인 통제는 채팅 승인 규칙 하나다.** 앱은 `--yes`·`approve` 를 사람이 직접 입력했는지 알 수 없다(터미널 확인이 없다). 그래서 AI 코딩 도구가 운영자의 승인 없이 대신 입력하는 것은 [`AGENTS.md`](../AGENTS.md) 규칙 7·9 로 막는다 — 앱이 막을 수 있는 것은 확인 표시 없이 실행하지 않는 것까지다.
- **머리말 값도 같다.** 제목·분야·태그·대표 이미지 주소·설명·출처의 HTML 태그·`{% %}`/`{{ }}`·`javascript:` 같은 주소·광고 스크립트와 줄바꿈·제어 문자·따옴표/꺾쇠가 든 주소·모르는 머리말 키(`published`·`permalink` 등)를 막는다(`HEADER_VALUE`·`RAW_HTML` …). 머리말 값은 사이트의 글 목록·카드에 들어가고 일부는 이스케이프 없이 HTML 에 들어간다. 렌더링은 한 줄 JSON 으로 이스케이프해 제목의 따옴표·콜론·`---`·`#` 가 머리말 구조를 깨거나 다른 키를 끼워 넣지 못하고(시험), 게이트는 저장된 글이 바뀌어 있어도 다시 본다. 글을 만들거나 고칠 때의 제목도 같은 검사를 거친다. 알려 둔 한계: 제목의 큰따옴표는 막지 않는다(실제 Chance 글에도 있다) — 첫 화면 카드가 속성 안에 제목을 이스케이프 없이 넣는 것은 `chanceblog` 쪽에서 고칠 일이다.
- 같은 글을 두 곳에서 동시에 올리지 못하도록 글마다 잠금을 잡고(`PUBLISH_IN_PROGRESS`), **서로 다른 두 글이 같은 저장소에 동시에 commit·push 하지 못하도록** 저장소마다 잠금을 한 번 더 잡는다(`PUBLISH_REPO_BUSY` — 글 잠금 먼저·저장소 잠금 나중의 고정 순서, 죽은 프로세스의 잠금은 바로 넘겨받음). 저장소 잠금 파일은 **연결한 저장소의 `.git` 안**(`.git/chanceblog-desktop-publish.lock`)에 만든다 — 서비스 층(`service/`)이 연결한 저장소에 직접 쓰는 파일은 이 잠금 파일 하나뿐이고(글 파일은 `publish/pages.py` 가 쓴다) 잠금 파일은 git 이 추적하지 않는다. 데이터 폴더(`--data-dir`)가 다른 앱끼리도 서로를 알게 하려는 것이고, `.git` 에 만들 수 없으면 데이터 폴더로 물러서지 않고 올리지 않는다(fail closed). 이 PC 의 폴더 경로·눈에 안 보이는 글자로 길이를 채운 글·글자의 표시 방향을 바꾸는 제어 문자(U+202A–202E·U+2066–2069 — 글을 다르게 보이게 위장할 수 있다)가 든 글도 막는다.

- **`주제 후보` 화면은 주제 엔진 보관함에 쓴다**(D-270~D-276, T2): `후보 만들기` → 미리 보기(읽기뿐) → 확인창(처음 포커스는 취소)의 `만들기` 를 눌렀을 때만 서비스 `generate_candidates(confirmed=True, trend=None)` 한 번이 `topic_engine/topic_engine.db` 에 후보를 **더한다**(서비스·엔진 코드는 이 묶음에서 바꾸지 않았다 — 보관함이 없으면 파일 하나를 새로 만들고 옛 구조는 `.v1.bak` 사본을 남기며 올린다, 후보는 지워지거나 바뀌지 않고 실패하면 쓰기 전 상태 그대로다). 열기·거르기·찾기·고르기·상세·창 크기 바꾸기·미리 보기·취소는 파일도 폴더도 만들지 않는다(임시 폴더 전체 바이트 비교 시험). 관심도(Trend) 공급자는 `None` 이라 네트워크를 쓰지 않고 키·자격 증명 저장소는 부르지 않는다(`security/` 불변 — 시험이 호출을 막아 확인). 후보 제목·키워드·이유에 키·토큰 모양 글이 있으면 서비스가 저장하지 않고 화면은 가려서 보이며, 화면 코드는 파일을 열거나 서비스를 직접 부르지 않는다(소스 시험). 후보 삭제·상태 바꾸기는 이 화면에 없다.
- **기존 글 읽기(`service/own_posts.py`)는 운영자가 파일 선택 창에서 직접 고른 txt·md 파일만 읽는다**(D-325–D-329, T1): 한 번에 1–2개·파일당 2MB·읽은 글 100,000자 이하를 넘으면 거절하고(잘라 쓰지 않는다) 인터넷 주소·네트워크 위치·와일드카드·폴더·심볼릭 링크·정션(경로 위 폴더까지)·이 PC 에 내려받지 않은 파일(이 표시는 파일 자신만 본다 — 경로 위 폴더는 링크 여부만 본다)·윈도 장치 이름·상대 경로는 읽지 않는다 — 네트워크 접근 0, 저장 0(반환값 말고는 파일·로그·캐시·설정·클립보드 어디에도 남기지 않고 어느 프로필에도 쓰지 않는다), 열기는 `rb` 하나뿐이고 연 핸들의 상태(`fstat`)가 검사 때와 같은 일반 파일이 아니면 읽지 않는다(검사와 열기 사이의 링크·파일 바꿔치기 거절). 오류는 고정 문장이고 경로·파일 이름·글 내용을 되풀이하지 않으며(OS 오류의 글도 버리고 읽은 뒤 거절할 때는 호출 흔적이 붙드는 지역 변수의 글도 비운다), 값에는 글·글자 수·읽은 글자표 이름(`utf-8`·`cp949`)만 담긴다. 알려 둔 한계: 윈도의 연결된 네트워크 드라이브(Z: 같은)와 리눅스·맥의 네트워크 마운트는 판별하지 못해 읽을 수 있다 · 열기 자체가 내려받기를 일으키는 OneDrive 온라인 전용 파일은 열기 전 표시로만 거른다 · CP949 는 'UTF-8 이 아니면' 이라는 기본값이라 EUC-JP·EUC-CN 으로 저장한 글은 한글 더미로 읽힐 수 있고 ESC 같은 제어 문자는 거르지 않는다(NUL 만 거른다).
- **내 글 문체 참고값 보기(N-3a — `ui/qt/style_dialog.py`·`content/style_stats.py`, D-330–D-339, T1)는 읽기만 한다 — 저장 0·AI 0·네트워크 0**: 운영자가 직접 고른 txt·md 파일(파일 선택 창)과 붙여 넣은 글을 합쳐 최대 2개를 기존 글 읽기(`service/own_posts.py` 의 `read_own_files`·`check_pasted_text`)의 한도와 고정 거절 문장으로 검사해 메모리에서 숫자만 세어 참고값 표로 보인다. 이 화면은 파일·설정·프로필(옛 `naver_profiles` 와 `topic_engine/channel_profiles.json`)·보관함·연결 저장소·자격 증명 관리자에 쓰지 않고 읽지도 않으며(위 '화면에서 파일에 쓰는 곳' 네 곳의 목록은 그대로다 — 시험이 그 문장을 못박는다) 로그·캐시·임시 파일·클립보드도 없다. 계산 값은 숫자·참/거짓뿐이고 고른 글의 문장은 뷰모델·표·오류·표준 출력에 없으며(카나리 시험: 표지 글의 8글자 이상 조각이 어느 순간의 위젯·상태·출력·가짜 클립보드·데이터 폴더 바이트에도 없다) 붙여 넣기 칸은 계산이 끝나면 되돌리기 기록까지 비우고 창을 닫는 어느 길로든 고른 글·결과를 버린다. 거절·실패는 기존 `CONTENT_INVALID` 의 고정 문장(새 오류 코드 0)이고 호출 흔적이 붙드는 경로·글은 비운 뒤 `except` 밖에서 낸다. 한계는 위 읽기 기반 항목과 같다 — 파이썬 문자열은 메모리에서 즉시 지울 수 없어 참조를 버려 회수되게 할 뿐이다.
## 6. 금지

로그인·쿠키·세션 자동화, 탐지 회피, CAPTCHA 우회, 무료 한도 우회용 다계정·키 회전, 유료 호출, 키를 저장소·로그에 기록, 한도 오류 무한 재시도.

## 7. 키 보관(연결 설정) — 설계 D-30·D-31

앱의 연결 설정(`keys` 명령 — 용도별로 키를 넣고, 같은 용도에 여러 개를 둘 수 있고(NAVER API HUB 는 하나만), 한도에 막혀 일이 멈추지 않게 하는 안전장치)은 **키를 Windows 자격 증명 관리자(OS 보안 저장소)에만** 둔다. 화면에 키 원문을 보이는 기능은 없다 — 보이는 것은 다섯 가지 상태 문구(연결 안 됨, 연결됨, 인증 정보 오류, 연결 확인 필요, 요청 한도 도달)와 이름·제공자·항목 번호·등록 시각뿐이다 — 끝 4자 같은 키의 일부는 명령줄 목록에도 보이지 않는다(PCSEC1 H2, D-346). 키를 다시 보여 주는 기능은 만들지 않는다(잃어버리면 서비스 쪽에서 폐기하고 새로 받아 넣는다).

**어디에 무엇이 있나.**

| 대상 | 두는 곳 | 비고 |
|---|---|---|
| 키 값(필드 묶음) | 자격 증명 관리자의 항목 `ChanceBlogDesktop:<용도>:<항목번호>`(범용 자격 증명, `CRED_PERSIST_LOCAL_MACHINE` — 재부팅 뒤에도 남고 이 PC 에서만 쓰인다) | 필드들을 JSON 한 덩어리로 묶어 UTF-16 으로 적는다. 값 한도 2,560바이트 — 넘으면 `KEY_TOO_LONG` |
| 이름·소속 프로젝트·순서·상태·확인 시각·한도 묶음 이름·약관 확인 시각 | 데이터 폴더의 `connections.json`(임시 파일에 쓰고 `fsync` 한 뒤 이름을 바꾸는 쓰기·구조 버전·낯선 칸 거절·직전의 올바른 사본 `.bak`) | **비밀이 아니다.** 이 파일에는 **비밀 칸의 값에서 만든 것(해시·지문·끝 글자)이 하나도 없다** — 약한 값은 해시만으로도 대입해 알아낼 수 있어서 지문을 두지 않고, 같은 값을 두 번 넣는지는 보관소의 값을 직접 비교해 막는다. 한도 묶음 이름의 해시는 클라이언트 ID·고객 ID 같은 비밀이 아닌 칸에서만 만든다 |
| 사용량·막힘 해제 시각·전환 기록(NAVER API HUB 는 시도·성공 수와 마지막으로 본 시각, 최근 200건의 호출 장부도) | 데이터 폴더의 `quota_state.json`(원자적 쓰기·잠금·구조 판 1 — 호출 장부가 있는 묶음이 하나라도 있는 파일만 판 2·깨지면 보통 용도는 보수적으로 오늘 한도의 절반을 쓴 것으로 가정하고, NAVER API HUB 는 절반으로 가정하지 않고 새 호출을 멈춘다) | 키 값 없음 — 호출 장부에도 키·응답 본문·요청 본문이 없다(요청 조건은 해시 앞 12자뿐) |

**하지 않는 것**: 키를 파일·환경 변수·설정 JSON·`.env`·로그·저장소·명령 인자로 받거나 쓰지 않는다. 앱은 환경 변수로 키를 읽지 않는다(시험이 지킨다 — 그래서 `.env.example` 에 키 칸을 더하지 않는다). 키는 **명령 인자로 받지 않고** 터미널의 숨김 입력(`getpass`)이나 `--stdin`(JSON 한 줄)으로만 받으며, 입력은 화면에 되풀이하지 않는다. 터미널이 아니고 `--stdin` 도 없으면 묻지 않고 멈춘다. **`--stdin` 은 자동 시험·스크립트용이다** — 키를 명령줄에 직접 쳐서(예: `echo '{…}' | …`) 넘기면 그 줄이 셸 기록에 남으니 사람이 넣을 때는 숨김 입력을 쓴다. 키를 받는 자리(`keys add`)에서는 화면·오류·`--json`·`--verbose`·`repr`·예외 문구 어디에도 입력한 값은 없고(모양 검사는 이유만 알린다), 키를 인자 자리에 잘못 쳤을 때의 사용법 오류도 입력한 값을 되풀이하지 않는다 — 모든 명령의 사용법 오류는 argparse 의 문구 대신 값 없는 고정 문장(틀린 옵션 이름·종류·고를 수 있는 값만)이고, 값 검사 문구 속 '받은 값'·「값」 도 지운다(`--옵션=값`·`-h값` 꼴 포함 — 시험이 26가지 명령 모양×값 3가지와 진짜 프로세스 24곳으로 확인). 후보·글 번호 자리와 `restore` 의 백업 파일 자리(번호를 받는 명령 22개 — 후보 9·`draft plan`·글 11·`restore`)에 키를 잘못 쳐도 오류 문구·`--json`·`--verbose` 의 기록용 한 줄은 친 글을 **번호 모양일 때만** 되풀이하고(16진수 8자 이하 — 순번과 화면에 보이는 짧은 번호, 백업은 앱이 만드는 `chanceblog-날짜-시각.db` 이름 하나) 아니면 `(입력한 번호)`·`(입력한 파일)` 로 바꾼다. 판정은 `echo.py` 한 곳이고 오류를 만드는 곳(`AppError` 의 칸 값)에서 바꾸므로 화면·`--json`·기록이 같으며 오류 코드·종료 코드·하실 일은 그대로다(D-34). 시험이 파서에서 번호 자리 27곳(위 22개 명령과 `candidates link` 의 둘째 자리·`keys` 4개)을 모아 가짜 키 28종을 넣어 출력(화면·`--json`·`--verbose`·`--yes`)과 데이터 폴더를 확인하고, 진짜 프로세스(cp949 콘솔·셸 인용 포함)로도 본다. **알려 둔 한계**: 번호 모양(16진수 8자 이하)은 그대로 되풀이한다 · 경로 자리는 어느 폴더가 문제인지 알려야 해서 경로를 적는다(`--data-dir` 의 폴더는 `doctor` 출력에 그대로 나온다) · 제목·주제·키워드·원고처럼 사용자가 쓴 글은 화면에 나가고 저장된다(마스크가 아는 모양만 가린다) · `restore` **성공** 문구('백업으로 되돌렸습니다: …')와 `connect` 의 폴더 경로도 친 경로를 그대로 적는다 · 표 시험은 위치 인자 번호 자리만 모은다(옵션 값 자리는 독립 검증이 전수로 확인했다) · 안전 시험은 `os.truncate`·`shutil.move`·`sqlite3.connect` 같은 쓰기 호출 32가지를 못 거른다(c3 이전부터). 그 밖의 오류 문구는 마지막 관문 `mask` 가 가린다(마스크가 모르는 일반 영숫자 키는 못 가린다 — 그래서 입력이 문구에 들어가는 곳을 따로 막았다). 마지막 관문으로 모든 출력은 `security.mask` 를 거친다. 이름·소속 프로젝트에 키 모양의 글이나 키 값이 그대로 들어 있으면 파일에 남기기 전에 거절한다(`security/shape.py` — 한글·괄호·따옴표·줄바꿈 바로 옆에 붙은 것도 찾는다).

**막는 것(위협 모델).** 저장소·`connections.json`·`quota_state.json`·로그·오류 보고서·백업(`backup` 은 글 저장소만 담는다)·설정 내보내기·진단 정보·화면·스크린샷·클립보드에 키가 남는 것을 막는다. 진단 요약(`connections.diagnostic_summary`)에는 용도별 항목 수뿐이고(옛 용도는 항목이 남아 있을 때만 한 줄) 이름·번호·끝 4자도 싣지 않는다. **막지 못하는 것**: 같은 Windows 사용자로 도는 악성 프로그램(자격 증명 관리자는 같은 사용자의 프로그램을 구분하지 않아 값을 읽을 수 있다)·PC 를 가진 관리자·메모리 덤프. 파이썬 문자열은 바꿀 수 없어 읽은 값을 메모리에서 완전히 지우지 못한다 — 앱은 자격 증명 관리자가 돌려준 원본 메모리와 보관소로 넘긴 사본을 바로 0 으로 덮고, 읽은 값을 필요한 순간에만 꺼내 쓰고 버리지만 파이썬 쪽 사본은 가비지 수집 때까지 남을 수 있다. 그래서 **키는 언제든 폐기·재발급할 수 있는 것만** 넣는다.

**키 노출이 의심될 때**: ① 그 서비스의 콘솔에서 키를 바로 폐기하고 새로 만든다(저장소에서 문자열만 지워도 이력에 남는다) ② `keys remove 번호 --yes` 로 보관소의 값을 지우고 `keys add` 로 새 키를 넣는다 ③ 그 키를 같이 쓰던 곳(클라우드 자동 발행의 GitHub Actions 시크릿 등)이 있으면 거기서도 바꾼다. 데스크톱용 키와 GitHub Actions 용 시크릿은 **같은 값을 쓰지 않는다**(이 앱은 Actions 시크릿을 읽지 않고 클라우드는 이 PC 의 키를 쓰지 않는다 — 같은 값이면 유출 범위와 한도가 함께 묶인다. Unsplash 는 데스크톱용으로 따로 앱을 등록해 한도도 따로 쓴다).

**시험 전용 가짜 보관소.** 명령줄을 진짜 프로세스로 시험할 때만 환경 변수 `CHANCEBLOG_KEYSTORE=memory-file` 이 임시 폴더의 가짜 JSON 파일 보관소를 연다. 이 값이 **정확히** 맞고, 폴더(`CHANCEBLOG_KEYSTORE_DIR`)가 운영체제 임시 폴더 안·이름이 `chanceblog-fake-keystore-` 로 시작·표시 파일이 있을 때만이며, 설치본(`sys.frozen`)에서는 환경 변수를 아예 무시한다. 환경 변수가 없으면 프로그램의 기본 경로는 언제나 진짜 자격 증명 관리자다(Windows 가 아니면 `KEY_STORE_UNAVAILABLE`). 이 가짜 보관소를 쓰는 중이면 화면에 경고가 나온다.

**한도 안전장치의 근거(확인한 사실).** Gemini API: 한도는 키가 아니라 **프로젝트** 단위다(같은 프로젝트에서 키를 더 만들어도 늘지 않는다). 네이버: 옛 용도(`naver_openapi`)의 '앱마다 하루 약 25,000회' 는 공식 문서가 아닌 제3자 문서의 값이었고, 그 용도를 NAVER API HUB 로 바꾸면서 더는 쓰지 않는다 — 지금 기준은 아래 'NAVER API HUB 검색어 트렌드' 에 있다. Unsplash: 데모 앱은 시간당 50회, 승인된 앱은 시간당 1,000회이고 `api.unsplash.com` 요청만 센다. 여러 프로젝트·계정으로 무료 한도를 나눠 쓰는 것은 서비스 약관과 공정 사용 규칙에 어긋날 수 있다. 그래서 한도 단위는 키가 아니라 한도 묶음(같은 앱·프로젝트)이고, 한도 오류 뒤에는 같은 묶음의 다른 키로 넘어가지 않으며, 용도마다 키는 3개까지(NAVER API HUB 는 1개)이고, 둘째 키를 넣을 때 약관 경고를 보이고 확인(`--i-understand-terms`)을 받아 항목에 기록하며, Unsplash 와 NAVER API HUB 는 어떤 오류에도 자동으로 다른 키로 넘어가지 않는다. 전환할 수 있는 결과는 429·기간 한도·일시 5xx(500·502·503·504)·시간 초과 네 가지뿐이고 401·403·400·422·정책 차단·콘텐츠 차단은 숨기지 않고 조치 안내만 한다. 기본 안전장치는 전환이 아니라 **절약**이다(예산의 마지막 10% 는 필수 호출 전용·저장해 둔 값 우선·`Denied(degraded)` — 호출하는 쪽은 '데이터 없음' 으로 계속한다). 다만 단계표가 있는 NAVER API HUB 는 '마지막 10%' 대신 아래 단계(70·80·90%)를 쓰고, 사용량을 확인할 수 없으면 절반으로 가정하지 않고 멈춘다.

**NAVER API HUB 검색어 트렌드 — 키 규칙(D-35).** 용도 `naver_apihub` 는 Client ID(비밀이 아님)와 Client Secret(비밀 — 화면에 보이지 않고 자격 증명 관리자에만 둔다)을 받는다. 두 칸 모두 영문·숫자·`_`·`-` 만 쓴 8~128자인지만 본다 — 실제 모양이 공식 문서에 없어서 일부러 느슨하게 확인하는 것이고, 어떤 입력 오류·기록에도 입력한 값은 들어가지 않는다. **키는 하나만 둔다**(`Purpose.max_entries = 1` — 둘째 항목은 쉬운 한국어 안내로 거절하고, 명령줄에서는 약관 질문보다 먼저 거절한다). **키 순환은 없다**(`rotation = never` — 429 를 포함한 어떤 오류에도 다른 키로 자동 전환하지 않는다. 한도를 늘리려고 같은 용도의 키·계정을 돌려 쓰는 것은 §6 에서 금지한다). 키를 바꿀 때는 기존 항목을 `keys remove 번호 --yes` 로 지운 뒤 새로 넣는다. 아직 호출 코드가 없어서 `keys test` 는 '준비 중' 이라고만 말한다.

**사용량을 모르면 호출하지 않는다(Fail-Closed).** 이 제공자만은 사용량·시계·인증 상태를 확인할 수 없을 때 '절반 썼다고 보고 계속' 하지 않고 **새 호출을 막는다.** 막는 경우: ① 사용량 기록 파일(`quota_state.json`)이 깨졌거나 읽을 수 없다 — 이 제공자는 깨진 파일을 스스로 고치거나 옮기지 않는다. 다른 제공자의 호출이 파일을 고쳤을 때는 '기록이 사라진 적이 있음' 표시가 저장되어 운영자가 확인(`acknowledge`)하기 전에는 열리지 않고, 확인하면 프로그램 안 한도의 절반을 이미 쓴 것으로 두고 다시 센다 ② 이번 달·오늘 숫자가 한도·과거 기록·호출 장부와 맞지 않는다(이번 달 시도 수가 이달에 본 최고치보다 낮음·성공이 시도보다 많음·하루 시도가 이번 달 시도보다 많음·남은 장부의 합이 계수보다 많음) ③ 컴퓨터 시계가 마지막으로 본 시각보다 5분을 넘게 되돌아갔다(정확히 5분까지는 흔들림으로 보고 허용한다. 되돌린 시계가 마지막으로 본 시각의 5분 안으로 돌아오면 — 시계를 바로잡거나 시간이 그만큼 흐르면 — 운영자 확인 없이 자동으로 다시 열리고, 그 전에 열려면 운영자가 확인(`acknowledge`)한다) ④ 연결 설정 파일(`connections.json`)이 깨졌다 ⑤ 인증 상태가 불분명하다(연결 시험이나 성공한 실제 호출의 기록이 24시간 안에 없거나 인증 실패로 멈췄다. 성공한 호출의 보고 — 응답 상태가 2xx 이거나 안 적었고 응답을 썼을 때 — 는 마지막 성공 시각을 갱신해 24시간 창을 이어 주고, 실패·모호한 결과는 갱신하지 않으며 인증 실패로 멈춘 항목은 되살리지 않는다. 호출 코드가 생기기 전에는 아무도 이 판정으로 호출하지 않는 틀이고, 연결 시험 호출 자신은 이 검사만 건너뛴다) ⑥ 잠금을 못 잡거나 상태를 쓰지 못한다. 이때 사용자에게 보이는 문장은 하나로 고정이다 — 'NAVER API HUB의 새로운 데이터 조회를 사용할 수 없습니다. 저장된 정보와 기본 주제 선정 규칙으로 후보 생성을 계속합니다.' — 구체적인 원인은 따로 둔다(`keys usage` 의 '사유' 줄). 다른 용도의 동작은 그대로다.

**한도·시도와 성공·호출 장부·단계.** 한도는 두 겹이다. 프로그램 안 기준은 하루 100회·이번 달 27,000회이고 둘 다 지켜서 먼저 닿는 쪽이 막는다. 서비스 콘솔의 월 한도(30,000회 — 계정 설정에 따라 최대 50,000회, 100% 에서 호출이 차단되고 알람은 50% 부터)는 마지막 안전장치이자 단계의 기준이다. 월 창은 **한국 시간 달력 월**이다(다음 달 1일 00:00 에 0 으로 돌아간다). 시도(실패한 호출도 센다 — 429·시간 초과 포함)와 성공을 따로 세고, 최근 200건의 호출 장부에는 호출 종류·시작/끝 시각·조건 해시(정규화한 요청의 해시 앞 12자)·성공 여부·HTTP 상태·재시도 수·응답을 썼는지·캐시 적중만 적는다. 키·응답 본문·요청 본문은 없고, 키처럼 보이는 칸 이름이 든 조건은 장부에 가기 전에 거절한다. 단계는 콘솔 월 한도 기준이다(이번 달 시도 수에 이 호출을 더한 값이 경계를 넘을 때): 21,000회(70%) 초과는 안내만, 24,000회(80%) 초과는 자동 새로고침·배치(`bulk_refresh`)를 거절하고 직접 시작한 분석(`new_candidate`)은 한 번에 5회까지(기본값)만 허용하며, 27,000회(90% = 프로그램 안 월 한도) 초과는 필수 호출(`critical`)까지 모든 새 호출을 거절한다. 이 제공자는 '마지막 10% 는 필수 호출 전용' 규칙을 쓰지 않는다(하루 100회 창에도 쓰지 않는다 — 구현 쪽 기본값이라 아래 알려 둔 한계에 적었다). 서버가 기간 한도 소진(`quota_exhausted`)을 알려 오면 다음 달 1일 00:00(한국 시간)까지 쉰다(서버가 48시간 안의 초기화 시각을 알려 주면 그 시각까지).

**모르는 것과 안전한 쪽의 선택.** ① 실패한 호출이 공식 사용량에 들어가는지 → 시도로 센다 ② 월 초기화 시각과 시간대(콘솔 쪽 값은 공개 문서에 없다) → 한국 달력 월로 잡고, 프로그램 안 월 한도(27,000)가 콘솔 한도(30,000)보다 10% 낮아 9시간쯤 어긋나도 흡수한다 ③ 받은 데이터를 저장·캐시하거나 AI 에 넣어도 되는지의 약관 → 이 묶음은 데이터를 저장하지 않으므로 다루지 않았다(쓰기 전에 먼저 확인한다) ④ Client ID/Secret 의 실제 모양 → 느슨한 확인 ⑤ 무료 기간은 한시적이고 끝나는 날이 공개되어 있지 않다. **알려 둔 한계**: 호출 코드가 없다(후속) · 확인 절차(`acknowledge`)는 아직 명령에 이어져 있지 않다 · 프로그램 안 하루·월 한도와 분석 5회 상한은 설정으로 낮출 수 없다 · 사용량은 이 앱이 센 것이라, 콘솔에서 같은 앱·키를 쓰는 다른 곳의 사용은 보이지 않는다(콘솔의 50% 알람이 운영자의 교차 확인이다) · 직접 고친 상태 파일이 서로 맞으면 알아내지 못한다 · 사용량 상태 파일(`quota_state.json`)을 통째로 지우면 새로 시작한 것으로 보아 사용량이 0 으로 돌아간다(깨진 파일과 달리 알아내지 못한다 — 콘솔의 사용량이 교차 확인이다) · 일 한도 100 이 먼저 막아 이 앱의 사용만으로는 한 달에 3,100회를 넘지 못하므로 월 단계(21,000·24,000·27,000회)는 실제로는 닿기 어렵다 — 콘솔 한도(30,000회)를 지키는 이중 안전장치이고 일 한도를 늘렸을 때를 위한 것이다 · 시계가 되돌아갔다가 마지막으로 본 시각의 5분 안으로 돌아오면(시계를 바로잡거나 시간이 그만큼 흐르면) 운영자 확인 없이 자동으로 다시 열린다 · 서버가 기간 한도 소진을 알리면 다음 달 1일 00:00(한국 시간)까지 쉬므로, 서버의 월 초기화가 한국 달력 월보다 늦은 월 초(최대 9시간)에 소진 응답이 오면 그 한 달을 쉬게 될 수 있다 · 하루 100회 안에서는 우선순위 몫 보호가 없다(구현 쪽 기본값 — 운영자가 정한 것은 월 70·80·90% 단계뿐이다): 자동 새로고침이 하루 100회를 다 쓰면 그날 사용자가 직접 고른 후보의 호출도 거절된다(일반 제공자는 일괄 갱신 70회·새 후보 80회·선택된 후보 90회에서 멈추고 필수 호출만 100회까지 한다). 되돌리려면 일 창에도 기존 몫 규칙을 쓰게 하거나 호출 코드를 만드는 다음 묶음(N2)에서 자동 새로고침의 하루 상한을 낮춘다 — 정하기 전의 기본값은 예약 없음이다.

**옛 용도(`naver_openapi`).** 옛 판이 만든 `connections.json` 에 `naver_openapi` 항목이 있어도 계속 읽는다(`CONNECTIONS_FILE_INVALID` 가 아니다). 이 용도는 '옛 용도' 로만 남아(`legacy_to = naver_apihub`) 새 항목을 키를 읽거나 묻기 전에 거절하고, 남은 항목은 `keys list` 에 '옛 항목' 표시와 함께 보인다(새 키는 `naver_apihub` 에 넣고 옛 항목은 `keys remove` 로 지우라는 안내가 붙는다). 키는 자동으로 지우지 않는다. 옛 용도는 `keys purposes`·`keys usage` 에 나오지 않고, `keys list` 의 상태 줄과 진단 요약에는 항목이 남아 있을 때만 나온다. 옛 용도로는 호출 몫도 주지 않는다(`QuotaGuard.acquire` 와 연결 시험용 `acquire_entry` 가 쉬운 한국어로 거절하고 새 용도로 안내한다).

## 8. 화면에서 키 넣기(P4f) — 설계 D-250~D-259

설정 화면의 연결 카드에서 키를 등록·삭제·시험하고 사용/예비·별칭·우선순위를 바꿀 수 있다(쓰기는 사용자가 단추를 눌렀을 때만 — 설정 화면을 열고 다시 읽는 것은 파일·보관소를 바꾸지 않는다). 저장 위치와 영구 저장 금지는 §7 그대로다: **키 원문은 Windows 자격 증명 관리자에만** 있고, 저장해도 되는 것은 별칭·제공자·등록 여부·사용 상태·마지막 성공 시각·마지막 확인 결과(`ok`·`auth_failed`·`error` 라는 결과 이름)·순서·약관 확인 시각뿐이다. **키 원문·앞뒤 일부 글자·길이·문자 구성·Authorization 헤더는 어디에도 저장하지 않는다.** 저장한 키는 화면에 다시 보이지 않는다(끝 4자도 — 화면과 명령줄 어디에도 없다, D-346).

**키가 지나가는 길과 막는 장치**(시험이 전수로 지킨다 — `tests/key_leak_support.py`: 가짜 키와 그 모든 네 글자 조각이 한 곳이라도 있으면 실패):

| 길 | 막는 방법 |
|---|---|
| 입력 칸 | 마스킹(`Password`) — 복사·잘라내기가 글을 클립보드에 내보내지 않고 Qt 가 예측 입력·민감 정보 표시를 켠다. 플레이스홀더·툴팁 없음. 키 칸에 `textChanged`·`textEdited` 를 잇지 않는다(글은 '다음'·'저장' 을 누르는 순간에만 읽는다) |
| 입력 칸을 비운 뒤 | `setText("")` — `clear()` 는 지운 글을 되돌리기 기록에 남기지만 `setText` 는 기록까지 지운다. 저장·취소·Esc·다른 대화상자로 바뀜·창 닫힘 어느 길로든 비운다 |
| 클립보드 | 붙여 넣은 글과 같은 글이 클립보드에 그대로 있으면 저장·닫을 때 비운다(다른 글은 건드리지 않고 앱이 키를 클립보드에 넣지 않는다) |
| 서비스까지 | `SecretBox`(꺼내면 비워지고 `repr`·복사·직렬화가 글을 보이지 않는다) → 서비스 함수 인자. 뷰모델·컨트롤러·등록 초안·값 클래스·결과·실패·알림·행 안내·진단에는 키를 담는 칸이 없다. 작업 스레드의 일감은 통만 쥔다 |
| 예외·호출 흔적 | 어댑터가 서비스 오류를 종류·칸 문제 이름·정해진 쉬운 문장으로만 바꾸고 서비스 오류의 `__traceback__` 를 끊으며 실패 객체는 `except` 밖에서 낸다(앞 오류가 `__context__` 로 따라붙지 않는다). 꺼낸 글을 담은 dict 는 `finally` 에서 비운다. 화면 쪽 슬롯에서 난 예기치 못한 예외는 표준 오류에 **예외 이름과, 비밀 모양을 가리고 경로를 지운 짧은 한 줄**만 남긴다(`ui/core/app_state.unexpected_line` — 추적은 내지 않는다. 키와 닿는 곳이라 어떤 글도 새지 않게) |
| 일이 끝난 뒤 | 컨트롤러가 등록 일감을 `try/finally` 로 감싸 공급자가 통을 꺼내지 않고 죽어도(예기치 못한 오류) 통을 비운다 — 끝난 일의 기록(`runner`)이 통을 쥐고 있어도 거기에 키가 없다(시험이 공급자를 일부러 죽여 확인한다) |
| 별칭 칸 | 키처럼 보이는 글은 바로 비우고(눈에 보이는 칸이라) 거절한다. 서비스는 이름·소속 프로젝트에 키 값이 그대로 들었는지 거절하고, 별칭 바꾸기는 보관된 값이 이름에 들었는지도 거절한다 |
| 로그·진단·파일 | 오류 문장은 종류별로 정해진 말이다. 진단 정보는 시각·개수뿐(별칭도 없다). `connections.json` 에는 비밀이 아닌 칸만 있다 |

**등록·삭제 도중 실패하면**: 등록은 보관소에 먼저 넣고 파일에 쓰다 실패하면 방금 넣은 키를 지운다 — 지우기마저 실패하면 화면이 그렇게 알린다(`보관소에 넣은 키를 지우지도 못했어요`). 삭제는 보관소를 먼저 지우고 파일에서 지운다 — 파일 쓰기가 실패하면 '항목은 있는데 키가 없는' 상태가 화면에 보이고 다시 지울 수 있다. **'항목 없는 키' 를 자동으로 정리하는 단추는 만들지 않았다**: 자격 증명 관리자의 이름 공간은 데이터 폴더가 아니라 Windows 사용자 하나라서 목록에 없는 키가 다른 데이터 폴더(`--data-dir`)의 진짜 키일 수 있다.

**연결 시험**: 사용자가 누를 때만, 호출 코드가 있는 용도에서만이고 시험에서 실제 네트워크를 부르는 일은 없다(지금 어느 용도도 호출 코드가 없다). 이용 약관을 확인하기 전 용도(NAVER API HUB)는 시험 함수를 건네줘도 호출하지 않는다. 시험은 다른 키로 바꿔 시도하지 않는다.

**막지 못하는 것**: §7 과 같다(같은 Windows 사용자의 악성 프로그램·PC 관리자·메모리 덤프·파이썬 문자열을 메모리에서 못 지우는 것). 이 묶음이 더한 한계: Windows 의 한글 입력기(IME)가 조합 중인 글을 어떻게 다루는지·화면 읽기 프로그램이 마스킹 칸의 글자 수를 읽는지는 운영자 PC 에서 확인한다.

## 본문 속 Secret 형태 검사(`security/scan.py`) — 설계 D-420–D-429

운영자 결정(2026-11-11): **글을 저장하거나 백업하기 전에, 사용자가 본문에 붙여 넣은 Secret 형태를 검사한다.** 발견하면 토큰을 다시 보이지 않고 **어디에·어떤 유형이 있는지**만 알리고, 기본 동작은 저장·백업 중지다. 앱은 글을 자동으로 지우거나 바꾸지 않으며 **'무시하고 저장'은 없다** — 이 검사기에는 발견을 끄는 인자도 함수도 없고(소스 이름 검사 시험이 못박는다) 글을 돌려주지도 않는다.

**찾는 것(여섯 가지)**: Google API 키(`AIza` + 35자 이상) · GitHub 토큰(`ghp_`·`gho_`·`ghu_`·`ghs_`·`ghr_` + 36자 이상, `github_pat_` + 22자 이상) · Bearer 토큰(`Bearer` + 공백 + 20자 이상) · OAuth 토큰(`ya29.`·`1//`·`GOCSPX-` + 20자 이상, JWT 세 덩어리, `access_token`·`refresh_token` 이름 뒤 20자 이상 값) · AWS 액세스 키 ID(`AKIA` 등 접두어 8가지 + 16자) · PEM 개인 키(`-----BEGIN` … `PRIVATE KEY` … `-----` 머리 줄). **모양만 본다** — 견본 키·공식 예시 키도 모양이 같으면 발견이다. 자세한 모양과 근거는 [`DECISIONS.md`](DECISIONS.md) D-421.

**누가 언제 부르나**: 초안 저장 직전(제목·본문·키워드·태그·요약) · 전체 백업과 글 보관함·주제 엔진 백업 직전(원고·후보·초안 표, 프로필·Seed·캘린더·`settings.json` 값 — 부분 폴더를 남기지 않는다) · 옛 명령줄 쓰기(`candidates add`·`naver-profile set`·원고 제목·본문 쓰기) · 화면 쓰기 경로(블로그 프로필·Seed·초안 화면). 이 부품은 문자열만 받고 파일·DB·네트워크를 읽지 않으므로 어디를 훑을지·어느 오류 코드로 거절할지는 부르는 묶음이 정한다(D-427). 마스킹(`mask.py` — 출력에서 가린다)·키 모양 입력 검사(`shape.py`)와는 따로다 — 이것은 **쓰기 전에 막는다**.

**사용자에게 보이는 것**: `describe`('본문 3번째 줄에 GitHub 토큰처럼 보이는 글이 있어요')와 `summarize`(칸·유형별 건수와 줄 번호, 마지막에 '해당 줄을 본문에서 지운 뒤 다시 저장해 주세요 — 앱은 자동으로 지우거나 바꾸지 않아요')뿐이다. 토큰 글자는 문장·결과 객체·예외 문구·직렬화(`asdict`·피클·JSON) 어디에도 없고, 문장에는 길이 힌트(열 범위를 풀어 쓴 글)도 없다(카나리 시험).

**위치와 성능**: 줄은 1부터(CRLF·LF·CR), 열은 그 줄 안의 파이썬 글자 1부터(`col_end` 는 마지막 글자, 포함). 전각·수학 글자·특수 공백은 글자 하나씩 NFKC 로 맞춰 길이를 그대로 두므로 위치가 원문 그대로다. 정규식은 모두 선형이고 10만 글자 병적 입력 55가지가 파이썬 3.12·3.10 에서 모두 0.5초 안이다(D-424).

**한계(사실대로)**: 이 검사기는 **모양을 아는 비밀만** 찾는다. ① 공백·줄바꿈·눈에 안 보이는 글자(`U+200B`·소프트 하이픈)로 쪼갠 토큰, 접두어 앞에 영문·숫자가 붙은 토큰(주소의 `%3D` 같은 퍼센트 구분자 바로 뒤는 괜찮다)은 못 찾는다 ② 여섯 가지 밖의 형식(OpenAI·Slack·텔레그램 봇·AWS 비밀 키·자유 글 속 비밀번호·이름 모르는 형식)과 하한보다 짧은 토큰은 못 찾는다 — 마스킹이 출력에서는 가려 주지만 쓰기를 막지는 않는다 ③ PEM 은 머리 줄만 본다(몸통만 붙여 넣으면 못 찾는다) ④ 견본 키·공식 문서의 예시 키·변수 이름처럼 긴 값(`access_token=` 뒤)도 모양이 같으면 걸린다 — 그 줄을 고쳐 쓰게 한다 ⑤ 글자 모양만 본다: 키가 진짜인지는 모른다 ⑥ 인코딩해 쓴 토큰(base64·16진수·퍼센트로 쓴 밑줄)·글자 순서를 뒤집은 토큰·대소문자를 바꾼 접두어·`Bearer` 와 값 사이의 줄바꿈은 못 찾는다(재귀적으로 풀어 찾지 않는다 — D-359). 올리는 글을 눈으로 확인하는 일(`AGENTS.md` §2 규칙 1)을 대신하지 않는다.

### 외부 게시는 완전히 꺼져 있다(H3 — D-341–D-343)

이 시험 버전에는 글을 외부로 쓰는 길이 **없다** — PC 에 Git 로그인이 이미 있어도 push 할 수 없다. 설정 스위치를 '기본 꺼짐'으로 둔 것이 아니라 네 겹이 서로를 받친다.

1. **서비스 비활성** — GitHub 에 올리기·올리기 권한 점검·원격 최신 받기·공개 확인·취소를 하는 모든 함수의 **첫 줄**이 `capabilities.require_external_write(작업)` 으로 `EXTERNAL_WRITE_DISABLED` 를 낸다(하위 프로세스·네트워크·파일 쓰기보다 먼저).
2. **어댑터 미등록** — Blogger·네이버로 보내는 어댑터는 없고 등록부(`service/external.py`)는 비어 있다. 기본 git 은 모든 호출을 거절하는 `refusing_git`, 기본 백엔드는 파일만 읽는 `LocalOnlyBackend` 다.
3. **소스 상수 Runtime Gate** — `capabilities.EXTERNAL_WRITE = False` 는 소스에 박힌 상수다. 설정 파일·환경 변수·명령줄·화면이 바꿀 수 없고 켜는 훅이 생산 코드에 없다(시험만 `mock.patch.object` 로 모듈 단위로 임시로 켠다).
4. **Network Write 0 시험** — 모든 부명령과 화면 어댑터의 연결을 감시기(소켓·HTTP·`urllib`·`subprocess.Popen`·`os` 의 프로세스 실행 함수·`webbrowser`)를 켠 채 돌려 나간 호출이 0 임을 확인하고, 나가는 호출이 있는 소스 위치를 허용 목록으로 못박는다. **한계(D-359)**: 위치 규칙(AST)은 import 구문과 `os.<이름>` 만 본다 — `__import__('subprocess')`·`importlib.import_module`·`ctypes.WinDLL`·`from os import system`·`getattr(os, '문자'+'이어 붙이기')` 같은 **의도적** 우회는 막지 못하고 런타임 감시기는 실행되는 경로만 본다. 우발적인 추가(`import subprocess`·`webbrowser`·`os.system`)는 확실히 잡는다. `keys purposes` 의 GitHub 안내와 `doctor` 의 '올리기 권한' 줄은 이 빌드에서 '이 시험 버전은 글을 GitHub 에 올리지 않아요' 라고 말한다(D7).

**한계(사실대로)**: ① **이름 표지가 없는 값**(경로 속 키·라벨 없는 한 줄·라벨 없는 10자 시크릿·64자 16진수·43자)은 가리지 않는다 — 모양만으로는 SHA-256·커밋 해시와 가를 수 없어 일부러 그렇게 했고 시험이 그 5건이 가려지지 않음을 못박는다 ② 이중 퍼센트·`\uXXXX` 로 쓴 이름·base64 두 겹·8192자 뒤에만 비밀이 있는 긴 base64 덩어리·이름 표지 없이 줄바꿈으로 쪼갠 값은 못 가린다 ③ 스트림 `.buffer` 로 바이트를 직접 쓰는 것·자식 프로세스의 직접 출력·`faulthandler`·Qt 가 아닌 라이브러리가 C 쪽에서 찍는 글은 경계를 지나지 않는다(앱 코드는 소스 규칙 시험이 막는다) ④ 설치 뒤 다른 코드가 `sys.stdout` 등을 다시 바꿔 끼우면 그 객체는 경계 밖이다(소스 규칙 시험이 앱 코드의 바꿔 끼움을 막는다) ⑤ 위젯 `setText` 161곳은 한 점에 모으지 않았다 — 위젯 글 전수 훑기 시험이 지킨다(새 화면은 그 시험에 장면을 더해야 한다) ⑥ 로그 파일 핸들러는 만들지 않았다(없는 기능) ⑦ **마스킹이 못 가리는 모양**(D-359): 이름과 값이 따로 있는 JSON·XML(`name`·`value` 칸 쌍·`<add key=… value=…/>`·`name=…&value=…`), YAML 블록 `api_key: >` 다음 줄, 닫히지 않은 따옴표(앞에서 잘린 글), HTML 엔티티 구분자(`&#61;`·`&equals;`)나 결합 글자가 낀 이름, `curl -u 사용자:값`·`passphrase=`·`password => x`, 줄바꿈으로 쪼갠 이름, JSON 배열의 `set-cookie`, 이름과 값 사이에 다른 낱말이 낀 문장(`my password is x`·`The api key is x`), 구분자 없이 이름 뒤에 오는 값이 짧거나(16자 미만) 숫자·글자 한쪽뿐인 것(`auth token x` — 낱말·번호와 가를 수 없어 일부러 그렇게 했다), 값이 빈 라벨 줄(`password:`) 바로 다음 줄의 헤더 일부(`X-API-Key` 값의 `_`·`-` 뒤 꼬리). 공백·점이 낀 이름(`API key: x`·`api.key=x`)·`Basic ` 낱말 바로 뒤의 `이름=값`·이름 낱말 바로 뒤에 구분자 없이 오는 값 모양(`auth token Zq8…`·`Your API key Zq8… is not valid` — 같은 줄에서 16자 이상이고 숫자와 글자가 모두 있을 때만, 규칙 사슬의 맨 끝)은 D4 에서 고쳤다 ⑧ **경계 스트림**(D-359): 공백 없는 조각이 16384자를 넘으면 쥐고 있던 것을 내보내 쪼갠 쓰기에서 라벨 뒤 값이 라벨 없이 나갈 수 있고, 이름과 값 사이에서 일부러 `flush()` 를 부르면 이름이 먼저 나간다 — 앱의 출력 경로는 출력 직전에 `mask_block` 을 먼저 지나므로 지금 영향이 없다. 헤더 줄(`Cookie`·`Set-Cookie`·`Authorization`)은 4096자를 넘어도 공백에서 자르지 않는다(D5 a 고침). 기존 시험 108곳(41개 파일)은 실패하면 비밀을 그대로 찍을 수 있어 목록으로 보고하고, `tests/run_masked.py` 로 돌리면 실패 글이 가려진다.

### 키는 다섯 가지만 보인다(H2 — D-346)

화면·명령줄(`keys list`·`keys add`)·`--json`·`doctor`·연결 시험에 보이는 키 관련 정보는 **제공자 이름·항목 번호(Key Slot)·등록 여부·마지막 연결 시험·등록 시각**뿐이다. 끝 4자·앞부분·접두어·길이는 어디에도 없고, 그것을 만들던 코드(`tail_hint`·`EntryView.tail`)도 지웠다. 소스 규칙 시험(`test_source_rules_key_display`)이 값의 일부를 자르는 이름·문구·식과 `reveal(` 호출이 `service/`·`ui/`·`security/` 에 없음을 확인하고, 화면 위젯 전수 훑기가 가짜 키와 그 모든 네 글자 조각이 어느 위젯 글에도 없음을 확인한다. `--json` 은 그 다섯 가지를 다루는 데 필요한 칸(항목 번호용 난수 `entry_id`·순서·상태·마지막 확인 시각과 결과·약관 확인 시각)만 낸다 — NAVER 고객 ID 같은 칸에서 만든 묶음 이름(`bucket`)은 싣지 않는다(D-358).

### Blogger OAuth 입력(D-347)

이 빌드에는 Blogger 를 부르는 코드가 없으므로 `BLOGGER_OAUTH_INPUT = False`(소스 상수 — 켜는 길 없음)로 입력을 막았다: 서비스(`add_entry`)와 명령줄(`keys add`)은 키를 묻기 전에 거절하고, 화면의 Blogger 카드에는 입력 칸·등록 단추 없이 '받지 않아요' 안내만 있다. 자격 증명 관리자에 저장하는 코드와 이미 저장된 항목의 지우기·시험은 그대로다. Blogger 초안 기능을 구현할 때 Scope·연결 해제·Token 삭제·재인증·초안 전용 정책과 함께 별도 검증을 거친 뒤 연다.

### 본문 속 Secret 형태의 적용 위치(M3 — D-348)

검사기(위 '본문 속 Secret 형태 검사' 절)를 `security/refuse.py` 가 부르기만 한다. ① 옛 명령줄 쓰기: 원고 제목·본문·출처·이미지(`new`·`edit`·`import-html`)·후보 주제·핵심 키워드·보조 키워드·추천 이유(`candidates add`)·네이버 프로필 글칸(`naver-profile set`)·검토 요청의 매개변수(`review` 의 분야·태그·한 줄 설명·대표 이미지 주소·출처 이름·주소·글 제목, 네이버 검토의 제목·본문 파일·태그·분야)·네이버 발행 주소(`naver-done --url`)는 쓰기 전에 `SECRET_SHAPE_FOUND` 로 멈추고 칸·줄·유형만 알린다. 후보 CSV 는 그 줄만 거절한다. ② 백업 전: `backup` 은 글·옛 판 기록·초안·후보를 훑어 있으면 백업을 만들지 않고, 주제 엔진 백업은 옛 정본 패턴과 검사기 여섯 유형을 **둘 다** 막으며 `TOPIC_BACKUP_BLOCKED` 의 이유에 위치(파일·줄 또는 표·행)와 유형을 말한다. 지우기·되돌리기 직전의 안전 사본은 막지 않는다 — 막으면 문제의 글을 지울 수도 되돌릴 수도 없다. ③ 화면 쓰기(블로그 프로필·Seed)는 같은 `scan_key_shape` 라 같은 종류를 막고, 초안 복사 관문은 검사기가 찾은 자리를 더하되 글자를 한 자도 되풀이하지 않는다. ④ 키 항목의 별칭(이름)·소속 프로젝트(평문 파일 `connections.json` 에 남는 칸): 가리기 규칙이 가릴 글(`client_secret=값`·`Cookie: …`·`Authorization: Bearer …`)이 있으면 `KEY_INVALID_SHAPE` 로 쓰기 전에 거절하고 칸 이름과 이유만 알린다(`keys add --name`·화면·이름 바꾸기가 같은 규칙, PCSEC1V). **'무시하고 저장'은 없다**(인자·명령줄 옵션·환경 변수·설정 없음 — 시험이 소스와 명령줄 파서에서 못박는다). 한계: 옛 명령줄 쓰기와 글 보관함 백업은 검사기의 여섯 유형만 본다(옛 패턴이 아는 OpenAI·Slack 등은 출력에서는 가려지지만 거기서는 막지 않는다), `edit` 는 바꾸지 않는 칸의 옛 비밀 모양을 막지 않고 백업 전 검사가 막는다.

### 그 밖에 사실대로 적는다(M1·M2·M4·M7·M8 — D-349–D-353)

- **데이터 폴더 위치(M1)**: 앱은 폴더 권한(NTFS ACL)을 설정하지도 확인하지도 않고 사용자 프로필 폴더의 상속에 기댄다. 데이터 폴더가 사용자 프로필 밖이면 `doctor` 가 '같은 PC 의 다른 사용자가 읽을 수 있어요' 라고 주의한다(문자열 경로 비교만 한다).
- **시험용 가짜 보관소(M2)**: `CHANCEBLOG_KEYSTORE` 로 연 시험 전용 보관소를 쓰는 중이면 키 화면이 '시험용 보관소 — 실제 키를 넣지 마세요' 를 알린다.
- **백업(M4)**: 주제 엔진 백업 목록에 `credential_excluded: true` 와 쉬운 문장이 있고 명령줄 백업 출력에 '키는 백업에 들어 있지 않아요' 한 줄이 있다. 무엇을 담는지는 바뀌지 않았다.
- **폴더 이름(M7)**: 코드의 `ChanceblogDesktop`·자격 증명 대상 `ChanceBlogDesktop:`·운영자 문서의 `ChanceBlog` 철자가 다른 것을 알고 있으며 바꾸지 않았다(바꾸면 저장된 키·데이터를 옮겨야 한다).
- **지운 글의 원문(M8)**: 글을 지우기 직전에 만드는 백업(`backups/before-delete`)에는 지운 글의 원문이 남고, 되돌리기 직전의 백업(`backups/before-restore`)에는 되돌리기 전의 글 전체가 남는다 — 소유자 권한 폴더 안에 두는 복구용 설계다(각 폴더에 최근 10개만 남기고 오래된 것은 앱이 지우므로 원문은 그동안만 남는다). 파이썬의 `.pyc` 캐시(`__pycache__`)는 소스 옆의 같은 사용자 폴더에 생기며 앱이 지우지 않는다.
- **로그 파일·내보내기**: 아직 없다. 만든다면 공통 경계가 이미 가린 기록을 쓴다.
## 9. 전체 백업·복원(BACKUPUI) — 설계 D-380–D-397

설정 화면의 `백업·복원` 카드가 글 보관함·주제 보관함·채널 프로필·Seed·캘린더·설정을 한 폴더(`backups/full-날짜-시각/`)에 담고 되돌린다(서비스 `service/backup_flow.py`, 화면 `ui/qt/backup_parts.py`). **쓰는 곳이 하나 더 는다**: `지금 백업` 은 백업 폴더를 만들고(쓰는 함수 — 폴더 만들기·파일 지우기·이름 바꾸기·제자리 교체 — 는 `tests/test_service_safety.py` 의 허용 목록에 이유와 함께 등록돼 있고 목록 밖의 쓰기는 시험이 잡는다), `복원` 은 확인창의 `복원하기` 를 눌렀을 때만 데이터 폴더의 보관함·JSON·설정을 바꾼다. 카드를 열고 목록을 읽는 것은 아무것도 만들거나 바꾸지 않는다. (§5 의 '화면에서 파일에 쓰는 곳' 목록은 이 묶음에서 고치지 않았다 — 병합할 다른 묶음과 줄이 겹치지 않게 맨 끝에만 적고, 목록 정리는 병합 뒤 한 번에 한다.)

**백업에 Credential 이 없다는 것을 어떻게 지키는가**(운영자 2026-11-11 결정 — 시험이 전수로 지킨다):

| 길 | 막는 방법 |
|---|---|
| 키 원문 | 이 앱은 키를 파일에 적지 않는다(§7). 백업 코드는 키 보관소·환경 변수·`connections.json`·로그·`print` 에 닿지 못한다(소스 규칙 시험) — 담는 파일은 이름이 정해진 여섯뿐이고 `connections.json`·`quota_state.json`·`publish/`·`locks/` 등 담지 않는 아홉 가지는 이유와 함께 목록 파일에 적힌다 |
| 사용자가 글에 실수로 붙여 넣은 키·토큰 모양 | **백업 직전에 만든 사본을 훑는다**(`security/scan.py` — Google API 키·GitHub 토큰·Bearer 토큰·OAuth 토큰·AWS 액세스 키·개인 키(PEM)). 하나라도 있으면 백업을 만들지 않고 폴더도 남기지 않으며 위치(어느 칸·몇 번째 줄)와 유형만 알린다. 앱은 글을 자동으로 지우거나 바꾸지 않고 **'무시하고 백업' 이 없다** — 운영자가 직접 지운 뒤 다시 누른다 |
| 훑는 범위 | 여섯 유형 × 아홉 자리(원고 본문·제목·저장한 초안·글 보관함 후보·주제 보관함 후보·채널 프로필·Seed·캘린더·설정) = 54칸 모두와 옛 판 기록. 엄격한 읽기가 키 모양 글을 '틀린 모양' 으로 거절해 파일을 빼먹는 길을 막으려고 훑기를 엄격한 읽기보다 먼저 한다(시험) |
| 훑지 않는 곳 | 발행 이력 장부(`history_ledger`) — D-75 와 같은 이유(이미 공개된 블로그 글을 읽어 둔 것이라 지울 길이 없다). 같은 글이 다른 곳에 있으면 그곳은 막는다 |
| 지운 글의 조각 | SQLite 는 지운 글의 조각을 파일의 빈 쪽에 그대로 둘 수 있다. 앱의 보관함은 연결마다 지울 때 덮어쓰도록(`secure_delete`) 열리지만 앱 밖의 도구가 쓴 파일·옛 파일·다른 곳에서 가져온 파일은 알 수 없다 — 그런 파일에서 키 모양 글을 지운 뒤 다시 백업하라고 안내하면 조각이 백업에 실려 갈 수 있다(기본 설정에서 지운 글이 파일에 남는 것을 확인했다). 그래서 **백업 사본은 만든 뒤 `vacuum` 으로 빈 쪽을 정리한다**(지금 쓰는 파일은 건드리지 않고 이름표·행은 그대로 옮겨진다. 정리하는 동안의 임시 사본은 시스템 임시 폴더가 아니라 메모리에 둔다 — D-398). 시험이 '큰 초안에 키 모양 글을 넣었다 지운 파일' 의 백업·복원 직전 사본에 조각이 없음을 여섯 유형 모두에서 본다 |
| 목록·화면·오류 | 고정 문장과 위치 줄뿐 — 키 글자·경로·예외 문구가 없다(카나리아 시험: 가짜 키를 가짜 보관소에 등록해 둔 채 백업·복원을 돌려도 백업 폴더·목록·안전 사본의 모든 바이트에 가짜 키의 여덟 가지 모습(utf-8·utf-16 둘·16진수 둘·base64 둘·퍼센트 인코딩)이 없다. 찾는 도구가 모든 모습을 실제로 찾는지도 따로 본다) |
| 복원 | 백업 안에 키 모양이 있으면 복원하지 않고, 지금 데이터에 키 모양이 있으면 안전 사본을 남길 수 없어 시작하지 않는다(앱이 고칠 수 없다고 말한다). 키·`connections.json` 은 바이트도 건드리지 않는다 |
| 안전 사본 | 같은 규칙이다 — 복원 직전 사본(`backups/before-restore/`)에도 키가 없다(시험이 같은 방법으로 훑는다) |

**복원이 안전한 이유**: 바꾸기 전에 백업을 읽기만 해서 목록 모양·파일 이름·크기·해시·보관함 이름표·판·점검을 모두 확인하고(한 바이트만 바뀌어도 거절 — 시험이 파일을 하나씩 바꿔 본다), 더 새로운 프로그램의 백업은 쓰지 않으며, 지금 데이터를 안전 사본으로 먼저 남기고(못 남기면 시작하지 않는다), 어느 단계든 실패하면 안전 사본으로 원래대로 돌린다(되돌리지 못한 것은 이름을 알린다). 백업과 복원은 같은 잠금(`locks/full-backup.lock`)을 써서 한 번에 하나만 돈다. 깨진 지금 파일은 지우지 않고 옆(`.bad-날짜-시각`)으로 옮긴다.

**밖으로 나가지 않는다**: 백업·복원은 네트워크·외부 쓰기·AI 호출이 0 이다(새 코드는 `subprocess`·`socket`·`urllib`·`webbrowser`·`os.startfile` 을 가져오지 않고 시험이 지킨다). 폴더를 여는 단추도 없다 — 백업 위치는 글자로만 보이고 USB·다른 PC 에 복사하는 것은 사용자가 직접 한다.

**막지 못하는 것·알려 둘 것**: ① 지금 쓰고 있는 보관함 파일(`chanceblog.db`·`topic_engine.db`)이 앱 밖에서 쓰였거나 옛 파일이면 그 빈 쪽에 지운 글의 조각이 남아 있을 수 있다 — 백업 사본에는 실리지 않지만(위) 그 파일은 사용자의 데이터 폴더에 그대로 있고, 이 묶음은 보관함을 고쳐 쓰지 않는다(앱이 쓰는 연결은 지울 때 덮어쓴다 — 후속 후보 D-399) ② 훑기는 여섯 모양을 규칙으로 찾는 것이라 모르는 모양의 비밀이나 쪼개 쓴 글은 못 잡는다(§7 의 한계와 같다) ③ 같은 Windows 사용자의 악성 프로그램은 백업 폴더도 읽을 수 있다 — 백업은 이 컴퓨터 안의 폴더이고 암호화하지 않는다(키가 없는 데이터라서다). USB 에 옮길 때는 그 USB 를 사용자가 관리한다.

**수정 라운드(2026-11-12 — 독립 검증 BACKUPUIV 지적 반영, 결정 D-460–D-466)**: ① **키 모양은 디스크에 닿기 전에 걸러진다** — 보관함 사본은 메모리 연결에 만들어 `vacuum` 한 뒤 그 자리에서 훑고(JSON·설정은 읽은 바이트를 먼저 훑고) 이상 없을 때만 파일로 쓴다.
그래서 강제 종료·창 닫기·이름 바꾸기 막힘 어느 때에도 키 모양이 든 사본은 디스크에 있었던 적이 없다(자식 프로세스를 `os._exit` 로 곳곳에서 죽인 시험이 지금 파일을 뺀 데이터 폴더의 모든 바이트를 8가지 인코딩으로 훑어 0 을 확인한다). 쓴 폴더를 한 번 더 훑는 이중 확인은 남아 있다
② 앱이 갑자기 꺼져 남은 임시 폴더(`full-….tmp`·`before-….tmp`, SQLite 짝 파일 포함)와 낡은 잠금은 다음 백업·복원이 잠금을 쥔 채 치우고, 목록을 보여 줄 때도 치울 흔적이 보이면(살아 있는 백업·복원이 없을 때만) 치운다
③ 복원이 도중에 멈추면 `backups/restore-in-progress.json`(이름·시각뿐 — 글 내용·경로 없음)이 남아 카드가 쉬운 안내와 '안전 사본으로 되돌리기'(확인창 먼저)를 보여 준다 — 앱이 시작하면서 혼자 되돌리지는 않는다
④ 정리가 방금 만든 백업을 지우지 않는다(시계가 거꾸로 가도 — 미래 날짜의 옛 것이 대신 정리된다) ⑤ WAL 저장 방식으로 바뀐 보관함도 백업된다(사본은 일반 방식) ⑥ 정리 못 한 저장(`-journal`)이 남은 보관함은 백업이 건드리지 않고 부분 백업으로 알린다
⑦ 이름 바꾸기·바꿔 넣기는 다른 프로그램이 잠깐 붙잡으면 0.2초씩 다섯 번까지 다시 한다. **여전히 막지 못하는 것**: 앱이 죽은 뒤 임시 폴더에 남은 것은 키 모양이 없는 내용이지만 다음 백업·복원·목록 전까지는 디스크에 있다(치우기는 다음 실행의 일이다).

## 10. 저장한 초안 — 설계 D-360 에서 D-374 까지 (LOCALSAVE)

초안 작성 화면의 `저장`(Ctrl+S)은 **새 저장 위치를 만들지 않는다** — 같은 글 보관함 `chanceblog.db` 의 `drafts` 표(`content/store.py` 에 원래 있던 표 — 구조 판은 그대로 2)에 초안 한 편이 한 행으로 들어가고, `Store.backup`·`restore_from` 이 파일 통째라 백업·되돌리기에 자동으로 따라간다. 위 §5 의 '화면에서 파일에 쓰는 곳은 … 네 곳이다' 에 이 묶음의 저장한 초안이 **한 곳 더해진다**(블로그 관리·Seed 관리·주제 후보·키 넣기 + 저장한 초안 — 새로 더해지는 곳만 `chanceblog.db` 이고 나머지 넷의 쓰는 곳은 그대로다). 전체 백업·복원이 더하는 쓰는 곳은 위 §9 에 따로 적혀 있다. §5 의 그 문장은 내 글 문체 참고값 보기(N-3a)의 시험이 글자 그대로 못박고 있어 이 묶음도 고치지 않았다 — 목록 정리는 병합 뒤 한 번에 한다. 서비스에서 이 표에 쓰는 함수는 `service/draft_store.py` 의 `save_draft`·`delete_draft` 둘뿐이고 `tests/test_service_safety.py` 의 `STORE_DRAFT_WRITERS`(이유 한 줄씩)가 못박는다 — 새 쓰기 위치·새 파일·새 네트워크 호출은 없다.

- **저장 직전 키·토큰 모양 검사**(`security/scan.py` — Google API 키·GitHub 토큰·Bearer 토큰·OAuth 토큰·AWS 액세스 키·개인 키(PEM)): 제목·본문·키워드·태그·카테고리·요약·후보 주제·후보 번호·선택 입력과 처음 만든 초안(제목·제목 후보·본문·확인 권장·분야·바꾼 형식)을 훑고, 하나라도 찾으면 **아무것도 쓰지 않고 글 보관함 파일을 열지도 않은 채** 멈춘다(`DRAFT_SECRET_FOUND`). 화면에는 위치(칸 이름과 몇 번째 줄)와 종류만 나오고 **찾은 글은 어디에도**(화면·오류 문구·알림·`repr`·피클) 다시 나오지 않는다. 앱은 글을 자동으로 지우거나 바꾸지 않고, **'무시하고 저장' 은 없다**: `save_draft` 에 검사를 건너뛰는 인자가 없고 화면·오류 문구 어디에도 그런 말이 없다(시험이 함수 서명과 모든 소스의 글을 훑는다). 만든 초안 칸에서만 찾았다고 그 칸을 빼고 저장하지도 않는다(D-368 — 예전에 있던 그 길을 운영자 결정 4항에 따라 없앴다): 화면에서 못 고치는 칸이라 안내가 후보·블로그 프로필(대상 독자·카테고리 같은 칸)과 선택 입력에서 키처럼 보이는 글을 지운 뒤 '다시 만들기' 를 하라고 알리고, 다시 만들면 지금 고친 글이 사라지니 먼저 복사하라고 한다.
- **저장은 복사가 아니다**: 복사 관문(건강 효과 단정·확인 권장·글 모양 점검)은 저장을 막지 않는다. 저장 실패(디스크 가득·읽기 전용·손상·잠김·한도)는 쉬운 안내이고 복사·편집은 그대로 쓸 수 있다. 떠나기·앱 닫기 앞의 확인창에서 `저장` 을 골랐는데 저장이 안 되면 나가기를 막지 않고 경고한다.
- **원자성**: 한 번의 저장은 `Store.update_draft` 한 트랜잭션(`BEGIN IMMEDIATE … COMMIT`)이라 쓰는 도중 끊기거나 디스크가 가득 차도 이전에 저장한 판이 그대로이고 반쯤 쓴 기록이 없다. 확인(저장 횟수 비교·300편 한도)과 쓰기가 같은 쓰기 잠금 안이라 같은 초안을 두 프로세스가 동시에 저장해도 갱신이 조용히 사라지지 않는다(D-369). 같은 초안을 다른 창이 그 사이 다시 저장했다면 덮어쓰지 않는다(`STORE_CONFLICT` — 저장 횟수 `expected_revision`). 깨진 기록 위에는 쓰지 않는다(`DRAFT_CORRUPT`). 앱이 큰 저장을 하다 꺼져 저널이 남은 보관함은 읽는 길이 한 번 보통 열기로 정리한 뒤 읽는다(D-370 — 저장해 둔 초안은 그대로).
- **지우기**: 확인창이 먼저이고 지우기 직전 상태를 `backups/before-delete` 에 사본으로 둔다(사본에는 지운 초안의 글이 그대로 있다 — 같은 사용자 폴더 안, 복구용 설계. 글 지우기와 같다). 사본을 못 만들면 지우지 않는다.
- **글 보관함 백업 전 검사(D-373)**: 백업 전 검사(PCSEC1 M3 — 위 '본문 속 Secret 형태의 적용 위치')는 저장한 초안(`dd-` 번호)을 풀어서 칸별로 훑는다 — 그 기록은 글칸을 이스케이프한 JSON 한 줄이라 날것 그대로 훑으면 줄 맨 앞·탭 뒤·한글 바로 뒤의 키 모양을 놓친다(독립 검증이 여섯 종류 x 다섯 자리 30조합 중 14곳을 놓친다고 쟀다). 위치는 '저장한 초안 N번째 · 칸 이름 N번째 줄'이고 글은 어디에도 없다. 저장 직전 검사가 막으므로 정상 경로로는 키 모양이 든 저장한 초안이 생기지 않는다 — 옛 데이터나 손으로 고친 파일을 위한 안전망이다. 전체 백업·복원(위 §9)의 검사도 같은 기록을 JSON 으로 풀어 글칸마다 훑는다 — 키 모양이 든 저장한 초안이 있으면 백업을 만들지 않고 키 모양이 든 백업은 복원하지 않으며, 위치는 '글 보관함 · 저장한 초안 · …' 로 시작하고 글은 어디에도 없다(`tests/test_service_backup_saved_drafts.py` 가 못박는다).
- **글에 담는 것·담지 않는 것**: 글칸은 글자 그대로(정규화·줄바꿈 바꾸기 없음 — 기록은 ASCII 로 이스케이프한 JSON. 화면의 편집기(Qt)만 따로 줄 끝 CRLF·CR·줄 구분 U+2028·문단 구분 U+2029 를 LF 하나로, 줄 안의 NBSP(U+00A0)를 보통 공백으로 바꿔 보이므로 열기만 하면 저장한 글 그대로지만 본문을 고치면 편집기가 내는 글이 저장 대상이다 — D-371). 키·계정·쿠키·토큰·네트워크·AI 정보를 담을 칸이 없다(칸은 글·선택 입력·후보 식별자·블로그 슬롯 이름·글 유형·생성기 판·시각). 번호는 저장 시각·후보·블로그·제목·본문의 지문이라 새 무작위·새 시계를 쓰지 않는다.
- **알려진 한계**: 키 검사는 모양이 알려진 여섯 종류만 본다(이름을 모르는 형식·아주 짧은 토큰·이미 쪼개진 토큰·모양 없는 비밀번호 같은 글은 못 찾는다 — `security/scan.py` 의 한계). 저장한 초안은 사용자 폴더(`%LOCALAPPDATA%\ChanceblogDesktop`)에 평문으로 있다 — 같은 계정의 다른 프로그램은 읽을 수 있고 다른 Windows 계정은 OS 권한이 막는다(원고와 같은 수준 — 이 앱은 원고를 암호화하지 않는다). 홈은 저장한 초안의 제목·개수만 읽는다(읽기뿐 — 파일을 만들지 않는다).

## 개인 PC 제한 시험용 Package(`packaging/`) — 보안 경계와 한계

- **묶음에 비밀·사용자 데이터가 없다**: 빌드가 묶음의 파일 이름(`settings.json`·`connections.json`·`*.db`·`*.pem`·`.env`·`token*.json` 등)과 글 파일 속 키 모양 문자열(저장소 시험과 같은 목록)을 훑어 하나라도 나오면 거절한다. 키는 사용자별 Windows 자격 증명 관리자에만, 데이터는 사용자별 `%LOCALAPPDATA%\ChanceblogDesktop` 에만 생긴다(이 묶음이 바꾼 것 없음).
- **명령줄이 열려 있지 않다**: 시작 파일은 인자를 하나도 받지 않는다(`publish-pages --yes` 같은 입력은 값을 되풀이하지 않는 고정 문장으로 거절하고 종료 코드 2). 숨은 `--selftest` 는 정확히 그 한 단어일 때만. 개발자용 명령줄은 소스 실행에서만 쓴다.
- **일반 사용자 권한**: 실행 파일 매니페스트가 `asInvoker` 임을 빌드와 `--selftest` 가 확인한다(관리자 요구 `requireAdministrator`·`highestAvailable` 는 거절). 쓰는 곳은 사용자 데이터 폴더·자격 증명 관리자·임시 폴더뿐이고 레지스트리·시작 메뉴·서비스에 쓰지 않는다.
- **무결성**: 서명이 없으므로 SHA-256 이 변조를 알아보는 유일한 수단이다 — 압축 파일의 SHA-256(`SHA256SUMS`), 묶음 안 모든 파일의 SHA-256 목록(`PACKAGE_INFO.json`, `--selftest` 가 실제 파일과 대조), 같은 커밋·같은 잠금 파일의 도구·같은 Python 이고 묶음의 DLL 이 같은 곳(가상환경·기본 Python·Windows 폴더)에서 오면 같은 압축 파일이 나오는 결정적 빌드(DLL 의 출처가 그 밖이면 빌드가 거절한다 — D-415). **한계**: 해시 파일을 압축 파일과 같은 곳에서 받으면 함께 바뀔 수 있다 — 값을 다른 길(워크플로 실행 로그에 찍힌 값 등)로도 확인한다.
- **미서명·SmartScreen·스마트 앱 컨트롤**: 파란 경고가 뜰 수 있고 스마트 앱 컨트롤이 켜진 PC 는 막을 수 있다. 이 묶음은 그 설정을 바꾸지 않으며 바꾸라고 권하지도 않는다(막히면 사실만 보고).
- **악성코드 검사**: Windows Defender 가 쓸 수 있으면 읽기 전용(`-DisableRemediation`)으로 압축 파일과 묶음 폴더를 검사해 결과를 정보 파일에 적고, 못 쓰면 '검사 안 함 — 이유' 로 정직하게 적는다. 운영자 개인 PC 에서의 직접 검사는 시험지 0단계다.
- **공급망 한계**: 의존성 잠금은 정확한 버전만이고 배포 파일(wheel)의 해시는 없다(대신 설치된 파일 내용의 지문을 적는다). 묶음에는 네트워크를 쓸 수 있는 표준 모듈과 `publish/` 코드가 들어 있을 수 있다 — 화면은 그 길을 부르지 않는다는 것은 보안 수정 묶음의 시험이 지키는 사실이고 이 묶음은 그것을 대신 보장하지 않는다. 자세한 내용은 [`PACKAGE.md`](PACKAGE.md) §7·§10.

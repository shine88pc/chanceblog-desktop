# 보안

이 저장소는 **공개**이고 앱은 운영자의 개인 PC 에서 키를 다룬다. 규칙의 정본은 `chanceblog` 의 `docs/SECURITY_GUARDRAILS.md`(G-S 비밀·G-L 호출·G-C 채널)이고, 여기에는 앱 고유의 것만 적는다.

## 1. 키와 비밀

| 비밀 | 어디에 | 이 저장소에 |
|---|---|---|
| 선택 보조 AI 키(Gemini 등 — 기본은 없음)·네이버·이미지 공급자 키 | **Windows 자격 증명 관리자**(OS 보안 저장소) — `keys add` 의 숨김 입력으로만 넣는다(§7). 키가 없어도 모든 핵심 기능이 동작한다 | 없음 |
| Blogger OAuth 토큰·클라이언트 비밀 | 같은 곳(앱이 브라우저 loopback 로그인으로 받음) — **이 시험 버전은 입력 칸이 없고 서비스·명령줄도 받지 않는다**(`BLOGGER_OAUTH_INPUT = False`, 아래 PCSEC1 절) | 없음 |
| 업데이트 서명 개인키 | GitHub Environment 시크릿 `UPDATE_SIGNING_KEY` + 운영자의 오프라인 백업 2곳 | 없음(공개키는 앱에 내장·저장소에 있음) |
| GitHub 토큰 | 앱에 내장하지 않는다. Pages 발행은 PC 의 Git 로그인(자격 증명 관리자)을 쓴다 — **이 시험 버전은 외부 게시가 소스 상수로 꺼져 있어 그 로그인도 쓰지 않는다**(아래 PCSEC1 절) | 없음 |

- 키는 소스·로그·설정 내보내기·DB 에 쓰지 않는다. 설정 내보내기 파일에는 키가 없다. 키가 없어도 앱은 수동 모드로 실행된다.
- 선택 보조 AI 키를 만들게 되면 자동 발행(Actions)에 쓰는 키와 **분리**한다(한도를 나눠 쓰지 않고, 유출 범위를 줄인다). 보조 AI 연결 실패는 해당 기능만 건너뛰고 프로그램 오류로 번지지 않는다(`ASSIST_UNAVAILABLE`).
- 실제 키가 든 `.env` 는 GitHub 에 올리지 않는다(`.gitignore`). **`.env.example` 에는 변수 이름만** 적는다. 클라우드(Actions)에서 필요한 키는 GitHub Secrets 에만 둔다.
- 유출이 의심되면 즉시 폐기·재발급한다. 저장소에서 문자열만 지워도 이력에 남는다.
- **업데이트 서명 개인키와 '공개키는 앱에 내장' 은 미구현 설계다 — 이 시험 버전에는 업데이트 경로가 없다**(앱·`packaging/`·`scripts/` 어디에도 내려받기·서명 검증 코드가 없고 README 는 '설치 파일과 자동 업데이트는 아직 없습니다', `docs/PACKAGE.md` 는 '업데이트·롤백·마이그레이션 코드가 없다', `docs/RELEASE.md` 맨 위는 '장래 설계(미구현)' 라고 적었다). 위 표의 그 줄을 읽고 서명 검증이 이미 있다고 믿지 않도록 덧붙인다(AS-S1 참고-20, D-614).

## 2. 로그

요청 헤더·키·토큰·개인정보를 출력하지 않는다. 로그·오류 보고서에 나가는 글은 `src/chanceblog_desktop/security/mask.py` 의 `mask`·`safe_detail`(이를 쓰는 `AppError.log_line()` 포함)을 거친다. 규칙은 ① `chanceblog` 의 비밀 패턴 `pipeline/secret_patterns.py` 14종(`vendor/` 에 원본 그대로 — 패턴이 늘면 시험이 새 표본을 요구한다) ② 주소 속 `사용자:토큰@`(비밀번호에 `@` 가 있어도) ③ 주소의 `?access_token=`·`code=`·`session=` 같은 인자 ④ `Bearer`·`Basic` 토큰·JWT·Slack 웹훅 주소·npm 토큰·`aws_secret_access_key=`·따옴표 없는 `password: 값`·개인 키 블록 전체 ⑤ 눈에 안 보이는 글자(폭 없는 글자·방향 제어 등)로 쪼갠 토큰(그 글자를 먼저 지운다) ⑥ 정본의 `sk-` 패턴(영숫자만)이 못 알아보는 붙임표·밑줄이 든 새 키 모양 — OpenAI 프로젝트 키(`sk-proj-…`)·Anthropic 키(`sk-ant-api03-…`)·OpenRouter 키(`sk-or-v1-…`)와 그 밖의 `sk-` 긴 모양(꼬리 40자 이상에 앞 60자 안의 대문자·숫자)이다. 정본은 고치지 않고 `mask.py` 에서 더했고 `shape.py` 의 자기 검사는 이미 이 모양들을 키로 본다(시험이 둘의 일치를 지킨다). 다만 이 '가린다' 는 화면·기록 쪽이다 — 발행 직전의 비밀 차단(`publish/pages.py`)은 이 새 모양 4가지(`sk-proj-`·`sk-ant-api03-`·`sk-or-v1-`·`sk-` 일반형)를 아직 모른다(c3 이전부터의 한계이고 같은 모양 판정을 쓰게 하는 일은 후속이다). `sk-` 일반형은 대문자·숫자가 든 40자 이상 붙임표 슬러그(`sk-Hynix-Q3-2026-…`·`sk-proj-weekly-…`)도 키로 보고 가린다(오탐 — 정상 글이 가려질 수 있다). 어떤 입력에도 예외를 내지 않고, 이미 가린 글을 다시 가려도 같다(입력이 20만 자 이하일 때 — 그보다 긴 글은 비밀이 반쪽으로 잘리지 않게 공백에서 잘라 앞부분만 가리고 나머지는 내보내지 않는다). `AppError.detail` 은 화면에 내지 않고 `log_line()` 으로만 기록하며, git 의 출력은 끝 400자만 남기되 **자르기 전에** 가린다. 작은 오류 기록 파일은 있지만(`logs/errors.log` — 오류 이름과 코드 위치만 남기고 공통 가림 규칙을 거친다, 맨 끝 '오류 기록' 절) 로그를 내보내는 기능은 아직 없다(기록은 만들어질 때 이미 가려져 있다 — 아래 PCSEC1 절 '공통 경계'). 이 규칙은 **알려진 모양**만 가린다 — 같은 종류의 토큰이 공백 없이 이어 붙은 것이나 낱말 경계로 시작하는 패턴이 앞 글자에 붙은 것(`키는ghp_…`), 이름 표지 없이 줄바꿈으로 쪼갠 토큰이나 무작위 40자 문자열(AWS 비밀 키처럼 git 해시와 구분할 수 없는 것)은 못 가리므로, 비밀을 애초에 로그에 넣지 않는 것(§1)이 먼저다. 가리기 규칙의 강화(이름 목록 확장·헤더 줄·눈속임 풀이)와 한계는 아래 PCSEC1 절이 정본이다.

명령줄(`service/cli.py`)은 화면에 나가는 모든 글 — 일반 출력·오류·`--json` 값 — 을 같은 `mask` 로 가린다(원고·제목·git 의 오류 세부에 키 모양 문자열이 있어도 출력에는 없다 — 가리는 함수 `mask_block`·`mask_deep` 은 공통 경계 `security/boundary.py` 에 있고 `cli` 는 같은 이름을 쓴다). 환경 변수는 데이터 폴더·저장소 폴더 위치(`CHANCEBLOG_DESKTOP_DATA`·`CHANCEBLOG_LOCAL_REPO`)만 읽고 키·토큰은 읽지 않으며(시험 전용 가짜 보관소를 여는 `CHANCEBLOG_KEYSTORE` 는 §7 의 안전장치를 모두 통과할 때만 열린다 — `Context.get_keystore()` 가 받은 환경 변수 모음을 보관소 모듈(`security/keystore.py`)에 그대로 넘기고 그 값을 읽는 곳은 그 모듈 한 곳이다), 사용자 데이터는 저장소(git) 안에 둘 수 없다(`DATA_DIR_UNSAFE`). 시험(`tests/test_service_safety.py`)이 이 규칙들을 소스에서 직접 확인한다. 여러 줄에 걸친 비밀(개인 키 블록 — `-----BEGIN … PRIVATE KEY-----` 부터 END 까지·다음 줄에 이어지는 값)이 줄 단위 가리기를 빠져나가지 않도록 **출력 전체를 통째로** 가린다(`cli.mask_block` — 글이 아주 길면 줄 경계에서 나눠 가리되 열린 개인 키 블록 안에서는 끊지 않는다).

## 3. 업데이트 보안

[`RELEASE.md`](RELEASE.md) 의 서명 매니페스트·해시 검증·다운그레이드 거부·불변 릴리스·백업/롤백이 핵심이다. 업데이트 경로는 HTTPS 와 고정 저장소 주소만 쓰고, 서명이 없거나 어긋나면 업데이트를 거부한다.

**이 시험 버전에는 업데이트 경로가 없다(미구현 설계).** 위 문단은 장래 설계이고 지금 코드에는 내려받기·서명 검증·다운그레이드 거부가 없다 — 새 버전은 새로 풀어서 쓴다(AS-S1 참고-20, D-614).

## 4. 공급망

액션은 전체 커밋 SHA 로 고정한다(`.github/workflows/`, 시험이 지킨다 — 갱신은 AI 가 같은 메이저 안의 최신 태그를 확인해 PR 로 올린다. Dependabot 은 알림·PR 이 늘어 기본은 켜지 않는다). 의존성은 생기면 해시 잠금, `pip-audit` 은 릴리스 전에 돌린다. 외부 AI 응답은 데이터이므로 HTML 은 허용 태그만 남기고(소독) 링크·스크립트를 제거한다.

`auto-pr.yml`(병합 부탁 PR 자동 만들기, D-175)은 **PR 만 만들고 병합하지 않는다.** 트리거는 병합 가지(`ai/claude/M###-*`)의 push 하나, 권한은 contents 읽기·pull-requests 쓰기·actions 읽기 셋뿐이고, `uses:`·시크릿·체크아웃이 없이 러너의 `gh` 로 정해진 API 여섯 가지만 부른다(병합·승인·라벨·코멘트·가지 삭제·설정 변경 호출 없음). 가지 이름·커밋 제목·본문은 AI 가 쓴 글이라 env 로만 넘기고 `run:` 에 표현식을 끼우지 않으며 정규식으로 거른 뒤 파일·따옴표 친 변수로만 다룬다(`pull_request_target`·`workflow_run`·`issue_comment`·`schedule` 은 쓰지 않는다). 시험 `tests/test_auto_pr_workflow.py` 가 모양을 고정하고, 이 파일을 바꾸는 변경은 T3 로 다룬다(워크플로는 `AGENTS.md` 3 표의 T2 인데 PR 만들기 권한과 저장소 설정 한 줄에 닿는 보안 영역이라 운영자 승인 병합으로 올린다). 커밋 제목·본문은 PR 로 그대로 공개되므로 비밀·키·`@이름` 멘션을 쓰지 않고, 포크에서 올라오는 PR 에는 돌지 않는다. 저장소 설정 `Allow GitHub Actions to create and approve pull requests` 는 운영자만 켠다(워크플로의 PR '승인'도 허용하는 설정이므로 승인 호출을 넣는 변경은 받지 않는다).

## 5. 올라가는 글과 승인

- **올라가는 것은 Markdown 원문이다.** 발행 전 검사(`service/gate.py`)는 그 원문에서 원시 HTML 태그·`javascript:`/`data:`/`vbscript:` 주소·`{% %}`/`{{ }}` 템플릿 표기·`{: }` 속성 붙이기·광고 스크립트를 막는다 — 공개 사이트(Jekyll)가 원시 HTML 을 그대로 내보내고 Liquid 를 글을 만들 때 실행하기 때문이다([`ARCHITECTURE.md`](ARCHITECTURE.md) §5).
- **승인 통제는 채팅 승인 규칙 하나다.** 앱은 `--yes`·`approve` 를 사람이 직접 입력했는지 알 수 없다(터미널 확인이 없다). 그래서 AI 코딩 도구가 운영자의 승인 없이 대신 입력하는 것은 [`AGENTS.md`](../AGENTS.md) 규칙 7·9 로 막는다 — 앱이 막을 수 있는 것은 확인 표시 없이 실행하지 않는 것까지다.
- **머리말 값도 같다.** 제목·분야·태그·대표 이미지 주소·설명·출처의 HTML 태그·`{% %}`/`{{ }}`·`javascript:` 같은 주소·광고 스크립트와 줄바꿈·제어 문자·따옴표/꺾쇠가 든 주소·모르는 머리말 키(`published`·`permalink` 등)를 막는다(`HEADER_VALUE`·`RAW_HTML` …). 머리말 값은 사이트의 글 목록·카드에 들어가고 일부는 이스케이프 없이 HTML 에 들어간다. 렌더링은 한 줄 JSON 으로 이스케이프해 제목의 따옴표·콜론·`---`·`#` 가 머리말 구조를 깨거나 다른 키를 끼워 넣지 못하고(시험), 게이트는 저장된 글이 바뀌어 있어도 다시 본다. 글을 만들거나 고칠 때의 제목도 같은 검사를 거친다. 알려 둔 한계: 제목의 큰따옴표는 막지 않는다(실제 Chance 글에도 있다) — 첫 화면 카드가 속성 안에 제목을 이스케이프 없이 넣는 것은 `chanceblog` 쪽에서 고칠 일이다.
- 같은 글을 두 곳에서 동시에 올리지 못하도록 글마다 잠금을 잡고(`PUBLISH_IN_PROGRESS`), **서로 다른 두 글이 같은 저장소에 동시에 commit·push 하지 못하도록** 저장소마다 잠금을 한 번 더 잡는다(`PUBLISH_REPO_BUSY` — 글 잠금 먼저·저장소 잠금 나중의 고정 순서, 죽은 프로세스의 잠금은 바로 넘겨받음). 저장소 잠금 파일은 **연결한 저장소의 `.git` 안**(`.git/chanceblog-desktop-publish.lock`)에 만든다 — 서비스 층(`service/`)이 연결한 저장소에 직접 쓰는 파일은 이 잠금 파일 하나뿐이고(글 파일은 `publish/pages.py` 가 쓴다) 잠금 파일은 git 이 추적하지 않는다. 데이터 폴더(`--data-dir`)가 다른 앱끼리도 서로를 알게 하려는 것이고, `.git` 에 만들 수 없으면 데이터 폴더로 물러서지 않고 올리지 않는다(fail closed). 이 PC 의 폴더 경로·눈에 안 보이는 글자로 길이를 채운 글·글자의 표시 방향을 바꾸는 제어 문자(U+202A–202E·U+2066–2069 — 글을 다르게 보이게 위장할 수 있다)가 든 글도 막는다.

- **`주제 후보` 화면은 주제 엔진 보관함에 쓴다**(D-270~D-276, T2): `후보 만들기` → 미리 보기(읽기뿐) → 확인창(처음 포커스는 취소)의 `만들기` 를 눌렀을 때만 서비스 `generate_candidates(confirmed=True, trend=None)` 한 번이 `topic_engine/topic_engine.db` 에 후보를 **더한다**(서비스·엔진 코드는 이 묶음에서 바꾸지 않았다 — 보관함이 없으면 파일 하나를 새로 만들고 옛 구조는 `.v1.bak` 사본을 남기며 올린다, 후보는 지워지거나 바뀌지 않고 실패하면 쓰기 전 상태 그대로다). 열기·거르기·찾기·고르기·상세·창 크기 바꾸기·미리 보기·취소는 파일도 폴더도 만들지 않는다(임시 폴더 전체 바이트 비교 시험). 관심도(Trend) 공급자는 `None` 이라 네트워크를 쓰지 않고 키·자격 증명 저장소는 부르지 않는다(`security/` 불변 — 시험이 호출을 막아 확인). 후보 제목·키워드·이유에 키·토큰 모양 글이 있으면 서비스가 저장하지 않고 화면은 가려서 보이며, 화면 코드는 파일을 열거나 서비스를 직접 부르지 않는다(소스 시험). 후보 삭제·상태 바꾸기는 이 화면에 없다.
- **기존 글 읽기(`service/own_posts.py`)는 운영자가 파일 선택 창에서 직접 고른 txt·md 파일만 읽는다**(D-325–D-329, T1): 한 번에 1–2개·파일당 2MB·읽은 글 100,000자 이하를 넘으면 거절하고(잘라 쓰지 않는다) 인터넷 주소·네트워크 위치·와일드카드·폴더·심볼릭 링크·정션(경로 위 폴더까지)·이 PC 에 내려받지 않은 파일(이 표시는 파일 자신만 본다 — 경로 위 폴더는 링크 여부만 본다)·윈도 장치 이름·상대 경로는 읽지 않는다 — 네트워크 접근 0, 저장 0(반환값 말고는 파일·로그·캐시·설정·클립보드 어디에도 남기지 않고 어느 프로필에도 쓰지 않는다), 열기는 `rb` 하나뿐이고 연 핸들의 상태(`fstat`)가 검사 때와 같은 일반 파일이 아니면 읽지 않는다(검사와 열기 사이의 링크·파일 바꿔치기 거절). 오류는 고정 문장이고 경로·파일 이름·글 내용을 되풀이하지 않으며(OS 오류의 글도 버리고 읽은 뒤 거절할 때는 호출 흔적이 붙드는 지역 변수의 글도 비운다), 값에는 글·글자 수·읽은 글자표 이름(`utf-8`·`cp949`)만 담긴다. 알려 둔 한계: 윈도의 연결된 네트워크 드라이브(Z: 같은)와 리눅스·맥의 네트워크 마운트는 판별하지 못해 읽을 수 있다 · 열기 자체가 내려받기를 일으키는 OneDrive 온라인 전용 파일은 열기 전 표시로만 거른다 · CP949 는 'UTF-8 이 아니면' 이라는 기본값이라 EUC-JP·EUC-CN 으로 저장한 글은 한글 더미로 읽힐 수 있고 ESC 같은 제어 문자는 거르지 않는다(NUL 만 거른다).
- **내 글 문체 참고값 보기(N-3a — `ui/qt/style_dialog.py`·`content/style_stats.py`, D-330–D-339, T1)는 읽기만 한다 — 저장 0·AI 0·네트워크 0**: 운영자가 직접 고른 txt·md 파일(파일 선택 창)과 붙여 넣은 글을 합쳐 최대 2개를 기존 글 읽기(`service/own_posts.py` 의 `read_own_files`·`check_pasted_text`)의 한도와 고정 거절 문장으로 검사해 메모리에서 숫자만 세어 참고값 표로 보인다. 이 화면은 파일·설정·프로필(옛 `naver_profiles` 와 `topic_engine/channel_profiles.json`)·보관함·연결 저장소·자격 증명 관리자에 쓰지 않고 읽지도 않으며(위 '화면에서 파일에 쓰는 곳' 네 곳의 목록은 그대로다 — 시험이 그 문장을 못박는다) 로그·캐시·임시 파일·클립보드도 없다. 계산 값은 숫자·참/거짓뿐이고 고른 글의 문장은 뷰모델·표·오류·표준 출력에 없으며(카나리 시험: 표지 글의 8글자 이상 조각이 어느 순간의 위젯·상태·출력·가짜 클립보드·데이터 폴더 바이트에도 없다) 붙여 넣기 칸은 계산이 끝나면 되돌리기 기록까지 비우고 창을 닫는 어느 길로든 고른 글·결과를 버린다. 거절·실패는 기존 `CONTENT_INVALID` 의 고정 문장(새 오류 코드 0)이고 호출 흔적이 붙드는 경로·글은 비운 뒤 `except` 밖에서 낸다. 한계는 위 읽기 기반 항목과 같다 — 파이썬 문자열은 메모리에서 즉시 지울 수 없어 참조를 버려 회수되게 할 뿐이다.
## 6. 금지

로그인·쿠키·세션 자동화, 탐지 회피, CAPTCHA 우회, 무료 한도 우회용 다계정·키 회전, 유료 호출, 키를 저장소·로그에 기록, 한도 오류 무한 재시도.

## 7. 키 보관(연결 설정) — 설계 D-30·D-31

앱의 연결 설정(`keys` 명령 — 용도별로 키를 넣고, 같은 용도에 여러 개를 둘 수 있고(NAVER API HUB 는 하나만), 한도에 막혀 일이 멈추지 않게 하는 안전장치)은 **키를 Windows 자격 증명 관리자(OS 보안 저장소)에만** 둔다. 화면에 키 원문을 보이는 기능은 없다 — 보이는 것은 다섯 가지 상태 문구(연결 안 됨, 연결됨, 인증 정보 오류, 연결 확인 필요, 요청 한도 도달)와 이름·제공자·항목 번호·등록 시각뿐이다 — 끝 4자 같은 키의 일부는 명령줄 목록에도 보이지 않는다(PCSEC1 H2, D-346). 키를 다시 보여 주는 기능은 만들지 않는다(잃어버리면 서비스 쪽에서 폐기하고 새로 받아 넣는다).

**어디에 무엇이 있나.**

| 대상 | 두는 곳 | 비고 |
|---|---|---|
| 키 값(필드 묶음) | 자격 증명 관리자의 항목 `ChanceBlogDesktop:<용도>:<항목번호>`(범용 자격 증명, `CRED_PERSIST_LOCAL_MACHINE` — 재부팅 뒤에도 남고 이 PC 에서만 쓰인다) | 필드들을 JSON 한 덩어리로 묶어 UTF-16 으로 적는다. 값 한도 2,560바이트 — 넘으면 `KEY_TOO_LONG` |
| 이름·소속 프로젝트·순서·상태·확인 시각·한도 묶음 이름·약관 확인 시각 | 데이터 폴더의 `connections.json`(임시 파일에 쓰고 `fsync` 한 뒤 이름을 바꾸는 쓰기·구조 버전·낯선 칸 거절·직전의 올바른 사본 `.bak`) | **비밀이 아니다.** 이 파일에는 **비밀 칸의 값에서 만든 것(해시·지문·끝 글자)이 하나도 없다** — 약한 값은 해시만으로도 대입해 알아낼 수 있어서 지문을 두지 않고, 같은 값을 두 번 넣는지는 보관소의 값을 직접 비교해 막는다. 한도 묶음 이름의 해시는 클라이언트 ID·고객 ID 같은 비밀이 아닌 칸에서만 만든다 |
| 사용량·막힘 해제 시각·전환 기록(NAVER API HUB 는 시도·성공 수와 마지막으로 본 시각, 최근 200건의 호출 장부도) | 데이터 폴더의 `quota_state.json`(원자적 쓰기·잠금·구조 판 1 — 호출 장부가 있는 묶음이 하나라도 있는 파일만 판 2·깨지면 보통 용도는 보수적으로 오늘 한도의 절반을 쓴 것으로 가정하고, NAVER API HUB 는 절반으로 가정하지 않고 새 호출을 멈춘다) | 키 값 없음 — 호출 장부에도 키·응답 본문·요청 본문이 없다(요청 조건은 해시 앞 12자뿐) |

**하지 않는 것**: 키를 파일·환경 변수·설정 JSON·`.env`·로그·저장소·명령 인자로 받거나 쓰지 않는다. 앱은 환경 변수로 키를 읽지 않는다(시험이 지킨다 — 그래서 `.env.example` 에 키 칸을 더하지 않는다). 키는 **명령 인자로 받지 않고** 터미널의 숨김 입력(`getpass`)이나 `--stdin`(JSON 한 줄)으로만 받으며, 입력은 화면에 되풀이하지 않는다. 터미널이 아니고 `--stdin` 도 없으면 묻지 않고 멈춘다. **`--stdin` 은 자동 시험·스크립트용이다** — 키를 명령줄에 직접 쳐서(예: `echo '{…}' | …`) 넘기면 그 줄이 셸 기록에 남으니 사람이 넣을 때는 숨김 입력을 쓴다. 키를 받는 자리(`keys add`)에서는 화면·오류·`--json`·`--verbose`·`repr`·예외 문구 어디에도 입력한 값은 없고(모양 검사는 이유만 알린다), 키를 인자 자리에 잘못 쳤을 때의 사용법 오류도 입력한 값을 되풀이하지 않는다 — 모든 명령의 사용법 오류는 argparse 의 문구 대신 값 없는 고정 문장(틀린 옵션 이름·종류·고를 수 있는 값만)이고, 값 검사 문구 속 '받은 값'·「값」 도 지운다(`--옵션=값`·`-h값` 꼴 포함 — 시험이 26가지 명령 모양×값 3가지와 진짜 프로세스 24곳으로 확인). 후보·글 번호 자리와 `restore` 의 백업 파일 자리(번호를 받는 명령 22개 — 후보 9·`draft plan`·글 11·`restore`)에 키를 잘못 쳐도 오류 문구·`--json`·`--verbose` 의 기록용 한 줄은 친 글을 **번호 모양일 때만** 되풀이하고(16진수 8자 이하 — 순번과 화면에 보이는 짧은 번호, 백업은 앱이 만드는 `chanceblog-날짜-시각.db` 이름 하나) 아니면 `(입력한 번호)`·`(입력한 파일)` 로 바꾼다. 판정은 `echo.py` 한 곳이고 오류를 만드는 곳(`AppError` 의 칸 값)에서 바꾸므로 화면·`--json`·기록이 같으며 오류 코드·종료 코드·하실 일은 그대로다(D-34). 시험이 파서에서 번호 자리 27곳(위 22개 명령과 `candidates link` 의 둘째 자리·`keys` 4개)을 모아 가짜 키 28종을 넣어 출력(화면·`--json`·`--verbose`·`--yes`)과 데이터 폴더를 확인하고, 진짜 프로세스(cp949 콘솔·셸 인용 포함)로도 본다. **알려 둔 한계**: 번호 모양(16진수 8자 이하)은 그대로 되풀이한다 · 경로 자리는 어느 폴더가 문제인지 알려야 해서 경로를 적는다(`--data-dir` 의 폴더는 `doctor` 출력에 그대로 나온다) · 제목·주제·키워드·원고처럼 사용자가 쓴 글은 화면에 나가고 저장된다(마스크가 아는 모양만 가린다) · `restore` **성공** 문구('백업으로 되돌렸습니다: …')와 `connect` 의 폴더 경로도 친 경로를 그대로 적는다 · 표 시험은 위치 인자 번호 자리만 모은다(옵션 값 자리는 독립 검증이 전수로 확인했다) · 안전 시험은 `os.truncate`·`shutil.move`·`sqlite3.connect` 같은 쓰기 호출 32가지를 못 거른다(c3 이전부터). 그 밖의 오류 문구는 마지막 관문 `mask` 가 가린다(마스크가 모르는 일반 영숫자 키는 못 가린다 — 그래서 입력이 문구에 들어가는 곳을 따로 막았다). 마지막 관문으로 모든 출력은 `security.mask` 를 거친다. 이름·소속 프로젝트에 키 모양의 글이나 키 값이 그대로 들어 있으면 파일에 남기기 전에 거절한다(`security/shape.py` — 한글·괄호·따옴표·줄바꿈 바로 옆에 붙은 것도 찾는다).

**막는 것(위협 모델).** 저장소·`connections.json`·`quota_state.json`·로그·오류 보고서·백업(`backup` 은 글 저장소만 담는다)·설정 내보내기·진단 정보·화면·스크린샷·클립보드에 키가 남는 것을 막는다. 진단 요약(`connections.diagnostic_summary`)에는 용도별 항목 수뿐이고(옛 용도는 항목이 남아 있을 때만 한 줄) 이름·번호·끝 4자도 싣지 않는다. **막지 못하는 것**: 같은 Windows 사용자로 도는 악성 프로그램(자격 증명 관리자는 같은 사용자의 프로그램을 구분하지 않아 값을 읽을 수 있다)·PC 를 가진 관리자·메모리 덤프. 파이썬 문자열은 바꿀 수 없어 읽은 값을 메모리에서 완전히 지우지 못한다 — 앱은 자격 증명 관리자가 돌려준 원본 메모리와 보관소로 넘긴 사본을 바로 0 으로 덮고, 읽은 값을 필요한 순간에만 꺼내 쓰고 버리지만 파이썬 쪽 사본은 가비지 수집 때까지 남을 수 있다. 그래서 **키는 언제든 폐기·재발급할 수 있는 것만** 넣는다.

**키 노출이 의심될 때**: ① 그 서비스의 콘솔에서 키를 바로 폐기하고 새로 만든다(저장소에서 문자열만 지워도 이력에 남는다) ② `keys remove 번호 --yes` 로 보관소의 값을 지우고 `keys add` 로 새 키를 넣는다 ③ 그 키를 같이 쓰던 곳(클라우드 자동 발행의 GitHub Actions 시크릿 등)이 있으면 거기서도 바꾼다. 데스크톱용 키와 GitHub Actions 용 시크릿은 **같은 값을 쓰지 않는다**(이 앱은 Actions 시크릿을 읽지 않고 클라우드는 이 PC 의 키를 쓰지 않는다 — 같은 값이면 유출 범위와 한도가 함께 묶인다. Unsplash 는 데스크톱용으로 따로 앱을 등록해 한도도 따로 쓴다).

**시험 전용 가짜 보관소.** 명령줄을 진짜 프로세스로 시험할 때만 환경 변수 `CHANCEBLOG_KEYSTORE=memory-file` 이 임시 폴더의 가짜 JSON 파일 보관소를 연다. 이 값이 **정확히** 맞고, 폴더(`CHANCEBLOG_KEYSTORE_DIR`)가 운영체제 임시 폴더 안·이름이 `chanceblog-fake-keystore-` 로 시작·표시 파일이 있을 때만이며, 설치본(`sys.frozen`)에서는 환경 변수를 아예 무시한다. 환경 변수가 없으면 프로그램의 기본 경로는 언제나 진짜 자격 증명 관리자다(Windows 가 아니면 `KEY_STORE_UNAVAILABLE`). 이 가짜 보관소를 쓰는 중이면 화면에 경고가 나온다.

**한도 안전장치의 근거(확인한 사실).** Gemini API: 한도는 키가 아니라 **프로젝트** 단위다(같은 프로젝트에서 키를 더 만들어도 늘지 않는다). 네이버: 옛 용도(`naver_openapi`)의 '앱마다 하루 약 25,000회' 는 공식 문서가 아닌 제3자 문서의 값이었고, 그 용도를 NAVER API HUB 로 바꾸면서 더는 쓰지 않는다 — 지금 기준은 아래 'NAVER API HUB 검색어 트렌드' 에 있다. Unsplash: 데모 앱은 시간당 50회, 승인된 앱은 시간당 1,000회이고 `api.unsplash.com` 요청만 센다. 여러 프로젝트·계정으로 무료 한도를 나눠 쓰는 것은 서비스 약관과 공정 사용 규칙에 어긋날 수 있다. 그래서 한도 단위는 키가 아니라 한도 묶음(같은 앱·프로젝트)이고, 한도 오류 뒤에는 같은 묶음의 다른 키로 넘어가지 않으며, 용도마다 키는 3개까지(NAVER API HUB 는 1개)이고, 둘째 키를 넣을 때 약관 경고를 보이고 확인(`--i-understand-terms`)을 받아 항목에 기록하며, Unsplash 와 NAVER API HUB 는 어떤 오류에도 자동으로 다른 키로 넘어가지 않는다. 전환할 수 있는 결과는 429·기간 한도·일시 5xx(500·502·503·504)·시간 초과 네 가지뿐이고 401·403·400·422·정책 차단·콘텐츠 차단은 숨기지 않고 조치 안내만 한다. 기본 안전장치는 전환이 아니라 **절약**이다(예산의 마지막 10% 는 필수 호출 전용·저장해 둔 값 우선·`Denied(degraded)` — 호출하는 쪽은 '데이터 없음' 으로 계속한다). 다만 단계표가 있는 NAVER API HUB 는 '마지막 10%' 대신 아래 단계(70·80·90%)를 쓰고, 사용량을 확인할 수 없으면 절반으로 가정하지 않고 멈춘다.

**NAVER API HUB 검색어 트렌드 — 키 규칙(D-35).** 용도 `naver_apihub` 는 Client ID(비밀이 아님)와 Client Secret(비밀 — 화면에 보이지 않고 자격 증명 관리자에만 둔다)을 받는다. 두 칸 모두 영문·숫자·`_`·`-` 만 쓴 8~128자인지만 본다 — 실제 모양이 공식 문서에 없어서 일부러 느슨하게 확인하는 것이고, 어떤 입력 오류·기록에도 입력한 값은 들어가지 않는다. **키는 하나만 둔다**(`Purpose.max_entries = 1` — 둘째 항목은 쉬운 한국어 안내로 거절하고, 명령줄에서는 약관 질문보다 먼저 거절한다). **키 순환은 없다**(`rotation = never` — 429 를 포함한 어떤 오류에도 다른 키로 자동 전환하지 않는다. 한도를 늘리려고 같은 용도의 키·계정을 돌려 쓰는 것은 §6 에서 금지한다). 키를 바꿀 때는 기존 항목을 `keys remove 번호 --yes` 로 지운 뒤 새로 넣는다. 아직 호출 코드가 없어서 `keys test` 는 '준비 중' 이라고만 말한다.

**사용량을 모르면 호출하지 않는다(Fail-Closed).** 이 제공자만은 사용량·시계·인증 상태를 확인할 수 없을 때 '절반 썼다고 보고 계속' 하지 않고 **새 호출을 막는다.** 막는 경우: ① 사용량 기록 파일(`quota_state.json`)이 깨졌거나 읽을 수 없다 — 이 제공자는 깨진 파일을 스스로 고치거나 옮기지 않는다. 다른 제공자의 호출이 파일을 고쳤을 때는 '기록이 사라진 적이 있음' 표시가 저장되어 운영자가 확인(`acknowledge`)하기 전에는 열리지 않고, 확인하면 프로그램 안 한도의 절반을 이미 쓴 것으로 두고 다시 센다 ② 이번 달·오늘 숫자가 한도·과거 기록·호출 장부와 맞지 않는다(이번 달 시도 수가 이달에 본 최고치보다 낮음·성공이 시도보다 많음·하루 시도가 이번 달 시도보다 많음·남은 장부의 합이 계수보다 많음) ③ 컴퓨터 시계가 마지막으로 본 시각보다 5분을 넘게 되돌아갔다(정확히 5분까지는 흔들림으로 보고 허용한다. 되돌린 시계가 마지막으로 본 시각의 5분 안으로 돌아오면 — 시계를 바로잡거나 시간이 그만큼 흐르면 — 운영자 확인 없이 자동으로 다시 열리고, 그 전에 열려면 운영자가 확인(`acknowledge`)한다) ④ 연결 설정 파일(`connections.json`)이 깨졌다 ⑤ 인증 상태가 불분명하다(연결 시험이나 성공한 실제 호출의 기록이 24시간 안에 없거나 인증 실패로 멈췄다. 성공한 호출의 보고 — 응답 상태가 2xx 이거나 안 적었고 응답을 썼을 때 — 는 마지막 성공 시각을 갱신해 24시간 창을 이어 주고, 실패·모호한 결과는 갱신하지 않으며 인증 실패로 멈춘 항목은 되살리지 않는다. 호출 코드가 생기기 전에는 아무도 이 판정으로 호출하지 않는 틀이고, 연결 시험 호출 자신은 이 검사만 건너뛴다) ⑥ 잠금을 못 잡거나 상태를 쓰지 못한다. 이때 사용자에게 보이는 문장은 하나로 고정이다 — 'NAVER API HUB의 새로운 데이터 조회를 사용할 수 없습니다. 저장된 정보와 기본 주제 선정 규칙으로 후보 생성을 계속합니다.' — 구체적인 원인은 따로 둔다(`keys usage` 의 '사유' 줄). 다른 용도의 동작은 그대로다.

**한도·시도와 성공·호출 장부·단계.** 한도는 두 겹이다. 프로그램 안 기준은 하루 100회·이번 달 27,000회이고 둘 다 지켜서 먼저 닿는 쪽이 막는다. 서비스 콘솔의 월 한도(30,000회 — 계정 설정에 따라 최대 50,000회, 100% 에서 호출이 차단되고 알람은 50% 부터)는 마지막 안전장치이자 단계의 기준이다. 월 창은 **한국 시간 달력 월**이다(다음 달 1일 00:00 에 0 으로 돌아간다). 시도(실패한 호출도 센다 — 429·시간 초과 포함)와 성공을 따로 세고, 최근 200건의 호출 장부에는 호출 종류·시작/끝 시각·조건 해시(정규화한 요청의 해시 앞 12자)·성공 여부·HTTP 상태·재시도 수·응답을 썼는지·캐시 적중만 적는다. 키·응답 본문·요청 본문은 없고, 키처럼 보이는 칸 이름이 든 조건은 장부에 가기 전에 거절한다. 단계는 콘솔 월 한도 기준이다(이번 달 시도 수에 이 호출을 더한 값이 경계를 넘을 때): 21,000회(70%) 초과는 안내만, 24,000회(80%) 초과는 자동 새로고침·배치(`bulk_refresh`)를 거절하고 직접 시작한 분석(`new_candidate`)은 한 번에 5회까지(기본값)만 허용하며, 27,000회(90% = 프로그램 안 월 한도) 초과는 필수 호출(`critical`)까지 모든 새 호출을 거절한다. 이 제공자는 '마지막 10% 는 필수 호출 전용' 규칙을 쓰지 않는다(하루 100회 창에도 쓰지 않는다 — 구현 쪽 기본값이라 아래 알려 둔 한계에 적었다). 서버가 기간 한도 소진(`quota_exhausted`)을 알려 오면 다음 달 1일 00:00(한국 시간)까지 쉰다(서버가 48시간 안의 초기화 시각을 알려 주면 그 시각까지).

**모르는 것과 안전한 쪽의 선택.** ① 실패한 호출이 공식 사용량에 들어가는지 → 시도로 센다 ② 월 초기화 시각과 시간대(콘솔 쪽 값은 공개 문서에 없다) → 한국 달력 월로 잡고, 프로그램 안 월 한도(27,000)가 콘솔 한도(30,000)보다 10% 낮아 9시간쯤 어긋나도 흡수한다 ③ 받은 데이터를 저장·캐시하거나 AI 에 넣어도 되는지의 약관 → 이 묶음은 데이터를 저장하지 않으므로 다루지 않았다(쓰기 전에 먼저 확인한다) ④ Client ID/Secret 의 실제 모양 → 느슨한 확인 ⑤ 무료 기간은 한시적이고 끝나는 날이 공개되어 있지 않다. **알려 둔 한계**: 호출 코드가 없다(후속) · 확인 절차(`acknowledge`)는 아직 명령에 이어져 있지 않다 · 프로그램 안 하루·월 한도와 분석 5회 상한은 설정으로 낮출 수 없다 · 사용량은 이 앱이 센 것이라, 콘솔에서 같은 앱·키를 쓰는 다른 곳의 사용은 보이지 않는다(콘솔의 50% 알람이 운영자의 교차 확인이다) · 직접 고친 상태 파일이 서로 맞으면 알아내지 못한다 · 사용량 상태 파일(`quota_state.json`)을 통째로 지우면 새로 시작한 것으로 보아 사용량이 0 으로 돌아간다(깨진 파일과 달리 알아내지 못한다 — 콘솔의 사용량이 교차 확인이다) · 일 한도 100 이 먼저 막아 이 앱의 사용만으로는 한 달에 3,100회를 넘지 못하므로 월 단계(21,000·24,000·27,000회)는 실제로는 닿기 어렵다 — 콘솔 한도(30,000회)를 지키는 이중 안전장치이고 일 한도를 늘렸을 때를 위한 것이다 · 시계가 되돌아갔다가 마지막으로 본 시각의 5분 안으로 돌아오면(시계를 바로잡거나 시간이 그만큼 흐르면) 운영자 확인 없이 자동으로 다시 열린다 · 서버가 기간 한도 소진을 알리면 다음 달 1일 00:00(한국 시간)까지 쉬므로, 서버의 월 초기화가 한국 달력 월보다 늦은 월 초(최대 9시간)에 소진 응답이 오면 그 한 달을 쉬게 될 수 있다 · 하루 100회 안에서는 우선순위 몫 보호가 없다(구현 쪽 기본값 — 운영자가 정한 것은 월 70·80·90% 단계뿐이다): 자동 새로고침이 하루 100회를 다 쓰면 그날 사용자가 직접 고른 후보의 호출도 거절된다(일반 제공자는 일괄 갱신 70회·새 후보 80회·선택된 후보 90회에서 멈추고 필수 호출만 100회까지 한다). 되돌리려면 일 창에도 기존 몫 규칙을 쓰게 하거나 호출 코드를 만드는 다음 묶음(N2)에서 자동 새로고침의 하루 상한을 낮춘다 — 정하기 전의 기본값은 예약 없음이다.

**옛 용도(`naver_openapi`).** 옛 판이 만든 `connections.json` 에 `naver_openapi` 항목이 있어도 계속 읽는다(`CONNECTIONS_FILE_INVALID` 가 아니다). 이 용도는 '옛 용도' 로만 남아(`legacy_to = naver_apihub`) 새 항목을 키를 읽거나 묻기 전에 거절하고, 남은 항목은 `keys list` 에 '옛 항목' 표시와 함께 보인다(새 키는 `naver_apihub` 에 넣고 옛 항목은 `keys remove` 로 지우라는 안내가 붙는다). 키는 자동으로 지우지 않는다. 옛 용도는 `keys purposes`·`keys usage` 에 나오지 않고, `keys list` 의 상태 줄과 진단 요약에는 항목이 남아 있을 때만 나온다. 옛 용도로는 호출 몫도 주지 않는다(`QuotaGuard.acquire` 와 연결 시험용 `acquire_entry` 가 쉬운 한국어로 거절하고 새 용도로 안내한다).

## 8. 화면에서 키 넣기(P4f) — 설계 D-250~D-259

설정 화면의 연결 카드에서 키를 등록·삭제·시험하고 사용/예비·별칭·우선순위를 바꿀 수 있다(쓰기는 사용자가 단추를 눌렀을 때만 — 설정 화면을 열고 다시 읽는 것은 파일·보관소를 바꾸지 않는다). 저장 위치와 영구 저장 금지는 §7 그대로다: **키 원문은 Windows 자격 증명 관리자에만** 있고, 저장해도 되는 것은 별칭·제공자·등록 여부·사용 상태·마지막 성공 시각·마지막 확인 결과(`ok`·`auth_failed`·`error` 라는 결과 이름)·순서·약관 확인 시각뿐이다. **키 원문·앞뒤 일부 글자·길이·문자 구성·Authorization 헤더는 어디에도 저장하지 않는다.** 저장한 키는 화면에 다시 보이지 않는다(끝 4자도 — 화면과 명령줄 어디에도 없다, D-346).

**키가 지나가는 길과 막는 장치**(시험이 전수로 지킨다 — `tests/key_leak_support.py`: 가짜 키와 그 모든 네 글자 조각이 한 곳이라도 있으면 실패):

| 길 | 막는 방법 |
|---|---|
| 입력 칸 | 마스킹(`Password`) — 복사·잘라내기가 글을 클립보드에 내보내지 않고 Qt 가 예측 입력·민감 정보 표시를 켠다. 플레이스홀더·툴팁 없음. 키 칸에 `textChanged`·`textEdited` 를 잇지 않는다(글은 '다음'·'저장' 을 누르는 순간에만 읽는다) |
| 입력 칸을 비운 뒤 | `setText("")` — `clear()` 는 지운 글을 되돌리기 기록에 남기지만 `setText` 는 기록까지 지운다. 저장·취소·Esc·다른 대화상자로 바뀜·창 닫힘 어느 길로든 비운다 |
| 클립보드 | 붙여 넣은 글과 같은 글이 클립보드에 그대로 있으면 저장·닫을 때 비운다(다른 글은 건드리지 않고 앱이 키를 클립보드에 넣지 않는다) |
| 서비스까지 | `SecretBox`(꺼내면 비워지고 `repr`·복사·직렬화가 글을 보이지 않는다) → 서비스 함수 인자. 뷰모델·컨트롤러·등록 초안·값 클래스·결과·실패·알림·행 안내·진단에는 키를 담는 칸이 없다. 작업 스레드의 일감은 통만 쥔다 |
| 예외·호출 흔적 | 어댑터가 서비스 오류를 종류·칸 문제 이름·정해진 쉬운 문장으로만 바꾸고 서비스 오류의 `__traceback__` 를 끊으며 실패 객체는 `except` 밖에서 낸다(앞 오류가 `__context__` 로 따라붙지 않는다). 꺼낸 글을 담은 dict 는 `finally` 에서 비운다. 화면 쪽 슬롯에서 난 예기치 못한 예외는 표준 오류에 **예외 이름과, 비밀 모양을 가리고 경로를 지운 짧은 한 줄**만 남긴다(`ui/core/app_state.unexpected_line` — 추적은 내지 않는다. 키와 닿는 곳이라 어떤 글도 새지 않게) |
| 일이 끝난 뒤 | 컨트롤러가 등록 일감을 `try/finally` 로 감싸 공급자가 통을 꺼내지 않고 죽어도(예기치 못한 오류) 통을 비운다 — 끝난 일의 기록(`runner`)이 통을 쥐고 있어도 거기에 키가 없다(시험이 공급자를 일부러 죽여 확인한다) |
| 별칭 칸 | 키처럼 보이는 글은 바로 비우고(눈에 보이는 칸이라) 거절한다. 서비스는 이름·소속 프로젝트에 키 값이 그대로 들었는지 거절하고, 별칭 바꾸기는 보관된 값이 이름에 들었는지도 거절한다 |
| 로그·진단·파일 | 오류 문장은 종류별로 정해진 말이다. 진단 정보는 시각·개수뿐(별칭도 없다). `connections.json` 에는 비밀이 아닌 칸만 있다 |

**등록·삭제 도중 실패하면**: 등록은 보관소에 먼저 넣고 파일에 쓰다 실패하면 방금 넣은 키를 지운다 — 지우기마저 실패하면 화면이 그렇게 알린다(`보관소에 넣은 키를 지우지도 못했어요`). 삭제는 보관소를 먼저 지우고 파일에서 지운다 — 파일 쓰기가 실패하면 '항목은 있는데 키가 없는' 상태가 화면에 보이고 다시 지울 수 있다. **'항목 없는 키' 를 자동으로 정리하는 단추는 만들지 않았다**: 자격 증명 관리자의 이름 공간은 데이터 폴더가 아니라 Windows 사용자 하나라서 목록에 없는 키가 다른 데이터 폴더(`--data-dir`)의 진짜 키일 수 있다.

**연결 시험**: 사용자가 누를 때만, 호출 코드가 있는 용도에서만이고 시험에서 실제 네트워크를 부르는 일은 없다(지금 어느 용도도 호출 코드가 없다). 이용 약관을 확인하기 전 용도(NAVER API HUB)는 시험 함수를 건네줘도 호출하지 않는다. 시험은 다른 키로 바꿔 시도하지 않는다.

**막지 못하는 것**: §7 과 같다(같은 Windows 사용자의 악성 프로그램·PC 관리자·메모리 덤프·파이썬 문자열을 메모리에서 못 지우는 것). 이 묶음이 더한 한계: Windows 의 한글 입력기(IME)가 조합 중인 글을 어떻게 다루는지·화면 읽기 프로그램이 마스킹 칸의 글자 수를 읽는지는 운영자 PC 에서 확인한다.

## 본문 속 Secret 형태 검사(`security/scan.py`) — 설계 D-420–D-429

운영자 결정(2026-11-11): **글을 저장하거나 백업하기 전에, 사용자가 본문에 붙여 넣은 Secret 형태를 검사한다.** 발견하면 토큰을 다시 보이지 않고 **어디에·어떤 유형이 있는지**만 알리고, 기본 동작은 저장·백업 중지다. 앱은 글을 자동으로 지우거나 바꾸지 않으며 **'무시하고 저장'은 없다** — 이 검사기에는 발견을 끄는 인자도 함수도 없고(소스 이름 검사 시험이 못박는다) 글을 돌려주지도 않는다.

**찾는 것(여섯 가지)**: Google API 키(`AIza` + 35자 이상) · GitHub 토큰(`ghp_`·`gho_`·`ghu_`·`ghs_`·`ghr_` + 36자 이상, `github_pat_` + 22자 이상) · Bearer 토큰(`Bearer` + 공백 + 20자 이상) · OAuth 토큰(`ya29.`·`1//`·`GOCSPX-` + 20자 이상, JWT 세 덩어리, `access_token`·`refresh_token` 이름 뒤 20자 이상 값) · AWS 액세스 키 ID(`AKIA` 등 접두어 8가지 + 16자) · PEM 개인 키(`-----BEGIN` … `PRIVATE KEY` … `-----` 머리 줄). **모양만 본다** — 견본 키·공식 예시 키도 모양이 같으면 발견이다. 자세한 모양과 근거는 [`DECISIONS.md`](DECISIONS.md) D-421.

**누가 언제 부르나**: 초안 저장 직전(제목·본문·키워드·태그·요약) · 전체 백업과 글 보관함·주제 엔진 백업 직전(원고·후보·초안 표, 프로필·Seed·캘린더·`settings.json` 값 — 부분 폴더를 남기지 않는다) · 옛 명령줄 쓰기(`candidates add`·`naver-profile set`·원고 제목·본문 쓰기) · 화면 쓰기 경로(블로그 프로필·Seed·초안 화면). 이 부품은 문자열만 받고 파일·DB·네트워크를 읽지 않으므로 어디를 훑을지·어느 오류 코드로 거절할지는 부르는 묶음이 정한다(D-427). 마스킹(`mask.py` — 출력에서 가린다)·키 모양 입력 검사(`shape.py`)와는 따로다 — 이것은 **쓰기 전에 막는다**.

**사용자에게 보이는 것**: `describe`('본문 3번째 줄에 GitHub 토큰처럼 보이는 글이 있어요')와 `summarize`(칸·유형별 건수와 줄 번호, 마지막에 '해당 줄을 본문에서 지운 뒤 다시 저장해 주세요 — 앱은 자동으로 지우거나 바꾸지 않아요')뿐이다. 토큰 글자는 문장·결과 객체·예외 문구·직렬화(`asdict`·피클·JSON) 어디에도 없고, 문장에는 길이 힌트(열 범위를 풀어 쓴 글)도 없다(카나리 시험).

**위치와 성능**: 줄은 1부터(CRLF·LF·CR), 열은 그 줄 안의 파이썬 글자 1부터(`col_end` 는 마지막 글자, 포함). 전각·수학 글자·특수 공백은 글자 하나씩 NFKC 로 맞춰 길이를 그대로 두므로 위치가 원문 그대로다. 정규식은 모두 선형이고 10만 글자 병적 입력 55가지가 파이썬 3.12·3.10 에서 모두 0.5초 안이다(D-424).

**한계(사실대로)**: 이 검사기는 **모양을 아는 비밀만** 찾는다. ① 공백·줄바꿈·눈에 안 보이는 글자(`U+200B`·소프트 하이픈)로 쪼갠 토큰, 접두어 앞에 영문·숫자가 붙은 토큰(주소의 `%3D` 같은 퍼센트 구분자 바로 뒤는 괜찮다)은 못 찾는다 ② 여섯 가지 밖의 형식(OpenAI·Slack·텔레그램 봇·AWS 비밀 키·자유 글 속 비밀번호·이름 모르는 형식)과 하한보다 짧은 토큰은 못 찾는다 — 마스킹이 출력에서는 가려 주지만 쓰기를 막지는 않는다 ③ PEM 은 머리 줄만 본다(몸통만 붙여 넣으면 못 찾는다) ④ 견본 키·공식 문서의 예시 키·변수 이름처럼 긴 값(`access_token=` 뒤)도 모양이 같으면 걸린다 — 그 줄을 고쳐 쓰게 한다 ⑤ 글자 모양만 본다: 키가 진짜인지는 모른다 ⑥ 인코딩해 쓴 토큰(base64·16진수·퍼센트로 쓴 밑줄)·글자 순서를 뒤집은 토큰·대소문자를 바꾼 접두어·`Bearer` 와 값 사이의 줄바꿈은 못 찾는다(재귀적으로 풀어 찾지 않는다 — D-359). 올리는 글을 눈으로 확인하는 일(`AGENTS.md` §2 규칙 1)을 대신하지 않는다.

### 외부 게시는 완전히 꺼져 있다(H3 — D-341–D-343)

이 시험 버전에는 글을 외부로 쓰는 길이 **없다** — PC 에 Git 로그인이 이미 있어도 push 할 수 없다. 설정 스위치를 '기본 꺼짐'으로 둔 것이 아니라 네 겹이 서로를 받친다.

1. **서비스 비활성** — GitHub 에 올리기·올리기 권한 점검·원격 최신 받기·공개 확인·취소를 하는 모든 함수의 **첫 줄**이 `capabilities.require_external_write(작업)` 으로 `EXTERNAL_WRITE_DISABLED` 를 낸다(하위 프로세스·네트워크·파일 쓰기보다 먼저).
2. **어댑터 미등록** — Blogger·네이버로 보내는 어댑터는 없고 등록부(`service/external.py`)는 비어 있다. 기본 git 은 모든 호출을 거절하는 `refusing_git`, 기본 백엔드는 파일만 읽는 `LocalOnlyBackend` 다.
3. **소스 상수 Runtime Gate** — `capabilities.EXTERNAL_WRITE = False` 는 소스에 박힌 상수다. 설정 파일·환경 변수·명령줄·화면이 바꿀 수 없고 켜는 훅이 생산 코드에 없다(시험만 `mock.patch.object` 로 모듈 단위로 임시로 켠다).
4. **Network Write 0 시험** — 모든 부명령과 화면 어댑터의 연결을 감시기(소켓·HTTP·`urllib`·`subprocess.Popen`·`os` 의 프로세스 실행 함수·`webbrowser`)를 켠 채 돌려 나간 호출이 0 임을 확인하고, 나가는 호출이 있는 소스 위치를 허용 목록으로 못박는다. **한계(D-359)**: 위치 규칙(AST)은 import 구문과 `os.<이름>` 만 본다 — `__import__('subprocess')`·`importlib.import_module`·`ctypes.WinDLL`·`from os import system`·`getattr(os, '문자'+'이어 붙이기')` 같은 **의도적** 우회는 막지 못하고 런타임 감시기는 실행되는 경로만 본다. 우발적인 추가(`import subprocess`·`webbrowser`·`os.system`)는 확실히 잡는다. 이 시험은 **정직한 코드의 회귀 그물**이다 — 뒤의 D-611·D-619 가 우회 모양을 더 보게 했지만(이 문서 끝의 AS-S1 절) 일부러 숨기는 코드(시험 `HONEST_LIMITS` 의 열 가지)는 여전히 막지 못한다. `keys purposes` 의 GitHub 안내와 `doctor` 의 '올리기 권한' 줄은 이 빌드에서 '이 시험 버전은 글을 GitHub 에 올리지 않아요' 라고 말한다(D7).

### 공통 경계와 가리기 규칙(H1 — D-344·D-345)

비밀이 프로세스 밖으로 나가는 출구는 한 곳(`security/boundary.py`)에서 거른다. 진입점의 맨 앞에서 설치하면(화면 진입점은 둘이다 — 소스 실행의 `__main__` 과 묶음 실행 파일이 바로 부르는 `ui/launcher.main`. 둘 다 맨 앞에서 부르고 멱등이라 한 번만 깔린다) ① `sys.stdout`·`sys.stderr` 가 줄 단위로 가려 쓰는 래퍼가 되고(여러 `write()` 에 쪼개진 비밀도 줄이 끝날 때 가려진다) ② `sys.excepthook`·`threading.excepthook`·`sys.unraisablehook` 이 비밀을 가린 추적을 남기며(`--debug` 의 되던진 예외도 같다) ③ `logging` 은 기록이 만들어지는 순간 문장·인자·추적을 가린 글로 굳히고 ④ 화면(GUI)은 Qt 가 직접 찍는 메시지도 가려 표준 오류로 보낸다. 오류 문구의 슬롯 값은 `errors/render.py` 가, 화면 글은 `ui/core/text.py` 의 `display_text` 한 점이 가린다. 가리는 규칙(정규식)은 `security/mask.py` 한 곳에만 있다.

가리는 이름: `Authorization`·`api_key`·`apikey`·`serviceKey`·`access_token`·`refresh_token`·`client_secret`·`password`·`Cookie`·`Set-Cookie`·`X-API-Key` 와 그 계열(`authKey`·`appKey`·`secretKey`·`X-Naver-Client-Secret`·`Ocp-Apim-Subscription-Key`·`crtfc_key`·`access_key`·`private_key`·`subscription_key`). `…key` 는 앞 낱말이 붙은 것만 이름이다(`monkey`·`keyword` 는 아니다). 규칙은 `Authorization` 줄은 값 전체(알려진 스킴 낱말만 남김), `Cookie` 는 **이름 불문 모든 값**(쿠키 이름은 남김), `Set-Cookie` 는 첫 쌍과 모르는 속성, 눈속임(전각·키릴·그리스 동형 문자·퍼센트·이스케이프 JSON·따옴표 두 겹·탭·base64 로 감싼 값 깊이 1·쪼갠 값)은 풀어서 가린다. 측정(`tests/pcsec1_mask_cases.py` 163건): 새는 입력 62 → 5, 오탐은 정상 글 122개와 앱이 실제로 내는 글 2,118개에서 0, 20만 자 입력 CPU 시간 최대 3.12 0.41초·3.10 0.50초(부하 PC 에서 세 번 중 최소 — 시험 한도는 2초).

**한계(사실대로)**: ① **이름 표지가 없는 값**(경로 속 키·라벨 없는 한 줄·라벨 없는 10자 시크릿·64자 16진수·43자)은 가리지 않는다 — 모양만으로는 SHA-256·커밋 해시와 가를 수 없어 일부러 그렇게 했고 시험이 그 5건이 가려지지 않음을 못박는다 ② 이중 퍼센트·`\uXXXX` 로 쓴 이름·base64 두 겹·8192자 뒤에만 비밀이 있는 긴 base64 덩어리·이름 표지 없이 줄바꿈으로 쪼갠 값은 못 가린다 ③ 스트림 `.buffer` 로 바이트를 직접 쓰는 것·자식 프로세스의 직접 출력·`faulthandler`·Qt 가 아닌 라이브러리가 C 쪽에서 찍는 글은 경계를 지나지 않는다(앱 코드는 소스 규칙 시험이 막는다) ④ 설치 뒤 다른 코드가 `sys.stdout` 등을 다시 바꿔 끼우면 그 객체는 경계 밖이다(소스 규칙 시험이 앱 코드의 바꿔 끼움을 막는다) ⑤ 위젯 `setText` 161곳은 한 점에 모으지 않았다 — 위젯 글 전수 훑기 시험이 지킨다(새 화면은 그 시험에 장면을 더해야 한다) ⑥ `logging` 에 로그 파일 핸들러를 달지 않았다(작은 오류 기록 파일은 `logging` 을 쓰지 않는 `security/errorlog.py` 가 따로 쓴다 — 맨 끝 '오류 기록' 절) ⑦ **마스킹이 못 가리는 모양**(D-359): 이름과 값이 따로 있는 JSON·XML(`name`·`value` 칸 쌍·`<add key=… value=…/>`·`name=…&value=…`), YAML 블록 `api_key: >` 다음 줄, 닫히지 않은 따옴표(앞에서 잘린 글), HTML 엔티티 구분자(`&#61;`·`&equals;`)나 결합 글자가 낀 이름, `curl -u 사용자:값`·`passphrase=`·`password => x`, 줄바꿈으로 쪼갠 이름, JSON 배열의 `set-cookie`, 이름과 값 사이에 다른 낱말이 낀 문장(`my password is x`·`The api key is x`), 구분자 없이 이름 뒤에 오는 값이 짧거나(16자 미만) 숫자·글자 한쪽뿐인 것(`auth token x` — 낱말·번호와 가를 수 없어 일부러 그렇게 했다), 값이 빈 라벨 줄(`password:`) 바로 다음 줄의 헤더 일부(`X-API-Key` 값의 `_`·`-` 뒤 꼬리). 공백·점이 낀 이름(`API key: x`·`api.key=x`)·`Basic ` 낱말 바로 뒤의 `이름=값`·이름 낱말 바로 뒤에 구분자 없이 오는 값 모양(`auth token Zq8…`·`Your API key Zq8… is not valid` — 같은 줄에서 16자 이상이고 숫자와 글자가 모두 있을 때만, 규칙 사슬의 맨 끝)은 D4 에서 고쳤다 ⑧ **경계 스트림**(D-359): 공백 없는 조각이 16384자를 넘으면 쥐고 있던 것을 내보내 쪼갠 쓰기에서 라벨 뒤 값이 라벨 없이 나갈 수 있고, 이름과 값 사이에서 일부러 `flush()` 를 부르면 이름이 먼저 나간다 — 앱의 출력 경로는 출력 직전에 `mask_block` 을 먼저 지나므로 지금 영향이 없다. 헤더 줄(`Cookie`·`Set-Cookie`·`Authorization`)은 4096자를 넘어도 공백에서 자르지 않는다(D5 a 고침). 기존 시험 108곳(41개 파일)은 실패하면 비밀을 그대로 찍을 수 있어 목록으로 보고하고, `tests/run_masked.py` 로 돌리면 실패 글이 가려진다.

**한계 ⑧ 보충(AS-S1 참고-9, D-612):** ⑧ 의 '이름이 먼저 나간다' 는 줄여 말한 것이다 — `password: ` 뒤에서 `flush()` 하고 값이 오면(`Authorization: Bearer ` 뒤도 같다) 이름만이 아니라 **값도 가려지지 않은 채** 나간다(감사 탐침). 앱 코드 중 이름과 값 사이에서 `flush()` 하는 곳은 없고(출력은 모두 `mask_block`·`mask_deep` 을 먼저 지난다) 쪼갬 쓰기·CR 만 있는 줄·유니코드 줄 구분자·개인 키 블록 쪼갬은 막힌다. 주소 인자 `client_id` 는 이름 목록에 더했다(D-612).

### 키는 다섯 가지만 보인다(H2 — D-346)

화면·명령줄(`keys list`·`keys add`)·`--json`·`doctor`·연결 시험에 보이는 키 관련 정보는 **제공자 이름·항목 번호(Key Slot)·등록 여부·마지막 연결 시험·등록 시각**뿐이다. 끝 4자·앞부분·접두어·길이는 어디에도 없고, 그것을 만들던 코드(`tail_hint`·`EntryView.tail`)도 지웠다. 소스 규칙 시험(`test_source_rules_key_display`)이 값의 일부를 자르는 이름·문구·식과 `reveal(` 호출이 `service/`·`ui/`·`security/` 에 없음을 확인하고, 화면 위젯 전수 훑기가 가짜 키와 그 모든 네 글자 조각이 어느 위젯 글에도 없음을 확인한다. `--json` 은 그 다섯 가지를 다루는 데 필요한 칸(항목 번호용 난수 `entry_id`·순서·상태·마지막 확인 시각과 결과·약관 확인 시각)만 낸다 — NAVER 고객 ID 같은 칸에서 만든 묶음 이름(`bucket`)은 싣지 않는다(D-358).

### Blogger OAuth 입력(D-347)

이 빌드에는 Blogger 를 부르는 코드가 없으므로 `BLOGGER_OAUTH_INPUT = False`(소스 상수 — 켜는 길 없음)로 입력을 막았다: 서비스(`add_entry`)와 명령줄(`keys add`)은 키를 묻기 전에 거절하고, 화면의 Blogger 카드에는 입력 칸·등록 단추 없이 '받지 않아요' 안내만 있다. 자격 증명 관리자에 저장하는 코드와 이미 저장된 항목의 지우기·시험은 그대로다. Blogger 초안 기능을 구현할 때 Scope·연결 해제·Token 삭제·재인증·초안 전용 정책과 함께 별도 검증을 거친 뒤 연다.

### 본문 속 Secret 형태의 적용 위치(M3 — D-348)

검사기(위 '본문 속 Secret 형태 검사' 절)를 `security/refuse.py` 가 부르기만 한다. ① 옛 명령줄 쓰기: 원고 제목·본문·출처·이미지(`new`·`edit`·`import-html`)·후보 주제·핵심 키워드·보조 키워드·추천 이유(`candidates add`)·네이버 프로필 글칸(`naver-profile set`)·검토 요청의 매개변수(`review` 의 분야·태그·한 줄 설명·대표 이미지 주소·출처 이름·주소·글 제목, 네이버 검토의 제목·본문 파일·태그·분야)·네이버 발행 주소(`naver-done --url`)는 쓰기 전에 `SECRET_SHAPE_FOUND` 로 멈추고 칸·줄·유형만 알린다. 후보 CSV 는 그 줄만 거절한다. ② 백업 전: `backup` 은 글·옛 판 기록·초안·후보를 훑어 있으면 백업을 만들지 않고, 주제 엔진 백업은 옛 정본 패턴과 검사기 여섯 유형을 **둘 다** 막으며 `TOPIC_BACKUP_BLOCKED` 의 이유에 위치(파일·줄 또는 표·행)와 유형을 말한다. 지우기·되돌리기 직전의 안전 사본은 막지 않는다 — 막으면 문제의 글을 지울 수도 되돌릴 수도 없다. ③ 화면 쓰기(블로그 프로필·Seed)는 같은 `scan_key_shape` 라 같은 종류를 막고, 초안 복사 관문은 검사기가 찾은 자리를 더하되 글자를 한 자도 되풀이하지 않는다. ④ 키 항목의 별칭(이름)·소속 프로젝트(평문 파일 `connections.json` 에 남는 칸): 가리기 규칙이 가릴 글(`client_secret=값`·`Cookie: …`·`Authorization: Bearer …`)이 있으면 `KEY_INVALID_SHAPE` 로 쓰기 전에 거절하고 칸 이름과 이유만 알린다(`keys add --name`·화면·이름 바꾸기가 같은 규칙, PCSEC1V). **'무시하고 저장'은 없다**(인자·명령줄 옵션·환경 변수·설정 없음 — 시험이 소스와 명령줄 파서에서 못박는다). 한계: 옛 명령줄 쓰기와 글 보관함 백업은 검사기의 여섯 유형만 본다(옛 패턴이 아는 OpenAI·Slack 등은 출력에서는 가려지지만 거기서는 막지 않는다), `edit` 는 바꾸지 않는 칸의 옛 비밀 모양을 막지 않고 백업 전 검사가 막는다.

### 그 밖에 사실대로 적는다(M1·M2·M4·M7·M8 — D-349–D-353)

- **데이터 폴더 위치(M1)**: 앱은 폴더 권한(NTFS ACL)을 설정하지도 확인하지도 않고 사용자 프로필 폴더의 상속에 기댄다. 데이터 폴더가 사용자 프로필 밖이면 `doctor` 가 '같은 PC 의 다른 사용자가 읽을 수 있어요' 라고 주의한다(문자열 경로 비교만 한다).
- **시험용 가짜 보관소(M2)**: `CHANCEBLOG_KEYSTORE` 로 연 시험 전용 보관소를 쓰는 중이면 키 화면이 '시험용 보관소 — 실제 키를 넣지 마세요' 를 알린다.
- **백업(M4)**: 주제 엔진 백업 목록에 `credential_excluded: true` 와 쉬운 문장이 있고 명령줄 백업 출력에 '키는 백업에 들어 있지 않아요' 한 줄이 있다. 무엇을 담는지는 바뀌지 않았다.
- **폴더 이름(M7)**: 코드의 `ChanceblogDesktop`·자격 증명 대상 `ChanceBlogDesktop:`·운영자 문서의 `ChanceBlog` 철자가 다른 것을 알고 있으며 바꾸지 않았다(바꾸면 저장된 키·데이터를 옮겨야 한다).
- **지운 글의 원문(M8)**: 글을 지우기 직전에 만드는 백업(`backups/before-delete`)에는 지운 글의 원문이 남고, 되돌리기 직전의 백업(`backups/before-restore`)에는 되돌리기 전의 글 전체가 남는다 — 소유자 권한 폴더 안에 두는 복구용 설계다(각 폴더에 최근 10개만 남기고 오래된 것은 앱이 지우므로 원문은 그동안만 남는다). 파이썬의 `.pyc` 캐시(`__pycache__`)는 소스 옆의 같은 사용자 폴더에 생기며 앱이 지우지 않는다.
- **로그 파일·내보내기**: 작은 오류 기록 파일 하나가 있다(맨 끝 '오류 기록' 절 — 오류 이름과 코드 위치만 남기고 공통 가림 규칙을 거친다, D-488). 로그를 내보내는 기능은 아직 없다.
## 9. 전체 백업·복원(BACKUPUI) — 설계 D-380–D-397

설정 화면의 `백업·복원` 카드가 글 보관함·주제 보관함·채널 프로필·Seed·캘린더·설정을 한 폴더(`backups/full-날짜-시각/`)에 담고 되돌린다(서비스 `service/backup_flow.py`, 화면 `ui/qt/backup_parts.py`). **쓰는 곳이 하나 더 는다**: `지금 백업` 은 백업 폴더를 만들고(쓰는 함수 — 폴더 만들기·파일 지우기·이름 바꾸기·제자리 교체 — 는 `tests/test_service_safety.py` 의 허용 목록에 이유와 함께 등록돼 있고 목록 밖의 쓰기는 시험이 잡는다), `복원` 은 확인창의 `복원하기` 를 눌렀을 때만 데이터 폴더의 보관함·JSON·설정을 바꾼다. 카드를 열고 목록을 읽는 것은 아무것도 만들거나 바꾸지 않는다. (§5 의 '화면에서 파일에 쓰는 곳' 목록은 이 묶음에서 고치지 않았다 — 병합할 다른 묶음과 줄이 겹치지 않게 맨 끝에만 적고, 목록 정리는 병합 뒤 한 번에 한다.)

**백업에 Credential 이 없다는 것을 어떻게 지키는가**(운영자 2026-11-11 결정 — 시험이 전수로 지킨다):

| 길 | 막는 방법 |
|---|---|
| 키 원문 | 이 앱은 키를 파일에 적지 않는다(§7). 백업 코드는 키 보관소·환경 변수·`connections.json`·로그·`print` 에 닿지 못한다(소스 규칙 시험) — 담는 파일은 이름이 정해진 여섯뿐이고 `connections.json`·`quota_state.json`·`publish/`·`locks/` 등 담지 않는 아홉 가지는 이유와 함께 목록 파일에 적힌다 |
| 사용자가 글에 실수로 붙여 넣은 키·토큰 모양 | **백업 직전에 만든 사본을 훑는다**(`security/scan.py` — Google API 키·GitHub 토큰·Bearer 토큰·OAuth 토큰·AWS 액세스 키·개인 키(PEM)). 하나라도 있으면 백업을 만들지 않고 폴더도 남기지 않으며 위치(어느 칸·몇 번째 줄)와 유형만 알린다. 앱은 글을 자동으로 지우거나 바꾸지 않고 **'무시하고 백업' 이 없다** — 운영자가 직접 지운 뒤 다시 누른다 |
| 훑는 범위 | 여섯 유형 × 아홉 자리(원고 본문·제목·저장한 초안·글 보관함 후보·주제 보관함 후보·채널 프로필·Seed·캘린더·설정) = 54칸 모두와 옛 판 기록. 엄격한 읽기가 키 모양 글을 '틀린 모양' 으로 거절해 파일을 빼먹는 길을 막으려고 훑기를 엄격한 읽기보다 먼저 한다(시험) |
| 훑지 않는 곳 | 발행 이력 장부(`history_ledger`) — D-75 와 같은 이유(이미 공개된 블로그 글을 읽어 둔 것이라 지울 길이 없다). 같은 글이 다른 곳에 있으면 그곳은 막는다 |
| 지운 글의 조각 | SQLite 는 지운 글의 조각을 파일의 빈 쪽에 그대로 둘 수 있다. 앱의 보관함은 연결마다 지울 때 덮어쓰도록(`secure_delete`) 열리지만 앱 밖의 도구가 쓴 파일·옛 파일·다른 곳에서 가져온 파일은 알 수 없다 — 그런 파일에서 키 모양 글을 지운 뒤 다시 백업하라고 안내하면 조각이 백업에 실려 갈 수 있다(기본 설정에서 지운 글이 파일에 남는 것을 확인했다). 그래서 **백업 사본은 만든 뒤 `vacuum` 으로 빈 쪽을 정리한다**(지금 쓰는 파일은 건드리지 않고 이름표·행은 그대로 옮겨진다. 정리하는 동안의 임시 사본은 시스템 임시 폴더가 아니라 메모리에 둔다 — D-398). 시험이 '큰 초안에 키 모양 글을 넣었다 지운 파일' 의 백업·복원 직전 사본에 조각이 없음을 여섯 유형 모두에서 본다 |
| 목록·화면·오류 | 고정 문장과 위치 줄뿐 — 키 글자·경로·예외 문구가 없다(카나리아 시험: 가짜 키를 가짜 보관소에 등록해 둔 채 백업·복원을 돌려도 백업 폴더·목록·안전 사본의 모든 바이트에 가짜 키의 여덟 가지 모습(utf-8·utf-16 둘·16진수 둘·base64 둘·퍼센트 인코딩)이 없다. 찾는 도구가 모든 모습을 실제로 찾는지도 따로 본다) |
| 복원 | 백업 안에 키 모양이 있으면 복원하지 않고, 지금 데이터에 키 모양이 있으면 안전 사본을 남길 수 없어 시작하지 않는다(앱이 고칠 수 없다고 말한다). 키·`connections.json` 은 바이트도 건드리지 않는다 |
| 안전 사본 | 같은 규칙이다 — 복원 직전 사본(`backups/before-restore/`)에도 키가 없다(시험이 같은 방법으로 훑는다) |

**복원이 안전한 이유**: 바꾸기 전에 백업을 읽기만 해서 목록 모양·파일 이름·크기·해시·보관함 이름표·판·점검을 모두 확인하고(한 바이트만 바뀌어도 거절 — 시험이 파일을 하나씩 바꿔 본다), 더 새로운 프로그램의 백업은 쓰지 않으며, 지금 데이터를 안전 사본으로 먼저 남기고(못 남기면 시작하지 않는다), 어느 단계든 실패하면 안전 사본으로 원래대로 돌린다(되돌리지 못한 것은 이름을 알린다). 백업과 복원은 같은 잠금(`locks/full-backup.lock`)을 써서 한 번에 하나만 돈다. 깨진 지금 파일은 지우지 않고 옆(`.bad-날짜-시각`)으로 옮긴다.

**복원이 더 보는 것(L8, D-554·D-555)**: 위 확인에 더해 되돌릴 보관함 파일의 **구조**(트리거·뷰·모르는 표와 색인 — 앱이 만들지 않는 개체)와 설정의 '연결한 폴더' 경로 **모양**(네트워크 경로·주소·제어 문자·1024자 초과)을 바꾸기 전에 보고, JSON·설정은 8MB 를 넘으면 읽기 전에 거절한다. 자세한 것과 한계는 이 문서 맨 끝의 'L8' 절(조작된 백업의 구조 검사)에 있다.

**밖으로 나가지 않는다**: 백업·복원은 네트워크·외부 쓰기·AI 호출이 0 이다(새 코드는 `subprocess`·`socket`·`urllib`·`webbrowser`·`os.startfile` 을 가져오지 않고 시험이 지킨다). 폴더를 여는 단추도 없다 — 백업 위치는 글자로만 보이고 USB·다른 PC 에 복사하는 것은 사용자가 직접 한다.

**막지 못하는 것·알려 둘 것**: ① 지금 쓰고 있는 보관함 파일(`chanceblog.db`·`topic_engine.db`)이 앱 밖에서 쓰였거나 옛 파일이면 그 빈 쪽에 지운 글의 조각이 남아 있을 수 있다 — 백업 사본에는 실리지 않지만(위) 그 파일은 사용자의 데이터 폴더에 그대로 있고, 이 묶음은 보관함을 고쳐 쓰지 않는다(앱이 쓰는 연결은 지울 때 덮어쓴다 — 후속 후보 D-399) ② 훑기는 여섯 모양을 규칙으로 찾는 것이라 모르는 모양의 비밀이나 쪼개 쓴 글은 못 잡는다(§7 의 한계와 같다) ③ 같은 Windows 사용자의 악성 프로그램은 백업 폴더도 읽을 수 있다 — 백업은 이 컴퓨터 안의 폴더이고 암호화하지 않는다(키가 없는 데이터라서다). USB 에 옮길 때는 그 USB 를 사용자가 관리한다.

**수정 라운드(2026-11-12 — 독립 검증 BACKUPUIV 지적 반영, 결정 D-460–D-466)**: ① **키 모양은 디스크에 닿기 전에 걸러진다** — 보관함 사본은 메모리 연결에 만들어 `vacuum` 한 뒤 그 자리에서 훑고(JSON·설정은 읽은 바이트를 먼저 훑고) 이상 없을 때만 파일로 쓴다.
그래서 강제 종료·창 닫기·이름 바꾸기 막힘 어느 때에도 키 모양이 든 사본은 디스크에 있었던 적이 없다(자식 프로세스를 `os._exit` 로 곳곳에서 죽인 시험이 지금 파일을 뺀 데이터 폴더의 모든 바이트를 8가지 인코딩으로 훑어 0 을 확인한다). 쓴 폴더를 한 번 더 훑는 이중 확인은 남아 있다
② 앱이 갑자기 꺼져 남은 임시 폴더(`full-….tmp`·`before-….tmp`, SQLite 짝 파일 포함)와 낡은 잠금은 다음 백업·복원이 잠금을 쥔 채 치우고, 목록을 보여 줄 때도 치울 흔적이 보이면(살아 있는 백업·복원이 없을 때만) 치운다
③ 복원이 도중에 멈추면 `backups/restore-in-progress.json`(이름·시각뿐 — 글 내용·경로 없음)이 남아 카드가 쉬운 안내와 '안전 사본으로 되돌리기'(확인창 먼저)를 보여 준다 — 앱이 시작하면서 혼자 되돌리지는 않는다
④ 정리가 방금 만든 백업을 지우지 않는다(시계가 거꾸로 가도 — 미래 날짜의 옛 것이 대신 정리된다) ⑤ WAL 저장 방식으로 바뀐 보관함도 백업된다(사본은 일반 방식) ⑥ 정리 못 한 저장(`-journal`)이 남은 보관함은 백업이 건드리지 않고 부분 백업으로 알린다
⑦ 이름 바꾸기·바꿔 넣기는 다른 프로그램이 잠깐 붙잡으면 0.2초씩 다섯 번까지 다시 한다. **여전히 막지 못하는 것**: 앱이 죽은 뒤 임시 폴더에 남은 것은 키 모양이 없는 내용이지만 다음 백업·복원·목록 전까지는 디스크에 있다(치우기는 다음 실행의 일이다).

## 10. 저장한 초안 — 설계 D-360 에서 D-374 까지 (LOCALSAVE)

초안 작성 화면의 `저장`(Ctrl+S)은 **새 저장 위치를 만들지 않는다** — 같은 글 보관함 `chanceblog.db` 의 `drafts` 표(`content/store.py` 에 원래 있던 표 — 구조 판은 그대로 2)에 초안 한 편이 한 행으로 들어가고, `Store.backup`·`restore_from` 이 파일 통째라 백업·되돌리기에 자동으로 따라간다. 위 §5 의 '화면에서 파일에 쓰는 곳은 … 네 곳이다' 에 이 묶음의 저장한 초안이 **한 곳 더해진다**(블로그 관리·Seed 관리·주제 후보·키 넣기 + 저장한 초안 — 새로 더해지는 곳만 `chanceblog.db` 이고 나머지 넷의 쓰는 곳은 그대로다). 전체 백업·복원이 더하는 쓰는 곳은 위 §9 에 따로 적혀 있다. §5 의 그 문장은 내 글 문체 참고값 보기(N-3a)의 시험이 글자 그대로 못박고 있어 이 묶음도 고치지 않았다 — 목록 정리는 병합 뒤 한 번에 한다. 서비스에서 이 표에 쓰는 함수는 `service/draft_store.py` 의 `save_draft`·`delete_draft` 둘뿐이고 `tests/test_service_safety.py` 의 `STORE_DRAFT_WRITERS`(이유 한 줄씩)가 못박는다 — 새 쓰기 위치·새 파일·새 네트워크 호출은 없다.

- **저장 직전 키·토큰 모양 검사**(`security/scan.py` — Google API 키·GitHub 토큰·Bearer 토큰·OAuth 토큰·AWS 액세스 키·개인 키(PEM)): 제목·본문·키워드·태그·카테고리·요약·후보 주제·후보 번호·선택 입력과 처음 만든 초안(제목·제목 후보·본문·확인 권장·분야·바꾼 형식)을 훑고, 하나라도 찾으면 **아무것도 쓰지 않고 글 보관함 파일을 열지도 않은 채** 멈춘다(`DRAFT_SECRET_FOUND`). 화면에는 위치(칸 이름과 몇 번째 줄)와 종류만 나오고 **찾은 글은 어디에도**(화면·오류 문구·알림·`repr`·피클) 다시 나오지 않는다. 앱은 글을 자동으로 지우거나 바꾸지 않고, **'무시하고 저장' 은 없다**: `save_draft` 에 검사를 건너뛰는 인자가 없고 화면·오류 문구 어디에도 그런 말이 없다(시험이 함수 서명과 모든 소스의 글을 훑는다). 만든 초안 칸에서만 찾았다고 그 칸을 빼고 저장하지도 않는다(D-368 — 예전에 있던 그 길을 운영자 결정 4항에 따라 없앴다): 화면에서 못 고치는 칸이라 안내가 후보·블로그 프로필(대상 독자·카테고리 같은 칸)과 선택 입력에서 키처럼 보이는 글을 지운 뒤 '다시 만들기' 를 하라고 알리고, 다시 만들면 지금 고친 글이 사라지니 먼저 복사하라고 한다.
- **저장은 복사가 아니다**: 복사 관문(건강 효과 단정·확인 권장·글 모양 점검)은 저장을 막지 않는다. 저장 실패(디스크 가득·읽기 전용·손상·잠김·한도)는 쉬운 안내이고 복사·편집은 그대로 쓸 수 있다. 떠나기·앱 닫기 앞의 확인창에서 `저장` 을 골랐는데 저장이 안 되면 나가기를 막지 않고 경고한다.
- **원자성**: 한 번의 저장은 `Store.update_draft` 한 트랜잭션(`BEGIN IMMEDIATE … COMMIT`)이라 쓰는 도중 끊기거나 디스크가 가득 차도 이전에 저장한 판이 그대로이고 반쯤 쓴 기록이 없다. 확인(저장 횟수 비교·300편 한도)과 쓰기가 같은 쓰기 잠금 안이라 같은 초안을 두 프로세스가 동시에 저장해도 갱신이 조용히 사라지지 않는다(D-369). 같은 초안을 다른 창이 그 사이 다시 저장했다면 덮어쓰지 않는다(`STORE_CONFLICT` — 저장 횟수 `expected_revision`). 깨진 기록 위에는 쓰지 않는다(`DRAFT_CORRUPT`). 앱이 큰 저장을 하다 꺼져 저널이 남은 보관함은 읽는 길이 한 번 보통 열기로 정리한 뒤 읽는다(D-370 — 저장해 둔 초안은 그대로).
- **지우기**: 확인창이 먼저이고 지우기 직전 상태를 `backups/before-delete` 에 사본으로 둔다(사본에는 지운 초안의 글이 그대로 있다 — 같은 사용자 폴더 안, 복구용 설계. 글 지우기와 같다). 사본을 못 만들면 지우지 않는다.
- **글 보관함 백업 전 검사(D-373)**: 백업 전 검사(PCSEC1 M3 — 위 '본문 속 Secret 형태의 적용 위치')는 저장한 초안(`dd-` 번호)을 풀어서 칸별로 훑는다 — 그 기록은 글칸을 이스케이프한 JSON 한 줄이라 날것 그대로 훑으면 줄 맨 앞·탭 뒤·한글 바로 뒤의 키 모양을 놓친다(독립 검증이 여섯 종류 x 다섯 자리 30조합 중 14곳을 놓친다고 쟀다). 위치는 '저장한 초안 N번째 · 칸 이름 N번째 줄'이고 글은 어디에도 없다. 저장 직전 검사가 막으므로 정상 경로로는 키 모양이 든 저장한 초안이 생기지 않는다 — 옛 데이터나 손으로 고친 파일을 위한 안전망이다. 전체 백업·복원(위 §9)의 검사도 같은 기록을 JSON 으로 풀어 글칸마다 훑는다 — 키 모양이 든 저장한 초안이 있으면 백업을 만들지 않고 키 모양이 든 백업은 복원하지 않으며, 위치는 '글 보관함 · 저장한 초안 · …' 로 시작하고 글은 어디에도 없다(`tests/test_service_backup_saved_drafts.py` 가 못박는다).
- **글에 담는 것·담지 않는 것**: 글칸은 글자 그대로(정규화·줄바꿈 바꾸기 없음 — 기록은 ASCII 로 이스케이프한 JSON. 화면의 편집기(Qt)만 따로 줄 끝 CRLF·CR·줄 구분 U+2028·문단 구분 U+2029 를 LF 하나로, 줄 안의 NBSP(U+00A0)를 보통 공백으로 바꿔 보이므로 열기만 하면 저장한 글 그대로지만 본문을 고치면 편집기가 내는 글이 저장 대상이다 — D-371). 키·계정·쿠키·토큰·네트워크·AI 정보를 담을 칸이 없다(칸은 글·선택 입력·후보 식별자·블로그 슬롯 이름·글 유형·생성기 판·시각). 번호는 저장 시각·후보·블로그·제목·본문의 지문이라 새 무작위·새 시계를 쓰지 않는다.
- **알려진 한계**: 키 검사는 모양이 알려진 여섯 종류만 본다(이름을 모르는 형식·아주 짧은 토큰·이미 쪼개진 토큰·모양 없는 비밀번호 같은 글은 못 찾는다 — `security/scan.py` 의 한계). 저장한 초안은 사용자 폴더(`%LOCALAPPDATA%\ChanceblogDesktop`)에 평문으로 있다 — 같은 계정의 다른 프로그램은 읽을 수 있고 다른 Windows 계정은 OS 권한이 막는다(원고와 같은 수준 — 이 앱은 원고를 암호화하지 않는다). 홈은 저장한 초안의 제목·개수만 읽는다(읽기뿐 — 파일을 만들지 않는다).

## 개인 PC 제한 시험용 Package(`packaging/`) — 보안 경계와 한계

- **묶음에 비밀·사용자 데이터가 없다**: 빌드가 묶음의 파일 이름(`settings.json`·`connections.json`·`*.db`·`*.pem`·`.env`·`token*.json` 등)과 글 파일 속 키 모양 문자열(저장소 시험과 같은 목록)을 훑어 하나라도 나오면 거절한다. 키는 사용자별 Windows 자격 증명 관리자에만, 데이터는 사용자별 `%LOCALAPPDATA%\ChanceblogDesktop` 에만 생긴다(이 묶음이 바꾼 것 없음).
- **명령줄이 열려 있지 않다**: 시작 파일은 인자를 하나도 받지 않는다(`publish-pages --yes` 같은 입력은 값을 되풀이하지 않는 고정 문장으로 거절하고 종료 코드 2). 숨은 `--selftest` 는 정확히 그 한 단어일 때만. 개발자용 명령줄은 소스 실행에서만 쓴다.
- **일반 사용자 권한**: 실행 파일 매니페스트가 `asInvoker` 임을 빌드와 `--selftest` 가 확인한다(관리자 요구 `requireAdministrator`·`highestAvailable` 는 거절). 쓰는 곳은 사용자 데이터 폴더·자격 증명 관리자·임시 폴더뿐이고 레지스트리·시작 메뉴·서비스에 쓰지 않는다.
- **무결성**: 서명이 없으므로 SHA-256 이 변조를 알아보는 유일한 수단이다 — 압축 파일의 SHA-256(`SHA256SUMS`), 묶음 안 모든 파일의 SHA-256 목록(`PACKAGE_INFO.json`, `--selftest` 가 실제 파일과 대조), 같은 커밋·같은 잠금 파일의 도구·같은 Python 이고 묶음의 DLL 이 같은 곳(가상환경·기본 Python·Windows 폴더)에서 오면 같은 압축 파일이 나오는 결정적 빌드(DLL 의 출처가 그 밖이면 빌드가 거절한다 — D-415). **한계**: 해시 파일을 압축 파일과 같은 곳에서 받으면 함께 바뀔 수 있다 — 값을 다른 길(워크플로 실행 로그에 찍힌 값 등)로도 확인한다.
- **미서명·SmartScreen·스마트 앱 컨트롤**: 파란 경고가 뜰 수 있고 스마트 앱 컨트롤이 켜진 PC 는 막을 수 있다. 이 묶음은 그 설정을 바꾸지 않으며 바꾸라고 권하지도 않는다(막히면 사실만 보고).
- **악성코드 검사**: Windows Defender 가 쓸 수 있으면 읽기 전용(`-DisableRemediation`)으로 압축 파일과 묶음 폴더를 검사해 결과를 정보 파일에 적고, 못 쓰면 '검사 안 함 — 이유' 로 정직하게 적는다. 운영자 개인 PC 에서의 직접 검사는 시험지 0단계다.
- **공급망 한계**: 의존성 잠금은 정확한 버전만이고 배포 파일(wheel)의 해시는 없다(대신 설치된 파일 내용의 지문을 적는다). 묶음에는 네트워크를 쓸 수 있는 표준 모듈과 `publish/` 코드가 들어 있을 수 있다 — 화면은 그 길을 부르지 않는다는 것은 보안 수정 묶음의 시험이 지키는 사실이고 이 묶음은 그것을 대신 보장하지 않는다. 자세한 내용은 [`PACKAGE.md`](PACKAGE.md) §7·§10.

## 단일 실행 장치(`ui/single_instance.py`) — 보안 경계와 한계 (SINGLEWIN, 설계 D-471 이후)

같은 윈도 로그온·같은 데이터 폴더로 앱을 두 번 열면 새 창 없이 열려 있는 창을 앞으로 가져오는 장치다. 새로 생기는 바깥과의 접점은 **윈도 커널의 이름 있는 뮤텍스 하나와 창 목록 읽기**뿐이다.

- **네트워크 0·하위 프로세스 0·파일 쓰기 0**: 소켓·HTTP·`subprocess`·`os.system`·`os.startfile`·파일 쓰기가 없다. Qt 도 가져오지 않는다(그래서 묶음에 Qt 네트워크 모듈이 딸려 오지 않는다). `ctypes` 는 윈도 길 안(`Win32Api`)에서만 가져오고 로컬 호출(`CreateMutexW`·`EnumWindows` 등)뿐이다 — 자격 증명 관리자 호출과 같은 종류다. 시험이 소스를 AST 로 읽어 가져오기·호출을 못박는다(`tests/test_single_instance.py`).
- **관리자 권한 0**: 뮤텍스 이름은 윈도 로그온 세션별 `Local` 이름 공간이라 일반 사용자 권한으로 만들 수 있다(`Global` 은 쓰지 않는다 — 관리자 권한 문제와 다른 계정 사이 충돌 때문이다). 실행 수준 `asInvoker` 는 그대로다.
- **키·비밀·경로가 나오지 않는다**: 뮤텍스 이름은 데이터 폴더 경로의 SHA-256 앞 16자리라 경로가 이름에 드러나지 않고, 안내 상자는 고정 문장이며, 장치가 남기는 이유(`last_note()`)는 종류 이름뿐이다. 환경 변수는 `CHANCEBLOG_DESKTOP_DATA`·`LOCALAPPDATA` 두 개만 읽는다(`service/context.py` 와 같은 폴더 규칙).
- **엉뚱한 창을 건드리지 않는다**: 창을 앞으로 가져오기 전에 보이는 최상위 창이고 제목이 앱의 창 제목으로 시작하며 **같은 실행 파일 경로의 다른 프로세스가 가진** 것인지 확인한다(탐색기 창 같은 다른 프로그램의 창은 같은 제목이어도 건드리지 않는다). 응답 없는 창은 만지지 않는다.
- **실패하면 막지 않는다**: 뮤텍스를 만들 수 없거나(접근 거부 등) 호출 층을 열 수 없으면 장치를 끄고 앱을 연다 — 보안 기능이 아니라 편의 장치이므로 앱을 못 쓰게 만들지 않는다. 이미 열려 있음이 확인된 뒤에는 어떤 호출이 실패해도 새 창을 열지 않는다.
- **넘겨받기는 뮤텍스가 정말 비었을 때만**: 기다리는 사이 먼저 열려 있던 앱이 끝나(방금 닫고 곧바로 다시 연 경우) 뮤텍스가 비면 그것을 넘겨받아 평소처럼 연다. 만들기가 '이미 있음(오류 183)' 이거나 실패하면 넘겨받지 않고 계속 기다리거나 안내 상자로 간다 — 먼저 열려 있던 앱이 살아 있는 동안 두 번째 창이 생기는 길이 아니다.
- **한계**: 같은 세션의 다른 사용자(`runas`)가 같은 이름을 먼저 만들면 접근 거부로 장치가 꺼진다. 같은 계정의 다른 프로그램이 일부러 같은 이름을 선점하면 앱이 '이미 열려 있음' 으로 판정할 수 있다(같은 계정이면 앱을 막는 방법이 여럿이라 새 위험이 아니며, 안내 상자가 작업 관리자 안내를 보인다). 뮤텍스는 프로세스 사이의 '있다·없다' 만 알려 줄 뿐 데이터 보호는 하지 않는다 — 쓰기 보호는 그대로 서비스의 잠금과 원자적 저장이 한다.

## 오류 기록(작은 로그 파일, `security/errorlog.py`) — 보안 경계와 한계 (AP14, 설계 D-488)

앱이 처리하지 못한 오류가 나도 남는 기록이 없어 알리기 어렵던 것(창 없는 실행 파일에는 표준 오류가 없다)을 위해 **데이터 폴더 안에 작은 기록 파일**을 허용했다(운영자 확인 015 승인 9번 — 이슈 #195, 2026-11-13).

- **무엇을 남기나**: 한 줄 — 시각(UTC)·들어온 곳(`main`·`thread`·`unraisable`·`slot`·`qt`)·**오류 클래스 이름**·**코드 위치(파일 이름:줄, 가장 안쪽부터 최대 여섯)**. **오류 메시지 글·값·경로(파일 이름 앞의 폴더도)·키·토큰·글 본문은 남기지 않는다** — 메시지는 읽지도 않고, 이름과 위치도 좁은 글자표(영문·숫자·밑줄·점·붙임표)를 통과한 것만 줄에 들어간다. 완성한 줄은 공통 가림 규칙(`security/mask.py` 의 `mask`)을 한 번 더 거친다 — 이 모듈에는 새 가림 규칙이 없다. Qt 의 치명적(Critical·Fatal) 메시지는 종류·분류 이름·C++ 쪽 파일:줄(있을 때)만 남기고 메시지 글은 읽지 않는다.
- **어디에, 언제**: 앱이 쓰는 데이터 폴더 해석 함수(`Workspace.resolve`)가 정한 폴더의 `logs/errors.log` 이고, 돌려쓰기 파일 `errors.log.1`·`errors.log.2` 와 합쳐 **256 KB 짜리 세 개**를 넘지 않는다(가장 오래된 것부터 사라진다). **첫 오류가 났을 때 처음 만든다** — 앱을 켜기만 해서는 폴더도 파일도 생기지 않는다. 쓰기·폴더 만들기·이름 바꾸기·폴더 해석이 실패하면 예외를 삼키고 그 줄만 버린다(앱 동작은 그대로이고 한도를 넘겨 쓰지 않는다). 돌려쓰기는 **이름을 바꾸기만** 한다(먼저 `errors.log.1` → `errors.log.2`, 그다음 `errors.log` → `errors.log.1`) — 가장 오래된 `errors.log.2` 를 먼저 지우지 않고 이름 바꾸기가 덮어쓴다. 그래서 **막힌 단계에 따라 남는 모습이 다르다**: 첫 단계(`.1` → `.2`)가 막히면 옛 파일 셋은 한 글자도 바뀌지 않고, 첫 단계가 끝난 뒤 현재 파일 쪽(`errors.log` → `.1`)이 막히면(다른 프로그램이 현재 파일을 잡고 있을 때) `.2` 가 옛 `.1` 의 내용으로 바뀌어 있고(옛 `.2` 는 덮어쓰여 사라진다) `.1` 은 비며 현재 파일은 그대로다. 어느 쪽이든 그 줄은 버려지고(한도를 넘겨 쓰지 않는다) 다음 줄이 이어서 끝낸다. **정해진 1분 구간마다 30줄까지만** 쓴다(구간은 첫 줄이 쓰일 때 시작하고, 구간 경계에서는 짧은 시간에 더 나올 수 있다).
- **누가 켜나**: 화면(GUI) 진입점(`ui/launcher.main` 이 `boundary.arm_error_log` 를 부른다) 하나뿐이다. 명령줄과 예시 화면(`--sample`)은 켜지 않고, 공통 경계를 되돌리면 함께 꺼진다. `--sample` 없이 `launcher.main` 을 끝까지 부르는 기존 시험은 켜진다 — 그래도 켜기만으로는 폴더 해석도 파일 만들기도 하지 않고(첫 오류가 날 때만 만든다) 시험의 뒷정리(`uninstall_boundary`)가 끈다(기본 데이터 폴더에는 아무것도 생기지 않는다). 이 길을 새로 시험할 때는 `--data-dir` 에 임시 폴더를 준다. 처리하지 못한 예외 훅 셋·화면의 한 줄 기록(`report_unexpected`)·Qt 메시지 핸들러가 이 기록으로 이어진다.
- **하지 않는 것**: 충돌 덤프(`faulthandler`·미니덤프)는 만들지 않는다 — 가림을 걸 수 없는 글이 파일에 들어갈 수 있기 때문이다(그래서 네이티브 충돌 자체는 기록되지 않는다 — 한계). 네트워크·외부 쓰기·하위 프로세스는 0 이고 표준 출력·표준 오류도 쓰지 않는다. **백업에 넣지 않고**(`security/backup_note.py` 의 담지 않는 것에 `logs/`) 복원도 건드리지 않는다.
- **알릴 때**: 문제를 알릴 때 `logs/errors.log` 의 마지막 몇 줄을 복사해 붙이면 된다(오류 이름과 코드 위치뿐이라 글·키·경로가 없다). 파일은 사용자 데이터 폴더 안에 있어 지워도 된다 — 다음 오류가 나면 다시 생긴다.
- **한계(기록이 닿지 않는 길)**: ① 묶음 실행 파일의 **시작 실패** — `packaging/gui_entry.py` 의 `start_gui` 가 예외를 잡아 메시지 상자로 오류 종류 이름만 알리고 끝내므로 처리하지 못한 예외 훅까지 오지 않아 `errors.log` 에 남지 않는다 ② **작업 스레드의 오류** — `ui/core/jobs.py` 의 작업 실행(`Job._run`)이 어떤 예외든 잡아 '작업 실패' 안내와 오류 이름으로 바꾸고 화면 콜백의 예외(`Job._emit`)는 이름만 기억하고 삼키므로 훅까지 올라오지 않는다 ③ **네이티브 충돌**(프로그램이 갑자기 꺼짐)은 충돌 덤프를 만들지 않으므로 기록되지 않는다 ④ **데이터 폴더를 풀지 못하면** 그 줄을 버린다. 이 길들에 기록을 잇는 일은 AP14 가 바꾸는 목록 밖의 코드 변경이라 하지 않았다(결정 D-488 의 후속 항목). 이럴 때 문제를 알리려면 메시지 상자·화면에 나온 오류 종류 이름과 안내 문장을 그대로 알린다.
- **시험**: `tests/test_security_errorlog.py` — 처음 만들기·메시지가 한 글자도 안 남음·돌려쓰기와 세 파일·실패 삼키기·속도 제한·경계 연결·화면 진입점만 켬·백업 제외·소스 가져오기·문서·이름 글자표 전수(파일·클래스 이름은 전체 유니코드 U+0000 에서 U+10FFFF 를 이름의 앞·가운데에, Qt 분류 이름은 U+0001 에서 U+024F 를 앞·가운데·끝에 끼움)·가장 안쪽 여섯 위치(깊이 300 이상과 1만 단계가 넘는 추적도)·돌려쓰기가 막혔을 때(첫 단계가 막히면 옛 파일 셋이 그대로, 현재 파일 쪽이 막히면 `.2` 가 옛 `.1` 이 됨)·돌려쓰기 한도의 바이트 단위 경계·기본 속도 제한·**기록이 닿지 않는 길을 동작으로 확인**(기록을 켠 채 `start_gui` 와 작업 스레드를 실패시켜 `logs` 폴더가 안 생김 — 낱말 검사가 아니다)·문서에 거짓이 된 문장이 남지 않음.

## 참고 글 보관함(`service/references.py`) — 쓰는 곳이 하나 더 는다 (D-489·D-490)

사용자가 올려 둔 참고 글을 이 PC 의 사용자 데이터 폴더에 파일로 보관하고 목록·고치기·지우기를 하는 기능이다(운영자 요청 #174·#205). **새 쓰기 위치는 하나** — 사용자 데이터 폴더 아래 `references/`(글 하나당 `ref-번호.json` 한 파일)다. 새로 생기는 바깥과의 접점은 없다(네트워크·하위 프로세스·AI·표준 출력 0).

- **쓰는 곳 목록**: 위 §5 의 '화면에서 파일에 쓰는 곳은 … 네 곳이다' 에 이 묶음의 참고 글 보관함 대화상자가 **한 곳 더해진다**(블로그 관리·Seed 관리·주제 후보·키 넣기 + 저장한 초안(§10) + 참고 글 보관함 — 새로 더해지는 곳만 `references/` 이고 나머지의 쓰는 곳은 그대로다). 그 문장은 내 글 문체 참고값 보기(N-3a)의 시험이 글자 그대로 못박고 있어 이 묶음도 고치지 않았다 — 목록 정리는 병합 뒤 한 번에 한다. 서비스에서 이 폴더에 쓰는 길은 `service/references.py` 안의 `write_json`(기존 원자적 저장) 호출과 `delete_reference` 의 `unlink`(그 번호의 임시 파일들과 글 파일 하나를 지우는 두 호출)뿐이고, `tests/test_service_safety.py` 의 허용 목록에는 `(references.py, delete_reference)` 의 `unlink` 한 줄만 더했다. 새 시험 `tests/test_service_references.py` 의 소스 규칙이 이 둘 말고 파일을 바꾸는 호출이 없음을 못박는다. 화면 코드(`ui/`)에는 파일을 쓰거나 지우는 호출이 없다.
- **사용자가 준 글자는 경로가 되지 않는다**: 글 번호는 앱이 만든 영문 소문자·숫자 8자(운영체제의 무작위 값)이고 파일 이름은 `ref-` 와 번호와 `.json` 뿐이다. 열기·고치기·지우기가 받은 번호도 `[a-z0-9]{8}` 모양이 아니면 파일을 만지지 않고 거절한다(`../`·경로 구분자·NUL·줄 바꿈·전각 글자·대문자·긴 글 모두). 제목·본문·고른 파일 이름은 파일 안의 글이나 제목 글자일 뿐 경로에 쓰이지 않는다. 보관함 폴더가 링크(윈도의 정션 포함)이거나 폴더가 아니면 목록·추가·열기·고치기·지우기 모두 거절한다(링크 너머로는 읽지도 쓰지도 지우지도 않는다 — D-489 ④, 진짜 정션·링크로 시험한다).
- **파일에서 올리기는 기존 읽기 규칙 그대로**: `own_posts.read_own_files`(txt·md·2MB·링크·네트워크 위치·글자표·빈 글)를 그대로 부르고 새 규칙을 만들지 않았다. 고른 원본 파일은 읽기만 하고 바꾸지 않는다.

- **본문은 편집 칸이 바꾸는 것만 통일해 저장한다**(D-489 ③): 줄 끝 CRLF·CR·U+2028·U+2029 는 LF 로, 맨 앞의 BOM 은 떼고, NBSP 는 보통 공백으로 — 그 밖의 글자는 하나도 안 바꾼다(실제 Qt 편집 칸이 바꾸는 목록과 같다). 그래서 저장한 글이 곧 화면의 글이다. 

- **저장 직전에 키·토큰 모양을 검사한다**(D-489 ⑫, `security/scan.py` — 초안 저장·백업과 같은 검사기, 제목·본문): 찾으면 아무것도 쓰지 않고 위치(칸·줄)와 종류만 알린다. 읽기(목록·열기)는 검사하지 않는다.
- **저장은 원자적이고 지우기는 정확하다**: 쓰는 일은 기존 `context.write_json`(임시 파일에 다 쓰고 디스크에 내려보낸 뒤 이름을 바꿔 넣는다)이라 쓰다 멈추거나 전원이 나가도 옛 파일이 그대로이고 반쯤 쓴 글이 글 자리를 차지하지 않는다. 임시 파일 이름은 쓸 때마다 다르다(`ref-번호.json.프로세스번호-무작위.tmp`) — 두 프로세스가 같은 글을 동시에 고쳐도 서로의 임시 파일을 덮지 않아 글 파일이 깨지지 않고 마지막 쓰기가 이긴다. 쓰다 실패하면 임시 파일을 지운다. 쓰다 **프로세스가 죽거나 전원이 나가면** 임시 파일이 남을 수 있다 — 안에 새 본문이 평문으로 들어 있고 목록·개수에는 안 잡히며, 그 글을 지울 때 함께 지운다(앱이 시작할 때 오래된 임시 파일을 치우지는 않는다). 지우기는 확인(`confirmed=True`)이 있어야 하고 번호가 정한 글 파일 하나와 그 번호의 임시 파일만 지운다(링크·폴더는 거절, 다른 글·다른 글의 임시 파일·다른 파일은 그대로, 임시 파일을 못 지우면 글 파일도 지우지 않는다). 화면의 삭제는 확인 줄 두 단계를 거친 뒤에만 서비스에 닿는다.
- **깨진 파일·큰 파일**: 읽을 수 없는 파일(JSON 불량·칸 모양 틀림·한도 초과·1MB 초과·링크)은 목록에서 건너뛰고 개수만 알린다 — 고치거나 지우거나 덮어쓰지 않는다. 한도는 50개·제목 80자·본문 100,000자이고 넘으면 잘라 쓰지 않고 거절한다.
- **글·제목·경로를 되풀이하지 않는다**: 오류는 기존 `CONTENT_INVALID`·`CONTENT_NOT_FOUND`·`CONFIRMATION_REQUIRED`·`FILE_WRITE_FAILED`·`DISK_FULL`(새 오류 코드 0)의 고정 문장이다. 쓰기 실패 문장의 경로 자리에는 실제 경로 대신 고정 이름 `참고 글 보관함 폴더` 를 쓰고, 거절 직전에 이 모듈의 틀이 쥔 글을 비워 호출 흔적이 글을 붙들지 않게 한다(시험이 오류의 호출 흔적이 붙든 지역 변수까지 훑는다). 화면 쪽 어댑터도 오류에서 고정 문장만 꺼내고 호출 흔적을 끊는다. 글 본문은 열어 둔 편집 칸 밖의 상태·오류·로그에 남지 않는다.
- **AI·네트워크·백업**: 글을 AI 나 네트워크로 넘기는 길이 없다. 전체 백업(§9)에는 **담지 않는다**(첫 판의 기본값 — 백업 형식·목록 파일의 모양은 그대로이고, 시험이 진짜 백업·복원으로 보관함의 파일·글이 백업에 없고 복원이 보관함을 건드리지 않음을 본다). 백업 카드의 '담지 않는 것' 목록(아홉 줄)은 줄 수와 이름을 그대로 두고 아홉째 줄(`외부에서 가져온 원본 자료`)의 이유 문장만 고쳐 보관함의 `references/` 폴더가 백업에 없으니 PC 를 바꿀 때 직접 옮기라고 말한다(옛 문장은 보관함이 생긴 뒤 거짓이었다 — D-492 ⑤).
- **알려 둔 한계**: 보관함은 글을 암호화하지 않는다 — 사용자 데이터 폴더 안의 평문 JSON 이라 그 폴더를 읽을 수 있는 사람(같은 PC 의 같은 윈도 계정으로 도는 다른 프로그램 포함)은 읽는다. 키·토큰 모양 검사는 여섯 가지 모양뿐이라 다른 모양의 비밀은 못 찾는다(D-489 ⑫). 같은 글의 동시 저장을 막는 잠금이 없다(같은 윈도 계정·같은 데이터 폴더에서는 앱이 한 번에 하나만 열린다 — D-471; 두 프로세스가 동시에 고치면 마지막 쓰기가 이기고 먼저 쓴 것은 사라지지만 파일이 깨지지는 않는다). 프로세스가 죽을 때 남은 임시 파일은 그 글을 지울 때까지 폴더에 남는다. 지운 글은 되돌릴 수 없고 백업에도 없어 PC 를 바꿀 때는 `references/` 폴더를 직접 옮겨야 한다. Qt 화면은 offscreen 으로 띄워 확인했고 실제 윈도 렌더·한글 입력기·화면 읽기 프로그램은 운영자 PC 에서 확인해야 한다(`UI_VISUAL_QA.md` 16절).

## 사진 Manifest(`content/photo_manifest.py`·`service/photo_manifest.py`) — 쓰는 곳이 하나 더 는다 (D-496·D-497·D-499·D-501, 사진 연동 1·2·3단계)

초안 하나에 붙는 사진들의 목록(파일 위치·순서·종류·사용자가 확인한 정보)을 이 PC 의 사용자 데이터 폴더에 파일로 보관한다(운영자 요청 #206·#209·#212). **화면(2단계 — 사진 정리 창)과 초안 저장·열기·지우기·글 만들기·복사(3단계)에 연결했다. 백업과 사진 파일 옮기기·올리기에는 연결하지 않았다.** **새 쓰기 위치는 하나** — 사용자 데이터 폴더 아래 `photo-manifests/`(초안 하나당 `<초안 번호>.json` 한 파일)다.

- **사진 자체는 다루지 않는다**: 원본 사진을 복사·저장하지 않으며 1단계 코드는 열지도 않는다(파일이 그 자리에 있는지는 `lstat` 으로만 본다). 2단계 화면은 이미지 읽기 도구(`imagecheck` — 읽기 전용)로 사진 파일을 **읽는다**: 크기·형식 확인과 메모리에서만 만드는 작은 미리보기뿐이고 파일을 쓰거나 복사하거나 바꾸지 않는다(시험이 진짜 사진 파일의 바이트·폴더 목록이 그대로임을 본다). EXIF·촬영 위치·기기·썸네일을 저장하지 않는다 — 사진 한 장의 칸은 운영자가 정한 열네 개뿐이고 다른 칸이 든 파일은 읽지 않는다. 사진을 PC 밖으로 보내는 길·AI·네트워크·하위 프로세스가 없다.
- **쓰는 곳 목록**: 새 쓰기는 `context.write_json`(임시 파일 → 디스크에 내려보냄 → 이름 바꾸기)·깨진 파일을 옆으로 옮기는 `context.keep_bad_copy`·지우는 `delete_manifest` 의 `unlink` 하나와 3단계의 되돌릴 사본 셋(`trash_manifest`·`restore_manifest` 의 `os.replace` 한 번씩, `clear_trash` 의 `unlink` 하나)이고, 허용 목록(`tests/test_service_safety.py`)에 (파일, 함수, 이유)로 올라 있다. 지우기·옮기기는 확인(`confirmed=True`)이 있어야 하고 번호가 정한 파일 하나와 그 번호의 사본·임시 파일만 건드린다.
- **사용자가 준 글자는 경로가 되지 않는다**: 파일 이름이 되는 것은 저장한 초안의 번호 모양(`dd-` + 16진수 20자)뿐이다. 사진 파일 위치(`local_path`)는 절대 경로만 받고(인터넷 주소·네트워크 위치·`..`·와일드카드·장치 이름·대체 스트림·260자 초과 거절 — `own_posts` 의 경로 모양 규칙을 바탕으로 하되 사진 쪽이 더 엄격하다: 서식·사용자 지정·줄/문단 구분 글자도 거절하고(`own_posts` 는 제어 문자만) 길이는 260자(`own_posts` 는 4096자)) 지원 확장자는 `ui/core/imagerules.py` 의 것을 읽는다.
- **경로·글이 새지 않는다**: `local_path` 는 윈도 사용자 이름이 들 수 있어 초안으로 보내는 정보(`draft_inputs`)·오류·`repr`·로그에 나오지 않는다. 초안으로 가는 것은 **확정한 사진의 확인한 것뿐**이다. 오류는 기존 `CONTENT_INVALID`·`CONTENT_NOT_FOUND`·`CONFIRMATION_REQUIRED`·`FILE_WRITE_FAILED`·`DISK_FULL`(새 오류 코드 0)의 고정 문장이고, 쓰기 실패 문장의 경로 자리에는 실제 경로 대신 고정 이름 `사진 정보 폴더` 를 쓴다.
- **저장 직전에 키·토큰 모양을 검사한다**(`security/scan.py` — 초안 저장·백업과 같은 검사기, 경로와 모든 글칸): 찾으면 아무것도 쓰지 않고 폴더도 만들지 않으며 위치(사진 번호·칸)와 종류만 알린다. 글칸에는 입력 단계에서도 같은 검사(`security/mask` 포함)와 주민등록번호·카드 번호 모양 거절이 있다.
- **분석 결과는 기본으로 저장하지 않는다**: 나중의 로컬 분석 플러그인이 채울 `observed_objects`·`visible_text` 는 메모리에서만 쓰고 파일에는 빈 목록으로 쓴다(분석 방법 이름도 `manual` 로 쓴다 — `persist_analysis=True` 일 때만 예외). 확인하기 전 항목은 초안으로 가지 않고, 관찰한 대상에서 얼굴·관계·감정·신원을 짐작한 말은 받지 않는다(낱말 목록 — 완전하지 않다).
- **깨진 파일·링크**: 읽을 수 없는 파일은 `broken` 으로만 알리고 열지도 고치지도 않는다(덮어쓰려면 `replace_broken=True` 이고 그때도 `.bak` 으로 옮겨 둔다). 지금 열지 못한 파일(윈도의 공유 위반 등)은 짧게 두 번 더 해 본 뒤 `unreadable` 로 따로 알리고 그 위에는 쓰지 않는다. `orphans` 는 잘못된 초안 번호 목록을 거절한다(fail closed). 폴더가 링크이거나 폴더가 아니면 모든 길을 거절한다. 사진 파일 확인은 경로 위의 모든 폴더가 링크가 아닌지, 이 PC 에 내려받은 파일인지(클라우드 '오프라인' 표시는 읽으면 내려받기가 일어나므로 거절)를 본다.
- **백업**: 전체 백업(§9)에는 **담지 않는다**(1단계의 기본값 — 백업 형식은 그대로 — 되돌릴 사본도 같은 폴더라 백업 밖이다). 저장한 초안을 지우면 사진 정보 파일은 완전히 지워지지 않고 초안마다 한 벌뿐인 되돌릴 사본(`<초안 번호>.json.trash` — 운영자 확인 024)으로 옮겨진다. 사본은 `list`·`orphans` 가 정상 파일로 읽지 않고, 되살린 초안에서 `사진 정보 되돌리기`(사본이 멀쩡할 때만, 이미 사진 정보가 있으면 덮어쓰지 않는다)·`사진 정보 사본 비우기`(확인창을 거쳐 사본 하나만)로 다룬다. **사진 파일은 어떤 경우에도 건드리지 않는다.**
- **사진 정리 화면(2단계, D-499)이 새로 읽는 것**: 사진 파일을 이미지 읽기 도구로 **읽기만** 한다(크기·형식·메모리의 작은 미리보기) — 파일을 쓰거나 지우거나 복사하거나 옮기지 않고 어디로도 보내지 않으며(네트워크·AI 0 — 이 화면 쪽은 하위 프로세스도 0이다. 글자 읽기 추가 기능이 켜졌을 때만 아래 '글자 읽기 작업자' 절의 별도 작업자 하나가 이 PC 안에서 계산한다) 미리보기 그림은 메모리에서만 만들고 닫으면 버린다. PNG 의 가로×세로가 6천만 화소를 넘으면 본문을 풀기 전(헤더에서 읽은 크기)에 막는다. 사진을 넣을 때·다시 찾을 때도 이미지를 읽기 전에 경로 위 폴더마다 `lstat` 으로 링크·정션·폴더·내려받지 않은 파일·없음을 거른다(`inspect_photo` — 목록 점검과 같은 코드) — 걸린 파일은 읽지 않는다. 사진을 수천 개 골라도 한도(30장)가 찬 뒤의 파일은 읽지도 판정하지도 않고 개수만 센다. 점검(lstat)과 이미지 읽기 사이에는 틈이 있다 — 점검이 끝난 뒤 같은 이름이 링크로 바뀌면 이미지 읽기 도구가 따라갈 수 있다(읽기만 하고 저장·전송이 없으며 다음 점검에서 `링크라서 쓰지 않아요` 로 바뀐다 — 파일 핸들을 점검 때 열어 쓰려면 이미지 읽기가 경로를 받는 구조라 이번 범위 밖, 검증 S U-3). **경로는 화면 뷰모델·오류·로그 어디에도 없고**(줄에는 폴더 없는 파일 이름만 보이고 못 넣은 파일도 이름과 고정 이유뿐) 읽기 도구가 낸 오류의 글도 화면에 되풀이하지 않는다. 한도를 넘기거나 검사에 걸려 반영하지 못한 글은 입력 칸에만 있고 컨트롤러의 어떤 상태·오류에도 두지 않는다. 소스에서 사진을 말하는 파일은 시험이 정해진 목록으로 못박는다(몰래 늘면 걸린다).
- **3단계(D-501)가 새로 하는 것**: ① 초안을 저장할 때 사진 정보도 쓴다(`save_manifest` — 위의 쓰기 규칙 그대로, 초안 먼저·사진 정보 나중이고 사진 정보 실패는 초안 저장을 되돌리지 않고 고정 문장으로만 알린다) ② 초안을 지울 때 사본으로 옮긴다(위) ③ 본문에 넣을 때는 **확정한 사진의 사용자 글만** 쓰고(`DraftPhoto` — 경로·파일 이름·번호 문자열 없음) 마지막 관문(`_final_guard` — 비밀 모양 검사)이 그대로 돈다. 사용자 글은 고치지 않고 '지어내지 않기' 검사에서 빼되 입력할 때 이미 '결과를 약속하는 표현'·키 모양·개인 번호 검사를 거쳤다 ④ 복사할 때 정확한 `{{사진 N}}` 을 `[이미지 N]` 으로 바꾸는 일은 **메모리의 글만** 바꾼다(파일·클립보드 외 어디에도 쓰지 않는다) ⑤ 복사 전 확인창이 **번호와 짧은 파일 이름**(폴더 없음)을 보인다 — 파일 이름은 이미 사진 정리 창에 보이는 것이고 비밀 모양은 가려서 보인다. 네트워크·하위 프로세스·새 의존성·새 오류 코드는 0 이다.
- **알려 둔 한계**: 암호화하지 않은 평문 JSON 이라 경로에 든 윈도 사용자 이름을 그 폴더를 읽을 수 있는 사람이 읽는다 · 되돌릴 사본(`photo-manifests/<초안 번호>.json.trash`)은 전체 백업에 들지 않고 앱에서 지우는 길이 **같은 번호의 초안을 되살린 뒤의 `사진 정보 사본 비우기`** 뿐이다 — 되살릴 일이 없는 초안의 사본은 사용자 데이터 폴더에 평문(사진 경로에 윈도 사용자 이름이 있을 수 있다)으로 남는다(운영자 확인 024 가 '남김' 을 승인 — 화면 없는 청소 길은 다음 묶음에서 T3 요청으로 정한다) · 같은 초안의 동시 저장을 막는 잠금이 없다(앱은 한 번에 하나만 열린다 — 마지막 쓰기가 이기고 파일은 깨지지 않는다) · 하드 링크·다른 경로의 같은 파일은 알아보지 못한다 · 키·토큰 모양 검사는 여섯 가지뿐이다.

## 조작된 백업의 구조 검사와 올리기 직전 관문의 비밀 모양 목록(L8 — 설계 D-554–D-558)

운영자 승인(확인 015 의 L8 묶음)으로 두 가지를 더했다. 둘 다 **검사를 더하기만** 했고 기존 검사와 시험의 단언은 약해지지 않았다. 백업 형식·저장 형식·설정 칸은 바뀌지 않았다.

### 백업을 되돌릴 때 보관함의 구조를 본다(F074 — D-554·D-555)

**위협**: 복원은 보관함 파일(`chanceblog.db`·`topic_engine.db`)을 SQLite 백업 방식으로 **통째 복사**한다. 예전 확인(이름표·판·점검·정해 둔 표의 열 이름)은 그 밖의 개체를 보지 않았다. 그래서 조작한 백업에 든 **트리거**(저장할 때마다 몰래 도는 문장 — 글을 바꾸거나 지울 수 있다)·**뷰**(열 이름이 같으면 표 행세를 하고 `INSTEAD OF` 트리거로 쓰기를 가로챈다)·**모르는 표와 색인**(유일 색인 하나면 같은 제목의 글 저장이 모두 막힌다)이 그대로 들어왔다. 백업 목록 파일의 크기·해시는 같은 폴더 안의 값이라 조작한 사람이 다시 계산하면 맞는다 — 해시는 깨짐을 막을 뿐 조작을 막지 않는다. 탐침(트리거가 든 백업을 복원한 뒤 앱이 초안을 저장해 본 것)에서 옛 코드는 저장한 글이 바뀌었고 고친 코드는 복원을 거절했다.

**고친 것**: `content/schema_guard.py` 의 순수 읽기 검사가 되돌릴 파일의 개체 목록(`sqlite_master`)에서 **앱이 만들지 않는 개체**를 찾는다. 기준은 손으로 적은 목록이 아니라 그 보관함이 새 파일을 만들 때 실행하는 문장(`SCHEMA`)을 메모리에서 한 번 실행해 얻은 개체 목록이라 판이 늘어도 같이 맞는다. 되돌릴 파일의 개체는 그 부분집합이어야 한다(옛 판의 백업은 표 몇 개가 없을 뿐이라 부분집합이다). 찾는 것은 고정 이름 열 가지다: 트리거 · 뷰 · 가상 표(전문 검색 같은 것) · 모르는 표 · 모르는 색인(유일·일부 행·식 색인 포함) · 정해 둔 색인과 다른 모양(같은 이름을 열·유일·일부 행 조건을 바꿔 쓴 것) · 숨은 열(`table_info` 가 보여 주지 않는 생성 열) · 모르는 종류의 개체 · 글자 인코딩이 UTF-8 이 아님(구조가 정상인 UTF-16 보관함은 통째 복사 뒤에야 SQLite 가 실패해 지금 보관함이 비워진 채 남았다 — 독립 검증 S 의 SP-1, 시작점에서도 같은 결함) · 너무 많은 개체(128개 초과). SQLite 가 스스로 만드는 통계 표(`sqlite_stat1`–`4`·`sqlite_sequence`)와 기본 키·유일 제약이 만드는 기본 색인(정본에 있는 이름뿐)은 정상으로 본다.

**어디서 부르나(복원 길 셋이 모두 막힌다)**: ① 전체 백업 복원(`service/backup_flow.py`) — 내용을 읽기 전에 구조부터 보고(`FULL_BACKUP_INVALID` 의 이유 `structure`: 안의 보관함에 앱이 만들지 않는 구조(트리거·뷰·모르는 표 같은 것)가 들어 있어요), 화면에는 이유 한 줄이 붙으며(`backup_invalid_structure`), 바꾼 뒤 확인에서 한 번 더 본다(복사하는 사이 원본이 바뀌었어도 걸러 안전 사본으로 원래대로 돌린다) ② 옛 `restore` 명령(`Store.restore_from`) ③ 주제 엔진 복원(`topicdb/backup.read_backup` 의 확인과 `EngineFile.restore_from`). 낮은 층의 `restore_from` 두 곳이 통째 복사 직전에 막으므로 어느 길로 와도 같다. 거절은 **바꾸기 전**이다(지금 데이터·안전 사본 폴더·복원 중 표지·잠금이 그대로 — 시험이 폴더 지문으로 확인한다). 거절 문구와 오류 세부에는 조작한 파일의 개체 이름·SQL 글이 없고 고정된 종류 이름뿐이다(카나리아 시험). 이 검사를 끄는 인자·설정은 없다(시험이 함수 서명을 못박는다).

**바뀌지 않은 것**: 백업을 **만드는** 쪽(지금 파일을 그대로 담는다 — 백업을 만들 때 지금 열려 있는 보관함은 이 검사를 받지 않는다. 복원을 시작할 때는 받는다 — 아래 L8b 절)·목록 읽기·보관함 열기·JSON(그쪽은 엄격한 읽기가 칸 모양과 크기를 이미 본다). 정상 백업은 한 글자도 다르게 복원되지 않는다 — 복원 뒤 보관함은 덤프와 개체 목록(종류·이름·딸린 표·SQL 글)이 백업과 같고, 안전 사본으로의 되돌리기와 옛 판(판 1) 백업도 그대로 된다.

**설정의 '연결한 폴더' 경로도 본다(같은 길의 다른 구멍 — D-554)**: 복원이 끝나면 앱은 설정의 `repo_path` 가 폴더인지 알아보려고 열어 보는데(복원 직후의 안내·이후의 점검) 그 글은 어떤 글이든 받았다. 조작한 백업이 **네트워크 경로(UNC)** 를 넣으면 이 PC 가 그 서버에 접속하면서 윈도 로그인 정보를 보낼 수 있다. 그래서 되돌릴 설정의 그 글은 **보통 폴더 경로 모양**이어야 한다(`service/backup_flow._repo_path_problem`): 빈 글·드라이브 경로·상대 경로·홈 폴더 약식 경로는 받고, 네트워크 경로(역슬래시나 슬래시 둘로 시작하는 서버 경로·확장·장치 경로)·주소(`://`)·제어 문자(보이지 않는 글자 포함)·1024자를 넘는 글은 **바꾸기 전에** 거절한다(`FULL_BACKUP_INVALID` 의 이유 `content`). 오류 세부에는 고정 낱말(`network`·`url`·`control`·`length`)뿐이고 경로 글은 없으며, 앱은 그 경로를 열어 보지도 않는다(시험이 경로 확인 호출을 감시한다). 백업을 만드는 쪽은 그대로다.

**한계(사실대로)**: ① 표 정의의 제약은 거의 보지 않는다 — 실제로 보는 것은 열 이름(기존 모양 확인)과 색인(정본에 없는 기본 색인·유일 색인, 같은 이름 색인의 열·유일·일부 행 모양)뿐이다. 기본 키가 빠졌거나 바뀐 표·`COLLATE`·`ON CONFLICT`·`CHECK`·외래 키가 붙은 표는 못 본다 — 그런 표는 트리거 없이도 새 글 만들기·초안 저장을 막거나 id 를 합칠 수 있다(복구는 다른 백업으로 다시 복원, 독립 검증 S 의 SP-2) ② 행의 값은 이 검사가 아니라 기존의 엄격한 읽기(`check()`)와 키 모양 훑기가 본다(저장한 초안·판 기록 행은 `check()` 가 읽지 않아 읽을 때 `DRAFT_CORRUPT` 로 걸린다). 보관함 파일의 크기 상한은 이 묶음에서 정하지 않았다 ③ 사용자가 앱 밖의 도구로 자기 보관함에 뷰·트리거를 직접 만들면 그 보관함의 백업은 (지금 파일을 그대로 담으므로) 만들어지지만 복원은 이 검사가 거절한다 — 앱이 쓰지 않는 개체를 보관함에 두지 않는 것이 규칙이다 ④ 복원이 도중에 실패해 안전 사본으로 되돌릴 때도, 복원이 끝난 뒤 사용자가 '복원 직전 사본으로 되돌리기' 를 눌러도 같은 검사를 받는다 — 안전 사본은 지금 파일을 그대로 담으므로 앱 밖의 도구로 보관함에 뷰·색인을 둔 사용자의 사본에는 그 개체가 있어 되돌리기가 거절될 수 있었다(자료는 사본 폴더의 `chanceblog.db` 에 그대로 있었다 — 독립 검증 S 의 SP-5·Q 의 QP-1). **이제 복원은 지금 보관함에 그런 개체가 있으면 시작하지 않으므로 이 경우는 생기지 않는다**(그 개체를 지운 뒤 복원한다 — 이 문서 아래 'L8b' 절). 옛 `restore` 명령과 `topics restore` 에는 그 시작 검사가 없다 ⑤ 확인과 복사 사이에 원본 파일이 바뀌는 경쟁은 바꾼 뒤 확인이 걸러 되돌리지만, 같은 사용자가 복원하는 바로 그 순간에 파일을 바꿀 수 있는 악의적 프로그램은 막지 못한다(백업 폴더를 읽고 쓸 수 있는 프로그램은 데이터 폴더도 쓸 수 있다) ⑥ 연결한 폴더를 네트워크 경로로 쓰는 사용자는 자기 백업을 복원할 수 없다(복원 전체가 거절된다) — 개인 PC 의 로컬 폴더가 이 앱의 전제다 ⑦ 새 판이 더한 표는 '앱이 만들지 않는 구조' 가 아니라 '더 새로운 프로그램' 으로 알린다(되돌릴 백업의 판 번호가 이 앱보다 크면 구조 확인을 미루고 이어지는 내용 확인이 거절한다).

## 글자 읽기 작업자(`ui/ocr_adapter.py`·`service/ocr_addon.py`·`ocr_addon/`) — 하위 프로세스를 띄우는 곳이 하나 더 는다 (D-512, 사진 글자 읽기 b 단계 1라운드, 운영자 확인 026 ②·028 ②)

사진 속 글자를 **이 PC 안에서만** 읽는 선택 기능이다. 추가 도구(작업자 프로그램)를 앱 본체와 따로 설치해야 하고, 소스 상수 `LOCAL_OCR`(기본 False)가 꺼져 있는 이 빌드에서는 코드가 있어도 작업자를 한 번도 띄우지 않는다. 켜는 것은 소스 한 줄을 고치는 별도 변경이고 운영자 승인이 따로 든다.
- **바뀐 안전 규칙(보안 정책 변경 — 운영자 승인 범위 안, 감시 이름을 늘리는 방향으로만)**: ① 바깥과 닿는 곳의 허용 목록에 `ui/ocr_adapter.py` 의 `subprocess` 한 줄을 더했다(이유: 이 PC 의 글자 읽기 작업자를 띄우는 유일한 곳). ② '바깥에 쓰는 곳은 하나' 단언을 '바깥에 쓰는 곳 하나(`publish/gitrepo.py`) + 이 PC 안 계산 작업자 하나'로 고쳤다 — 하위 프로세스·소켓·웹 모듈이 허용 목록에 이 둘 말고는 없고 네트워크 모듈은 어느 허용에도 없다는 단언을 함께 건다.
  ③ 감시 이름을 늘렸다: `QProcess`·`multiprocessing`·`concurrent.futures.ProcessPoolExecutor`·`os.posix_spawn`(예전 목록에는 `QProcess` 가 없어서 새 코드가 그 길로 시험을 통과할 틈이 있었다). ④ `capabilities.py` 에 `LOCAL_OCR = False`·`local_ocr_enabled()`·`require_local_ocr()` — 외부 쓰기 관문과 같은 모양이고 설정·환경 변수·명령줄·화면에 켜는 길이 없다(시험만 patch 로 켠다).
  ⑤ 본체 묶음 자가 점검(`packaging/gui_entry.py`)은 `LOCAL_OCR` 을 실패 조건이 아닌 정보 줄로만 알린다. ⑥ 동적 막이(`tests/outgoing_support.py`)도 `posix_spawn` 을 감시한다.
- **작업자를 지키는 겹**: 작업자를 띄우는 길은 `_launch` 하나이고 첫 문장이 `require_local_ocr` 다(이 파일의 다른 하위 프로세스 호출은 시간 초과·취소 때 자식까지 끄는 `kill_tree` 의 `taskkill` 하나뿐이고, 이름만이 아니라 윈도 시스템 폴더의 절대 경로로 부른다 — D-586). 인자는 고정이고 셸이 없다. 윈도에서는 창이 안 뜨고 낮은 우선순위로 띄우며 Job 개체(`KILL_ON_JOB_CLOSE` + 프로세스 메모리 1GB)에 넣어 앱이 죽어도 남지 않게 한다. 환경 변수는 부모 것을 넘기지 않고 새로 짠다(PROXY 가 든 이름은 닫힌 로컬 포트로, NO_PROXY 는 없애고, 오프라인·텔레메트리 끔 값, 전용 임시 폴더, 시스템 폴더만 든 PATH).
  요청은 머리 한 줄과 픽셀 바이트뿐이고 사진 경로·파일 이름·사진 번호·종류·메모·`Exif` 가 들어갈 자리가 없다(시험이 작업자가 받은 바이트를 가로채 본다). 응답은 모두 데이터로만 보고 알려진 칸·형식·한도·요청 번호가 어긋나면 응답 전체를 버리고 작업자를 끝낸다. 표준 오류는 비우기만 한다. 준비 150초·사진 90초를 넘기거나 취소 뒤 3초 안에 못 끝내면 프로세스 트리를 끈다.
  연속 실패 3번이면 이번 실행 동안 끄고, 네트워크 시도 차단 보고·약속 위반·시작 막힘·도구 이상은 한 번에 끈다. 읽은 줄은 확인 전 후보일 뿐이고(저장하지 않는다) 기존 입구 검사(`check_text`·`set_analysis`)를 다시 거친다.
- **추가 도구 확인(`service/ocr_addon.py`)**: 폴더를 읽기만 해서 파일 목록·크기·SHA-256 을 확인하고, **앱에 박은** 모델 둘·글자 사전의 해시가 그 셋의 신뢰의 뿌리다(정보 파일과 모델을 함께 바꿔도 통과하지 못한다). 띄우기 전에 늘 해시까지 확인한다. 작업자 실행 파일과 DLL 은 앱 소스에 박혀 있지 않고 정보 파일이 스스로 적은 해시와만 견준다 — 아래 'OCR-S1 권고 처리' 절의 R1.
- **알려 둔 한계**: 네트워크 0의 파이썬 가드(`ocr_addon/netguard.py`)는 파이썬 소켓과 `_socket` 을 곧바로 쓰는 호출(감사 훅 한 겹, D-587)만 본다. 네이티브가 직접 여는 연결(윈도 기본 asyncio 의 연결 포함 — 아래 '글자 읽기 안전 감사' 절의 R5 남은 한계)은 빌드의 가져오기 표 점검과 운영자의 비행기 모드 시험이 보완한다(빌드 흐름은 다음 단계). Job 개체는 프로세스를 띄운 뒤에 넣으므로 아주 짧은 틈이 있다(트리 종료와 유휴 종료가 따로 있다). 파이썬 객체의 수명은 메모리 지움을 보증하지 못한다.

## 글자 읽기 작업자 — 라운드 2·3 보강(D-526, 앱 CI 조각 2·3 실패 고침·안전 시험 보강과 독립 검증 S·Q 반영)

앱 CI 가 조각 2·3 에서 실패한 것을 고치고 안전 시험을 보강했다. 허용을 넓힌 곳은 셋이고 시험의 취지를 약하게 만든 곳은 없다: 서비스의 읽기 전용 열기(`READ_OPENS`)와 화면 코드의 임시 폴더 지우기 호출은 **(파일, 함수) 단위**, 어댑터 파일의 `subprocess` 가져오기 허용(`test_source_rules_outgoing` 의 `ALLOWED`)은 **파일 단위**다. 파일 단위 허용 안에서는 감시 이름(Popen·run·call·check_* 와 이번에 더한 getoutput·getstatusoutput) 밖의 길이 다른 규칙에 안 걸리므로, 아래 라운드 3 의 닫힌 집합 시험이 이 파일이 하위 프로세스에 닿는 길을 따로 못박는다.
- **CI 실패와 고침**: ① `tests/test_service_safety.py` — 서비스 코드가 파일을 여는 곳(`READ_OPENS`)에 `service/ocr_addon.py` 의 `_open_read` 한 함수를 더했다(열기 모드는 글자 `rb`, 몸통은 `return open(path, 'rb')` 한 줄뿐임을 소스에서 확인 — 허용 +1). 같은 시험에 어댑터의 파일 시스템 사용을 (함수) 단위로 못박는 `OcrAdapterFileUseTest` 를 새로 더했다: 임시 폴더를 만드는 `_launch` 의 `mkdtemp` 와 지우는 `_remove_temp` 의 `rmtree` 둘뿐이고 그 밖의 열기·쓰기·지우기·`tempfile` 계열·목록 읽기는 걸린다(예전에는 이 파일이 어떤 시험에도 안 걸렸다).
  ② `tests/test_ui_blogs_core.py` 의 '화면 코드는 파일을 쓰지 않는다' 규칙에는 어댑터 `_remove_temp` 안의 `shutil.rmtree` **한 호출**만 허용을 더했다(그 함수 밖의 같은 호출·다른 쓰기 이름·다른 파일의 같은 호출은 그대로 걸린다).
- **어댑터 보강(`ui/ocr_adapter.py`)**: 나쁜 요청(크기 이름·너비·높이·픽셀 길이가 안 맞음, 긴 변 1600 초과)은 작업자를 띄우기 전에 경계에서 거절한다. 요청은 별도 스레드가 쓰고 읽는 쪽은 쓰기 전부터 사진 한 장의 시간을 센다 — 작업자가 안 읽어 파이프가 차도 시간 초과·취소·앱 종료가 지켜진다. 요청을 다 읽기도 전에 응답하면 약속 위반이다.
  시작 때 작업자가 준비 대신 보내는 오류 줄은 이름(`net_blocked`·`engine`)으로 알린다. 너무 깊게 겹친 JSON 등 응답을 읽다 난 모든 예외는 응답 전체를 버리는 약속 위반으로 본다(약속 사본 `loads_strict` 도 `RecursionError` 를 `ValueError` 로 바꿔 앱·작업자가 같게 거절한다). 해시 확인 함수가 터져도·임시 폴더를 못 만들어도 띄우지 않는다.
  유휴 확인은 읽는 중에 기다리지 않는다(화면 스레드의 타이머가 부른다). 작업 폴더는 작업자 폴더가 기본이고 환경 변수의 `PATH` 는 윈도 시스템 폴더 둘뿐이다(작업자 폴더의 DLL 이 먼저 잡히고 다른 프로그램의 DLL 이 섞이지 않게 — 설계 3-6 의 1겹).
  앱이 죽으면 Job 개체(`KILL_ON_JOB_CLOSE`)가 작업자를 끝내고, Job 개체에 못 넣었어도 표준 입력이 닫혀 작업자가 입력 끝으로 끝난다(윈도에서는 못 넣으면 그 작업자를 아예 쓰지 않는다 — D-585). 표준 오류의 글은 결과·기록·화면·임시 폴더 어디에도 없다(시험이 비밀 닮은 글과 경로를 표준 오류에 쓰는 가짜 작업자로 확인한다).
- **T-G(1) 소켓 가드 시험**: `tests/ocr_worker_probe.py`(시험 전용 실행기 — 동결 작업자에는 없고 `worker_main.py` 는 한 글자도 안 바꿨다)가 진짜 `worker_main`·`netguard`·`protocol` 을 파이썬으로 띄우고 엔진 만들기·모델 파일 확인 이름만 바꿔 끼운다. 시험이 만드는 바깥 연결 시도는 **패킷이 나갈 수 없는 주소(`0.0.0.1`)와 숫자 주소**뿐이고 루프백은 `127.0.0.1` 닫힌 포트다 — 가드를 일부러 망가뜨린 변이에서도 실제 연결은 일어나지 않는다.
  확인한 것: 바깥 시도 여섯 길(connect·connect_ex·create_connection·getaddrinfo·gethostbyname·sendto)이 막혀 `net_blocked` 오류와 종료 코드 5 로 끝난다 · 루프백은 통과하고 센 횟수에 안 잡힌다(가드는 바깥 시도와 루프백을 따로 세고 비운 뒤 다시 센다) · 라이브러리를 가져오는 도중의 시도도 잡힌다(가드가 가져오기보다 먼저) · 가드를 못 켜면 종료 코드 70 으로 시작하지 않는다(fail closed) · 가드는 `worker_main.py` 의 첫 문장이고 엔진 라이브러리는 함수 안에서만 가져온다(소스 규칙) · 진짜 `serve` 의 약속 처리(나쁜 머리·모르는 칸·`opts`·너무 긴 머리는 종료 코드 2, 크기 불일치·너무 큼은 오류 응답 뒤 계속, 본문 도중 입력 끊김은 3, `bye`·EOF 는 0)와 진짜 응답(줄 200개로 줄임·`dropped`·`trunc`·글 400자 자름)이 앱의 응답 검사를 그대로 통과한다.
- **변이 시험(T-J)**: 새 안전 논리마다 변이를 항목당 두 개 이상 만들어 시험이 빨개지는지 보았다 — 라운드 2 까지는 177개(잡힘 176·동등 1)였고, 라운드 3 에서 검증자의 변이와 새 변이를 더해 모두 293개 중 291개가 잡히고 2개는 결과가 같은 동등 변이(N6·NG9)로 근거를 적었다. 숫자와 근거는 이 문서와 `docs/DECISIONS.md` 의 D-526 에 직접 적는다(변이 도구·정의·표는 저장소 밖 작업 폴더에 있다).

  GEOS 라이선스 전문(`LICENSE_GEOS`)을 못 찾으면(GEOS 판을 못 읽거나 별도 `geos*.dll` 이 없을 때도) 조용히 건너뛰지 않고 빌드가 실패하고, 산출 목록에 고지문·`licenses/`·GEOS 전문이 없으면 정보 파일을 쓰지 않는다. 원본 소스 압축 파일은 넣지 않는다(새 내려받기 없음 — 같은 버전 소스를 공식 배포처에서 받으라고 안내한다).

## 글자 읽기 작업자 — 라운드 3 독립 검증 S·Q 지적 반영(D-526, S 필수 2·권고 7, Q 필수 4·권고 9, B2 검증 S 의 B1 쪽 뿌리 1)

두 독립 검증이 낸 지적을 반영했다. 앱 안전 규칙의 허용은 이번에는 넓히지 않았고(새 허용 0 — 감시 이름 둘을 더했고 어댑터 파일의 길을 닫힌 집합으로 못박았다) 시험을 약하게 만든 곳은 없다.
- **빌드 점검 관문(SP-1·SP-11)**: 추가 도구 빌드의 `all` 단계는 점검(묶음 안 모든 exe·DLL·pyd 의 가져오기 표에서 네트워크 DLL·금지 파일·모델 해시·동결본 자가 점검)이 실패하면 거기서 멈추고 종료 코드 1 로 끝나며 정보 파일·zip 을 만들지 않는다(예전에는 실패를 버리고 0 으로 끝났다). 가져오기 표의 허용 예외는 `_internal` 바로 아래의 `_socket.pyd`·`select.pyd`·`python312.dll` 셋뿐이고 경로까지 맞아야 한다.
- **소켓 가드 시험(SP-2)**: 가드의 분류(루프백만 통과, 사설망·링크 로컬(169.254 클라우드 메타데이터 포함)·IPv6·`localhost` 로 시작하는 바깥 이름은 차단)와 래퍼 열 개를 진짜 `netguard.py` 소스를 **가짜 소켓 모듈** 위에 얹어 하나씩 따로 시험한다 — 진짜 소켓·패킷 없이, 막혔다면 가짜 원본이 한 번도 안 불린다는 사실로 본다.
- **어댑터(SP-3·SP-4·SP-5·SP-15)**: 정리에서 Job 개체를 파이프 핸들 닫기보다 먼저 닫아(작업자가 손자를 남기고 죽어 손자가 표준 출력 파이프를 쥐어도 `KILL_ON_JOB_CLOSE` 가 손자를 끝낸다) 정리·앱 종료가 매달리지 않고, 핸들 닫기에는 3초 제한을 둔다. 표준 출력 줄 대기열은 16줄 한도라 작업자가 요청하지 않은 줄을 쏟아내도 앱 메모리가 늘지 않는다(다음 읽기가 약속 위반으로 끝나 정리된다).  `verify`(해시 확인)는 필수 인자이고 작업자 실행 파일은 절대 경로여야 한다(상대 경로는 현재 폴더 탐색으로 다른 실행 파일이 뜰 수 있다). Job 개체에 넣었는지는 `job_assigned` 에 남는다.
- **응답 번호·정보 파일(SP-6·SP-9)**: 응답의 요청 번호는 정수 그 값이어야 하고(참·거짓·실수는 안 됨) 오류 응답의 번호는 없음이거나 요청 번호여야 한다(두 약속 사본에 같은 변경). 정보 파일의 너무 깊은 JSON 은 예외 대신 invalid 로 거절한다.
- **하위 프로세스에 닿는 길의 닫힌 집합(QP-2)**: 어댑터 파일은 안전 규칙에서 `subprocess` 가 파일 단위로 열려 있어 이름 목록 밖의 길(`getoutput`·`getstatusoutput` 은 셸 명령을 그대로 돌린다, 이름을 바꿔 가져온 `Popen`)이 걸리지 않았다. 두 안전 시험의 이름 목록에 `getoutput`·`getstatusoutput` 을 더했고(`publish/gitrepo.py` 의 같은 틈도 함께 막힌다), 어댑터 시험이 이 파일의 `subprocess` 이름(`Popen` 한 곳·`run` 한 곳·`PIPE`),  `os` 이름 다섯, `ctypes` 이름, kernel32 에서 부르는 이름 넷(Job 개체), 동적 이름 찾기(`getattr` 두 줄뿐)를 닫힌 집합으로 못박고 별칭·from 가져오기·이름만 따로 쓰기를 거절한다. 새 길이 생기면 시험이 빨개져 사람이 그 길이 관문 안인지 본다.
- **작업자 표준 입출력(QP-3)**: 시험이 `Popen` 인자의 `stdin`·`stdout`·`stderr` 가 모두 파이프임을 못박는다(표준 오류를 앱 콘솔로 흘리거나 표준 출력에 합치면 시험이 빨개진다).
- **되돌리기 규칙(QP-4)**: 읽은 결과가 오거나 줄을 고치면(확인·고침·빼기·합치기·모두 맞아요) '사진 지우기 되돌리기' 와 '모두 확인했어요' 확인 줄이 사라지고, 거절된 되돌리기가 읽은 글·확인한 줄을 건드리지 않음을 시험이 못박는다(목록 전체를 옛 판으로 되돌리면 확인해 둔 줄이 한 번에 사라지는 자료 손실이 된다). 읽은 결과가 도착해서 되돌리기가 사라지는 것은 사용자의 조작이 아니라 백그라운드 결과 도착이 원인이라 놀랄 수 있다 — 되돌리기 줄에 알릴지·읽는 중에는 지킬지는 B2 가 정한다(SP-14).
- **'모두 맞아요' 질문의 신선도(B2 검증 S SP-1)**: 질문은 그 사진의 새 결과가 오거나 다시 읽기가 줄을 설 때 닫히고, 질문을 띄운 때의 읽은 줄(글·확인 상태)과 눌린 때의 줄이 다르면 낡은 '네' 는 아무것도 확인하지 않고 거절된다(예전에는 3줄을 묻고 다시 읽은 5줄 전부가 확인되었다 — 확인한 줄만 초안에 간다는 조건을 지키는 곳이다). 거절 값은 기존 `refused` 다. 다른 사진의 읽기는 이 사진의 줄을 바꾸지 않으므로 그 질문을 닫지 않는다. 시험은 무작위 동작에서도 떠 있는 질문의 줄이 질문을 띄운 때와 늘 같음을 본다.
- **그 밖의 Q 권고**: 컨트롤러 곁가지 셋(시간 초과·종료 뒤 준비 시계, 크게 다시 읽기 크기, 끈 동안 시작 안 함)과 어댑터 곁가지(취소 뒤 끝난 결과를 어댑터가 버림·정중한 bye·가짜 프로세스의 정리 순서가 트리 종료를 직접 봄)를 시험이 못박고, `ocr_addon/` 를 저장소 비밀 훑기 범위에 넣었으며(새는 것은 없었다), 안내문·README 의 낡은 문장을 바로잡았다.
- **텔레메트리 한계(SP-7)**: 앱이 하는 일은 끄는 호출(`disable_telemetry_events`)과 환경 변수(`ORT_DISABLE_TELEMETRY=1`·`DO_NOT_TRACK=1`)까지다. onnxruntime 윈도 이진의 운영체제 이벤트 추적(ETW)은 끌 수만 있고 효과를 증명하지는 못한다 — '텔레메트리 0' 은 이 한계 안에서의 말이다.
- **시험 틈 메움(SP-8·SP-17·SP-13·SP-16·SP-18)**: 어댑터 기본값(150·90·3·300초·낮은 우선순위)을 글자 그대로 못박고 시간 경계는 가짜 시계로 본다(실제 시간이 아니라 시계 값이라 CPU 가 바빠도 흔들리지 않는다). 병합이 사진 확정을 풀고, 엔진이 표준 출력에 쓴 글이 프로토콜 줄을 못 더럽히고, 부모 환경 변수 통과 목록이 열 개 그대로이고, 낯선 파일 허용이 정확히 두 이름뿐인지 시험한다.
- **변이 시험**: 검증자의 변이와 내가 겨눈 변이를 새 코드·새 시험 이름으로 모두 돌려 293개 중 291개가 잡히고 2개는 동등 변이(N6 — 합친 글 이중 방어, NG9 — 파이썬 3.9 이상은 IPv6 구역 표지를 스스로 받아들임)로 근거를 적었다.
- **알려 둔 한계(추가 2)**: 소켓 가드의 파이썬 래퍼는 `bind`·`listen`(들어오는 쪽)과 `sendmsg`(유닉스 전용)를 감싸지 않는다 — 설계는 나가는 시도만 다루고 작업자는 윈도 전용이다(그 뒤 감사 훅 한 겹이 `bind`·`sendmsg` 이벤트를 루프백 밖이면 막게 됐다 — D-587, `listen` 은 아직 보지 않는다). Job 개체에 못 넣은 작업자는 이제 윈도에서 쓰지 않고 `blocked` 로 끝낸다(D-585 — 옛 문장 '못 넣어도 조용히 뜬다·띄울지는 B2·B3 가 정한다' 는 이 결정으로 정해졌다). 윈도가 아닌 곳은 Job 개체가 없어 이 규칙이 없다.  작업자 임시 폴더(`cbd-ocr-`)는 앱이 강제 종료되면 빈 채로 남을 수 있다(지우는 코드는 파일 시스템 허용 +1 이라 넣지 않았다). 표준 오류가 앱 콘솔로 새지 않음은 `Popen` 인자까지만 보고 실제 파일 핸들로 새는지는 보지 않는다. 하위 프로세스 호출 이름을 문자열로 조립하는 길은 어댑터 파일만 닫힌 집합으로 막았고 다른 파일은 정적 규칙으로 막지 못한다.  낮은 우선순위(BELOW_NORMAL) 작업자는 CPU 가 아주 바쁜 PC 에서 굶어 느려질 수 있고 그러면 시간 초과로 끝난다(사용자 문구는 다른 프로그램을 닫고 다시 하라고 알린다). 설계의 선택 신호 alive 는 만들지 않았다(약속에 없다).
## 글자 읽기 — 확정한 글자만 초안 본문에 들어간다 (D-520에서 D-525, 사진 글자 읽기 b 단계 B3, 운영자 확인 026 ②·028 ②)

글자 읽기가 읽은 줄은 **확인 전 후보**이고, 사용자가 줄마다 '맞아요' 를 누르고 사진도 확정한 줄만 초안 본문에 들어간다. 이 연결은 새 입·출력도 새 쓰기도 만들지 않는다 — 순수 함수 `photo_lines`(`content/photo_flow.py`) 한 곳이 바뀌었고 네트워크·하위 프로세스·새 파일·새 의존성·새 오류 코드·저장 형식 변경이 0이다.
- **들어가는 것**: 확정한 사진의 확정한 줄뿐이다(`draft_inputs` 가 그대로 거른다 — 확인 전 줄·확정 안 한 사진의 줄·관찰한 대상은 가지 않는다). 본문에는 틀 문장 한 줄 `사진에 적힌 글이에요.`(틀로 만든 글 — 사실이 없는 한 줄이라 '지어내지 않기' 검사와 마지막 관문 `_final_guard` 를 지난다. 합니다체 글에서는 `사진에 적힌 글입니다.`)과 확정한 줄들을 줄바꿈으로 이은 문단 하나(사용자 글)가 들어간다. 줄은 한 글자도 고치지 않고 앱이 가격·메뉴 이름·상호를 뽑거나 해석하지 않는다(새 칸이 없다).
- **입구는 그대로다**: 줄은 읽는 순간(`set_analysis`)·고칠 때(`edit_item`)·합칠 때(`merge_items`) 기존 입구 검사(`check_text`)를 지난 것뿐이다. 템플릿 표기(`{{`)·HTML 태그·스크립트 주소·키·토큰 모양·주민등록번호와 카드 번호 모양·빈칸처럼 보이는 글자는 확정 줄이 될 수 없고, 보이지 않는 글자와 줄바꿈은 입구가 지운다(그래서 한 줄에 줄바꿈이 없고 줄 구분이 흔들리지 않는다). 마지막 관문은 본문 전체를 한 번 더 본다 — 입구와 `draft_inputs` 를 지나지 않은 손으로 만든 값에 키 모양이 있어도 초안을 만들지 않는다(시험이 본다).
- **이은 줄도 사진 정보 검사가 미리 본다(독립 검증 SP-1)**: 줄 하나씩은 입구를 지나도 줄바꿈으로 이은 본문이 `security.mask` 의 '이름: 값' 꼴(이름 뒤 쌍점·등호, 그 다음 줄바꿈을 건너 네 글자 이상)로 읽히면 마지막 관문이 초안 전체를 막고 화면이 엉뚱한 이유를 말하던 틈이 있었다(막는 쪽으로 실패하므로 유출·자료 손실은 없었다). `draft_inputs` 의 마지막 관문이 사진마다 확정한 줄을 줄바꿈으로 이은 글(+ 뒤에 이어질 글을 뜻하는 낱말 `JOIN_PROBE`)에도 같은 `mask` 검사를 걸어(`joined_looks_secret`) 걸리면 사진 번호만 담은 `CONTENT_INVALID` 로 멈추고 화면은 `사진 정보에 키처럼 보이는 글이 있어 초안을 만들지 않았어요` 를 말한다 — 글은 오류에도 기록에도 없고 공급자는 부르지도 않는다. 이름 줄이 맨 끝이어도 같이 거절한다. 마지막 관문 `_final_guard` 는 그대로다.
- **복사 관문도 그대로다**: 복사할 때 확정한 글자도 다른 본문 글과 똑같이 훑는다 — 건강 효과를 단정하는 표현이 있으면 막고(그 문단을 본문에서 지우면 풀린다), 확인하지 않은 가격·날짜는 확인 권장으로 알리고, 파일 경로처럼 보이는 글은 정보 한 줄로 알린다. 읽은 글을 AI 에 보내는 길은 없다(이 기능은 AI 를 쓰지 않는다).
- **저장은 그대로다(초안 저장 형식·사진 정보 저장 형식·백업 형식 변경 0)**: 읽은 글은 저장하지 않는다 — 사진 정보 파일에는 줄이 없고(`visible_text` 빈 목록, 분석 방법 `manual`) 칸은 열네 개 그대로다. 이미 만든 본문은 사용자의 글이라 저장한 초안에 확정한 글자 문단이 그대로 들어 있다.
- **알려 둔 한계**: ① 저장한 초안을 다시 열어 `다시 만들기` 를 하면 읽은 글이 없어 확정한 글자 문단이 새 본문에 들어가지 않는다 — 저장한 본문을 안 고쳤으면 확인창도 없이 바뀐다(이미 저장한 본문에는 그대로 있다 — 다시 읽고 확인해야 한다) · ② 본문 크기 한도가 셋이다: 처음 만든 초안 본문 30,000자(`saved_draft.MAX_BASE_BODY_CHARS`)를 확정한 글자가 넘기면 저장이 한도 문장(`DRAFT_LIMIT`)으로 거절된다 — 본문은 잘리지 않고 화면에 남는다. 10만 자(`security.shape.MAX_SCAN_CHARS` 100,000자)를 넘으면 복사 관문이 키 모양 검사를 믿을 수 없다고 보고 복사를 막는다(fail closed — 10만 자 이하에서는 복사가 되고, 막을 때 문구는 키 모양 문구라 길이 때문이라는 말이 없다). 20만 자(`security.mask.MAX_MASK_INPUT` 200,000자)를 넘는 극단은 마지막 관문이 `CONTENT_INVALID` 로 통째로 거절한다(화면에는 일반 실패 문장 — 몰래 자르지 않는다) · ③ 마크다운 길(원고에서 네이버 패키지를 만드는 `render/naver.py`)은 한 문단의 줄을 공백으로 합친다 — 초안 본문은 그 길을 지나지 않고, 호출처가 `service/naver_flow.py` 하나뿐임을 시험이 지킨다 · ④ 읽은 글이 틀릴 수 있다는 점은 사용자의 줄 확인(숫자 줄은 사진과 다시 견주기)이 막는 마지막 방어선이고 앱은 판단하지 않는다. · ⑤ 같은 줄이 둘이면 본문에는 한 줄만 들어간다(`draft_inputs` 의 B1 규칙 — 사용자가 확인한 줄 수와 본문의 줄 수가 다를 수 있다) · ⑥ 입구와 이은 줄 검사는 영어 이름(`password`·`token`·`secret`·`api key` …)의 '이름: 값' 꼴만 알아본다 — `비밀번호:`·`PW:`·`ID:`·전화번호·주소·이름은 통과하므로 줄을 확인하는 사용자가 마지막 방어선이다 · ⑦ 사진 대상 칸이 이름 줄로 끝나는 틈(예: 대상 `Token:` 은 본문에 `Token: 사진이에요.` 가 되어 마지막 관문이 일반 실패 문장으로 막는다 — main 때부터)은 확정한 글자 줄만 보는 이은 줄 검사가 보지 않는다.


## 복원은 지금 보관함이 복원 직전 사본으로 되돌릴 수 있을 때만 시작한다(L8b — 설계 D-570–D-574)

앞 절(L8)의 독립 검증이 남긴 권고(Q 의 QP-1·QP-3·QP-4·QP-5, S 의 SP-5)를 닫았다. 제품 코드는 **복원을 시작하는 곳의 읽기 검사 하나**와 화면 문구뿐이다. 백업 형식·복원이 쓰는 길·잠금·저장 형식·서비스 쓰기·새 오류 코드·검사를 끄는 길은 바뀌지 않았다.

### 문제(검증자 둘이 따로 재현)

복원 직전 안전 사본은 지금 파일을 그대로 담고, 복원 확인창은 '잘못 복원했다면 목록에서 그 사본을 골라 다시 복원하면 돼요' 라고 약속한다. 그런데 앞 절의 구조 검사는 **들어오는 파일**만 본다. 그래서 사용자가 앱 밖의 도구로 자기 보관함에 뷰·색인·트리거를 두었다면 깨끗한 백업의 복원은 경고 없이 끝나고, 그 복원 직전 사본에도 같은 개체가 있어 **그 사본으로 되돌리기만 거절**됐다(복원이 도중에 실패해 자동으로 되돌릴 때도 같다). 자료가 사라지지는 않지만(사본 폴더의 보관함 파일은 평범한 SQLite 파일이다) 확인창의 약속이 이 사용자에게는 거짓이었다.

### 고친 것 — 되돌릴 수 없는 보관함이면 복원을 시작하지 않는다

복원이 안전 사본을 만들기 **전에**(`service/backup_flow._refuse_if_undo_impossible`) 이 복원이 바꿀 지금 보관함(백업에 든 글 보관함·주제 엔진 보관함 중 멀쩡히 열리는 것)을 읽기 전용으로 열어 앞 절과 **같은 구조 검사**(`_foreign_in`)를 한다. 앱이 만들지 않는 개체가 하나라도 있으면 복원을 **시작하지 않는다** — `RESTORE_FAILED`(이유 `live_structure`, 있던 오류 코드라 새 코드는 없다). 안전 사본·복원 중 표지·임시 파일을 만들기 전이라 아무것도 쓰지 않고(시험이 쓰기 함수 여섯을 감시하고, 지금 보관함을 여는 연결이 읽기 전용 주소(`mode=ro`)이며 그 주소가 쓰기를 거절하는지도 센다) 지금 데이터는 한 바이트도 바뀌지 않는다(앱이 만드는 삭제 저널 방식의 보관함 기준 — 외부 도구가 쓰기 먼저 기록(WAL) 방식으로 바꾼 보관함은 SQLite 가 읽기 연결에서도 짝 파일을 만들 수 있고, 기존 흐름의 지금 파일 상태 확인이 이 검사보다 먼저 그렇게 한다). 이 검사를 끄는 인자·설정은 없다.

화면은 첫 문장 '복원을 시작하지 않았어요. 지금 데이터는 그대로예요.' 와 이유 한 줄('이유: 지금 이 컴퓨터의 보관함에 앱이 만들지 않는 구조(트리거·뷰 — 저장할 때 몰래 도는 동작이나 표 행세를 하는 목록 같은 것)가 있어요. 이대로 복원하면 ‘복원 직전 사본’ 으로 되돌릴 수 없어서 멈췄어요. 그 구조를 지운 뒤 다시 복원해 주세요.')과 다음에 할 일 한 줄('그 구조를 지우는 방법을 모르겠다면 설정의 정보 카드에 있는 ‘진단 정보 복사’ 단추로 복사한 글을 함께 알려 주세요.' — 이미 있는 단추를 가리킨다)을 보인다. 개체 이름·경로·오류 코드는 화면과 오류 세부 어디에도 없고 고정된 종류 낱말뿐이다. 확인창의 약속 문장은 그대로이고, 이제 복원이 시작하는 경우마다 지켜진다(아래 한계 ① 의 네트워크 경로 설정은 제외) — 그 개체를 지우면 복원이 되고 그 복원 직전 사본으로 되돌리기도 된다(시험이 끝까지 본다).

### 막을지 알리기만 할지(D-570 ③)

막는다. 근거는 위임 규칙의 우선순위다 — 데이터 보존과 복구 가능성(5)·되돌릴 수 있는 안전한 기본값(8)·쓰기보다 읽기 전용, 그리고 기존 결정 D-387('안전 사본도 같은 복원 길로 되돌릴 수 있다 — 못 남기면 시작하지 않는다')의 직접 적용이다. 알리기만 하려면 복원 확인창이 지금 보관함을 읽어야 하는데 화면 계층은 데이터를 읽지 않고, 사용자가 안내를 넘기고 복원하면 약속이 그대로 거짓이 된다. 막아서 잃는 것은 작다 — 해당자는 앱 밖에서 보관함 구조를 바꾼 드문 사용자뿐이고, 그 개체를 지우면 복원이 된다.

### 보는 범위

- 이 복원이 안전 사본에 담고 바꿀 보관함만 본다: 백업에 든 것 가운데 지금 파일이 멀쩡히 열리는 것. 깨져서 옆으로 옮길 파일·없는 파일·0바이트 파일은 안전 사본에 담지 않으니 보지 않고, 백업에 없는 보관함은 이 복원이 건드리지 않으니 보지 않는다.
- 읽을 수 없으면 건너뛴다. 안전 사본을 만드는 다음 단계가 같은 파일을 읽다가 멈추거나(잠겨 있으면 '다른 곳에서 쓰는 중' 으로 알린다) 통과한다.
- 새 판(판 번호가 더 큰) 파일은 구조로 거절하지 않는다 — 지금 파일 상태 확인이 먼저 '더 새로운 프로그램' 으로 멈추고, 이 검사를 따로 불러도 들어오는 백업의 확인과 같은 규칙으로 미룬다.
- 앱이 스스로 만드는 모양은 걸리지 않는다: 옛 판(판 1) 보관함과 `ANALYZE` 가 만드는 통계 표(`sqlite_stat1`)가 든 지금 파일은 그대로 복원되고 되돌려진다.

### 한계(사실대로)

① 같은 부류가 하나 더 있다 — 연결한 폴더를 네트워크 경로로 쓰는 설정(앞 절 한계 ⑥)도 그 안전 사본이 같은 확인에 걸려 되돌리기가 거절된다. 막으면 그 사용자는 어떤 복원도 못 하게 되는 정책 결정이라 운영자 확인 ⑦ 과 함께 정해야 해서 이번에 건드리지 않았다. ② 옛 `restore` 명령과 주제 엔진의 `topics restore` 는 이 시작 검사를 하지 않는다(개발자용이고 안전 사본 위치가 명령 글에 적혀 있다). 그쪽의 안전 사본은 같은 구조 검사를 받아 되돌리기가 거절될 수 있고 자료는 사본 폴더에 그대로 있다. ③ 검사와 안전 사본 사이에 다른 프로그램이 보관함에 개체를 더하는 경쟁은 막지 못한다(복원하는 순간까지 쓰는 프로그램은 막을 수 없다). ④ 백업을 **만드는** 쪽은 그대로다 — 앱 밖에서 구조를 바꾼 사용자의 새 백업은 만들어지지만 앱으로는 복원되지 않고, 그 사실은 복원할 때에야 알려진다(백업을 만들 때 미리 알리는 것은 제안으로만 남긴다).

### 시험 틈과 문서 시험(QP-3·QP-4·QP-5 — D-571·D-572)

검증자가 새로 겨눈 변이 중 시험 틈으로 남은 일곱 가지(생성 열은 표마다·개체 목록 읽기 상한·SQL 머리 40자·NVIDIA 앞내다보기 창·Slack 앱 토큰 덩어리 길이·긴 키 꼬리 가림·DigitalOcean 16진 대소문자)는 시험만 더해 닫았다 — 제품 코드는 맞았다. 문서 시험이 이 묶음의 줄을 찾는 방법은 다른 갈래가 문서 끝에 덧붙이거나 이 묶음의 후속이 같은 결정 번호를 되풀이해도 흔들리지 않도록 이 묶음이 여는 말로 찾게 바꿨다.

### 독립 검증 권고 반영(D-574)

L8b 의 독립 검증(S·Q 모두 pass, 필수 0)이 남긴 권고 넷을 같은 가지에서 작게 반영했다. ① 시작 검사가 지금 보관함을 읽기 전용으로만 여는지를 시험이 센다(연 연결의 주소가 프로젝트의 읽기 전용 주소와 같고 그 주소가 쓰기를 거절한다). ② 화면 시험이 실패 뒤 쓰기 표시가 지워지는지를 실제로 센다. ③ 막힌 사용자에게 다음에 할 일 한 줄(진단 정보 복사)을 더했다 — 앱 안의 구조 정리 도구나 '그래도 계속하기' 길은 만들지 않았고 운영자 확인 항목으로 남긴다. ④ 개체 검사 모듈의 머리 설명이 복원 시작 때의 검사를 사실대로 말하게 고쳤다. 같이 한 참고: 서비스 시험이 숨은 열·가상 표도 훑고, '시작하는 복원마다 지켜진다' 에 네트워크 경로 설정의 예외를 붙였다.

## 글자 읽기 추가 도구 빌드 흐름(`.github/workflows/package-ocr.yml`·`ocr_addon/` 빌드 쪽) — 밖으로 나가는 곳이 빌드에 둘 더 는다 (D-527에서 D-533, 사진 글자 읽기 d 단계, 운영자 확인 026 ②·028 ②)

추가 도구(글자 읽기 작업자)를 GitHub 의 Windows 러너에서 만드는 빌드 흐름이다. 앱이 실행되는 동안의 경계가 아니라 **빌드의 경계**이고, 앱(`src/`)에는 새 네트워크 코드가 없다(시험이 `src/` 를 훑어 모델 주소·내려받기 낱말이 없음을 본다). 사용법과 점검은 [`PACKAGE_OCR.md`](PACKAGE_OCR.md).
- **승인 조건**(`package.yml` 과 같다): 수동 실행(`workflow_dispatch`)만·입력칸 0·`permissions: contents: read` 하나(작업 단위로 넓히지 못한다)·비밀 값 0·서명·릴리스 게시 0·액션은 `package.yml` 이 쓰는 **같은 전체 커밋 SHA 셋뿐**(새 액션 0 — 시험이 두 파일의 `uses:` 를 견준다). `run:` 안에는 `${{ }}` 가 하나도 없고(주입 길 0) 단계마다 명령이 하나이며(PowerShell 은 마지막 명령의 종료 코드만 본다), 올리는 것은 압축 파일·`SHA256SUMS`·`PACKAGE_INFO.json` 셋뿐(보존 14일·없으면 실패 — 본체의 산출물 허용 목록 시험도 그대로 통과한다). **병합과 실행은 운영자만** 한다 — 이 파일은 NO-MERGE 가지에 준비만 했다.
- **밖으로 나가는 곳 둘**: ① 파이썬 패키지 저장소(PyPI) — 잠금 파일(패키지 21개·빌드 도구 7개, 해시 포함)대로 `--require-hashes --only-binary=:all:` 로만 설치(소스 빌드 0). ② Hugging Face — 모델 2파일을 **커밋 고정 주소**로 받아 크기와 SHA-256 이 잠금 값과 같을 때만 남긴다. 허용 호스트는 `huggingface.co`·`hf.co` 와 그 하위뿐이고 리디렉션이 https 가 아니거나 그 밖으로 가면 그 자리에서 거절한다(닮은 이름·`http`·IP 주소 포함 시험). 읽는 양도 잠금 크기를 넘지 못해 거대 응답으로 디스크를 채울 수 없고, 토큰·계정·쿠키 머리말을 쓰지 않는다. 받기 코드는 빌드 전용 파일 한 곳(`ocr_addon/fetch_models.py`)에만 있다.
- **공급망**: 런타임 핀 21개는 PyPI 업로드 14일 이상(업로드 날짜 칸과 시험)이고 설치된 판이 잠금 파일과 다르면 빌드가 멈춘다(`--require-hashes` 를 빠뜨려도 판 차이로 잡는 두 번째 그물) — 빌드 도구 7개는 `--require-hashes` 로 내용만 고정되고 판 일치·14일 규칙은 기계로 점검하지 않는다(실제 나이는 겹치는 `packaging` 을 뺀 여섯 모두 48일 이상, `docs/PACKAGE_OCR.md` 4절). 모델·사전의 크기·SHA-256 은 **세 곳**(빌드의 `models.lock.json`·작업자의 기대값·앱 소스에 박은 값)이 같아야 하고 시험이 같음을 지킨다 — 앱은 띄우기 전에 설치된 파일을 박은 값과 견주므로 빌드 쪽 잠금이 틀려도 틀린 모델은 쓰이지 않는다.
- **묶음 점검**(하나라도 걸리면 산출물 0): 가져오기 표(예외는 `_internal` 의 `python312.dll`·`_socket.pyd`·`select.pyd` 셋뿐, 위치까지 정확히) · FFmpeg DLL·인증서 파일·기본 모델 부재와 모델·사전 해시 · OpenSSL·진짜 `requests` 계열 부재(동결본이 직접 가져와 보지 못함을 적은 기록까지) · 동결본 `--selftest`(소켓 가드 음성 대조·정상 읽기 시도 0, 실행하는 동안 묶음·임시 폴더에 파일을 쓰면 실패) · DLL 출처 허용 뿌리(러너 PATH 의 자바 DLL 사건 D-468 — PyInstaller 는 PATH 를 좁혀 부른다) · 키 모양 글(`licenses/` 아래는 확장자가 없어도)·본체의 금지 파일 이름·라이선스 고지 산출물(고지문·`licenses/` 파일·GEOS 전문)이 있는지. 올리기 직전에는 별도 **산출물 점검** 단계(`ocr_addon/verify_release.py`)가 만든 압축 파일·`SHA256SUMS`·`PACKAGE_INFO.json` 을 **파일 자체에서** 다시 읽어 해시·크기·파일 목록(안의 정보 파일과 한 줄씩)·모델 잠금 값과 **라이선스 고지 파일**(`licenses/` 의 파일과 그중 GEOS 라이선스 전문 `licenses/shapely/LICENSE_GEOS`·비어 있지 않고 GEOS·LGPL 을 말하는 `THIRD_PARTY_NOTICES.txt`·별도 DLL 로 있는 GEOS)이 압축 파일 안에 있는지 확인한다(운영자 확인 030 ②). 어긋나면 그 단계가 빨갛게 끝나 아무것도 올라가지 않는다. 이 단계는 '없어야 할 것'도 압축 파일 쪽에서 다시 본다 — FFmpeg DLL·인증서 파일·기본 모델(R2)과 OpenSSL·진짜 `urllib3`·`certifi`(R3)와 정보 파일에 적힌 빌드 점검 결과가 통과인지 — 그래서 빌드의 점검이 건너뛰어지거나 실패하고도 산출물이 만들어지는 길이 다시 열려도 금지 부품이 든 압축 파일은 올라가지 못한다(독립 검증 S 의 SP-1). 압축 파일 안 정보 파일이 JSON 객체가 아니어도 실패한다(SP-7 — 아니면 정보 파일 검사 전체가 조용히 건너뛰어진다).
- **알려 둔 한계**: ① 이 흐름은 GitHub 러너에서 **한 번도 돌려 보지 못했다**(병합 뒤 운영자의 첫 실행이 첫 관측). ② 가져오기 표는 '네트워크 DLL 을 부르는 부품이 묶음에 있는가' 를 보는 정적 점검이다 — 연결을 만들지 않는다는 증거는 소켓 가드(파이썬 소켓만 본다)와 비행기 모드 시험의 몫이다. ③ 위 쓰기 점검은 묶음 폴더와 임시 폴더만 본다. ④ Windows Defender 읽기 검사와 서명은 이 흐름에 없다. ⑤ GEOS(LGPL-2.1) 등 라이선스 의무는 운영자 확인 030 ②(2026-11-22)로 **고지문·소스 안내문을 추가 도구 폴더에 넣는 방식**이 정해졌다(원본 소스 압축 파일은 넣지 않는다 — 새 내려받기 없음, GEOS 는 별도 DLL 파일이라 바꿔 끼울 수 있다). 산출물 점검이 그 파일들이 압축 파일 안에 있는지 확인한다(정정: 이 절의 앞선 판은 '병합 전에 운영자께 따로 여쭙는다' 고 적었다). ⑥ 러너의 파이썬 3.12.x 패치 판이 다르면 압축 파일 해시가 이 PC 값과 다르다(점검과 `--selftest` 는 같다).

## 글자 읽기 안전 감사(OCR-S1) 권고 처리 — 작은 코드 보강·문구·켜기 전에 알아 둘 한계 (D-585에서 D-591·D-593, 2026-11-23)

독립 감사(OCR-S1 — 판정 pass, 필수 0·권고 5·참고 10, 불변 조건 일곱은 깨지지 않았다)가 합쳐진 main 의 글자 읽기를 적대적으로 읽고 남긴 권고 가운데 지금 고치기로 한 것을 처리했다(변경 등급 T2). `LOCAL_OCR` 는 여전히 False 라 이 빌드에서 작업자는 한 번도 뜨지 않는다. 켜기 값·앱에 박은 모델·글자 사전의 크기와 해시(`EMBEDDED_FILES`)·`models.lock.json`·`.github/`·잠금 파일은 바뀌지 않았다.
- **R3 — 트리를 끄는 `taskkill` 을 절대 경로로(D-586)**: `kill_tree` 가 `taskkill` 을 이름만으로 불러, 앱 폴더나 현재 작업 폴더에 같은 이름의 실행 파일이 있으면 시간 초과·취소 때마다 그것이 대신 실행될 수 있었다(감사가 작은 실험으로 재현). 이제 `taskkill_path()` 가 `build_environment` 와 같은 출처(`system_root` — `SystemRoot`·`SYSTEMROOT`·`windir` 순)의 `System32` 아래 `taskkill.exe` 절대 경로를 만들어 부른다. **윈도에서는**(2차 보강, D-593) 환경 값이 아니라 윈도에 직접 물은 폴더(`GetSystemWindowsDirectoryW`, `ui/winroot.py`)를 믿는다 — 환경의 `SystemRoot` 는 그 폴더와 같은 폴더일 때만 쓰고 `D:\evil`·`C:\Windows\..\Users` 같은 다른 값은 따라가지 않는다. 윈도에 물을 수 없을 때(윈도가 아니거나 호출 실패)는 예전 그대로다: 값이 없거나 드라이브 글자로 시작하는 절대 경로가 아니면(상대 경로·네트워크 위치·장치 경로) 윈도 기본 폴더(`C:\Windows`)를 쓰고, 그 자리에 파일이 없어도 이름만 부르는 대체 호출은 하지 않는다(작업자 하나는 직접 끄고 손자는 Job 개체가 끈다). 이름만 부르는 호출이 다시 생기면 어댑터 시험의 소스 낱말 검사·글자 읽기 관문 시험의 호출 모양 검사가 빨개진다. 작업자의 PATH 를 짜는 `build_environment` 도 이제 같은 함수(`trusted_system_root`)를 쓴다(감사 후속 AS2-A, D-600) — 환경의 `SystemRoot` 가 윈도가 알려 준 폴더와 다른 곳을 가리켜도 작업자의 PATH 는 윈도가 알려 준 폴더 아래뿐이다. 앞서 걱정한 '시험이 이 PC 의 윈도 폴더에 기댄다' 는 윈도에 묻는 일을 가짜로 바꾼 시험으로 풀었다. 작업자에게 넘기는 `SystemRoot`·`ComSpec` 환경 값은 아직 환경 값 그대로다(작업자가 절대 경로로 뜨고 작업 폴더가 자기 폴더라 닿는 길이 좁다).
- **R2 — Job 개체에 못 넣은 작업자는 쓰지 않는다(D-585)**: Job 개체(메모리 1GB 한도 + 앱이 죽으면 작업자도 끝남)가 두 장치의 유일한 자리인데 만들기·넣기가 실패해도 작업자가 조용히 떴다. 이제 윈도에서 `job_assigned` 가 거짓이면 방금 띄운 트리를 끝내고 임시 폴더를 지운 뒤 어댑터 오류 `blocked` 로 끝낸다(요청은 한 바이트도 보내지 않고, 컨트롤러가 이번 실행에서 글자 읽기를 끈다). 윈도가 아닌 곳은 Job 개체가 없어 이 규칙이 없다. 프로세스를 띄운 뒤에 넣는 짧은 틈은 그대로다. `blocked` 는 화면에서 '이 PC 의 보안 프로그램이 글자 읽기 도구를 막은 것 같아요' 로 보이는데(원인 대부분이 보안 프로그램이라 문구는 그대로 둔다) 오류 카탈로그(`OCR_BLOCKED`)·문제 해결 표의 원인 칸에는 이제 윈도의 작업 한도 장치(Job 개체)에 못 넣은 경우와 시작하자마자 끝난 작업자도 적혀 있다(검증 SQ 권고 1, D-585·D-593). 이미 끝난 프로세스는 Job 개체에 넣을 수 없어서 띄우자마자 죽은 작업자는 예전의 '읽다가 죽음'(연속 세 번까지 다시 시도) 대신 `blocked`(한 번에 이번 실행 동안 끔)가 된다 — 검증이 즉시 끝나는 프로세스 40개가 모두 Job 에 들어감(띄운 뒤 넣기까지 수 밀리초)과 어댑터 전체 15번이 모두 '읽다가 죽음' 이었음을 재서 이 틈은 좁다.
- **R5 — 소켓 가드 위의 감사 훅 한 겹(D-587)**: 파이썬 래퍼는 `_socket`(C 모듈)을 곧바로 쓰는 호출을 못 봤다(감사가 패킷이 나갈 수 없는 `0.0.0.1` 로 재현 — 가드는 0 으로 셌다). `netguard.install()` 이 `sys.addaudithook` 로 `socket.connect`(connect_ex 포함)·`bind`·`sendto`·`sendmsg`·`getaddrinfo`·`gethostbyname`(_ex 포함)·`gethostbyaddr`·`getnameinfo` 이벤트를 보고 루프백 밖이면 같은 방식으로 세고 막는다(래퍼가 먼저 막은 호출은 훅까지 가지 않아 두 번 세지 않는다). 감사 훅은 한 번 걸면 못 빼므로 **켜짐 표시로만** 일한다 — 꺼진 동안은 아무것도 하지 않고, 훅은 한 사본에서 한 번만 걸며, 가짜 소켓 모듈 위에서 도는 시험은 훅을 걸지 않는다. 훅이 정말 걸렸는지 확인 이벤트로 보고 아니면 예외라 작업자는 시작하지 않는다(fail closed). 대상 모양을 읽지 못한 이벤트는 막는 쪽으로 간다.
- **I7·I8 — 추가 도구 확인의 두 틈(D-588)**: 정보 파일의 `packages` 가 목록이 아닌 값(null·참거짓·숫자 …)이면 다른 검사를 모두 통과한 경우에 예외가 새던 것(`_version` 의 `TypeError`)을 고쳐 `invalid`(`info`)로 끝낸다. 폴더 안의 디렉터리 링크는 `os.walk` 가 안을 돌지 않아 링크 뒤의 낯선 파일이 `extra` 로 안 잡혔고 링크 너머의 목록 파일도 통과하던 틈을 `link` 문제로 센다(링크 파일은 예전처럼 `missing`).
- **R4·I9 — 사용자 문구를 실제 동작에 맞췄다(D-589)**: 읽은 글의 입구 검사가 실제로 가리는 것은 너무 긴 줄(200자 넘음)·눈에 보이지 않거나 빈칸 같은 글자·겹쳐 쌓이거나 홀로 붙은 결합 문자·주민등록번호 모양·카드 번호(검사 숫자가 맞는 것)·키 모양·태그와 `{{ }}` 표시다. 거른 줄 안내를 그 범위로 고쳤다(검증 SQ 권고 3 으로 보이지 않는 글자 둘을 안내에 더했다 — D-593; '개인 번호처럼 보여요' 가 전화번호·주소까지 가린다는 오해를 줬다 — 전화번호·이메일·주소 모양은 가려지지 않고 목록에 그대로 보인다). '읽은 글은 저장되지 않아요' 는 '확인 전 후보와 읽은 결과 목록은 저장되지 않아요. 맞아요로 확인해 초안에 넣은 글은 초안과 함께 저장돼요' 로 구체화했다(초안 본문에 넣은 글은 사용자의 글이라 초안과 함께 저장된다 — 불변 조건 ④ 그대로. 저장해 둔 초안을 다시 만들 때의 확인창 두 문구도 같은 '읽은 결과 목록' 말씨로 맞췄다 — 검증 SQ 참고 7, D-593). **전화번호·이메일·주소 모양 줄을 새로 가리거나 경고하는 동작은 더하지 않았다.**
- **I5 — 낡은 문장(D-590)**: '다음 라운드 B3 가 병합되기 전에는 `LOCAL_OCR` 를 켜지 않는다'(`ui/core/photo_text.py` 주석·`docs/UI_STATES.md`)를 지금 사실('B3 는 병합됐고 켜기는 운영자 확인 뒤 별도 번호 요청으로')로, `ocr_addon/call_worker.py` 머리의 '앱 저장소에 넣지 않는다' 를 사실('저장소에 있지만 저장소 밖 도구를 가져와 쓰므로 저장소 안에서는 그대로 돌지 않는다')로 고쳤다. `ocr_addon/README.md`·`NOTICE`·`docs/PACKAGE_OCR.md` 의 같은 종류 낡은 문장은 그 문서를 고치는 다른 갈래(OCR-N1)의 몫이다.

### 켜기 전에 알아 둘 한계와 할 일 (D-591)
- **R1 — 신뢰의 뿌리는 모델 둘·글자 사전에만 앱 소스다**: 앱 소스에 박힌 것은 모델 둘과 글자 사전의 크기·SHA-256 뿐이다. 작업자 실행 파일(`ocr_worker.exe`)과 런타임 DLL·pyd(묶음 파일 107개 가운데 그 셋을 뺀 나머지)는 정보 파일(`OCR_INFO.json`)이 스스로 적은 크기·해시와만 견준다 — 정보 파일과 실행 파일을 함께 바꾼 묶음(예: 다른 곳에서 받은 가짜 추가 도구 압축 파일)은 `verify()` 가 ok 로 보고 사용자 권한으로 실행된다(같은 권한의 악성코드는 앱 본체도 바꿀 수 있어 새 권한은 아니지만 '추가 도구를 따로 받아 푸는' 흐름의 속임수는 못 막는다). 그래서 '신뢰의 뿌리는 앱 소스' 를 모델 둘·글자 사전에만 참인 말로 바로잡았다. **켜기 전 할 일**: 켜기 승인 변경(`LOCAL_OCR` 를 켜는 소스 한 줄)을 만들 때 같은 변경에 이번 릴리스의 `ocr_worker.exe` SHA-256(또는 정보 파일의 파일 목록을 정규화한 해시) 한 줄을 앱 소스에 박고 `verify()` 가 견주게 한다 — 추가 도구를 다시 만들면 앱 소스도 함께 바뀌는 짝 배포이고, 켜기 승인이 어차피 앱 소스 변경이다. **지금은 박지 않는다**: 진짜 값은 운영자의 첫 수동 빌드·실행 결과로 정해진다(빌드 흐름은 아직 러너에서 한 번도 돌지 않았다).
- **I1 — 해시 확인과 실행 사이의 틈**: `verify()`(약 206MB 전체 해시)와 작업자를 띄우는 사이, 그리고 작업자가 `_internal` 의 DLL 을 읽는 때까지의 몇 초 동안 파일이 바뀔 수 있다. 같은 사용자 권한의 공격자는 앱도 바꿀 수 있어 새 권한은 아니지만, 다른 사용자가 쓸 수 있는 폴더(공유 폴더 등)에 풀어 두면 열린다 — **추가 도구는 본인만 쓰는 폴더에 푼다**(설치 안내 문서에 같은 권고를 넣는 일은 그 문서를 고치는 갈래와 총괄이 합친다).
- **I2 — 윈도 오류 보고(WER)**: 작업자(또는 앱)가 네이티브 수준에서 비정상 종료하면 윈도 오류 보고가 그 순간의 메모리(사진 픽셀·읽은 글이 들 수 있다)로 보고서나 덤프를 만들 수 있고 PC 정책에 따라 밖으로 갈 수 있다. 앱이 막을 수 있는 일은 크지 않다(레지스트리 설정은 시스템 설정 변경이라 하지 않는다) — 운영자 PC 확인 목록의 한 줄로 둔다.
- **I3 — 운영체제 수준 격리가 없다**: Job 개체는 메모리 한도와 종료만 건다. 낮은 무결성 수준·AppContainer(네트워크 능력 없음)·방화벽 규칙이 없어서 '네트워크 0'·'경로를 안 받음' 은 작업자 코드의 정직성(위 R1 의 해시)과 파이썬 가드·감사 훅에 기댄다. AppContainer 로 띄우는 것이 '네트워크 0' 을 운영체제가 지키게 하는 가장 큰 한 수지만 별도 설계·운영자 승인 사항이라 이번에 하지 않았다.
- **R5 — 남은 한계**: 감사 훅으로 `_socket` 직접 호출은 닫혔다. 닫히지 않은 것은 `ctypes` 로 WinSock·WinINet·WinHTTP 를 직접 부르거나 네이티브 확장이 운영체제 API 를 곧바로 여는 연결이다(파이썬 소켓 모듈도 감사 훅도 거치지 않는다 — 빌드의 가져오기 표 점검과 운영자의 비행기 모드 시험이 보완한다). `listen`(들어오는 쪽)은 보지 않는다. 같은 프로세스 안의 악성 코드는 가드 자체를 끌 수 있다(파이썬 수준 가드의 본질적 한계 — 운영체제 격리가 I3). 그 밖의 한계(검증 SQ 참고 1·2·3, D-593): ① 윈도의 기본 asyncio(`ProactorEventLoop`)가 거는 연결(`_overlapped` 의 ConnectEx)은 소켓 가드(래퍼)도 감사 훅도 거치지 않는다(검증이 숫자 주소 `0.0.0.1` 로 재현 — 운영체제까지 가고 가드 시도는 0). 풀린 소스에서는 열려 있지만 배포 묶음은 빌드 규칙이 asyncio 와 `_overlapped` 를 빼므로(`FORBIDDEN_MODULES`·`RUNTIME_ABSENT` — 동결본 `--selftest` 가 asyncio 를 못 가져와야 통과) 동결본에는 이 길이 없다. 그 보증은 첫 수동 빌드의 점검부터이므로 아래 켜기 변경 목록에 '동결본에서 asyncio 불가' 확인을 둔다. ② `install()` 은 `enable_audit()` 의 거짓 반환(소켓 모듈에 `_socket` 이 없음 — 진짜 CPython 에서는 일어나지 않고 시험의 가짜 소켓 모듈에서만 쓴다)을 무시한다 — '훅이 안 걸리면 작업자가 시작하지 않는다' 는 `enable_audit()` 가 예외를 낼 때에만 하는 말이다(진짜 `worker_main` 에 앞선 훅이 걸기·확인 이벤트를 거절하게 한 검증 실험 둘이 모두 종료 코드 70). 동결본에서 감사 훅이 켜졌는지(`stats()['audit']`)는 첫 수동 빌드의 `--selftest` 로 확인하는 일을 켜기 변경 목록에 둔다(`worker_main.py` 가 보고에 그 칸을 싣고 `build_rules` 가 켜짐 아님이면 실패로 보는 일은 동결본 코드와 빌드 갈래의 변경이라 이번 범위 밖 — 제안). ③ 빈 주소(모든 인터페이스) 묶기 `bind(('', n))` 는 통과하고(`'0.0.0.0'` 은 막는다) `listen` 은 보지 않는다 — 들어오는 연결로는 작업자가 응답할 코드가 있어야 정보가 나간다.
- **운영자에게 물을 후보(지금 결정하지 않았다)**: ① 읽은 글의 전화번호·이메일·주소 모양을 가리지 않고 `맞아요` 를 누를 때 한 번 더 경고할까요(추천: 가리지 않고 경고 — 영수증·명함 사진의 전화번호가 공개용 초안으로 가는 것을 막되 정상 글을 잃지 않는다) ② 켜기 승인 변경에 작업자 실행 파일 해시 고정(R1)을 같이 넣을까요(추천: 예) ③ AppContainer 로 띄우는 별도 설계를 할까요(I3).

### 켜기 변경 목록 — 켜기 승인 변경과 첫 수동 빌드·실행에서 같이 할 일 (D-593)

켜기(`LOCAL_OCR` 를 켜는 소스 한 줄)는 지금 정하지 않았고 운영자 확인 뒤 별도 번호 요청으로 한다. 그 변경을 만들 때 같이 해야 할 일을 한곳에 모은 목록이다 — 위 한계에서 '켜기 전에' 라고 한 것들의 색인이고 지금은 아무것도 켜거나 바꾸지 않는다(검증 SQ 참고 1·2 반영).
- **작업자 실행 파일 해시 고정(R1, D-591)**: 켜기 변경과 같은 변경에 이번 릴리스의 `ocr_worker.exe` SHA-256(또는 정보 파일의 파일 목록을 정규화한 해시) 한 줄을 앱 소스에 박고 `verify()` 가 견주게 한다. 값은 운영자의 첫 수동 빌드·실행 결과로만 정해진다.
- **동결본에서 감사 훅이 켜졌는지(R5 ②, 검증 SQ 참고 2)**: 첫 수동 빌드의 `--selftest` 로 `stats()['audit']` 가 켜짐임을 확인한다. 지금 `--selftest` 보고에는 소켓 가드 칸(`guard_active`)만 있고 감사 훅 칸이 없다 — `worker_main.py` 는 동결본에 들어가는 파일이라 이번에 바꾸지 않았다. 그래서 켜기 변경과 함께 보고에 그 칸을 싣고 켜짐이 아니면 빌드 점검(`build_rules`)이 실패로 보게 하는 변경을 묶는다(제안 — 동결본 코드와 빌드 갈래의 일). 소스로 도는 작업자에서는 `tests/test_ocr_worker_guard.py` 가 같은 칸을 이미 확인한다.
- **동결본에서 asyncio 불가(R5 ①, 검증 SQ 참고 1)**: 첫 수동 빌드의 `--selftest` 보고(`imports_optional`)에서 `asyncio` 가 '없음' 이어야 한다 — 빌드 점검(`RUNTIME_ABSENT`)이 이미 요구하므로 첫 빌드가 통과하면 확인된 것이고, 통과하지 못하면 윈도 기본 asyncio 의 연결이 가드 밖에서 열려 있다는 뜻이라 켜기 전에 막는다. 풀린 소스(개발·a 단계 가상환경)로 작업자를 띄우는 경우에는 이 보증이 없다.
- **I1·I2(위)**: 추가 도구는 본인만 쓰는 폴더에 푼다(설치 안내 문서의 같은 권고는 그 문서를 고치는 갈래와 총괄이 합친다). 윈도 오류 보고(WER)는 운영자 PC 확인 목록의 한 줄로 둔다.
- **이번에 하지 않은 것(제안으로만 — 범위 밖)**: `worker_main.py` 보고의 `audit` 칸과 `build_rules` 의 켜짐 점검 · `--selftest` 에 `_socket` 직접 음성 대조 여섯째를 더하는 일(D-592 ④) · (작업자 PATH 를 짜는 `build_environment` 를 윈도에 직접 물은 폴더로 바꾸는 일은 AS2-A 가 했다 — D-600) · `publish/gitrepo.py` 와 `ocr_addon/call_worker.py` 의 이름만 부르는 `taskkill`(앞은 외부 쓰기 관문 뒤라 이 빌드에서는 닿지 않고 뒤는 묶음에 들어가지 않는 시험용 기록 도구다) · 윈도 디렉터리 정션(`os.path.islink` 가 링크로 보지 않는다 — D-588).

## 백업·복원·키·시험 훑기 감사(AS-S1) 필수·권고 처리 — 허용 목록·되돌리기·링크·WAL (D-605에서 D-619, 2026-11-23)

독립 감사 AS-S1(앱 main f815812, 글자 읽기 제외)이 낸 필수 4·권고 6·참고 22 중 백업·복원·키·시험 훑기 쪽(필수-3·4, 권고-1·2·3·6, 참고 일부)을 처리했다. 기존 검사와 시험은 약해지지 않았고(바뀐 기존 단언은 D-612 의 하나뿐 — 누설 쪽으로 더 엄격하다. 기존 시험 파일 둘에는 항목과 훑기 도우미만 덧붙였다) 앞 절(L8·L8b)의 줄은 고치지 않는다. 앞 절이 '해결' 이라 적은 줄 중 하나가 사실이 아니었으므로 아래 첫 항목이 바로잡는다. 이어서 합친 묶음의 독립 검증(안전 렌즈 S·시험 렌즈 Q)이 낸 지적 — 점 마디 가드·WAL 사본·링크 폴더 자신·소스 훑기 — 을 같은 절에 D-616에서 D-619 로 이었다(해당 항목 끝에 '2차' 로 적었다).

### 정정 — 연결한 폴더 경로의 네트워크 가드는 NT 이름공간 표기에 뚫려 있었다(D-605)

앞 절 L8 의 '설정의 연결한 폴더 경로도 본다' 는 글이 역슬래시 둘로 시작할 때만 막았다. 윈도 파일 호출은 `\??\` 를 NT 경로로 받아 `\??\UNC\서버\공유` 를 네트워크 공급자로 보내므로(루프백으로만 확인 — 오류 67) 그 표기와 `/??/UNC/서버/공유`·`\??\GLOBALROOT\Device\Mup\서버\공유` 는 가드를 지났다. 이제 허용 목록(`_plain_local_shape`)이다: 빈 글·드라이브 글자 절대경로·맨 앞이 구분자가 아닌 글(상대·홈 약식)·구분자 하나로 시작하는 경로(`\??\`·`\DosDevices\`·`\GLOBAL??\` 제외 — 대소문자 무시·`/` 와 `\` 같게·앞 공백 걷음)만 받는다. 복원 직후 그 경로를 열어 보는 곳도 한 번 더 거친다. 한계: 연결 화면에서 사용자가 직접 고른 경로·매핑된 네트워크 드라이브 글자·링크가 가리키는 네트워크는 글자만으로는 알 수 없어 받는다. 복원 되돌리기 거절(앞 절 L8b 한계 ①)의 정책은 정하지 않았다. **2차(D-616):** 이 가드는 글자 그대로의 맨 앞만 봐서, 구분자 바로 뒤에 점 마디가 오는 글(`/./??/UNC/서버/공유` 꼴 — 점 마디·겹친 구분자 접두)은 보통 경로로 보였는데 앱이 여는 글(`Path(os.path.expanduser(글))` — pathlib 이 겹친 구분자와 `.` 마디를 지우고 다시 만든다)은 NT 이름공간 표기의 UNC 경로였다. 이제 원문과 정리한 글(`_opened_text` — 윈도 방식 정리라 리눅스 CI 에서도 같다) **둘 다** 보통 경로 모양일 때만 받는다. `..` 접두는 정리 뒤에도 NT 접두가 아니라(윈도도 현재 드라이브 뿌리 안으로 푼다) 받는다. 연결 화면·`--repo`·환경 변수로 사용자가 정한 경로(`Context.repo_path`)에는 이 가드를 걸지 않았다 — 사용자의 선택이고 UNC 저장소를 쓰는 길을 막게 된다(복원이 설정에 새 글을 넣는 길만 이 가드가 닫는다).

### 복원 도중 판 올리기가 실패해도 지금 보관함은 원래대로다(D-606·D-607)

복원은 보관함을 SQLite 백업 호출로 한 번에 덮은 뒤 판 올리기를 한다. 그 뒤 단계가 실패하면 예전에는 되돌리기가 그 보관함을 건너뛰어 지금 보관함이 백업 내용으로 남았는데 화면은 '원래대로 돌려 두었어요' 라고 했다(앞 절 L8b·D-387·D-463 의 약속이 깨졌다 — 원본은 안전 사본에 있었다). 겹이 셋이다: ① 낮은 층(`restore_from`)이 덮기 전에 지금 내용을 메모리에 담고 실패하면 되돌린다(켠 쪽만 — 전체 복원·옛 `restore` 명령·주제 엔진 복원. 기본은 옛 동작 그대로) ② 전체 복원이 '덮인 채 남았다' 표시를 보면 안전 사본에서 되돌리고 되돌린 뒤 안전 사본과 같은지 확인해 다르면 notes 와 표지로 알린다 ③ 주제 엔진 복원은 직전 상태 백업에서 되돌린다. 덮이지 않은 채 실패한 보관함(다른 곳이 쓰는 중)은 건드리지 않아 다른 창의 새 글을 잃지 않는다. 덮은 뒤 `KeyboardInterrupt`·`SystemExit` 같은 중단이 나도 같은 길로 되돌리고, 되돌린 뒤 그 예외를 삼키지 않고 다시 던진다(D-619 시험이 못박는다).

### 링크를 따라가지 않는다(D-608)

백업 폴더 자리에 놓인 junction·심볼릭 링크는 목록·정리·복원이 따라가지 않는다(`_is_link` 하나 — 클라우드 자리표시는 링크가 아니다). 복원 임시 파일 `이름.restoring` 의 자리는 쓰기 전에 비운다. 앞 절·주석의 '링크는 따라가지 않는다' 가 junction 에는 사실이 아니었다. **2차(D-618): 폴더 자신과 그 바로 아래 항목까지** 본다 — 처음에는 항목마다만 검사해서 안전 사본 폴더(`backups/before-restore`) 자체가 junction 이면 목록을 보기만 해도 목적지의 폴더가 지워졌다. 이제 백업 폴더 둘(`backups`·`backups/before-restore`) 자신이 링크이면 목록은 비고, 임시 폴더·옛 사본 정리는 아무것도 지우지 않고, 그 안의 이름은 되돌릴 사본으로 받지 않는다. **한계(사실대로):** 그 위(데이터 폴더·`backups` 의 윗 폴더)가 링크인 경우는 같은 사용자의 선택이라 따라간다. 링크인 폴더에 새 사본을 쓰는 쪽(백업 만들기)은 막지 않는다 — 그 안은 목록에 보이지 않는다. `backups` 를 일부러 링크로 옮겨 쓰는 PC 에서는 목록이 비어 보인다.

### WAL 머리표시 보관함은 열기 전에 거절한다(D-609)

앱은 롤백 저널 방식만 만든다. 들어오는 보관함의 머리 20바이트가 WAL 표시(18·19번째 바이트가 2)이면 SQLite 로 열기 전에 거절한다 — 열면 백업 폴더에 `-wal`·`-shm` 이 생겨 '읽기만 한다' 가 깨진다. 전체 복원은 `FULL_BACKUP_INVALID` 이유 `structure`, 옛 복원 길은 '온전한 백업이 아님'. 새 종류를 `schema_guard` 에 더하지 않고 별도 함수로 했다(그 모듈은 연결 없이 읽는 잎 모듈로 못박혀 있다). **2차(D-617):** 지금 보관함이 앱 밖 도구로 WAL 방식이 된 PC 에서는 앱이 만든 사본(`Store.backup`·`EngineFile.copy_to` — 지우기 전 사본·`backup` 명령·복원 직전 사본·`topics backup`)도 SQLite 백업이 머리를 그대로 옮겨 WAL 머리가 되어 이 거절에 걸렸다(옛 `restore` 명령의 '검사 실패 시 방금 만든 사본으로 되돌리기'와 수동 복구가 막혔다). 이제 사본을 만들 때 사본 연결을 `journal_mode=DELETE` 로 낮춰 앱이 만든 사본은 늘 롤백 저널 머리다(낮추지 못하면 사본을 쓰지 않고 `BACKUP_FAILED`). 이 수정 전에 만든 사본이 WAL 머리면 앱 밖 도구로 열어야 한다. 앱 밖에서 들어온 WAL 파일의 거절은 그대로다.

### 키 보관소와 가리기(D-610·D-612)

`KeyStore.exists()` 는 값을 파이썬 bytes 로 꺼내지 않고(`Win32CredApi.exists` — OS 쪽 사본을 읽지 않고 0 으로 덮고 `CredFree`) 존재 여부만 묻는다. `decode_fields` 는 `RecursionError` 도 쉬운 오류로 바꾸고, `KEY_TOO_LONG` 세부는 입력의 크기를 말하지 않는다. 주소 인자 `client_id` 의 값을 가린다(알려 둔 오탐: OAuth 의 `client_id` 도 값이 가려진다). 앞 절의 한계 ⑧(`RedactingStream`)의 보충은 그 자리(한계 문단 바로 뒤)에 적었다.

### 시험 훑기와 깊은 JSON(D-611·D-613)

'바깥과 닿는 길은 표가 전부' 시험은 **정직한 코드의 회귀 그물**이다 — 새로 쓴 평범한 코드가 바깥으로 나가는 길을 만들면 빨개지게 할 뿐 일부러 숨기는 코드를 막는 방어가 아니다(D-359). 그 시험이 우회 모양(`from os import …`·`import os as 별칭`·`getattr(os, …)`·`ctypes`·`winreg`·`msvcrt`·`pty`·`runpy`·`importlib.import_module`·`__import__`·`exec`·`eval`)을 보고, `ctypes` 를 가져오는 다섯 파일(`security/keystore.py`·`service/liveness.py`·`ui/single_instance.py`·`ui/winroot.py`·`ui/ocr_adapter.py`)과 `vendor/` 안의 바깥 모듈을 이유가 달린 표로 못박는다. **2차(D-619)** 로 더 본다: 운영체제 내장·C 쪽 모듈(`nt`·`posix`·`_winapi`·`_socket`·`_ssl`·`_posixsubprocess`·`_multiprocessing`)·`antigravity`·파이썬 3.10 의 `asyncore`·`smtpd`, 내장 이름을 속성으로 부르는 `builtins.__import__`·`__builtins__.exec`·`from builtins import exec`, 이름 없이 꺼내는 `os.__dict__`·`os.__getattribute__`·`vars(os)`·`vars(__builtins__)`·`getattr(builtins, …)`·`sys.modules[…]` 읽기, 다른 모듈이 다시 내놓는 `glob.os.system`·`gitrepo.subprocess`·`from ..publish.gitrepo import subprocess`, `QtGui.QDesktopServices`·`getattr(QtGui, 'QDesktopServices')`, `import importlib as 별칭`. 이름 규칙으로는 **보지 못하는** 것 열 가지(글을 실행하는 표준 모듈 `timeit`·`cProfile`·`pdb`·`code`·`ensurepip`, `operator.attrgetter`, `compile` 로 만든 함수, `importlib.util.module_from_spec`(앱의 적재기 둘이 평범하게 쓴다), 글자 속 경로(`ATTACH`·`Path` 의 서버 경로))는 시험의 `HONEST_LIMITS` 표에 이유와 함께 적어 두었고, 지금 소스는 위반 0 이며 허용 표는 정확히 일치한다. 깊게 겹친 JSON(1000–1500 단)은 원시 `RecursionError` 가 아니라 쉬운 오류가 되고, 훑기가 재귀 한도에 걸려도 글 전체를 일반 글로 다시 훑어 숨긴 키 모양을 놓치지 않는다(`FULL_BACKUP_BLOCKED`). 파이썬의 json 이 그 깊이를 읽지도 못하는 판(3.10 은 약 990단부터)에서는 훑기 앞의 읽기에서 `FULL_BACKUP_INVALID` 로 거절된다 — 어느 쪽이든 복원은 거절되고 아무것도 바뀌지 않는다.

### 이 묶음이 하지 않은 것(D-615)

감사 참고-4·5·6·14–17·19·22 는 이월한다(막지 않아도 되는 참고 — 대부분 외부 쓰기를 켜는 변경 때 같이). 되돌리기의 메모리 사본은 보관함 크기만큼 메모리를 쓰고 시간 한도는 없다(전체 백업의 사본에는 있다). `requirements-package.txt` 해시 잠금은 `.github/`·잠금 파일이라 제안만이다. 2차 검증의 참고 가운데 이월·한계로 적어 두는 것: `same_database` 는 두 보관함의 판이 다르면 표마다 행 수만 견준다(판이 다르고 행 수가 같은데 내용이 다른 경우는 못 본다 — 안전 사본이 옛 판일 때뿐이고 되돌림이 페이지 단위 복사라 실제 위험은 작다) · 옛 `restore` 명령은 덮인 채 되돌리지 못해도 방금 만든 사본으로 되돌리지 않는다(이중 실패에서만이고 옛 동작과 같다) · 복원 임시 파일 `.restoring` 을 O_EXCL 로 만들지 않는다(지운 직후 같은 이름에 링크를 다시 심는 틈 — 같은 사용자 위협) · 링크 종류는 심볼릭 링크·마운트 지점 둘로 못박았다(이름을 돌리는 새 종류는 name surrogate 비트로 가를 수 있다) · 백업 설정 경로 안내 한 줄(`INCLUDED_PATH_NOTE`)은 아직 화면에 오르지 않는다 · `client_id` 가림은 주소 인자 꼴뿐이다(폼 본문·설정 줄·JSON 은 한계 ⑦ 과 같은 부류).

## 앱 2차 독립 감사(AS-S2) 필수·권고 처리 — 사진 입력 표지 확인·복사 관문·복원 훑기 정규화·속도 (D-680에서 D-684)

앱 2차 독립 감사(AS-S2, 2026-11-24, 대상 main 9439047)의 필수 1건과 권고 4건(권고-1·3·4)을 이 묶음(구현 갈래 ASFIX-A)이 고쳤고, 같은 파일의 참고 항목 일부를 함께 처리했다. 나머지 권고(백업·복원 순서·vendor·시험 틈)는 다른 갈래의 몫이다.

### 사진은 형식을 확인하기 전에 해석하지 않는다(필수-1 — D-680)

**문제(감사가 직접 재현).** 이름이 `.jpg`·`.jpeg`·`.png`·`.webp` 이고 안이 SVG 인 파일(100바이트면 된다)을 사진 정리 창에 넣기만 해도, 판정이 형식을 보기 전에 이미지 읽기 도구(`QImageReader`)에 크기를 물었고 Qt 가 SVG 를 통째로 해석하면서 그 안의 `<image href>` 경로(상대 경로·절대 경로·네트워크 위치)를 **앱 프로세스가 직접 열었다**. 네트워크 위치면 윈도가 파일 공유 접속과 로그인 시도를 한다(IP·윈도 계정 이름·열람 확인 신호가 나갈 수 있다 — 사진이나 글 내용이 나간 것은 아니다). 형식 거절은 그 뒤라서 거절돼도 이미 열린 뒤였다. 미리보기와 글자 읽기 입력도 판정 없이 같은 해석기를 바로 썼다.

**고친 것 — 순서가 안전이다.** 사진 한 장을 읽는 길 셋(넣을 때의 판정 `imagecheck.judge`·화면의 미리보기 `imagecheck.make_thumbnail`·글자 읽기에 보낼 사진 준비 `ocr_input.prepare`)이 모두 같은 관문을 읽기 직전에 지난다.

1. 파일 앞 12바이트(JPEG `FF D8 FF`·PNG 서명 여덟 바이트·WebP `RIFF`+`WEBP`)를 앱이 직접 본다(`imagerules.sniff_format`). 읽기 도구가 말하는 것을 믿지 않는다.
2. 표지가 있을 때**만** 읽기 도구를 만들고, 만들 때 **형식을 못박고 자동 추측을 끈다**(`imagecheck.pinned_reader` — `QImageReader(경로, 형식)` + `setAutoDetectImageFormat(False)`). 파일 속 내용이 다른 형식이어도 SVG 같은 해석기가 골라질 수 없다.
3. 표지가 없는 파일(SVG·GIF·BMP·TIFF·PDF·글자·빈 파일)에는 읽기 도구를 **만들지 않는다**. 흔한 다른 형식으로 보이면 '지원하지 않는 파일이에요', 아니면 '사진 파일이 아니에요' 로 알린다(안내 문구는 그대로).
4. 읽기 도구가 지원하지 않는 형식을 말해도 `size()` 는 부르지 않는다(읽을 수 있나 → 형식 → 지원 형식일 때만 크기). 크기를 읽지 못한 잘린 사진(머리만 있는 JPEG·서명만 있는 PNG)은 '사진을 읽지 못했어요' 로 안내한다(예전에는 크기 -1x-1 로 통과했다 — 감사 참고-1).

**시험.** 순수 `tests/test_ui_imagegate.py`(가짜 읽기 객체의 호출 기록 — 표지 없는 파일에는 읽기 도구가 만들어지지 않고 지원하지 않는 형식에는 크기를 묻지 않는다, 지원 형식 집합을 글자 그대로 못박기, 소스 규칙으로 `QImageReader(...)` 를 직접 만드는 곳이 없음을 확인)와 Qt `tests/test_ui_qt_imagegate.py`(진짜 위장 SVG·GIF·PDF·TIFF·BMP 로 세 입구를 돌려 읽기 도구가 하나도 만들어지지 않음을 본다. 옛 방식으로 읽으면 바깥 그림의 화소가 그려진다는 대조 포함). 윈도 이름 있는 파이프로 '앱이 경로를 여는가' 를 직접 재 보는 탐침은 감사 보고서의 것을 보고서 폴더에 복사해 고치기 전·후를 견줬다(시험에는 윈도 전용 호출을 넣지 않는다).

**하지 않은 것(운영자 몫 — 제안).** 포장에서 `imageformats/qsvg.dll` 을 빼면 SVG 는 아예 읽히지 않아 공격면이 사라진다(`packaging/build_package.py`·`gui_entry.py`·`docs/PACKAGE.md` 44·85줄·점검 항목 `qt_plugins` 의 기대값을 함께 고쳐야 한다). 화면 아이콘은 `QSvgRenderer` 를 직접 써서(`ui/qt/theme.py`) 이미지 형식 플러그인이 필요 없어 보이지만, **포장본을 만들어 실행해 확인해야** 하므로 이 묶음은 하지 않았다. 위 관문이 있어서 플러그인이 들어 있어도 사진 길로는 SVG 가 해석되지 않는다.

### 큰 글에서 복사 관문이 제곱 시간이 걸리지 않는다(권고-4 — D-681)

**문제(감사가 실측).** 같은 24자 토큰이 되풀이되는 글에서 막은 자리를 짚는 함수(`draft_rules.secret_places`)가 2천 자 0.07초 → 4천 자 0.26초 → 8천 자 0.99초 → 1만 6천 자 3.79초로 두 배마다 3.8배 늘었다(저장 한도 15만 자까지 같은 모양이면 약 5분 — 복사 단추를 누르는 화면 스레드가 멈춘 듯 보인다). 원인 둘: ① 막은 자리마다 글 **전체**를 본문 속 비밀 형태 검사기로 다시 훑었는데 그 결과로 바뀌는 값이 없었다(바로 위 한 줄이 이미 같은 값을 정한다) ② 검사기가 찾은 자리를 더할 때 자리마다 앞의 모든 자리와 하나씩 견줬다.

**고친 것.** 쓸모없는 되훑기를 지우고 겹침 판정을 정렬한 목록의 이분 탐색으로 바꿨다(`_add_free_spans`). **판정은 한 글자도 바뀌지 않는다** — 옛 구현을 시험 도구(`tests/draft_gate_oracle.py`)에 그대로 옮겨 두고 서로 다른 입력 2,400개와 무작위 구간 6천 쌍에서 걸린 자리·미리보기가 같음을 견줬다. 검사기는 글 하나에 한 번만 돈다(호출 횟수 시험 — 시간 비율은 흔들려서 보조로만 본다).

**고친 뒤 실측(같은 입력 사다리).** 같은 24자 토큰의 `secret_places`: 고치기 전 8천 자 1.44초 → 1만 6천 자 7.35초(2.5초를 넘어 중단), 고친 뒤 1만 6천 자 0.13초 → 3만 2천 자 0.27초 → 6만 4천 자 0.41초(두 배마다 약 2배). 검사기 모양(`AKIA…`)이 되풀이되는 글의 `secret_spots`: 고치기 전 3만 2천 자 0.42초 → 6만 4천 자 2.09초(두 배마다 약 5배), 고친 뒤 3만 2천 자 0.03초 → 6만 4천 자 0.06초. (이 PC 는 공용이라 시각에 따라 절대값이 흔들린다 — 같은 때 두 번 쟀다. 길이 열 배에 시간 스무 배 미만은 시험이 지킨다.)

### 복사 전 관문이 '이름 붙은 값'도 막는다(권고-1 — D-682)

**문제(감사가 재현).** 복사 전 관문(`ui/core/draft_rules.py`)은 접두사 모양(`AIza…`·`ghp_…`)·24자 넘는 영숫자 덩어리·검사기 여섯 유형만 봤다. 그래서 운영자가 메모(계정·비밀번호 줄)를 글에 붙여 넣으면 `password: Hunter2xyz`·`secret=Ab12Cd34` 같은 글이 막힘도 확인창도 없이 클립보드로 갔다 — 로그에는 가려지는 값이 블로그 글을 거쳐 나가는 길이 열려 있었다(가리기 규칙 `security/mask` 는 이런 글을 가리지만 복사 관문은 그 규칙을 쓰지 않았다).

**고친 것.** `security/shape.py` 에 `named_secret_spans`·`is_secret_like_value` 를 더하고, 복사 관문의 `secret_spots` 가 **주소를 지운 글**에서 그 자리도 걸린 자리로 센다(제목·본문·작은 복사 모두 — `글 검사하기` 의 보이는 조각 가리기도 같은 함수를 쓴다). 올리기 직전 관문(`service/gate.py`)에도 같은 검사를 더했다(`[NAMED_SECRET]`).

- **이름**: 가리기 규칙의 이름 목록(`mask._NAME_WORDS` — password·secret·token·credential·sessionid·`api key` 계열)과 같은 것 + 한국어 비밀번호·비번·패스워드·시크릿·인증키. `:`·`=`(전각 포함)로 값이 이어지는 꼴이다(`password: 값`·`"secret" = "값"`·`DB_PASSWORD=값`·`비밀번호：값`).
- **값이 키·비밀번호처럼 생겼을 때만**: 키·토큰에 쓰이는 글자(`A-Z a-z 0-9 _ - + / = . : ! @ # $ % ^ *` 와 물결표)로 이어진 머리가 6자 이상 200자 이하이고 영문자와 숫자가 함께 있다. 설명 문장(`비밀번호: 8자 이상`)·코드(`token = get_token(user1)`·`req.body.password1`)·자리 표시(`<your password>`·`YOUR_API_KEY`·`********`·`$TOKEN_1`)·숫자뿐이거나 글자뿐인 값은 막지 않는다. 주소 인자(`?token=…`)는 이 규칙이 아니라 주소 규칙이 본다(옛 판정 그대로 — D-312 의 한계).
- **안전한 기본값은 '막고 수정을 요청한다'**(위임 규칙) — 예시 값이 비밀번호처럼 생겼으면 예시여도 막는다. 안내 문구(`drf_secret_body`)가 '이름 뒤에 값을 적은 글도 같아요 — 값을 지우거나 문장으로 바꿔 쓰면 복사할 수 있어요' 로 풀어 준다(앞부분은 기존 시험이 못박은 그대로).
- 막은 자리의 미리보기는 값을 되풀이하지 않는다(이름 쪽 앞 글과 `[가림]` 표시뿐). 또 미리보기의 앞 글(14자)이 바로 앞의 다른 비밀의 꼬리를 그대로 보이던 것(감사 참고-12 — `gap=' '` 에서 재현)도 함께 고쳤다: 짧은 이름 붙은 값이 이웃하면 앞 값 전체가 보일 수 있기 때문이다. 앞 글 안의 걸린 자리는 `[가림]` 표시로 바뀐다.

**시험.** `tests/test_ui_named_secret_gate.py` 23개 — 이름 × 구분 × 값 조합 1,488가지가 모두 막히고 미리보기가 값을 되풀이하지 않는다 · 설명 문장·코드·자리 표시 49개와 기존 정상 예문 205개(일상·건강 대조·정상 주소·파일 이름·88개 주소)는 하나도 막히지 않는다 · 이름 붙은 값이 없는 글의 판정은 옛 판정과 한 글자도 다르지 않다 · 이웃한 비밀이 미리보기에 되풀이되지 않는다 · 병적인 글에서도 길이에 비례해서만 늘어난다. 4번 묶음의 속도 시험이 옛 방식과 견주는 기준(`tests/draft_gate_oracle.py`)도 이 이웃 가림 한 가지만 새 방식을 따르게 고쳤다 — 옛 출력과 달라지는 입력은 걸린 자리가 둘 이상인 글뿐이다.

**한계(사실대로).** 값이 숫자뿐이거나 글자뿐이거나 여섯 글자 미만인 비밀번호, 공백이 든 값, 이름 없이 적은 값은 못 본다(막으면 `비밀번호: 1234` 같은 설명이 모두 잠긴다). 한국어 이름은 다섯 개뿐이다('암호'·'토큰' 은 일반 낱말로도 흔해 뺐다). 쪼갠 이름·전각 이름·키릴 동형 글자로 바꾼 이름은 이 규칙이 못 본다(적대적 쪼개기는 운영자 자신의 사고를 막는 이 관문의 범위 밖 — 감사 참고-10·11). **운영자에게 알림: 오탐 정책** — 예시 값도 막으므로 비밀번호 설명 글에서 막힐 수 있다. 막힘이 너무 잦다고 느끼면 '그래도 복사' 확인창으로 바꾸는 선택지가 있으나(안전 쪽을 줄이는 변경이라 승인이 필요하다) 이 묶음은 안전한 기본값을 골랐다.

### 복원 전 비밀 모양 훑기 앞에 정규화를 둔다(권고-3 — D-683)

**문제(감사가 재현).** 복원할 백업의 비밀 모양 훑기가 칸의 바이트를 UTF-8 로만 풀었고(전체 백업) 아예 풀지 않았다(주제 엔진 백업 — SQLite 덤프는 BLOB 을 16진수로 적는다). 그런데 앱은 같은 칸을 `json.loads(바이트)` 로 읽고, 그 함수는 UTF-16·UTF-32 를 알아서 알아본다. 그래서 가짜 키를 **UTF-16 BLOB** 으로 담은 조작 백업(목록의 해시·크기·항목 수까지 맞게 만든 것)이 `verify_backup` 을 통과해 복원됐고 지금 보관함에 키 글이 들어왔다(복사 관문이 마지막에 막으므로 곧바로 새는 길은 아니지만 '자격 증명은 백업에서 제외' 규칙과 훑기의 보증이 약해진다). JSON 파일(씨앗·캘린더)은 원문 글자를 훑어 **`\uXXXX` 이스케이프**로 쪼갠 가짜 키를 못 봤다(JSON 으로는 같은 글).

**고친 것.** 새 모듈 `security/views.py` — 훑기 앞의 정규화이며 **글자를 바꾸지 않고 보기만 늘린다**: 바이트는 UTF-8(예전 그대로)·앱이 읽는 방식과 같은 감지(`json.detect_encoding` — BOM·널 바이트 모양)·널 바이트를 뺀 글(감지가 어긋나도 걸리게)·UTF-16/32 두 바이트 순서로 푼 보기들, 글은 널 글자를 뺀 보기와 JSON 이스케이프를 푼 보기. 전체 백업의 칸 훑기(`backup_flow._scan_cell`)와 주제 엔진 백업의 훑기(보관함 덤프 줄의 BLOB 16진수 값을 바이트로 풀기(그 글의 이스케이프도 푼다) · JSON 글의 이스케이프 풀기 — 백업을 만들 때·복원 전 확인·지금 파일 확인 세 곳)가 모든 보기를 훑어 하나라도 걸리면 걸린 것으로 본다. 풀 수 없는 모양은 없다(대체 글자로 풀리고 예외를 내지 않는다 — 길이가 홀수인 16진수 글은 BLOB 이 아니라 글이라 풀지 않는다). 발행 이력 장부 행은 여전히 훑지 않는다(D-75). 널 바이트가 없는 바이트는 UTF-16·UTF-32 로 풀어 볼 까닭이 없어(영문 키 모양이 나올 수 없다) 보기가 하나뿐이라 큰 BLOB 의 비용은 그대로다.

**시험.** `tests/test_security_decoded_scan.py` 21개 — 열두 가지 인코딩(UTF-8·BOM·UTF-16 LE/BE/BOM·UTF-32 …·널 바이트 끼움·한 바이트 어긋난 UTF-16·JSON 한 줄 UTF-16)의 가짜 키가 두 훑기 모두에서 걸리고, 평범한 BLOB·UTF-16 글·정상 JSON 은 막히지 않는다 · 조작 백업(전체·주제 엔진)은 `verify_backup`·`read_backup`·`make_backup` 에서 거절된다 · 이스케이프로 쪼갠 키가 든 씨앗 파일은 만들 때·복원 전·지금 파일 확인에서 모두 걸린다.

**한계(사실대로).** base64·16진수로 다시 인코딩한 값·전각 글자·이름 없는 값은 이 정규화가 풀지 않는다(결정된 여섯 유형 범위 — 이 문서 앞 절의 알려진 한계와 같다). 복원 직전 사본을 훑은 뒤 그 사본에서 복원하는 틈 메우기(감사 참고-4)는 이 묶음이 아니다.

### 이 묶음이 하지 않은 것과 운영자에게 남기는 제안(D-684)

- **복사 관문의 두 보강 분기는 중복이 아니다(감사 참고-21).** 검사기 분기는 `access_token=` 뒤 글자뿐인 값과 전각 키에서만, 정본 패턴 분기는 `sk_live_` 뒤 글자뿐인 값과 `Bearer` 뒤 글자 17자에서만 잡힌다. 그래서 코드는 그대로 두고 각 분기만 잡는 입력을 시험(`tests/test_ui_gate_branches.py`)으로 못박았다 — 분기를 지우면 시험이 빨개진다.
- **고치지 않은 참고(이 갈래의 파일 밖)**: 참고-3(사진 목록 파일에 심은 '확인한 글자' 칸 — 불러올 때 분석 항목을 비우는 것을 제안)·참고-4·5·6·7·9(복원 순서·임시 파일 링크·잠금 시간 상한·제약 비교·데이터 폴더 네트워크 경로 — 백업·복원 갈래)·참고-8(단일 실행 이름 철자)·참고-13(이모지 오탐 — 안전한 쪽)·참고-14(오류 카드의 절대 경로).
- **운영자 승인이 필요한 제안(T3)**: 포장에서 `qsvg.dll` 빼기(위 '사진은 형식을 확인하기 전에 해석하지 않는다' 절)·윈도 클립보드 기록(Win+V)에 키가 남을 수 있다는 안내 문구(참고-15)·글자 읽기·외부 쓰기를 켜기 전 준비물(참고-17)·저장소 설정(참고-18)·의존성 해시 잠금(참고-19).
- **알려 두는 한계**: 이름 붙은 값 규칙은 숫자뿐·글자뿐·여섯 글자 미만 값과 쪼갠 이름을 못 본다. 복원 훑기 정규화는 base64·16진수로 다시 인코딩한 값과 전각 글자를 풀지 않는다. 사진 표지 확인은 JPEG·PNG·WebP 세 형식만 인정한다(앞이 어긋난 JPEG 은 사진 파일이 아니라고 알린다).

### 앱 독립 감사 2차(AS-S2) 백업·복원·vendor·시험 틈 처리(asfixb, D-690 에서 D-696)

- **주제 엔진 백업의 링크·정션(D-690)**: 전체 백업과 같은 링크 기준(`fslink.py` — 심볼릭 링크·윈도 재해석 지점 중 링크 종류, 클라우드 자리표시는 링크가 아님, 읽을 수 없으면 링크)을 주제 엔진 백업의 목록·정리·임시 폴더 자리·읽을 백업 폴더와 그 안의 파일·복원 임시 이름에 건다. 링크는 따라가지 않고(목록에서 빼고 지우지 않고 쓰지 않는다) 읽을 백업이 링크이면 쉬운 이유('링크')로 거절한다. 알려진 한계는 전체 백업과 같다: 폴더 위쪽(데이터 폴더·`backups` 의 부모)이 링크인 것은 같은 사용자의 선택이라 따라가고, 검사와 사용 사이의 틈(같은 사용자 권한의 경쟁)은 남는다.
- **받은 주제 엔진 백업을 읽는 순서와 한도(D-691)**: `topics restore` 가 되돌릴 보관함의 구조(뷰·트리거·모르는 표·색인)를 내용 질의보다 먼저 본다. 받은 보관함을 읽는 연결에만 시간 상한(60초 — 진행 처리 콜백)·길이 한도(`Connection.setlimit`, 파이썬 3.11 부터)·읽기 전 크기 상한(보관함 512MiB·설정 JSON 8MB·목록 1MiB)을 건다. 정상 데이터에는 걸리지 않고(지금 데이터를 점검하는 길에는 걸지 않는다) 걸리는 것은 조작했거나 이 프로그램의 것이 아닌 파일이다. **한계**: 파이썬 3.10 에는 `setlimit` 가 없어 길이 한도는 건너뛴다(시간 상한·크기 상한·구조 먼저가 지킨다). 전체 백업의 받은 보관함 연결에는 아직 이 한도를 걸지 않았다(순서는 이미 구조 먼저다 — D-696). 시간 상한은 SQLite 질의가 도는 동안만 끊고 파이썬이 행을 풀어 보는 시간은 끊지 않는다.
- **vendor/ 총 요약값(D-692)**: `src/chanceblog_desktop/vendor_pin.py` 의 `PINNED_DIGEST` 가 원본 커밋과 파일 이름·해시의 요약을 소스에 고정한다(`sync_core.py` 가 가져올 때만 바뀐다). 앱을 열 때(`ui/launcher.py`)·자가 점검(`vendor_core`)·`sync_core.py --check` 가 같은 값으로 견주고, 설치본의 시작과 자가 점검은 목록 밖 파일(`json.py`·`__pycache__`·링크)도 거절한다. 어긋나면 화면을 열지 않고 경로·값 없는 쉬운 한 문장으로 알린다(설치본을 다시 풀어 새로 설치). 이것은 자기참조의 높이를 한 단 올린 것이다 — vendor/·VENDOR.json·`vendor_pin.py` 를 모두 고친 변경은 여전히 통과하므로 사람이 검토해야 하고, 완전한 해결(원본 저장소의 같은 커밋과 대조하는 CI·CODEOWNERS)은 새 외부 접속·저장소 설정이라 운영자 승인이 필요한 제안이다.
- **워크플로 시험(D-693)**: `ci.yml`·`package.yml` 은 승인된 구조·액션 쌍과 글자 그대로 같아야 한다(`tests/workflow_golden.py`). 액션 SHA·단계·`with`·`env`·`run` 을 바꾸려면 시험의 목록도 같이 바꿔야 하므로 승인 때 눈에 띈다. `.github/` 파일 자체는 바뀌지 않았다.

# 화면 설계 기준 — 값·틀·검증 환경 (PySide6, 화면 기초 'G0')

> 정식 화면(GUI) 첫 묶음의 설계 기준이다. 화면 도구는 **PySide6** 로 확정됐다([`DECISIONS.md`](DECISIONS.md) D-32, D-04 의 '또는' 을 닫음). 값의 출처는 운영자가 승인한 화면 목업과 UI 명세(v1.0.0·정밀 보완 v1.1.0)·2026-11-03 22:27 채팅 세부 기준이고, **원문은 비공개라 여기에는 값(색·크기·간격)과 이름만 옮기고 문장은 새로 썼다.** 2026-11-06 부터는 운영자의 **C-Type UI 디자인 시스템 v1.0.0**(2026-11-03 기준과 같은 방향의 다듬기 — 첫 묶음 'UI-C0', 결정 D-150~D-161)이 값의 새 기준이고, 바뀐 값은 아래에 '이전 → 현재'로 적었다(참고 그림의 사진·로고는 저장소에 올리지 않는다). 구조는 [`ARCHITECTURE.md`](ARCHITECTURE.md) §5.1, 부품은 [`UI_COMPONENTS.md`](UI_COMPONENTS.md), 상태는 [`UI_STATES.md`](UI_STATES.md), 검수는 [`UI_VISUAL_QA.md`](UI_VISUAL_QA.md).

## 1. 목표 한 줄

비개발자가 설명서 없이 **추천 주제 확인 → 블로그 선택 → 초안 만들기 → 항목별 복사** 네 걸음을 끝낼 수 있게, 화면은 기능 수보다 **다음에 할 행동**을 먼저 보여 준다. 내부 값(번호·영문 상태 코드·경로·원문 응답·오류 코드)은 기본 화면에 내지 않는다(오류 코드는 접어 둔 '진단 정보' 에만).

## 2. 값은 한 곳에서 — 디자인 토큰 (`src/chanceblog_desktop/ui/core/tokens.py`)

Qt 스타일시트(`ui/qt/theme.py` 의 `build_qss`)는 이 파일의 값으로만 만든다. 화면 코드에 색(`#RRGGBB`)·글꼴 이름·인라인 스타일·배율 값을 직접 쓰지 않는다 — 시험이 소스를 훑어 막는다.

**첫 버전은 밝은 테마만이고 사용자 화면에 테마 선택이 없다** — 다만 모든 색이 `THEMES` 의 테마 값으로 한 곳에서 관리되므로 어두운 테마는 같은 키를 가진 사전을 하나 더하면 된다(시험: 팔레트 하나를 바꾸면 스타일시트가 따라 바뀜). **이름 정리(D-151)**: 예전 `primary_600` 은 이름과 달리 진한 쪽 값이었다 → 문서의 이름에 맞춰 `primary_700`(진한 쪽)·`primary_pressed`(눌림)로 바꾸고, `primary` 가 문서의 'Primary 600'(기본 파랑)이다. 화면 코드는 이 이름을 `theme.py` 한 곳에서만 불러서 바꿀 곳이 거기뿐이었다.

**간격·모서리·그림자·움직임**

- **구현(D-152)**: Qt 스타일시트로는 그림자를 못 그리므로 `theme.shadow_effect(이름)` 이 토큰 값으로 `QGraphicsDropShadowEffect` 를 만들고, `components.set_card_state(카드 틀, 상태)` 가 상태 속성(`cardstate` — 테두리 두께·색은 스타일시트가 `K.CARD_STATES` 로 만든다)과 그림자 효과를 한 번에 입힌다. 상태별 값은 `theme.card_look` 한 곳이 돌려준다. 효과는 **카드 틀 하나에만** 입힌다 — 글자가 든 위젯 전체에 입히면 효과가 안의 글자까지 한 장의 그림으로 다시 그려 흐려지고 느려질 수 있어서, 글자가 많은 부품 위에는 쓰지 않는다. 그림자는 위젯 밖으로 번지므로 효과를 입힌 카드의 **부모에 번짐(번짐 + 세로 이동)만큼 여백이 있어야 잘리지 않는다**(부품 모음의 카드 견본이 그렇게 둔다). 선택 때 테두리가 1px 두꺼워지므로 안쪽 배치를 함께 주면 안쪽 여백을 1px 줄여 안의 글이 밀리지 않는다. **지금 홈·설정의 카드는 그림자 없이 테두리만 그대로**다(구조·모양을 바꾸지 않는 것이 이번 묶음의 범위) — 그림자를 쓰는 곳은 부품 모음의 카드 견본이고, 다음 묶음의 카드가 이 두 함수를 쓴다. 카드가 많아 그림자가 무겁거나 번짐이 잘리면 테두리 강조(선택 2px 파란 테두리·가리킴 테두리 색)만으로 대신하고 그 이유를 이 문서에 적는다.
- **움직임**: 안내(토스트) 3.5초 · 움직임은 **서랍 여닫기 200ms 만 실제로 쓴다**(`MOTION_MS["panel"]`), 과한 효과 없음.
**쓰는 값과 안 쓰는 값**(시험 `test_the_tokens_nobody_uses_yet_are_the_documented_ones` 가 지킨다): UI-C0 부터 **쓰는 값** — 간격 `SPACE`(새 부품·새 스타일시트 규칙의 여백)·그림자 `SHADOW` 와 카드 상태 `CARD_STATES`(`theme.shadow_effect`·`set_card_state`)·포커스 테두리 두께 `FOCUS_RING_PX`(2)·점수 링 선 두께 `RING_STROKE_RATIO`(지름의 11%). **안 쓰는 값**(토큰에 정해만 두었고 화면 코드는 쓰지 않는다): 복사 표시 시간 `COPY_FEEDBACK_MS`(1.8초 — 이미지 화면 묶음에서 단추의 '복사됨' 상태에 쓴다)·움직임 `MOTION_MS` 의 `hover` 120ms·`page` 180ms(마우스를 올릴 때·화면이 바뀔 때 효과를 입히지 않는다 — 예전 문서의 '올림 120ms·화면 전환 180ms' 는 값만 있었다)·새 틀 크기 `FRAME`(아래 §3-3 — 쓰는 것은 UI-C1)·카드 규격 `CARD`(폭 230 이상·권장 260~300, 높이 280~330, 안쪽 여백 16, 간격 16(좁으면 12), 이미지 높이 120 — 카드 부품을 만드는 묶음이 쓴다)·크기 `SIZE` 의 `search_h`(40)·`table_head_h`(40)·`table_row_h`(48)·`hit_min`(32)·`hit_comfort`(40)(검색 칸·표를 만들 때 쓴다)·팔레트의 `focus_ring`·`focus_ring_input`.

## 2-2. 새 부품의 표시 규칙 (UI-C0 — 점수 링·구성 막대·사용량 막대·배지·탭·행동 줄)

점수 링·구성 막대·배지·탭·행동 줄은 어떤 화면에도 아직 연결하지 않은 독립 부품이다(샘플 값으로 시험하고 사진을 찍는다 — [`UI_VISUAL_QA.md`](UI_VISUAL_QA.md) §7). **사용량 막대(`UsageBar`)만 UI-C1b 부터 설정 화면의 용도 카드가 쓴다**(§4-2). 계산은 `ui/core/gauges.py`·`part_rules.py`(PySide6 없이 시험)가 하고 `ui/qt/gauges.py`·`bars.py`·`components.py` 는 그리기만 한다. 결정은 D-153~D-160.

**점수 링과 이름표(`ScoreRing`·`ScoreWithLabel`)**

| 점수 | 구간 이름 | 링 색(토큰) | 이름 글자 색(토큰) |
|---|---|---|---|
| 80 이상 | 우선 추천 | 초록(`score_high`) | `success_text` |
| 65~79 | 일반 후보 | 파랑(`score_good`) | `primary_text` |
| 50~64 | 보류 | 노랑(`score_mid`) | `warning_text` |
| 0~49 | 제외 | 빨강(`score_low`) | `danger_text` |

- **구간 경계 80·65·50 과 이름은 엔진의 점수 구간과 같은 기준이다**(`topics.channels.GRADE_CUTOFFS`·`score.band_of` — 이름은 엔진의 '우선 추천'·'일반 후보'·'보류함(점수 구간)'을 화면에서 줄여 '보류'·'제외'). UI 가 따로 지어낸 기준이 아니라는 것을 시험이 **0~100 의 모든 정수에서 엔진의 `band_of` 와 구간이 같은지**로 확인한다.
- **링 안에는 숫자만** 넣는다. 구간 이름과 변화량은 링 옆·아래의 **별도 라벨**이다 — 그래서 숫자만 그리는 `ScoreRing` 과 이를 감싸는 `ScoreWithLabel`(링 + 구간 이름 라벨 + 변화량 라벨)을 따로 둔다. 색만으로 구간을 알리지 않고 숫자와 구간 이름이 함께 보인다.
- **크기**: 카드용 지름 44(문서 40~44)·상세용 72(문서 68~80), 선 두께 지름의 11%, 빈 길은 `track`, 숫자는 18(카드용)·22(상세용) 굵게 — 세 자리 숫자(100)가 링 안쪽에 안 들어가면 글자를 한 자씩 줄여 맞춘다.
- **배치**: 카드형(`layout="card"`)은 링 오른쪽에 구간 이름(예: `[92] 우선 추천`), 그 아래 줄에 변화량(`▲ +12`) — 카드 아래 줄용이다. 상세형(`layout="detail"`)은 링 아래에 구간 이름, 그 아래에 변화량을 가운데 맞춰 놓는다 — 상세 창 머리용이다.
- **변화량**: 상승 `▲ +12`(초록 `success_text`)·하락 `▼ -5`(빨강 `danger_text`)·0 이면 `― 변화 없음`(회색 `text_secondary`). 변화 값을 모르면 변화량 줄이 없다. 색과 함께 늘 글자(▲▼―)가 있다. 문서는 '변화 없음' 을 Muted 로 말하지만 대비 3.2 라 읽기 어려워 Secondary(대비 5.4)로 했다(D-154).
- **데이터 부족은 링을 그리지 않는다**: 점수가 없거나(`None`)·숫자가 아니거나·소수이거나·0~100 밖이면 링도 빈 길도 변화량도 없이 `데이터 부족` 글만 보인다(카드형·상세형 모두 — 링이 있을 때와 같은 높이를 지켜 줄이 흔들리지 않게). **0점으로 그리지 않는다** — 실제 0점은 빈 길 위에 `0` 이 있는 링이고 '제외' 구간이다.
- 점수는 엔진처럼 **정수만** 받는다(92.0 처럼 정수인 실수는 92). 79.5 같은 소수는 구간이 엔진과 어긋날 수 있어 반올림해서 그리지 않고 데이터 부족으로 본다.
- **접근 이름**: `점수 92, 우선 추천, 12 상승`(점수·구간·변화량 순서 — 변화가 없으면 `변화 없음`), 데이터 부족은 `점수 데이터 부족`. 링 단독은 `점수 92, 우선 추천` 이고 같은 글이 툴팁으로 뜬다. 보기 부품이라 Tab 정거장은 아니다.

**구성 막대(`BarGauge`)**

- 입력은 `(이름, 값, 종류)` 의 나열이다. 종류 `base`·`data`·`trend`·`other` 가 색을 정한다(고정색 — `bar_base` `#8191AA`·`bar_data` `#42A5F5`·`bar_trend` `#21B77A`·`bar_other` `#F4C04B`). 순서를 바꿔도 색은 그대로이고, 모르는 종류는 코드 실수라 오류(`ValueError`)다.
- 막대는 높이 12·모서리 6, 길이는 **양수인 구성끼리의 비율**이다(음수 값은 길이가 없고 숫자만 남는다). 아래에 구성마다 색 표시(8×8)·이름(작은 글)·숫자(`h3`)를 적는다 — 첫 구성은 그대로(`55`), 나머지는 부호를 붙인다(`+12`). 맨 오른쪽에 `최종 점수` 와 큰 총점(`h2`)이 있고, 총점은 따로 주지 않으면 값의 합이다. 색만 보지 않도록 이름과 값이 글자로 늘 함께 있다.
- 숫자가 아닌 구성은 그리지 않고, 하나도 없으면 막대 없이 `구성 정보 없음` 만 보인다. 접근 이름은 `점수 구성: 기존 점수 55, 추가 근거 +12, … , 최종 점수 92`.

**사용량 막대(`UsageBar`)**

- `이번 달 12,400 / 27,000회` + `46%` — **숫자와 단위를 늘 함께** 적는다. 막대 높이 8·모서리 4, 채움은 기본 파랑이다.
- **표시한(반올림한) 퍼센트로 상태를 정한다**: 80 이상이면 경고색(`warning`)과 `주의`, 90 이상이면 위험색(`danger`)과 `위험`. 한도를 넘으면 위험색과 `한도 넘음`(막대는 가득, 퍼센트는 실제 값 — 예 111%). 한도에 딱 닿은 100% 는 '넘음' 이 아니라 `위험` 이다. 79.6% 가 화면에 80% 로 보이는데 정상 색이면 어긋나기 때문이다(D-158). 색과 함께 글(`주의`·`위험`)이 따라온다.
- 사용량을 모르면(없음·음수·한도 0 이하·숫자 아님) **막대(빈 길 포함)를 아예 만들지 않고** `확인할 수 없어요` 글만 보인다 — 0 으로 채우지도, 빈 길을 남기지도 않는다(빈 길은 0% 로 읽힌다. UI-C0 의 부품은 이 점이 문서와 달랐고 UI-C1b 에서 고쳤다 — D-180). 실제 0회는 알려진 값이라 빈 길에 `0 / 27,000회` + `0%` 로 보인다. 접근 이름은 `이번 달 12,400 / 27,000회, 46%`(경고·위험이면 뒤에 `, 주의`·`, 위험`, 예시 값이면 끝에 `, 예시`).
- **줄 끝 꼬리표**(UI-C1b): 예시 값은 줄 끝(퍼센트 뒤)에 작은 `예시` 배지가 붙고 접근 이름에도 같은 말이 들어간다(`이번 달 340 / 27,000회, 1%, 예시`). 꼬리표를 안 주면 배지도 없다.

**의미별 배지(`SemanticBadge`)**

- 11종(공공데이터·추천·해외비교·문화행사·가격변화·여행·기술·정책·생활·주의·차단)의 색 쌍은 위 표다. 높이 24·글자 12/600·좌우 여백 12(`SPACE["3"]`)의 알약이고 **색과 글자를 함께**(색만으로 뜻을 알리지 않는다)·**한 줄**이다.
- 글을 안 주면 종류 이름이 글이다. 글자 수가 16자를 넘으면 `…` 로 줄이고 전체 글은 툴팁에 둔다. 접근 이름은 종류 이름이고 글이 다르면 `종류: 글` 이다. 모르는 종류는 코드 실수라 오류다.
- 카드 하나에 배지는 최대 2개(카드 부품을 만드는 묶음이 지킨다). **공공데이터 배지와 데이터 신호 표를 실제 화면에 넣는 것은 후속 공공데이터 프로젝트**의 몫이다 — 이번 묶음은 부품 모양만 만든다.

**탭 줄(`TabBar`)**

## 6. 화면 배율 — 지원 제한이 아니라 검증 범위

## 7. 접근성·키보드

Tab 으로 모든 눌리는 곳을 한 바퀴 돌 수 있고(중간에 갇히지 않음), Enter·Space 로 단추·카드·행을 누르며, 포커스 링을 지우지 않는다(채워진 단추는 어두운 링 — 시험이 단추 종류마다 포커스 전후의 모양과 테두리 색을 잰다). 윈도 기본 포커스 사각형이 메뉴 단추의 파란 링 안에 겹치던 것은(진짜 윈도 창에서만 보였다) 스타일시트의 `outline: none` 으로 막았다 — offscreen 에서도 윈도 11 스타일에 진짜 Tab 키 이벤트를 주면 같은 사각형이 그려져 시험한다(고치기 전 검은 점 356 → 0). 서랍·대화상자가 열려 있으면 Tab 은 그 안에서만 돌고, Esc 로 닫으면(대화상자 먼저) 눌렀던 곳으로 포커스가 돌아온다. 아이콘만 있는 단추는 접근 이름과 툴팁이 필수이고 툴팁은 마우스를 올릴 때와 키보드 포커스가 올 때 모두 보인다. 색만으로 상태를 구분하지 않는다(블로그 글자·추세 아이콘). 안내(토스트)는 화면 읽기 프로그램에 알림 이벤트로 알린다. 화면이 다시 그려져도(서랍을 닫을 때·다시 불러올 때) 포커스는 같은 추천 줄·단추에 남는다(`focus_key`). 홈의 Tab 한 바퀴는 13곳(메뉴 둘·예시 데이터·다시 불러오기·추천 줄 아홉)이고 읽는 순서(위에서 아래로, Naver A 다음 Naver B)이며, KPI 카드·글 줄·연결 한 줄은 포커스를 받지 않는다. **UI-C0 의 새 기준**: 누르는 칸은 문서가 최소 32×32·권장 40×40 이라 하고 이 앱은 **36 이상**을 기본으로 지킨다(시험이 단추를 잰다) · 포커스는 2px 파란 테두리(위 '포커스 링 결정') · 탭 줄은 Tab 정거장이 고른 탭 하나이고 ←·→·Home·End 로 옮긴다 · 행동 줄의 `더보기 ⋮` 는 접근 이름 `더보기 메뉴 열기` 와 툴팁(키보드 포커스에도 보임)이 있고 꺼진 행동은 이유를 툴팁으로 알린다 · 점수·상태는 색과 함께 글자(▲▼―·구간 이름·`주의`·`위험`)를 늘 쓰고, 글자 색은 흰 바탕 대비 4.5 이상인 변형만 쓴다(세 배지 쌍은 예외 — 위 표와 D-157). **실제 화면 읽기 프로그램(Narrator 등)·한글 입력기 확인은 운영자 PC 검증으로 남는다.**

- **경로 지우기가 알아보는 모양**(한 줄 기록 `unexpected_line`, 'G0c'): 드라이브(`C:\`·`C:/`)·네트워크(`\\서버\공유`·`//서버/…`)·유닉스식(`/home/…`·`경로:/home/…`)·`~/`·`file:///…`(윈도·유닉스 모두, 대소문자 무관)이다. 경로의 시작을 보이지 않는 글자(폭 없는 글자 등)로 쪼갠 것은 줄 가르는 글자를 줄바꿈 하나로 통일하고 보이지 않는 글자를 지운 뒤에 알아본다. **알아보지 못하는** 모양: 상대 경로(`폴더\파일`)·`%USERPROFILE%`·`$HOME`·퍼센트로 인코딩한 경로(`file:///%2Fhome/…`)·다른 사용자의 홈(`~사용자/…`)·따옴표로 연 `file://` 주소(따옴표를 못 알아봄)·호스트가 있는 주소(`file://서버/…`·`https://…` — 주소는 경로가 아니라 그대로 둔다). 따옴표로 연 경로는 짝이 되는 따옴표 앞까지, 아니면 그 줄 끝까지 지워 뒤 설명도 함께 사라질 수 있다(어디서 끝나는지 모를 때는 더 지우는 쪽이 안전하다). 날짜(`11/04`)·`a/b`·닫는 태그·나눗셈은 경로가 아니다.
- **표준 오류가 없는 실행**: 처리하지 못한 예외의 한 줄 기록(`report_unexpected`)은 표준 오류에 쓴다. `pythonw`·창 없는 exe 처럼 표준 오류가 없는 실행에서는 어디에도 남지 않는다(`False` 를 돌려주고 화면에는 쉬운 안내만 보인다) — '조용한 실패도 아니다' 는 **콘솔 실행 기준**이다. 로그 파일은 설치 파일 묶음에서 정한다(이 묶음은 파일을 쓰지 않는다 — 읽기 전용 원칙).
- **취소**: 실제 서비스 어댑터는 단계 사이(후보 읽기 뒤·글 목록 읽기 뒤·홈의 새 구역을 읽는 사이마다 — 최근 발행은 글 사이마다)에만 취소를 확인한다 — 한 단계가 도는 동안은 끊지 못하고 끝난 결과를 버린다 — 그래도 화면은 취소를 누르는 즉시 보이던 모습으로 돌아간다([`UI_STATES.md`](UI_STATES.md) §2). 창을 닫을 때는 창을 먼저 숨기고 끝나지 않은 작업을 최대 1초 기다린다.
- **성능**: 후보 10만 개에서 `home_view()` 가 0.52초(화면 스레드)다 — 후보가 그렇게 많아지면 목록 화면 묶음에서 나눠 그린다.
- **설정 화면(P4a)의 한계**: ① 접이식 머리의 칩은 머리 단추 위에 얹혀 있어, 칩이 아주 많고 폭이 아주 좁으면 제목과 겹칠 수 있다(실제 서비스 표로 생길 수 있는 가장 긴 머리 — 칩 셋 — 는 최소 창 900×560 에서도 겹치지 않는다: 시험이 잰다) ② 키 보관소(윈도 자격 증명 관리자)를 실제 PC 에서 읽는 것은 이 묶음에서 확인하지 못했다(시험은 가짜 보관소 — 운영자 PC 확인으로 남는다) ③ 어떤 서비스도 아직 실제로 부르지 않아 실제 모드의 사용량 숫자는 모두 0 이다 ④ 용도 카드의 항목 이름이 `<b>` 같은 모양이어도 글자로만 보이지만, 그 이름을 담는 툴팁은 Qt 가 서식 글로 읽을 수 있다(홈의 블로그 이름 툴팁과 같은 한계) ⑤ CI 는 Qt 코드를 돌리지 않는다(D-32 (l)) — 화면 증거는 로컬 실행 줄과 사진이다.
- **설정 화면(UI-C1b)의 한계**: ① 막대 색(월 한도 27,000 대비 80·90%)과 서비스 안내 단계(콘솔 한도 30,000 대비 70·80·90%)는 분모가 달라 같은 사용량에서 퍼센트 숫자가 다르다(21,000회 = 막대 78%·안내 70%) — 안내문이 기준을 스스로 말하고 막대 옆에 분모가 늘 보이며 시험이 0~30,000회 전수로 모순이 없음을 확인한다(D-181) ② 카드 제목 '연결 관리'(운영자 지정 이름) 아래에 서비스가 아닌 '정보' 묶음이 같이 있다 — 이름을 바꿀지는 묶음이 6개 이상이 되어 2단(왼쪽 목록 + 오른쪽 내용) 전환을 검토할 때 함께 정한다(D-182, `DEFERRED`) ③ 줄인 카드 문장 중 이미지 공급자의 `자동으로 다른 키로 넘어가지 않아요. 한도에 닿으면 …` 는 서비스 문구의 뜻을 지키려 두 문장 그대로라 좁은 카드(논리 폭 1280 안팎)에서 두 줄로 꺾인다 ④ 실제 윈도 125·150%·화면 읽기 프로그램에서 막대와 '정보' 묶음이 어떻게 읽히는지는 운영자 PC 확인으로 남는다 ⑤ `UsageBar` 의 접근 이름과 안의 글 라벨이 함께 읽힐 수 있다(UI-C0 L11 과 같은 한계) ⑥ 서비스가 한도를 모르는 용도는 카드에 '사용량' 줄 자체가 없다.
- **창을 띄우지 않은 확인**: 실제 윈도 125·150% 렌더·한글 입력기·화면 읽기 프로그램·고대비 모드·개인 PC 는 운영자 PC 검증으로 남는다([`UI_VISUAL_QA.md`](UI_VISUAL_QA.md) §6).
- **UI-C0(C-Type 기초)의 한계**: ① 추천 행 제목과 설정 용도 카드 이름은 `h3`(17/600) 역할로 옮겨 굵기 위계를 지켰다(D-150 ①). 그 밖의 `body_lg` 글자 역할을 쓰는 곳(행의 월 검색량 같은 지표 값·빠른 작업 제목·블로그 이름·활용 팁 제목·서랍의 항목 값)은 15/600 → 15/400 으로 **얇아졌다**(새 기준의 '본문 큰 글씨' 가 보통 굵기라서) — 이들을 제목으로 볼지는 화면을 새로 만드는 UI-C1 에서 정한다 ② 세 배지 쌍(추천·가격변화·주의)의 글자 대비가 4.5 미만이다(운영자 결정 대기, D-157) ③ 새 부품은 어떤 화면에도 연결하지 않았다 — 부품 모음 사진과 시험으로만 확인했고, 실제 화면에서의 모습은 연결하는 묶음의 몫이다(사용량 막대는 UI-C1b 에서 설정 화면에 연결했다 — D-180) ④ 카드 그림자는 부품 모음의 견본에서만 쓰고 홈·설정의 카드는 그대로다(그림자 카드가 많을 때의 성능은 재지 않았다 — 카드를 만드는 묶음이 잰다) ⑤ 포커스 바깥 옅은 링은 값만 정하고 그리지 않는다(스타일시트가 바깥 링을 못 그린다) ⑥ 지금 빌드의 자리표시 메뉴 4개는 메뉴 규칙(§3-2)보다 먼저 만든 것이라 UI-C1 에서 맞춘다 ⑦ 사이드바 현재 메뉴 색·오른쪽 선은 아직 옛 값이다(UI-C1 에서 토큰으로 더한다).
- **홈 데이터(UI-C1c)의 한계**: ① 실제 연결에서는 **이전 점수를 서비스가 주지 않아 변화량이 늘 숨겨진다**(예시에서만 보인다) ② '후보 N개' 는 홈에 보이는 우수 후보 수이고 채널 전체 후보 수가 아니다(가벼운 수 세기가 서비스에 없다) ③ 서비스의 우수 후보 읽기는 안에서 후보 전체를 읽어(합성 1,000개에 1.4초 — 이 PC 측정) 후보가 아주 많으면 느릴 수 있다(작업 스레드라 화면은 안 막힌다) ④ 최근 발행은 글마다 읽는 임시 방식이라 '최근에 고친 발행 글 다섯 편' 중에서 고른다 ⑤ 홈이 열릴 때 설정 정보를 함께 읽지 않아 연결 요약은 설정 화면을 연 뒤에 값이 생긴다(UI-C1d 에서 정한다). 서비스 수정이 필요한 것은 D-194(`DEFERRED`, T2). 속도는 모두 합성 데이터 측정이고 운영자 PC 의 실제 크기는 못 봤다.
- **홈 모양(UI-C1d)의 한계**: ① 추천 줄의 서랍은 줄이 아는 값(제목·채널·관심도)만 채워 대부분 `데이터 없음` 이다(서랍 데이터를 새로 만들지 않는다는 지시 — 서비스가 줄에 점수 구성·이유를 주면 채운다) ② 옛 후보 저장소의 후보는 홈에 그려지지 않는다(추천은 주제 엔진의 우수 후보뿐 — D-201 ④) ③ 홈의 `다시 불러오기` 는 연결 정보를 다시 읽지 않는다(설정 화면을 열 때마다 새로 읽는다 — D-203) ④ 엔진 보관함이 잠겨 있으면 서비스의 대기 시간(UI-C1c 검증 L3 — 이 PC 에서 7.6초)이 추천 구역 읽기를 늦춘다(작업 스레드라 화면은 안 막힌다 — T2 서비스 후속, D-204) ⑤ 카드 그림자의 선명도·속도와 실제 윈도 125·150% 렌더는 운영자 PC 확인으로 남는다(이 PC 의 offscreen·배율 흉내로만 봤다) ⑥ 이미지 자리 부품 `ImagePlaceholder` 는 지금 쓰는 곳이 없다(후보 목록·이미지 화면이 쓴다).

# 이관 노트(MIGRATION_NOTES) 틀 — 버전을 올릴 때 내 데이터가 어떻게 되는지 알리는 형식 (초안, 2026-11-24)

> 한 줄: **새 버전으로 올릴 때 사용자의 데이터(글·주제 후보·설정·백업)가 어떻게 달라지는지, 올리기 전·후에 무엇을 하면 되는지, 문제가 생기면 어떻게 되돌리는지**를 버전마다 같은 모양으로 적는 틀이다. [`RELEASE.md`](RELEASE.md) 는 릴리스마다 `MIGRATION_NOTES.md` 를 함께 공개한다고 적었고, 이 문서는 그 파일을 쓰는 **형식**만 정한다 — 실제 노트는 첫 정식 버전을 올릴 때(DOCS(b)) `docs/MIGRATION_NOTES.md` 로 만들고 이 틀의 모양을 따른다. 지금은 사용자 데이터를 바꾸는 새 버전이 아직 없고 이 틀은 아무것도 구현하지 않는다.

> 이 문서의 사실(데이터 위치·판 번호·오류 이름)은 2026-11-24 의 소스와 [`ARCHITECTURE.md`](ARCHITECTURE.md) §9·§10·§12·[`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) 에서 읽은 것이다. **새 노트를 쓸 때는 반드시 그때의 소스와 시험에서 다시 확인한다**(아래 '6. 사실을 읽는 곳').

## 1. 언제 쓰나

- 버전을 올리면서 **사용자 데이터의 모양이 바뀌는** 변경이 하나라도 들어갈 때 — 글 보관함·주제 엔진 보관함의 판(구조 번호)이 오르거나, 설정·프로필·씨앗·캘린더 같은 JSON 파일의 `schema` 숫자가 오르거나, 파일 이름·위치가 바뀌거나, 백업의 모양이 바뀔 때.
- 바뀌는 것이 없어도 **'달라지는 것 없음' 한 줄 노트는 쓴다**(없다고 적어야 확인했다는 뜻이다). 릴리스 본문의 '이관 노트' 줄([`RELEASE.md`](RELEASE.md) 의 '릴리스 노트 규칙')이 이 노트의 같은 버전 절을 가리킨다.

## 2. 파일의 모양 — 버전마다 절 하나, 새 절이 맨 위

`docs/MIGRATION_NOTES.md`(첫 정식 버전 때 만든다)는 제목 아래에 **가장 새 버전의 절이 맨 위**에 오고(`CHANGELOG.md` 와 같은 순서), 절 머리 줄은 `## [X.Y.Z] — YYYY-MM-DD` 꼴이다(CHANGELOG 의 같은 버전 절과 버전·날짜가 같다). 옛 절은 고치지 않는다.

## 3. 절의 틀 — 아래를 복사해 「 」 칸을 채운다

```text
## [「X.Y.Z」] — 「YYYY-MM-DD」 (「이전 버전」 에서 올릴 때)

### 한눈에
- 내 데이터를 손볼 일: 없음 / 있음(아래 '직접 해야 할 일')
- 처음 실행 때 앱이 데이터를 자동으로 바꾸나: 아니요 / 예(아래 표)
- 이전 버전으로 되돌리면 이 버전의 데이터를 이전 버전이 열 수 있나: 예 / 아니요
- 되돌리는 방법: 올리기 전에 만든 백업을 복원한다(설정 → 백업·복원)

### 올리기 전에
1. 설정 → 백업·복원 → 지금 백업. 목록의 새 줄에 `Credential 제외됨` 이 보이는지 본다.
2. 백업은 같은 PC 에 만들어지는 사본이다. 중요한 데이터면 백업 폴더를 USB 같은 다른 곳에도 복사해 둔다.
3. 열려 있는 앱 창을 모두 닫는다.

### 데이터가 바뀌는 곳 (바뀌는 것만 적는다 — 안 바뀌면 '바뀌지 않음')
| 데이터 | 위치 | 이전 모양 | 이 버전 모양 | 처음 실행 때 앱이 하는 일 | 남기는 사본 |
|---|---|---|---|---|---|
| 「글 보관함」 | `chanceblog.db` | 판 「N」 | 판 「M」 | 「열 때 판을 올린다」 | 「옛 판 사본 이름」 |

### 직접 해야 할 일 (없으면 '없음')
- 「내가 할 일을 순서대로, 화면의 단추 이름 그대로」

### 올린 뒤에 확인할 것
- 설정 → 연결 관리 → 정보 에서 버전이 「X.Y.Z」 인지.
- 블로그 관리·Seed 관리·주제 후보·저장한 초안이 올리기 전과 같은지.
- 설정 → 백업·복원 에 올리기 전에 만든 백업이 그대로 있는지.

### 문제가 생기면
| 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| 「오류 이름 — TROUBLESHOOTING 의 것」 | 「쉬운 말」 | 「하실 일」 |

### 되돌리기
- 「올리기 전 백업으로 복원하는 순서」
- 「이전 버전을 다시 설치하는 방법 — 설치 방법이 정해진 뒤에 적는다」

### 알려 둔 한계
- 「사실대로」

### 근거
- 결정: 「D 번호」 · 시험: 「시험 이름」
```

## 4. 쓰는 규칙

1. **쉬운 한국어**로 쓴다(읽는 사람은 비개발자 운영자다). 영문 약어·파일 이름에는 풀이를 붙이고 화면의 단추·카드 이름은 화면과 글자 그대로 쓴다.
2. **사실만 쓴다.** '안전하다·문제없다' 처럼 증거 없는 말을 쓰지 않고, 확인하지 못한 것은 '확인 못 함' 이라고 적는다. 시험이 지키는 사실에는 '근거' 에 그 시험 이름을 적는다.
3. **되돌릴 수 있는지를 반드시 쓴다.** 이 앱은 더 새로운 버전이 만든 데이터를 낮은 버전이 열지 않는다(글 보관함은 `STORE_VERSION_UNSUPPORTED`, 주제 엔진 보관함은 `TOPIC_STORE_VERSION_UNSUPPORTED` — 데이터가 망가지지 않게 한 바이트도 바꾸지 않는다). 그래서 '이전 버전으로 되돌리기'는 **올리기 전에 만든 백업을 복원**하는 일이다. 이 문장은 데이터 판이 오른 버전의 노트에 늘 들어간다.
4. **키(API 키·토큰)는 데이터가 아니라 Windows 자격 증명 관리자에 있다.** 백업에는 담기지 않고(`Credential 제외됨`) 업데이트로 바뀌지 않는 것이 보통이다 — 바뀌는 버전이면 맨 위 '한눈에' 에 따로 적는다.
5. 경로는 `%LOCALAPPDATA%\ChanceblogDesktop` 처럼 환경 변수로 쓰고 실제 사용자 이름이 든 경로·실제 블로그 이름·개인 정보를 쓰지 않는다(예시는 가짜 이름만).
6. 물결표·웹 주소·이중 중괄호를 쓰지 않는다(숫자 범위는 en dash). 이 틀의 「 」 는 채울 곳을 뜻할 뿐이다.
7. 같은 버전의 CHANGELOG 절 '이관 노트' 줄과 **같은 사실**이어야 한다(한쪽만 고치지 않는다).

## 5. 사용자 데이터가 어디에 있나 — 바뀔 수 있는 곳의 목록

모두 `%LOCALAPPDATA%\ChanceblogDesktop\` 아래다(앱이 정한 사용자 데이터 폴더 — [`ARCHITECTURE.md`](ARCHITECTURE.md) §10). 백업에 담기는지는 §12 를 따른다.

| 데이터 | 위치 | 구조 번호가 있나 | 지금 판 | 판이 오를 때 앱이 하는 일 | 전체 백업에 담기나 |
|---|---|---|---|---|---|
| 글 보관함(프로젝트·판 기록·저장한 초안·주제 후보) | `chanceblog.db` | 있음(`user_version`) | 2 | 열 때 쓰기 잠금을 잡은 뒤 판을 올리고, 판 1 파일은 사본 `.v1.bak` 을 먼저 남긴다. 환경 문제로 못 하면 파일을 바꾸지 않고 `MIGRATION_BLOCKED`, 변환이 실패하면 되돌리고 `MIGRATION_FAILED` | 담는다 |
| 주제 엔진 보관함 | `topic_engine/topic_engine.db` | 있음(자체 `user_version`) | 2 | 판 1 파일은 사본 `.v1.bak` 을 남기고 한 트랜잭션으로 올린다 | 담는다 |
| 블로그 프로필·Seed·캘린더 | `topic_engine/channel_profiles.json`·`seeds.json`·`calendar.json` | 있음(파일 안의 `schema` 숫자) | 파일마다 다름 | 저장할 때 직전 내용을 `.bak`(판 1 이면 `.v1.bak`)으로 먼저 남긴다 | 담는다 |
| 설정(연결한 chanceblog 폴더·네이버 프로필) | `settings.json` | 소스를 확인한다 | — | — | 담는다(연결한 폴더의 전체 경로가 들어 있다) |
| 연결 설정(키 항목의 이름·상태) | `connections.json` | 소스를 확인한다 | — | — | 담지 않는다 |
| 키(API 키·토큰) | Windows 자격 증명 관리자(`ChanceBlogDesktop:` 로 시작하는 항목) | — | — | 업데이트가 건드리지 않는다 | 담지 않는다 |
| 참고 글 보관함 | `references/`(글 하나에 파일 하나 `ref-번호.json`) | 소스를 확인한다 | — | — | 담지 않는다 |
| 백업 | `backups/` | 목록 파일의 `schema` | — | 더 새로운 앱·판이 만든 백업은 `STORE_VERSION_UNSUPPORTED` 로 거절한다(D-389) — 낮은 버전의 백업은 받는다 | — |
| 작은 오류 기록·사용량·잠금 | `logs/errors.log`·`quota_state.json`·`locks/` | — | — | 지워도 되는 부산물이다 | 담지 않는다 |

표의 '소스를 확인한다' 는 이 문서를 쓰면서 구조 번호의 유무를 확인하지 못한 곳이다(**확인 못 함** — 새 노트를 쓸 때 소스를 읽어 채운다).

## 7. 이 틀이 아직 정하지 못한 것

- **이전 버전을 다시 설치하는 방법**은 설치 도구(확인 A)와 업데이트 방식(확인 B)이 정해져야 적을 수 있다 — 그때까지 틀의 '되돌리기' 에는 백업 복원만 적는다.
- 사용자 데이터 폴더가 압축·설치 폴더 **밖**(`%LOCALAPPDATA%\ChanceblogDesktop`)에 있는 것은 지금도 사실이다([`ARCHITECTURE.md`](ARCHITECTURE.md) §10·[`PACKAGE.md`](PACKAGE.md) §9) — 업데이트가 앱 폴더만 바꾸면 데이터는 남는다(업데이트 방식이 정해진 뒤 시험으로 확인한다). 제거할 때 데이터를 지우는지(추천: 기본 보존, 지우는 법은 문서로)는 확인 C 의 몫이다.
- 이 틀로 **만든 노트**를 지키는 시험은 아직 없다(이 틀 문서의 사실 — 구조 번호·오류 이름·백업이 담는 파일 — 은 `tests/test_v1_docs.py` 의 MigrationNotesTemplateTest 가 지킨다). 첫 노트를 만들 때 '절 머리 줄이 CHANGELOG 의 같은 버전과 같다·틀의 소제목이 모두 있다·금지 글자가 없다' 를 지키는 시험을 더한다(시험 아이디어는 [`RELEASE.md`](RELEASE.md) 의 '릴리스 노트 규칙' 5).

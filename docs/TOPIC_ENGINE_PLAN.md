# 주제 엔진 계획 — 5채널 주제 선정 전략을 지금 코드에 얹는 순서

> **이 문서는 계획이다. 1단계(P0)는 `src/` 를 한 줄도 바꾸지 않았다.** 기존 동작을 시험(`tests/test_topic_protect_*.py`)으로 먼저 못박고, 이 문서와 결정(D-36~D-41)을 더했을 뿐이다. 2단계(P0b)가 `src/` 의 계절 일치만 고쳤다(D-42). P1(순수 핵심 `topics/`)은 병합됐고(PR #23) P2a(P1 인수 + 씨앗·캘린더·중복 판정·이력 읽기, D-43~D-45)가 그 위에 새 모듈을 더했다.
> `topics/` 패키지는 P1·P2a 에서 **코드에 생겼다**(저장·화면 없음) — `service/topics.py`·`topic_engine.db`·명령줄 `topics`·`주제 후보` 화면은 **아직 없고** 해당 단계(P3~)에서 만든다.
> 결정 A~H 는 **운영자 승인(2026-11-04 채팅)** 으로 확정됐다(10절 — 선택값 A~H 모두 1 + 조건 7개). 운영자의 전략 문서(비공개)는 값(가중치·구간·한도 같은 숫자)만 옮겼고 설명은 새로 썼다. 원문과 실제 Seed 목록은 공개 저장소에 올리지 않는다.

## 한눈에

1. 전면 교체가 아니라 새 순수 모듈 `topics/` 를 **나란히** 얹는다. 기존 `suggest*`·`Candidate`·홈 화면은 그대로 둔다.
2. 상태는 두 축이고 **이름까지 나눈다** — `work_status`(작업 흐름)와 `recommendation_band`(추천 구간). 점수 체계는 둘(기존 5요인 + 새 6항목)이 함께 있다.
3. 새 데이터는 **별도 SQLite `topic_engine.db` 와 사용자 데이터 JSON 셋**에 둔다. 기존 `chanceblog.db`(판 2)·`settings.json`·후보 JSON 은 바꾸지 않으므로 **기존 데이터 마이그레이션이 없다.**
4. Search Trend 지표는 기존 `search_demand`(Legacy)와 **분리한 새 칸**에 둔다. 실제 호출은 맨 뒤(P5)이고 그 전까지는 '없음/가짜' 틀과 규칙 기반만으로 돈다.
5. 처음 켜는 채널은 네이버 A·B 뿐이다(`generation_enabled`). 나머지 3채널은 프로필·이력 읽기·중복 검사용 정규화까지만 한다(`history_enabled`).
6. 단계는 P0 → 독립 검증 → 결과 보고 → P0b … 순서이고, 단계 보고는 같은 6항목으로 쓴다(8.2).

## 1. 목적과 원칙

**목적**: 운영자가 5개 채널(GitHub Pages·Blogger 한글·Blogger 영문·네이버 A·네이버 B)에 공통으로 쓸 주제 선정 전략을 데스크톱 프로그램에 '엔진'으로 얹는다. 엔진은 후보를 만들고·점수를 매기고·채널마다 상위 후보를 고르는 **순수 계산**이고, 화면·초안·발행은 엔진을 부르기만 한다.

### 3.2 의존 방향

```text
지금 : errors ← { check, security } ← content ← render ← publish ← service ← ui
제안 : topics 는 표준 라이브러리와 errors·check.claims·content 의 순수 부품(작업 상태 상수 같은 것)만 가져온다(content.store·service·ui 는 가져오지 않는다)
       service/topics.py 가 topics 와 content(보관함·Candidate)를 이어 준다
       실제 Trend 호출(HTTP)은 service/ 밖 별도 패키지에 두고 호출자(명령줄·화면 진입점)가 service 함수에 넘긴다
```

기존 `suggest_score.combine` 은 5요인 이름에 묶여 있어(다른 이름은 `ValueError`) 6항목에 그대로 쓰지 못한다. 같은 원칙('없는 항목은 빼고 다시 나눈다')의 새 함수를 `topics/score.py` 에 둔다.

`tests/test_service_safety.py` 가 `service/*.py` 전체를 훑어 지키는 규칙과 맞추는 방법:

| 규칙 | 맞추는 방법 |
|---|---|
| 서비스 코드는 네트워크·프로세스 부품(`urllib`·`socket`·`http`·`subprocess`·`ctypes` 등)을 가져오지 않는다 | 실제 HTTP 는 `service/` 밖 별도 패키지(이름은 P5 에서 정함)에 두고 호출자가 주입한다 |
| 서비스 코드가 파일을 쓰는 곳은 (파일, 함수) 허용 목록뿐이다 | 새 JSON 저장은 `context.write_json` 경유. 허용 목록을 늘리는 것은 시험 변경이므로 P3(T2)의 독립 검증에서 함께 본다 |
| 조용한 실패 금지(`except: pass` 안 됨) | 실패는 오류 코드로 — `TROUBLESHOOTING.md` 표에 행을 더하고 `scripts/sync_errors.py` 로 카탈로그를 다시 만든다 |

### 3.3 서비스 층·명령줄·화면 자리

| 자리 | 제안 | 단계 |
|---|---|---|

### 4.2 Trend 지표 분리 — Legacy `search_demand` 와 섞지 않는다

| 칸 | 누가 정했나 | 값 | 규칙 |
|---|---|---|---|
| `search_demand_count` | 운영자(조건 1) | 정수 또는 없음 | **실제 검색 횟수 데이터가 있을 때만** 쓴다. 6항목 점수는 P1 에서 이 칸을 읽지 않는다 |
| `search_count_source` | 이 계획(해석) | 글 또는 없음 | 위 값을 준 공급자 이름 — `search_demand_count` 에 값이 있으면 꼭 있어야 한다 |
| `trend_ratio` | 운영자(조건 1) | 정수 또는 없음(0~100 범위는 이 계획의 해석) | NAVER Search Trend 의 **상대지수**. 어떤 경우에도 `search_demand_count` 로 흘러가지 않는다(시험으로 못박음) |
| `trend_status` | 운영자(조건 1) | `rising`·`flat`·`falling`·`insufficient`(영문 값은 이 계획의 이름) | 화면 글은 운영자가 쓴 상승·보통·하락·데이터 부족 |
| `trend_period` | 운영자(조건 1) | 한 줄 글 | 비교 기간 |
| `trend_compared_group` | 운영자(조건 1) | 글 목록 | 비교 키워드 그룹 |
| `trend_queried_on` | 이 계획(해석) | 날짜 | 조회일 — 오래된 데이터 판정용 |
| `data_status` | 이 계획(해석) | `sufficient`·`partial`·`insufficient`·`unavailable` | 전략 문서 §15 의 '장애와 실제 데이터 부재 구분'을 담는 칸 — **API 장애(`unavailable`)와 데이터 부족(`insufficient`)을 구분**한다. 이 구분은 `trend_status` 가 아니라 이 칸이 맡는다 |

- **운영자 지시(조건 1)**: Search Trend 값은 화면에서 `최근 관심도(상대값)` 로 보이고 `월 검색량`·`회` 단위를 쓰지 않는다. 기존 절대 검색량 칸은 덮어쓰거나 재해석하지 않는다. **이 계획의 해석·추가**: `검색량 예측`·`volume`·`조회수` 같은 이름도 Trend 값에 쓰지 않고, 이름 검사 시험은 `search_demand_count` 하나만 예외로 허용한다(P1).
- **기존 `Candidate.search_demand`·`related_blog_results`·`mobile_share` 는 Legacy 로 그대로 둔다**(운영자 지시: 의미가 불명확하면 Migration 하지 않고 Legacy 로 유지). 덮어쓰기·재해석·자동 이전이 없고 새 점수(`topics/score.py`)는 Legacy `search_demand` 를 읽지 않는다. 의미가 불명확하다는 판단은 **이 조사의 결론**(7절 — 코드·문서 근거)이다.
- 결정 E=1 의 적용(**이 계획의 해석**): `최근 관심도(상대값)` 는 **새 Trend 칸의 이름**이고 기존 절대 횟수 칸의 라벨을 바꿔 다는 것이 아니다 — 기존 칸의 `월 검색량`·`월간 검색량`·`회` 는 `tests/test_topic_protect_ui.py` 가 현재 모습으로 못박았다. Legacy 입력값임을 보이고 Trend 칸과 섞여 보이지 않게 하는 화면 처리는 P4 세부 설계이고, P0 는 화면 문구를 바꾸지 않는다.

## 5. 상태 두 축과 채널 이름

### 5.1 상태는 두 축 — 필드 이름을 나눈다

| 축 | 필드 | 값 | 누가 정하나 |
|---|---|---|---|
| 작업 흐름 | `work_status` | **저장하는 값**: NEW·REVIEW·SELECTED·HOLD·REJECTED(기존 `Candidate` 와 같고 이동표를 `ARCHITECTURE.md` §9 와 시험이 못박는다). **계산하는 표시값**(저장하지 않음): DRAFTING·DRAFT_READY·COPIED·PUBLISHED — 연결된 글(프로젝트)의 상태에서 기존 `FOLLOW_ON` 대응으로 계산한다 | 사람(선택·보류·제외), 글의 진행 |
| 추천 구간 | `recommendation_band` | RECOMMENDED(80~100)·GENERAL(65~79)·HOLD(50~64)·EXCLUDED(0~49), 점수가 없으면 UNRATED | 점수에서 계산 |

하나의 `status` 로 합치지 않는다. **HOLD 가 두 축에 있다** — 작업 축의 HOLD 는 사람이 누른 보류이고, 구간 축의 HOLD 는 점수 50~64 의 자동 보류함(90일)이다. 이름·주석·문서에서 구분하고, 화면 글에서 어떻게 달리 부를지는 P4 에서 정한다. 필드 이름 `work_status`·`recommendation_band` 와 값 `UNRATED`·`COPIED` 는 이 계획의 이름이고, 운영자(조건 3)는 '별도 필드·하나의 `status` 로 합치지 않음' 과 예시 값(작업: NEW·REVIEW·SELECTED·DRAFTING·DRAFT_READY·PUBLISHED / 구간: RECOMMENDED·GENERAL·HOLD·EXCLUDED)만 정했다. 기존 우선도 라벨 '높음·보통·낮음'(구간 70/40)은 그대로이고, 코드의 `FOLLOW_ON` 은 후보와 글의 상태 대응이라서 전략의 '후속 후보'(글 한 편당 최대 3개)와는 다른 말이다.

### 5.2 채널 이름 대응 (결정 B, D-40)

| 전략 문서 | 코드 키 | 비고 |
|---|---|---|
| GitHub Pages | `github_pages` | 같음 |
| Blogger A(한글) | `blogger_ko` | |
| Blogger B(영문) | `blogger_en` | 코드의 `PLATFORMS` 순서는 영문(`blogger_en`)이 한글(`blogger_ko`)보다 앞이라 전략의 A→B 와 반대다 |

## 6. 점수·구간·선택·중복 (값은 데이터로 둔다)

### 6.1 6항목 가중치 (채널 프로필에 두는 처음 값, 각 열의 합 100 — 채널마다 글이 30~50편쯤 쌓이면 다시 정한다)

| 항목 | GitHub Pages | Blogger 한글 | Blogger 영문 | 네이버 A | 네이버 B |
|---|---:|---:|---:|---:|---:|
| 채널 적합도 | 20 | 25 | 30 | 25 | 25 |
| 작성 가능성 | 15 | 25 | 25 | 15 | 15 |
| 차별성(기존 글과) | 15 | 20 | 20 | 10 | 10 |
| 시기(상대 관심도 포함) | 15 | 10 | 5 | 15 | 20 |
| 근거(확보 가능성) | 25 | 10 | 10 | 10 | 10 |
| 수익화(협업 적합도) | 10 | 10 | 10 | 25 | 20 |

### 6.2 데이터가 없을 때

- 데이터가 없는 항목은 **0점으로 치지 않는다.** 평가할 수 있는 항목만 남겨 합 100 이 되게 다시 나눈다(기존 5요인의 재분배와 같은 원칙).
- 장애로 못 가져온 것(`unavailable`)과 실제로 데이터가 없는 것(`insufficient`)을 구분해 기록한다(4.2 `data_status`). Blogger 영문에는 Search Trend 를 기본으로 쓰지 않는다.

### 6.3 구간과 상위 선택

| 점수 | 구간(`recommendation_band`) | 처리 |
|---|---|---|
| 80~100 | RECOMMENDED(우선 추천) | 채널의 기본 화면 상위 후보 |
| 65~79 | GENERAL(일반) | 전체 후보에 저장 |
| 50~64 | HOLD(보류) | 보류함에 90일 보관, 변화(관심도 상승·계절 진입 등)가 있으면 다시 평가 |
| 0~49 | EXCLUDED(제외) | 생성 이력과 제외 사유만 남김 |

상위 선택 규칙: 채널마다 **5개**, 같은 주제 묶음은 **최대 2개**, 80점 이상이 모자라면 65~79 에서 채우되 50~64 로는 억지로 채우지 않는다. 5개가 안 되면 '이번 분석에서 기준을 충족한 주제는 N개입니다'라고 알린다(화면 글에는 `보장` 낱말이 시험으로 막혀 있어 부가 설명은 문서에만 둔다). 90일이 지나도 변화가 없으면 상세 후보는 정리하고 이력(정규화한 키워드·주제 요약·처음 생성일·마지막 평가일·보류·제외 사유)은 남긴다.

### 6.4 중복 판정

| 범위 | 유사도 | 처리 |
|---|---|---|
| 같은 채널 안 | 0~39% | 다른 주제 |
| 같은 채널 안 | 40~59% | 비슷한 요소 있음 |
| 같은 채널 안 | 60~74% | 다른 관점이 필요 |
| 같은 채널 안 | 75% 이상 | 중복 또는 기존 글 업데이트 후보 |
| 채널 사이 | — | 대상 독자·언어·검색 의도·관점·목차·채널 고유 정보·수익 목적이 충분히 다르면 **최대 2채널**까지 허용 |

숫자만으로 자동 삭제하지 않는다. 유사도에 핵심 키워드·검색 의도·주제 묶음·관점·대상 독자를 함께 본다. 기존 `check/similarity.py`(초안 A/B 비교용)와 제안의 낱말 겹침 판정은 그대로 두고, 새 판정은 `topics/dedupe.py` 에 둔다.

**⑥ 결론 — Legacy 로 유지하고 새 `search_demand_count` 로 자동 이전하지 않는다.** 이것은 운영자 말이 아니라 **이 조사의 결론**(코드·문서 근거)이고, **운영자의 지시(조건 1: 의미가 불명확하면 Migration 하지 말고 Legacy 필드로 유지한다)** 를 이 값에 적용한 것이다. 근거: 코드 전체가 말하는 뜻은 '월간 검색 수(회)'로 일관되지만(사실), 어느 공급자의 어느 기간 값인지 적는 칸이 없고 수집 코드도 없어 보관함에 든 숫자가 무엇인지 알 수 없다(사실) — 자동 이전하면 알 수 없는 값에 출처를 붙여 주는 셈이다. 덧붙여 확인한 사실(`3b1294b` 기준): 설계 흔적이 공급자 한 곳만 가리키지 않는다(검색광고 API 와 오픈 API(데이터랩)가 모두 같은 지표 칸을 채우는 용도로 적혀 있다 — 데이터랩 값이 상대지수라면(**추정**, 코드·문서에 그 설명은 없다) '상대값을 횟수 칸에 넣는' 혼동이 이미 생길 수 있다). **N1 병합 뒤에는 이 근거가 약해진다** — 오픈 API 는 옛 항목이고 데이터랩 검색어 트렌드는 새 `naver_apihub` 가 '관심도 변화' 를 조회하는 용도로 적혀 있어(호출 코드는 아직 없음) '공급자가 한 곳이 아니다·상대값을 횟수 칸에 넣는 혼동' 은 N1 뒤에는 근거로 약하고, 남는 것은 '이미 들어 있는 값이 무엇이었는지 알 수 없다' 쪽뿐이다. 코드·문서의 설명은 '월간 검색 수요(회)' 뿐이고 PC·모바일을 합친 값인지는 적혀 있지 않다. 이 결론(Legacy 유지·자동 이전 없음)은 N1 이 먼저 병합되든 아니든 같다.
이에 따라 새 점수는 Legacy `search_demand` 를 읽지 않고 Trend 값은 새 칸으로만 받는다. 값의 출처를 아는 사람이 나중에 명시적으로 새 `search_demand_count`(+출처 이름)로 옮기는 길은 **후속 결정**으로만 둔다.

- 이 문서는 계획이다. `topics/`(P1·P2a)만 코드에 있고 `service/topics.py`·`topic_engine.db`·명령줄 `topics`·`주제 후보` 화면은 아직 없다.
- 조사는 읽기 전용이었고 시험 전체를 돌리지 않았다. P0 시험은 무거운 전체 실행 없이 관련 모듈만 따로 돌려 확인하고, 전체는 CI 가 본다.
- 블로그 쪽 이력 파일의 모양은 P2a 가 블로그 저장소 사본에서 읽기 전용으로 확인했다(`posts.json` 은 Jekyll 틀이라 만든 결과를 읽어야 한다 — `history.py`, D-45). 전략 원문은 이 PC 에 없어 P1·P2a 숫자는 요약·계획과만 대조했다.
- UI 설계 문서 일부와 보안·이관 문서 본문 일부는 읽지 못했다 — 해당 단계에서 다시 확인한다.
- 연결·한도·키 부분은 'NAVER API HUB 안전 틀' 묶음이 같은 저장소에서 고치는 중이라 P3·P5 는 그 병합 뒤 충돌을 다시 본다.
- 기존 `search_demand` 에 이미 들어 있는 값이 어느 공급자·기간의 값인지는 알 수 없다(7절). Legacy 로 두고 새 점수에 쓰지 않는다.
- 전략의 후속 후보(글당 3개)·협찬 경제적 이해관계 표시·영어 Seed·지역 목록은 P6 이후에 다룬다.

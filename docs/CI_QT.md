# 정식 CI 의 화면(Qt) 시험 칸

> 상태: **준비만 해 둔 가지**(`ai/claude/NO-MERGE-v1ciqt2-wip`)다 — 병합 전이다. 운영자 확인 037 ① 승인(이슈 #264, 2026-11-24 19:43)과 확인 042 ① 승인(이슈 #277, 2026-11-25 19:32 — 화면 칸을 병합 가지와 main 푸시마다 돌린다)의 범위 안에서 만들었고, 새 모양의 실제 조각 시간을 재는 진단 실행과 병합은 따로 부탁한다(`ci.yml` 변경은 T3). 결정 번호는 `docs/DECISIONS.md` 의 D-710 에서 D-719 다. 첫 실행이 시간 한도를 넘은 일(진단 두 번)을 풀려고 조각 수·무게 표·돌 때 조건·자동 PR 기다림을 정한 것이 D-717 에서 D-719 이고, 1·2·4·5·7절은 그 값으로 고쳤다(12–14절이 근거다). 2026-11-26 에는 새 모양(열두 조각)을 진짜 러너에서 돌려 본 3차 진단(실행 45715001306·45720452621)의 실측으로 7절의 무게 표를 다시 맞췄다 — 표 기준 조각마다 약 15분이고 가장 느린 조각이 이상의 1.00배로 예측된다(7절·12절 끝).

## 1. 한눈에

- 정식 CI 의 열두 칸(환경 4개 × 조각 3개)에는 화면 도구 PySide6 가 없어서 화면(Qt) 시험 약 1,200개가 모두 '건너뜀'이다. 건너뛴 시험은 초록으로 끝나므로 화면이 깨져도 병합을 막지 못했다. 지금까지 Qt 시험은 임시 가지와 임시 워크플로로 따로 돌렸다(D-32).
- 새 칸 `qt` 는 **같은 `ci.yml` 의 둘째 잡**이다. 윈도·파이썬 3.12 에서 PySide6 두 파일(합쳐 약 83MB, 비용 0)만 받아 화면 시험까지 모두 돌린다. 창은 띄우지 않는다(`QT_QPA_PLATFORM=offscreen`). 시험 파일 전체(약 354개 — 러너에서 합쳐 약 2.9시간 분량)를 **열두 조각**으로 나눠 동시에 돌리고, 조각은 러너에서 잰 시간 표(`QT_WEIGHTS`, 7절)로 고르게 나눈다(표 기준 조각마다 약 15분).
- 같은 파일의 잡이라 `auto-pr.yml` 의 병합 문턱(그 커밋의 `ci.yml` 실행이 모두 성공해야 PR 을 만든다)이 새 칸을 포함한다. 새 칸은 **병합 가지(`ai/claude/M…`)와 main 에서만** 돈다(13절) — 작업 중 가지(`NO-MERGE-…` 등)의 검사는 열두 칸만 돌고 건너뛴 새 칸은 초록으로 친다. 병합 가지 검사 시간은 약 19분에서 약 30분대가 된다(운영자 확인 042 ① 이 받아들였다). `auto-pr.yml` 은 숫자 둘(기다림 최대 시간·작업 시간 한도)만 올렸다 — 새 칸이 줄을 서서 늦게 시작해도 끝까지 기다리게(14절, D-719).
- 기존 열두 칸(`test` 잡)은 한 글자도 바뀌지 않았다. 그래서 열두 칸에서는 Qt 시험의 건너뜀이 지금처럼 정상이다.
- PySide6 가 안 깔려 시험이 건너뛰어졌는데 초록이 되는 일은 막는다(3절).

## 2. 칸 구성

| 항목 | 값 | 이유 |
|---|---|---|
| 잡 이름 | `Qt 시험 (windows-latest, Python 3.12, 조각 N/12)` | 기존 두 이름 접두어(`시험 (`·`시험 실행(`)로 시작하지 않아 이름을 못박는 기존 시험과 안 부딪힌다 |
| 돌 때 조건 | 작업 수준 `if` 한 줄 — 병합 가지(`ai/claude/M…`)와 main 에서만(13절) | 작업 중 가지(`NO-MERGE-…`)는 열두 칸만 돌아 검사가 빠르고 러너 시간을 아낀다(확인 042 ①) |
| 러너·파이썬 | `windows-latest`, `'3.12'` | 설치 파일 묶음과 같은 판(D-400) |
| 조각 | `[1, 2, …, 12]`(열둘), 총수 `'12'`, `fail-fast: false` | 같은 `scripts/ci_shard.py` 규칙이되 Qt 칸 전용 무게 표로 나눈다(7절). 열둘인 까닭은 12절의 계산. 바꾸려면 목록·총수·두 이름의 `/12` 와 시험(골든 표, 11절)을 함께 고친다 |
| 시간 한도 | `timeout-minutes: 40` | `test` 잡과 같다. 조각 하나는 표 기준 약 15분(조각마다 886–887초)에 설치 1–1.5분을 더해 16분 남짓이라 한도의 약 40% 다 — 실측이 +35% 흔들려도 약 21분, 한도의 절반 남짓이다(7절·12절) |
| 권한·비밀 | 최상위 `contents: read` 그대로, 비밀 값 0 | 잡 권한·환경 변수 주입 없음 |
| 단계 | ① 가져오기 ② 파이썬 3.12 ③ `python scripts/ci_qt_setup.py` ④ `python scripts/ci_shard.py` | ①②는 `test` 잡과 같은 SHA 의 같은 액션 둘뿐(새 액션 0) |
| ④의 환경 변수 | `PYTHONUTF8`·`CI_SHARD`·`CI_SHARD_TOTAL`·`CI_WEIGHTS=qt`·`CI_REQUIRE_QT=1`·`QT_QPA_PLATFORM=offscreen` | 앞의 셋은 기존 단계와 같고 `CI_WEIGHTS` 가 Qt 칸 전용 무게 표를 고르며(7절) 뒤의 둘이 Qt 칸 표시와 화면 방식 |
| 시험 범위 | 전체 시험 파일(비 Qt 시험도 PySide6 가 있는 환경에서 한 번 돈다) | 제품 환경과 같고 분류에서 빠뜨릴 위험이 없다 |

**`scripts/ci_qt_setup.py`(표준 라이브러리만)가 하는 일**
1. `packaging/requirements-package.txt` 의 `# [runtime]` 아래 줄을 읽는다. **정확히 두 줄**(`PySide6_Essentials==X`·`shiboken6==X`, 같은 X)이 아니면 종료 코드 2 로 거절한다. runtime 에 줄이 더해지면 이 칸이 빨개져 의식적으로 고치게 된다. `이름==버전` 이 아닌 모양(범위·주소·옵션)도 거절한다.
2. `python -m pip install --disable-pip-version-check --isolated --only-binary=:all: --no-deps 두 줄` 을 고정 인자 목록으로(셸 없음) 돌린다. 설치처를 바꾸는 옵션은 없고 `--isolated` 가 환경 변수·사용자 설정의 영향을 끊는다. 잠금 줄에 `--hash` 가 생기면 그 두 줄만 담은 임시 요구 파일과 `--require-hashes` 로 바꿔 부른다(해시 잠금은 따로 승인받는 일).
3. 설치된 버전이 잠금과 같은지, 화면 없는 `QApplication` 이 만들어지는지 본다. 그리고 버전·글꼴 이름 몇 줄을 찍는다(경로·사용자 이름 없음). 한글을 그릴 수 있는 글꼴이 없으면 알림 한 줄만 낸다(실패 아님 — 6절).

개발 PC 에서는 `python scripts/ci_qt_setup.py --dry-run`(명령만 보여 주고 아무것도 설치하지 않는다)과 `--probe-only`(설치 없이, 이미 PySide6 가 있을 때 3번 점검만)로 확인한다. **인자 없이 부르면 진짜로 설치한다** — `ci.yml` 만 그렇게 부르고, 시험은 진짜 설치를 하지 않는다.

## 3. 건너뜀 가드와 종료 코드

`ci.yml` 의 시험 단계는 `CI_REQUIRE_QT=1` 로 `scripts/ci_shard.py` 를 부른다. 이 값이 있으면 다음을 한다(없으면 오늘과 똑같다).

| 종료 코드 | 어디서 | 뜻 |
|---|---|---|
| 2 | `ci_shard.py` | `CI_REQUIRE_QT` 값이 1·0·없음이 아니다(오타로 가드가 꺼진 채 초록이 되는 것을 막는다) |
| 2 | `ci_shard.py` | `CI_WEIGHTS` 값이 `qt` 도 없음도 아니다(오타로 기본 무게 표를 쓴 채 조각이 쏠려 시간 한도에 걸리는 것을 막는다) |
| 3 | `ci_shard.py` | 시작 전에 PySide6 를 못 찾았다 — 시험을 하나도 돌리지 않고 멈춘다 |
| 1 | `ci_shard.py` | 시험이 끝난 뒤 건너뛴 시험 중 이유에 PySide6(대소문자 무시)가 든 것이 하나라도 있다 — 시험 파일별 개수를 찍는다 |
| 2·3·4·5 | `ci_qt_setup.py` | 잠금·인자 거절 · pip 설치 실패 · 설치된 버전이 잠금과 다름 · Qt 점검 실패 |

- 건너뜀 가드는 PySide6 이유가 아닌 건너뜀(git·링크·권한 같은 환경 이유)은 정보로만 센다. 첫 실행에서 어떤 이유가 나오는지 본 뒤 허용 목록으로 굳힌다.
- 시험 단계 끝에 `건너뛴 시험 N개 — PySide6 이유 0개` 줄과, 이유별 개수, **시험 파일별 걸린 시간 상위 15개**가 찍힌다. 걸린 시간은 7절의 무게 표를 고칠 때 쓴다. 5초 넘게 걸린 시험 파일은 끝나는 즉시 `[걸린 시간] 파일 초` 한 줄도 찍히므로 칸이 시간 한도에 잘려도 로그에 남는다.
- 새 Qt 시험 파일은 건너뜀 문구에 `PySide6` 낱말을 쓴다(지금 모든 파일이 그렇다). `tests/test_ci_shard.py` 의 정적 시험이 Qt 깃발(`HAVE`)을 조건으로 건너뛰는 모든 곳을 훑어 이를 지킨다.

| 붉은 시험 | 이름과 메시지 | 5번 분류의 (가)(나)(다)로 가른다 |
| 흔들림 후보 | 아래 | 같은 커밋 3번 안정 확인에서 갈리는 시험 |

흔들림 후보는 소스에서 읽은 것이다(첫 실행 전 추정).
- 시간을 재서 한도를 거는 시험: `test_ui_qt`(0.5초)·`test_ui_qt_c1a`(1초)·`test_ui_qt_drafts`(1초·20초)·`test_ui_qt_ocr_input`(큰 사진 한 장 5초)·`test_ui_qt_photo_ocr`(닫기 6초·갱신과 이동 시간)·`test_ui_qt_backup`(기다림 0.25초 이상). 러너 시계가 느리면 갈릴 수 있다. 고치는 일은 이 갈래 밖이고 시험을 약하게 하지 않는다.
- 글자 잘림·삐져나옴 점검(`find_clipping`·`find_squeezed`)을 쓰는 시험 파일 27개: 글꼴·언어가 개발 PC 와 다르면 글자 너비 숫자가 달라질 수 있다(6절).
- 기록상 `test_ui_qt_drafts` 는 시험이 끝났는데 프로세스가 끝나지 않은 적이 있다(옛 PC, 2026-11-16 기록). 그러면 40분 한도에 걸려 빨개진다.
- 전체 시험 파일이 한 프로세스에서 PySide6 와 함께 처음 도는 것이라 시험 사이의 오염(앞 시험이 만든 화면 객체·전역 상태)이 처음 드러날 수 있다.

## 6. 한글 글꼴·언어가 다를 때(첫 실행이 가른다)

| 관찰 | 대응 |
|---|---|
| 글꼴 목록에 한글 글꼴이 있고 시험이 모두 초록 | 그대로 |
| 한글 글꼴이 없고 글자 잘림 시험만 붉음 | ① 러너에 글꼴을 깔지 않는다(내려받기·라이선스) ② 시험의 글꼴 흉내(`install_system_fonts`)에 '한글 글꼴이 없으면 알림' 만 더하고 **판정 기준은 낮추지 않는다** ③ 그래도 붉으면 그 시험들을 목록으로 만들어 운영자에게 '이 칸은 글꼴 때문에 일부를 개발 PC 에서만 본다' 는 결정을 번호 있는 확인으로 묻는다 |
| 윈도 표시 언어(영어)가 달라 문구 비교가 틀림 | 시험이 윈도 언어를 읽는 곳이 있는지 소스로 확인한 뒤 시험을 고친다 |

## 7. 무게 표와 다시 재는 법(측정값 — 결정 D-717)

`scripts/ci_shard.py` 의 `QT_WEIGHTS` 는 3차 진단(병합 금지 가지 `NO-MERGE-diag-qtt3` 에서 지금 모양 그대로 `qt` 잡 열두 조각을 돌린 임시 실행 두 번 — 45715001306 은 조각별 시간, 45720452621 은 시험 파일별 시간까지)이 윈도 러너·파이썬 3.12·PySide6 에서 잰 **시험 파일마다 걸린 초**다. 이번에는 시험 파일 354개 전부의 초를 주석으로 뽑았다(측정 합계 10,549초, 약 2.9시간 분량, 중앙값 3.2초). 값은 `max(1, round(초))` 정수라 1초 미만은 1초로 올려 쳐서 표 합계는 10,641초이고, 이 표로 열두 조각을 나누면 표 기준 조각마다 886–887초(약 14.8분)다. 측정 초로 더하면 875–883초라 가장 느린 조각이 이상(전체 ÷ 12)의 1.00배이고 가장 무거운 열두 파일이 서로 다른 조각에 든다(예측). 환경 변수 `CI_WEIGHTS=qt` 일 때만 쓰이며(`ci.yml` 의 `qt` 잡이 준다) 정식 CI 열두 칸은 옛 표(`WEIGHTS`, 개발 PC 에서 잰 20초 이상의 큰 파일)를 그대로 쓴다. 표에 없는 파일(새 시험 파일)은 기본 무게 3초(`QT_DEFAULT_WEIGHT`, 측정 중앙값 근처)로 친다 — 새 시험 파일이 몰려도 한 조각에 쏠리지 않게만 하고, 큰 Qt 시험 파일이면 다음 진단 뒤 표에 넣는다.

**왜 다시 맞췄나(2차 진단 값의 첫 표는 쏠렸다).** 2차 진단(실행 45585260861, 10조각)의 값 209개로 채웠던 첫 표로 열두 조각을 진짜 러너에서 돌려 보니(3차 진단 두 번) 실제 Qt 시험은 열두 조각 모두 통과했지만 조각의 시험 단계 시간이 쏠렸다 — 첫 실행 654·444·506·872·525·489·1,177·696·658·957·1,243·1,097초, 둘째 실행 634·531·409·1,102·560·456·1,590·836·676·849·1,618·1,444초로 가장 느린 조각이 이상의 약 1.8배였다(가장 느린 칸이 총 27분이라 한도 40분 안이었다). 새 모듈별 실측과 견주면 새/옛 비율이 중앙값 0.94 인데 0.07배에서 2.02배까지 흩어져 옛 표의 상대 무게가 많이 틀렸다. 옛 표로 나눈 조각별 합계를 새 실측으로 다시 더한 값은 623·518·400·1,090·549·443·1,572·823·664·837·1,601·1,430초(가장 느린 조각이 이상의 1.82배)로 실제 쏠림과 같은 모양이다. 옛 표는 표에 없는 145개 파일을 5초씩 쳐 합 725초로 계획했지만 실제 합은 82초였다(평균 0.6초). 새 표로 같은 실측을 나누면 조각마다 875–883초다.

가장 큰 일곱은 `test_ui_qt_polish1` 747초·`test_ui_qt_photo` 605·`test_ui_qt_photo_ocr` 544·`test_ui_qt_posts` 508·`test_ui_qt_blogs` 459·`test_ui_qt_drafts` 455·`test_ui_qt_keys` 385 다(이어서 `test_ui_qt_scale` 380·`test_ui_qt_references` 330·`test_ui_qt_seeds` 310). 비 Qt 큰 파일도 러너 값이다(`test_pages_publish` 157초·`test_service_recovery` 104·`test_service_repolock` 80 — 열두 칸 표의 780·460·430 은 개발 PC 값이라 서로 다르다). 이 표가 틀려도 시험 결과는 같다 — 조각이 쏠려 시간만 달라질 뿐이다.

**주의 — 시험 수는 시간의 길잡이가 못 된다.** 개발 PC 에서 `test_ui_qt_names` 는 시험 9개에 116초(앱 창 전체를 만드는 시험)가 걸렸고 `test_ui_qt_images` 는 10개에 6초였다(러너 값은 위 표: 93초·1초). 그래서 표는 반드시 러너가 잰 시간으로 정한다.

**한계 — 한 번의 실행값이다.** 이 표는 3차 진단의 둘째 실행 하나에서 뽑았다. 같은 구성의 두 실행에서 같은 조각의 시험 단계 시간이 둘째가 첫째의 0.81배에서 1.35배까지 달랐다(러너 속도 차이 — 실행마다 ±30% 흔들린다). 그래서 표의 숫자는 ±30% 오차가 있는 값이고, 조각마다 고르게 나눈 예측(886–887초)도 실제로는 조각마다 흔들린다. 그 흔들림을 +35% 까지 보아도 가장 느린 조각은 설치 1.5분을 더해 약 21분이라 한도 40분의 절반 남짓이다(12절 끝의 표). 2차 진단(조각 구성이 달랐던 10조각)의 값과 견주면 같은 파일이 0.07–2.02배로 달랐는데, 러너 속도와 조각 구성(같은 프로세스에서 앞서 도는 시험)이 섞였을 수 있고 원인은 가르지 못했다. 한 번의 실행 차이만으로 표를 고치지 않는다 — 같은 조각이 거듭 느린지 두 번 이상 본다.

**다시 재는 법**(표를 갱신할 때 — 새 시험 파일이 크게 늘었거나 5절에서 같은 조각이 거듭 느릴 때)

1. 병합 가지나 main 푸시의 Qt 칸(열두 조각) 로그를 모은다. 작은 파일까지 시험 파일 전부의 초가 필요하거나 작업 중 가지에서 재고 싶으면 **진단 가지**(`NO-MERGE-diag-…`, 3차 진단이 그렇게 했다)에서 같은 칸을 돌린다. 13절처럼 그 가지에서만 `if` 줄에 가지 이름을 임시로 더하고, `scripts/ci_shard.py` 의 `main()` 에서 시험을 돌린 직후 `result.module_seconds`(정식 칸의 `[걸린 시간]` 줄과 표가 쓰는 같은 값)를 GitHub 주석 한 줄로 찍는 코드 몇 줄을 더한다 — 표준 출력에 `::notice title=QTT-FINAL::` 다음 `이름=초 ; 이름=초 …` 꼴. 이 계측은 진단 가지에만 두고 정식 칸에는 넣지 않는다(정식 칸에는 기존 '걸린 시간' 표 출력 외에 새 쓰레드·주석을 더하지 않는다). 검사 로그는 로그인 없이 읽을 수 없지만 주석은 REST 로 읽을 수 있다. 같은 칸을 두 번 이상 돌려야 실행 사이 흔들림을 가늠한다(3차 진단은 두 번).
2. 정식 칸의 출력만 쓸 때는 조각마다 두 곳을 읽는다. ① 5초 넘게 걸린 시험 파일은 끝나는 즉시 `[걸린 시간] 파일 초` 한 줄이 찍힌다(칸이 시간 한도에 잘려도 남는다). ② 시험 단계 끝의 `시험 파일별 걸린 시간` 표(걸린 순 상위 15개와 이 조각 합계)에는 마지막 파일도 든다. 이 출력은 큰 파일만 보여 주므로 작은 파일의 값은 기본 무게가 맡는다. 이 출력 외에 새 쓰레드·주석은 더하지 않았다.
3. 조각마다 계획과 실제를 견준다. 시험 단계 첫머리의 `조각 N/12: … — 무게 표 qt: 이 조각 M초` 가 표 기준 계획이고(이 나무에서는 시험 파일 전부가 표에 들어 있어 886–887초 — 1초로 올려 친 값 때문에 측정 합계보다 조각마다 4–11초 크다. 다른 갈래가 더한 새 시험 파일은 3초씩 더해진다), 표 머리의 `이 조각 합계` 가 실제다. 가장 느린 조각이 한도 40분의 70%(28분)를 넘거나 같은 조각이 거듭 느리면 표를 고친다.
4. 표를 갱신한다: 시험 파일마다 `max(1, round(초))` 정수를 `QT_WEIGHTS` 에 옮긴다(무거운 순, 같으면 이름 순). 주석으로 뽑은 이름이 진짜 시험 파일과 다 맞는지 확인한다 — 이름 앞의 `test_` 를 떼어 찍는 계측이면 이름 가운데에 `test_` 가 든 파일이 잘못 복원될 수 있다(시험이 잡는다). 없어진 시험 파일의 이름은 반드시 지운다 — 시험이 지킨다.
5. 같은 변경에서 `tests/test_ci_shard.py` 의 고정 값(`QT_MEASURED_TOP`·`(개수, 합계)`·세 큰 비 Qt 파일 값·기본 무게·계획 줄의 조각 초)과 이 절·`docs/DECISIONS.md` D-717 의 숫자를 함께 고친다. 시험이 개수·합계·상위 일곱·세 큰 비 Qt 파일 값·기본 무게·계획 줄의 조각 초를 못박아 두어 이 값들을 슬쩍 바꾸면 빨개진다(합이 같은 두 값의 자리 바꿈처럼 이 값들에 닿지 않는 변경은 못 잡는다). 조각 수나 시간 한도를 바꾸는 일은 11절·12절을 따른다.

**병합 때 조심할 것(다른 갈래가 시험 파일을 옮기거나 지우거나 더할 때).** 병합 가지는 여러 갈래를 한 나무로 합치므로 시험 파일이 바뀐 만큼 표를 맞춘다.
- **지우거나 이름을 바꾼 시험 파일**: 표에 든 이름이면 `QtWeightsTableTest` 의 `test_every_key_is_a_test_file_that_exists…` 가 빨개지고 낡은 이름을 모두 보여 준다. 지운 파일은 그 키를 `QT_WEIGHTS` 에서 지우고 같은 변경에서 `(개수, 합계)` 고정 값을 그만큼 낮춘다(지금 값은 `python -c "import sys; sys.path.insert(0, 'scripts'); import ci_shard; print(len(ci_shard.QT_WEIGHTS), sum(ci_shard.QT_WEIGHTS.values()))"` 로 읽는다). 이름만 바꾼 파일은 키 이름을 새 이름으로 바꿔 값을 그대로 옮긴다(안 그러면 새 이름이 기본 무게 3초로 쳐진다). 상위 일곱이나 세 큰 비 Qt 파일이 사라지거나 이름이 바뀌면 그 고정 값도 함께 고친다.
- **시험 파일 안의 시험만 새 파일로 옮긴 경우**(한 시험 파일의 시험들을 새 시험 파일들로 나눔): 이름이 사라지지 않아 시험이 빨개지지 않는다. 옛 파일의 표 값은 실제보다 커지고 새 파일은 기본 무게 3초로 쳐져 조각 하나가 수십 초 쏠릴 수 있다(조각 전체 약 880초에 견주면 몇 퍼센트 — 허용 범위). 다음 진단 뒤 표를 다시 맞춘다.
- **더한 시험 파일**: 표에 없어도 된다(3초로 친다). 큰 Qt 시험 파일이면 그 조각이 길어질 수 있으니 병합 뒤 첫 실행의 계획 줄과 실제 합계를 견준다.

시험이 지키는 것(`tests/test_ci_shard.py`): 표의 모든 키가 진짜 시험 파일 이름이고(없어진 이름이 쌓이지 않는다) 값이 양의 정수·표로 나눈 가장 무거운 조각이 이상(전체 ÷ 조각 수)의 1.15배 이하(깨지면 표를 다시 재라는 신호)·가장 무거운 파일들이 서로 다른 조각에 하나씩 들어감·모든 시험 파일이 정확히 한 조각에 들어가고 빈 조각이 없음·`CI_WEIGHTS` 의 다른 값은 종료 코드 2·표의 숫자(개수·합계·상위 일곱·세 큰 비 Qt 파일 값·기본 무게)는 고정 값. 열두 칸의 기본 표·기본 무게·나누기 결과는 옛 코드에서 뽑은 고정 값으로 못박았다. 다만 균형 시험은 표의 숫자로 계산하므로 표가 실제 러너 시간과 어긋나도 알아채지 못한다(2차 진단 값의 옛 표도 이 시험은 통과했지만 실제로는 가장 느린 조각이 이상의 약 1.8배였다) — 어긋남은 5절과 위 3단계의 계획 줄·실제 합계 견주기가 가려낸다.

## 11. 승인된 모양을 글자 그대로 못박는 시험(결정 D-716)

## 13. 돌 때 조건과 진단 가지에서 바꿀 한 줄(결정 D-718, 운영자 확인 042 ① 승인 — 이슈 #277)

`ci.yml` 의 `qt` 잡에 작업 수준 `if` 한 줄이 있다: `github.ref` 가 `refs/heads/main` 이거나 `refs/heads/ai/claude/M` 로 시작하면 돈다(`startsWith`). 그러므로 병합 가지(`ai/claude/M번호-이름`)와 main 푸시에서 돌고, 작업 중 가지(`ai/claude/NO-MERGE-…`·`desktop/…` 등)와 태그에서는 건너뛴다. 수동 실행(`workflow_dispatch`)은 main 을 골라 돌릴 때 이 조건을 만족해 이 칸도 돈다(다른 가지를 고르면 건너뛴다). `test` 잡(열두 칸)은 `if` 가 없어 모든 가지에서 돈다.

- **왜 작업 중 가지에서는 안 도나.** 이 칸은 러너 약 3.2시간(표 기준 조각 열둘의 합 — 조각마다 설치를 더해 약 16분)을 쓰고 동시 작업 20개 한도의 자리를 차지해 다른 검사를 늦춘다. 작업 중 가지는 푸시마다 열두 칸이 돌면 충분하고, 화면 시험은 병합 가지가 만들어질 때 한 번 도는 것으로 병합 문턱 구실을 한다. 병합 가지 검사 시간은 약 19분에서 약 30분대로 는다(운영자 확인 042 ① 이 받아들였다).
- **건너뛴 잡은 초록 취급이다.** GitHub 는 `if` 가 거짓이라 건너뛴 잡을 실패로 치지 않고, 그 실행의 결론은 나머지 잡이 정한다. `auto-pr.yml` 은 병합 가지(`ai/claude/M번호-…`)에서만 시작하고 그 커밋의 `ci.yml` 실행이 `completed:success` 인지만 본다 — 병합 가지에서는 `qt` 도 돌므로 `test` 와 `qt` 모두가 문턱이다. 작업 중 가지에서는 `auto-pr.yml` 이 시작하지 않고 검사는 `test` 칸만으로 끝난다. `scripts/release_check.py` 는 CI 실행 결과를 읽지 않는다.
- **시험이 이 줄을 글자 그대로 못박는다**: `tests/workflow_golden.py` 의 `QT_IF`(골든 표)·`tests/test_ci_workflow_qt.py`·`tests/test_ci_shard.py`. 없애거나 `true`·`always()`·다른 가지 패턴·진단 가지 이름으로 바꾼 사본, `test` 잡이나 단계에 `if` 를 끼운 사본, `if` 를 두 번 쓴 사본을 모두 거절한다. 파일 전체에서 `if:` 는 이 한 줄뿐이다(옛 '`if:` 는 어디에도 없다' 를 '정해진 한 줄만' 으로 좁힌 것이지 푼 것이 아니다).
- **진단 가지에서 바꿀 줄(이 한 줄뿐이어야 한다).** 병합 금지 가지에서 새 모양의 조각 시간을 재려면 그 가지의 `.github/workflows/ci.yml` 에서 아래 한 줄을, 같은 줄에 `|| github.ref == 'refs/heads/ai/claude/NO-MERGE-진단가지이름'` 만 덧붙인 것으로 바꾼다.

  `    if: github.ref == 'refs/heads/main' || startsWith(github.ref, 'refs/heads/ai/claude/M')`

  그 가지에서는 위 시험들이 빨개지는 것이 맞다(그 한 줄이 승인값과 다르므로). 병합 가지에는 이 변경을 섞지 않는다 — 섞이면 같은 시험이 막는다.

## 14. 자동 PR 의 기다림 숫자(결정 D-719 — 승인된 T3 의 '숫자만')

병합 가지에 Qt 칸 열두 조각이 더해지면 동시 작업 한도 때문에 일부 조각이 줄을 서서 늦게 시작한다(12절). `auto-pr.yml` 이 검사가 끝나기를 기다리는 시간이 작업 시간 한도(40분)와 같은 40분이면 늦게 시작한 조각이 끝나기 전에 PR 을 만들지 않고 끝낼 수 있다(모의: 다른 가지가 한 건 겹치면 54%). 그래서 숫자 둘만 올렸다 — 기다림 최대 40분 → 60분(`AUTOPR_MAX_WAIT_SECONDS` 2400 → 3600 과 기본값 둘, 경고 문구의 분), 그 작업의 시간 한도 45분 → 65분(기다림 + 마지막 걸음 몫 5분). 60분은 작업 시간 한도 40분에 줄 서는 시간 20분을 더한 값이다. 이 값에서는 다른 가지가 두 건 겹쳐도(중앙 46분) 모의 실험에서 60분을 넘긴 일이 없었다(이 절의 모의 숫자는 2차 진단 표 기준의 옛 값이다 — 3차 진단 뒤 조각이 짧아져(7절·12절 끝) 여유가 더 크지만 자동 PR 숫자 3600초·65분은 그대로 둔다).

이 변경은 `auto-pr.yml` 의 숫자(와 그 숫자를 설명하는 머리 주석 한 문단)뿐이고 단계·권한·`gh` 호출·가지 필터·비밀은 그대로다(`tests/test_auto_pr_workflow.py` 가 줄마다 고정한다). 시험은 숫자를 새 값으로 고쳤다 — `tests/test_ci_workflow_qt.py` 는 옛 '대기 = 작업 한도' 를 '대기 = 작업 한도 + 줄 서는 20분, 자동 PR 작업 한도 = 대기 + 5분' 으로(더 엄격하게) 못박는다. 옛 서술 '최대 40분'(D-175·D-176·D-716 과 `auto-pr.yml` 머리 주석의 옛 판)은 이 절이 대체한다. 이 절의 숫자 변경만 따로 빼도 앞의 절은 성립한다(그때는 기다림이 짧아 겹침이 있으면 PR 을 노란 배너로 만든다).

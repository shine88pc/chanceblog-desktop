# 정식 CI 의 화면(Qt) 시험 칸

> 상태: **준비만 해 둔 가지**(`ai/claude/NO-MERGE-v1ciqt2-wip`)다 — 병합 전이다. 운영자 확인 037 ① 승인(이슈 #264, 2026-11-24 19:43)과 확인 042 ① 승인(이슈 #277, 2026-11-25 19:32 — 화면 칸을 병합 가지와 main 푸시마다 돌린다)·확인 046 ① 승인(이슈 #284, 2026-11-26 — 화면 칸의 시간 한도를 40분에서 60분으로 올린다)의 범위 안에서 만들었고, 새 모양의 실제 조각 시간을 재는 진단 실행과 병합은 따로 부탁한다(`ci.yml` 변경은 T3). 결정 번호는 `docs/DECISIONS.md` 의 D-710 에서 D-719 다. 첫 실행이 시간 한도를 넘은 일(진단 두 번)을 풀려고 조각 수·무게 표·돌 때 조건·자동 PR 기다림을 정한 것이 D-717 에서 D-719 이고, 1·2·4·5·7절은 그 값으로 고쳤다(12–14절이 근거다). 2026-11-26 에는 새 모양(열두 조각)을 진짜 러너에서 돌려 본 3차 진단(실행 45715001306·45720452621)과 4차 진단(실행 45746502211)의 실측으로 7절의 무게 표를 두 실행의 모듈별 평균으로 다시 맞췄다. 표 기준 조각마다 913초(약 15분)이지만 같은 프로세스에서 앞서 돈 작업량 때문에 같은 시험 파일의 시간이 실행마다 크게 달라 실제 조각 시간은 고르지 않았고(4차 진단: 조각마다 252–1,875초, 가장 느린 조각이 설치까지 약 33분), 표만으로는 고르게 맞출 수 없어 화면 칸의 시간 한도를 60분으로 올렸다(7절·12절 끝). 근본 해결(화면 시험 파일마다 새 프로세스)은 이 갈래 밖의 후속이다.

## 1. 한눈에

- 정식 CI 의 열두 칸(환경 4개 × 조각 3개)에는 화면 도구 PySide6 가 없어서 화면(Qt) 시험 약 1,200개가 모두 '건너뜀'이다. 건너뛴 시험은 초록으로 끝나므로 화면이 깨져도 병합을 막지 못했다. 지금까지 Qt 시험은 임시 가지와 임시 워크플로로 따로 돌렸다(D-32).
- 새 칸 `qt` 는 **같은 `ci.yml` 의 둘째 잡**이다. 윈도·파이썬 3.12 에서 PySide6 두 파일(합쳐 약 83MB, 비용 0)만 받아 화면 시험까지 모두 돌린다. 창은 띄우지 않는다(`QT_QPA_PLATFORM=offscreen`). 시험 파일 전체(약 354개 — 러너에서 합쳐 약 3시간 분량)를 **열두 조각**으로 나눠 동시에 돌리고, 조각은 러너에서 잰 시간 표(`QT_WEIGHTS`, 7절)로 나눈다(표 기준 조각마다 913초, 약 15분 — 다만 실제 시간은 실행마다 고르지 않다, 7절).
- 같은 파일의 잡이라 `auto-pr.yml` 의 병합 문턱(그 커밋의 `ci.yml` 실행이 모두 성공해야 PR 을 만든다)이 새 칸을 포함한다. 새 칸은 **병합 가지(`ai/claude/M…`)와 main 에서만** 돈다(13절) — 작업 중 가지(`NO-MERGE-…` 등)의 검사는 열두 칸만 돌고 건너뛴 새 칸은 초록으로 친다. 병합 가지 검사 시간은 약 19분에서 약 30분대 이상이 된다(운영자 확인 042 ① 이 받아들였다 — 4차 진단에서 가장 느린 화면 조각이 설치까지 약 33분이었고, 줄 서기와 다른 가지의 겹침이 더해지면 더 늘어난다). 화면 칸의 시간 한도는 60분이다(운영자 확인 046 ①, 12절). `auto-pr.yml` 은 숫자 둘(기다림 최대 시간·작업 시간 한도)만 올렸다 — 새 칸이 줄을 서서 늦게 시작해도 끝까지 기다리게(14절, D-719).
- 기존 열두 칸(`test` 잡)은 한 글자도 바뀌지 않았다. 그래서 열두 칸에서는 Qt 시험의 건너뜀이 지금처럼 정상이다.
- PySide6 가 안 깔려 시험이 건너뛰어졌는데 초록이 되는 일은 막는다(3절).

## 2. 칸 구성

| 항목 | 값 | 이유 |
|---|---|---|
| 잡 이름 | `Qt 시험 (windows-latest, Python 3.12, 조각 N/12)` | 기존 두 이름 접두어(`시험 (`·`시험 실행(`)로 시작하지 않아 이름을 못박는 기존 시험과 안 부딪힌다 |
| 돌 때 조건 | 작업 수준 `if` 한 줄 — 병합 가지(`ai/claude/M…`)와 main 에서만(13절) | 작업 중 가지(`NO-MERGE-…`)는 열두 칸만 돌아 검사가 빠르고 러너 시간을 아낀다(확인 042 ①) |
| 러너·파이썬 | `windows-latest`, `'3.12'` | 설치 파일 묶음과 같은 판(D-400) |
| 조각 | `[1, 2, …, 12]`(열둘), 총수 `'12'`, `fail-fast: false` | 같은 `scripts/ci_shard.py` 규칙이되 Qt 칸 전용 무게 표로 나눈다(7절). 열둘인 까닭은 12절의 계산. 바꾸려면 목록·총수·두 이름의 `/12` 와 시험(골든 표, 11절)을 함께 고친다 |
| 시간 한도 | `timeout-minutes: 60` | `test` 잡의 40분과 다르다(운영자 확인 046 ① 승인). 조각 하나는 표 기준 913초(약 15분)지만 실제는 고르지 않아 4차 진단에서 가장 느린 조각이 시험 단계 1,875초(설치까지 약 33분 = 한도 40분의 82%)까지 갔다. 교차 평가의 최악 약 39분에 설치 1.5분을 더해도 한도 60분의 약 67% 다(7절·12절) |
| 권한·비밀 | 최상위 `contents: read` 그대로, 비밀 값 0 | 잡 권한·환경 변수 주입 없음 |
| 단계 | ① 가져오기 ② 파이썬 3.12 ③ `python scripts/ci_qt_setup.py` ④ `python scripts/ci_shard.py` | ①②는 `test` 잡과 같은 SHA 의 같은 액션 둘뿐(새 액션 0) |
| ④의 환경 변수 | `PYTHONUTF8`·`CI_SHARD`·`CI_SHARD_TOTAL`·`CI_WEIGHTS=qt`·`CI_REQUIRE_QT=1`·`QT_QPA_PLATFORM=offscreen` | 앞의 셋은 기존 단계와 같고 `CI_WEIGHTS` 가 Qt 칸 전용 무게 표를 고르며(7절) 뒤의 둘이 Qt 칸 표시와 화면 방식 |
| 시험 범위 | 전체 시험 파일(비 Qt 시험도 PySide6 가 있는 환경에서 한 번 돈다) | 제품 환경과 같고 분류에서 빠뜨릴 위험이 없다 |

**`scripts/ci_qt_setup.py`(표준 라이브러리만)가 하는 일**
1. `packaging/requirements-package.txt` 의 `# [runtime]` 아래 줄을 읽는다. **정확히 두 줄**(`PySide6_Essentials==X`·`shiboken6==X`, 같은 X)이 아니면 종료 코드 2 로 거절한다. runtime 에 줄이 더해지면 이 칸이 빨개져 의식적으로 고치게 된다. `이름==버전` 이 아닌 모양(범위·주소·옵션)도 거절한다.
2. `python -m pip install --disable-pip-version-check --isolated --only-binary=:all: --no-deps 두 줄` 을 고정 인자 목록으로(셸 없음) 돌린다. 설치처를 바꾸는 옵션은 없고 `--isolated` 가 환경 변수·사용자 설정의 영향을 끊는다. 잠금 줄에 `--hash` 가 생기면 그 두 줄만 담은 임시 요구 파일과 `--require-hashes` 로 바꿔 부른다(해시 잠금은 따로 승인받는 일).
3. 설치된 버전이 잠금과 같은지, 화면 없는 `QApplication` 이 만들어지는지 본다. 그리고 버전·글꼴 이름 몇 줄을 찍는다(경로·사용자 이름 없음). 한글을 그릴 수 있는 글꼴이 없으면 알림 한 줄만 낸다(실패 아님 — 6절).

개발 PC 에서는 `python scripts/ci_qt_setup.py --dry-run`(명령만 보여 주고 아무것도 설치하지 않는다)과 `--probe-only`(설치 없이, 이미 PySide6 가 있을 때 3번 점검만)로 확인한다. **인자 없이 부르면 진짜로 설치한다** — `ci.yml` 만 그렇게 부르고, 시험은 진짜 설치를 하지 않는다.

## 3. 건너뜀 가드와 종료 코드

`ci.yml` 의 시험 단계는 `CI_REQUIRE_QT=1` 로 `scripts/ci_shard.py` 를 부른다. 이 값이 있으면 다음을 한다(없으면 오늘과 똑같다).

| 종료 코드 | 어디서 | 뜻 |
|---|---|---|
| 2 | `ci_shard.py` | `CI_REQUIRE_QT` 값이 1·0·없음이 아니다(오타로 가드가 꺼진 채 초록이 되는 것을 막는다) |
| 2 | `ci_shard.py` | `CI_WEIGHTS` 값이 `qt` 도 없음도 아니다(오타로 기본 무게 표를 쓴 채 조각이 쏠려 시간 한도에 걸리는 것을 막는다) |
| 3 | `ci_shard.py` | 시작 전에 PySide6 를 못 찾았다 — 시험을 하나도 돌리지 않고 멈춘다 |
| 1 | `ci_shard.py` | 시험이 끝난 뒤 건너뛴 시험 중 이유에 PySide6(대소문자 무시)가 든 것이 하나라도 있다 — 시험 파일별 개수를 찍는다 |
| 2·3·4·5 | `ci_qt_setup.py` | 잠금·인자 거절 · pip 설치 실패 · 설치된 버전이 잠금과 다름 · Qt 점검 실패 |

- 건너뜀 가드는 PySide6 이유가 아닌 건너뜀(git·링크·권한 같은 환경 이유)은 정보로만 센다. 첫 실행에서 어떤 이유가 나오는지 본 뒤 허용 목록으로 굳힌다.
- 시험 단계 끝에 `건너뛴 시험 N개 — PySide6 이유 0개` 줄과, 이유별 개수, **시험 파일별 걸린 시간 상위 15개**가 찍힌다. 걸린 시간은 7절의 무게 표를 고칠 때 쓴다. 5초 넘게 걸린 시험 파일은 끝나는 즉시 `[걸린 시간] 파일 초` 한 줄도 찍히므로 칸이 시간 한도에 잘려도 로그에 남는다.
- 새 Qt 시험 파일은 건너뜀 문구에 `PySide6` 낱말을 쓴다(지금 모든 파일이 그렇다). `tests/test_ci_shard.py` 의 정적 시험이 Qt 깃발(`HAVE`)을 조건으로 건너뛰는 모든 곳을 훑어 이를 지킨다.

## 7. 무게 표와 다시 재는 법(측정값 — 결정 D-717)

`scripts/ci_shard.py` 의 `QT_WEIGHTS` 는 **3차·4차 진단 두 실행의 모듈별 평균**이다. 3차 진단(병합 금지 가지 `NO-MERGE-diag-qtt3` 에서 지금 모양 그대로 `qt` 잡 열두 조각을 돌린 임시 실행 두 번 — 45715001306 은 조각별 시간, 45720452621 은 시험 파일별 시간까지)과 4차 진단(`NO-MERGE-diag-qtt4`, 실행 45746502211 — 재작업 1 의 표 그대로 열두 조각을 돌림)이 윈도 러너·파이썬 3.12·PySide6 에서 잰 **시험 파일마다 걸린 초**를 시험 파일 354개 전부에 대해 주석으로 뽑았다(측정 합계 3차 10,549초·4차 11,183초, 중앙값 3.2초·2.8초). 파일마다 두 값의 평균을 `max(1, round(평균))` 정수로 했다(평균이 정확히 x.5 면 짝수 쪽 — 파이썬 `round`; 그런 파일이 23개이고 그중 8개는 올림이면 값이 달라져 합이 10,964초가 된다). 1초 미만은 1초로 올려 쳐서 표 합계는 10,956초(평균의 합 10,866초)이고, 이 표로 열두 조각을 나누면 표 기준 조각마다 913초(약 15.2분)다. 환경 변수 `CI_WEIGHTS=qt` 일 때만 쓰이며(`ci.yml` 의 `qt` 잡이 준다) 정식 CI 열두 칸은 옛 표(`WEIGHTS`, 개발 PC 에서 잰 20초 이상의 큰 파일)를 그대로 쓴다.

가장 큰 일곱은 `test_ui_qt_seeds` 656초·`test_ui_qt_photo_ocr` 600·`test_ui_qt_drafts` 468·`test_ui_qt_photo` 463·`test_ui_qt_settings` 455·`test_ui_qt_polish1` 445·`test_ui_qt_polish2` 408 이다(이어서 `test_ui_qt_posts` 389·`test_ui_qt_scale` 380·`test_ui_qt_blogs` 350·`test_ui_qt_keys` 350·`test_ui_qt_candidates` 286·`test_ui_qt_references` 283). 비 Qt 큰 파일도 러너 값이다(`test_pages_publish` 157초·`test_service_repolock` 97·`test_service_recovery` 96 — 열두 칸 표의 780·430·460 은 개발 PC 값이라 서로 다르다). 이 표가 틀려도 시험 결과는 같다 — 조각이 쏠려 시간만 달라질 뿐이다.

**기본 무게 3초(`QT_DEFAULT_WEIGHT`)의 근거.** 표에 없는 파일(새 시험 파일)은 3초로 친다. 354개 평균값의 중앙값이 2.9초(3차 3.15초·4차 2.8초)이고 표 값의 중앙값이 3초다. 옛 표(209개) 밖의 145개 파일은 실제로 합 82–86초(3차 82.3초·4차 86.4초, 파일당 0.6초 안팎)라 표 값으로는 파일당 1초 남짓(합 172초)으로 올려 쳐진다 — 그러니 3초는 작은 비 Qt 파일에는 넉넉한 쪽이다. 큰 Qt 시험 파일이 새로 들어오면 3초로는 어림도 안 되지만(다른 갈래가 더하는 화면 시험 파일은 수백 초일 수 있다) 어떤 기본값도 그것을 맞출 수 없으므로 병합 때 표에 넣어 다시 맞춘다(아래 '병합 때 조심할 것'). 열두 칸 기본 표의 기본 무게(4초)와 달라야 한다(시험이 지킨다).

**왜 다시 맞췄나 — 표 하나로는 고르게 맞출 수 없다(4차 진단).**

- **(1) 2차 진단 값 209개로 채웠던 첫 표는 쏠렸다.** 열두 조각을 진짜 러너에서 돌려 보니(3차 진단 두 번) 실제 Qt 시험은 열두 조각 모두 통과했지만 가장 느린 조각이 이상의 약 1.8배였다(조각별 시험 단계 초 첫 실행 654·444·506·872·525·489·1,177·696·658·957·1,243·1,097, 둘째 실행 634·531·409·1,102·560·456·1,590·836·676·849·1,618·1,444). 새 모듈별 실측과 견주면 새/옛 비율이 중앙값 0.94 인데 0.07배에서 2.02배까지 흩어졌고(옛 표는 표에 없는 145개를 5초씩 쳐 합 725초로 계획했지만 실제 합은 82초), 옛 표로 나눈 조각별 합계를 새 실측으로 다시 더하면 623·518·400·1,090·549·443·1,572·823·664·837·1,601·1,430초(가장 느린 조각이 이상의 1.82배)로 실제 쏠림과 같은 모양이었다.

1. 병합 가지나 main 푸시의 Qt 칸(열두 조각) 로그를 모은다. 작은 파일까지 시험 파일 전부의 초가 필요하거나 작업 중 가지에서 재고 싶으면 **진단 가지**(`NO-MERGE-diag-…`, 3차·4차 진단이 그렇게 했다)에서 같은 칸을 돌린다. 13절처럼 그 가지에서만 `if` 줄에 가지 이름을 임시로 더하고, `scripts/ci_shard.py` 의 `main()` 에서 시험을 돌린 직후 `result.module_seconds`(정식 칸의 `[걸린 시간]` 줄과 표가 쓰는 같은 값)를 GitHub 주석 한 줄로 찍는 코드 몇 줄을 더한다 — 표준 출력에 `::notice title=QTT-FINAL::` 다음 `이름=초 ; 이름=초 …` 꼴. 이 계측은 진단 가지에만 두고 정식 칸에는 넣지 않는다(정식 칸에는 기존 '걸린 시간' 표 출력 외에 새 쓰레드·주석을 더하지 않는다). 검사 로그는 로그인 없이 읽을 수 없지만 주석은 REST 로 읽을 수 있다. **같은 칸을 두 번 이상 돌려야 한다** — 한 번의 값으로 고른 표가 4차 진단에서 틀렸다. 진단 가지의 `ci.yml` 은 `test` 잡을 빼면 빨리 끝나지만(3차 둘째·4차가 그랬다) 그 가지에서 구조·문서 시험이 빨개지는 것은 의도다.
2. 정식 칸의 출력만 쓸 때는 조각마다 두 곳을 읽는다. ① 5초 넘게 걸린 시험 파일은 끝나는 즉시 `[걸린 시간] 파일 초` 한 줄이 찍힌다(칸이 시간 한도에 잘려도 남는다). ② 시험 단계 끝의 `시험 파일별 걸린 시간` 표(걸린 순 상위 15개와 이 조각 합계)에는 마지막 파일도 든다. 이 출력은 큰 파일만 보여 주므로 작은 파일의 값은 기본 무게가 맡는다. 이 출력 외에 새 쓰레드·주석은 더하지 않았다.
3. 조각마다 계획과 실제를 견준다. 시험 단계 첫머리의 `조각 N/12: … — 무게 표 qt: 이 조각 M초` 가 표 기준 계획이고(이 나무에서는 시험 파일 전부가 표에 들어 있어 913초 — 1초로 올려 친 값 때문에 측정 합계보다 조금 크다. 다른 갈래가 더한 새 시험 파일은 3초씩 더해진다), 표 머리의 `이 조각 합계` 가 실제다. 가장 느린 조각이 한도 60분의 70%(42분)를 넘거나 같은 조각이 거듭 느리면 표를 고친다.
4. 표를 갱신한다: **최근 두 번 이상의 실행**(진단 가지를 두 번 이상 돌려 얻는다)에서 시험 파일마다 걸린 초를 평균해 `max(1, round(평균))` 정수를 `QT_WEIGHTS` 에 옮긴다(무거운 순, 같으면 이름 순. 평균이 정확히 x.5 면 파이썬 `round` 처럼 짝수 쪽). 주석으로 뽑은 이름이 진짜 시험 파일과 다 맞는지 확인한다 — 이름 앞의 `test_` 를 떼어 찍는 계측이면 이름 가운데에 `test_` 가 든 파일이 잘못 복원될 수 있다(시험이 잡는다). 없어진 시험 파일의 이름은 반드시 지운다 — 시험이 지킨다. **병합 때 다른 갈래가 더한 새 Qt 시험 파일은 표에 넣어 다시 맞춘다**(병합 가지에서 총괄이 한다 — 진단 전에는 추정값으로 넣거나 기본 무게 3초로 두고 병합 뒤 첫 진단에서 맞춘다).
5. 같은 변경에서 `tests/test_ci_shard.py` 의 고정 값(`QT_MEASURED_TOP`·`(개수, 합계)`·세 큰 비 Qt 파일 값·기본 무게·계획 줄의 조각 초)과 이 절·`docs/DECISIONS.md` D-717·`scripts/ci_shard.py` 표 위 주석·`ci.yml` 의 `qt` 잡 주석의 숫자를 함께 고친다. 시험이 개수·합계·상위 일곱·세 큰 비 Qt 파일 값·기본 무게·계획 줄의 조각 초를 못박아 두어 이 값들을 슬쩍 바꾸면 빨개지고(합이 같은 두 값의 자리 바꿈처럼 이 값들에 닿지 않는 변경은 못 잡는다), `TableNumbersAreWrittenDownTest` 가 개수·합계·조각 계획·상위 일곱·기본 무게·시간 한도가 이 문서·D-717·`ci_shard.py` 주석·`ci.yml` 주석에 같게 적혀 있는지 본다 — 한 곳을 빠뜨리면 빨개지고 어느 곳에 무슨 숫자가 없는지 알려 준다. 조각 수나 시간 한도를 바꾸는 일은 11절·12절을 따른다.

**병합 때 조심할 것(다른 갈래가 시험 파일을 옮기거나 지우거나 더할 때).** 병합 가지는 여러 갈래를 한 나무로 합치므로 시험 파일이 바뀐 만큼 표를 맞춘다.
- **지우거나 이름을 바꾼 시험 파일**: 표에 든 이름이면 `QtWeightsTableTest` 의 `test_every_key_is_a_test_file_that_exists…` 가 빨개지고 낡은 이름을 모두 보여 준다. 지운 파일은 그 키를 `QT_WEIGHTS` 에서 지우고 같은 변경에서 `(개수, 합계)` 고정 값을 그만큼 낮춘다(지금 값은 `python -c "import sys; sys.path.insert(0, 'scripts'); import ci_shard; print(len(ci_shard.QT_WEIGHTS), sum(ci_shard.QT_WEIGHTS.values()))"` 로 읽는다). 이름만 바꾼 파일은 키 이름을 새 이름으로 바꿔 값을 그대로 옮긴다(안 그러면 새 이름이 기본 무게 3초로 쳐진다). 상위 일곱이나 세 큰 비 Qt 파일이 사라지거나 이름이 바뀌면 그 고정 값도 함께 고친다.
- **시험 파일 안의 시험만 새 파일로 옮긴 경우**(한 시험 파일의 시험들을 새 시험 파일들로 나눔): 이름이 사라지지 않아 시험이 빨개지지 않는다. 옛 파일의 표 값은 실제보다 커지고 새 파일은 기본 무게 3초로 쳐져 조각 하나가 수십 초 쏠릴 수 있다(조각 전체 약 880초에 견주면 몇 퍼센트 — 허용 범위). 다음 진단 뒤 표를 다시 맞춘다.
- **더한 시험 파일**: 표에 없어도 된다(3초로 친다). **큰 Qt 시험 파일**(예: 화면 갈래가 더하는 `test_ui_qt_posts_1b` — 추정 수백 초)은 3초로는 어림도 안 되어 그 조각이 길어지므로 병합 가지를 만들 때 추정값으로 표에 넣고 `(개수, 합계)`·상위 일곱 고정 값을 같이 고치거나, 병합 뒤 첫 실행의 계획 줄과 실제 합계를 견주어 다음 진단에서 맞춘다.

시험이 지키는 것(`tests/test_ci_shard.py`): 표의 모든 키가 진짜 시험 파일 이름이고(없어진 이름이 쌓이지 않는다) 값이 양의 정수. **표 자체 점검**: 표의 숫자로 나눈 가장 무거운 조각이 이상(전체 ÷ 조각 수)의 1.15배 이하·가장 무거운 파일들이 서로 다른 조각에 하나씩 들어감·모든 시험 파일이 정확히 한 조각에 들어가고 빈 조각이 없음 — 이 점검은 표의 숫자로만 계산하므로 **표가 실제 러너 시간과 어긋나도 초록이다**(3차 한 번 값의 표는 이 점검을 통과했지만 4차 진단의 실제 가장 느린 조각은 이상의 약 2배였다). 그래서 이 점검이 초록이어도 실제 조각이 고르다는 뜻은 아니고, 어긋남은 5절과 위 3단계의 계획 줄·실제 합계 견주기와 진단 실행이 가려낸다. 그 밖에 `CI_WEIGHTS` 의 다른 값은 종료 코드 2·표의 숫자(개수·합계·상위 일곱·세 큰 비 Qt 파일 값·기본 무게)는 고정 값·계획 줄의 조각 합계와 표 밖 파일의 기본 무게는 가짜 시험 폴더로 고정(재작업 2)·표의 숫자와 시간 한도가 문서·결정·주석에 같게 적혀 있음. 열두 칸의 기본 표·기본 무게·나누기 결과는 옛 코드에서 뽑은 고정 값으로 못박았다.

## 11. 승인된 모양을 글자 그대로 못박는 시험(결정 D-716)

`tests/workflow_golden.py`(결정 D-693)가 `ci.yml` 의 두 잡(`test`·`qt`)의 이름·순서·개수와 잡마다의 값을 글자 그대로 못박는다. `qt` 잡의 승인값은 2절 표의 값 그대로다 — 이름(`/12`)·`windows-latest`·작업 수준 `if` 한 줄(글자 그대로, 13절)·시간 한도 정확히 60분(`test` 잡은 D-693 의 범위 그대로이고 `tests/test_ci_workflow_qt.py` 가 정확히 40분으로 못박는다)·조각 열둘 하나뿐인 `strategy`·단계 넷과 환경 변수 정확히 여섯·같은 승인된 액션 쌍. 그래서 조각 수 바꾸기(목록과 총수와 두 이름의 `/12`)나 시간 한도·`if` 변경처럼 `ci.yml` 에서 이 잡을 고치면 **같은 변경에서** `tests/workflow_golden.py` 의 `CI_QT_JOB`·`CI_QT_STEPS` 와 `tests/test_workflow_golden.py` 의 승인값 시험(`TwoJobsAreBothPinnedTest`)도 함께 고친다. 안 고치면 시험이 빨개지고, 고치면 '무엇이 바뀌었는가' 가 글자로 남는다(`.github/` 변경은 어차피 T3). 작업을 더하거나 이름·순서를 바꾸는 것도 마찬가지다. `if` 줄은 값만이 아니라 줄 전체가 글자 그대로여야 한다 — 줄 끝 주석·뒤 공백도 골든·`test_ci_workflow_qt`·`test_ci_shard`·`test_repo_layout` 네 묶음이 모두 거절한다(재작업 2 에서 한 가지 잣대로 맞췄다).

**4차 진단 뒤(2026-11-26) — 화면 칸의 시간 한도를 40분에서 60분으로 올린다(운영자 확인 046 ① 승인, 이슈 #284).** 위 3차 진단 뒤의 계산(표 기준 가장 느린 조각 14.7분 → 설치까지 16.2분 = 한도의 41%, 나쁜 경우 53%)은 표 안의 숫자였다. 4차 진단(실행 45746502211)이 그 표로 실제 열두 조각을 돌린 결과는 7절 '왜 다시 맞췄나' 와 같다: 가장 느린 조각 1,875초(31.3분), 설치 1.5분을 더해 약 33분 = 한도 40분의 82%. 한도 40분은 조각 열둘에서 시간 초과 위험이 있었다 — 세 실행(2차·3차·4차 진단)에서 한 실행을 빼고 나머지 둘의 모듈별 평균으로 표를 만들어 뺀 실행의 값으로 평가한 가장 느린 조각의 최악이 N=12 에서 38.7분이라 설치 1.5분을 더하면 40.2분으로 한도 40분을 넘는다(2차 진단 값은 조각마다 상위 30개뿐이라 꼬리가 빠져 오히려 낮게 잡힌 값이다).

| 조각 수 N | 교차 평가의 최악(가장 느린 조각) | 설치 1.5분 더해 | 한도 40분 대비 | 한도 60분 대비 |
|---|---|---|---|---|
| **12** | 38.7분 | 40.2분 | 101% | **67%** |
| 13 | 33.3분 | 34.8분 | 87% | 58% |
| 14 | 33.8분 | 35.3분 | 88% | 59% |
| 16 | 23.8분 | 25.3분 | 63% | 42% |

고른 길: **조각 수는 12 그대로, 시간 한도만 60분.** 이유: ① 조각을 13–14 로 늘려도 최악이 5분쯤 줄 뿐이고 표만으로는 흔들림이 사라지지 않는다(눈덩이 효과 — 7절) ② 조각을 늘리면 승인된 모양(목록·총수·두 이름의 `/12`·골든 표)을 바꿔야 하고 줄 서는 조각이 늘어(위 줄 서기 계산: 14 부터는 윈도 시험 칸이 비우기를 기다린다) 끝까지가 늦어질 수 있다 ③ 한도 인상은 `ci.yml` 의 `qt` 잡 `timeout-minutes` 한 칸이라 가장 작은 변경이다(`test` 잡은 글자 그대로 40분). 남는 여유: 교차 평가의 최악 38.7분 + 설치 1.5분 = 40.2분 → 한도 60분의 약 67%, 4차 진단에서 잰 가장 느린 조각 31.3분 + 1.5분 = 32.8분 → 약 55%. 한도에 닿으면(60분에서 설치를 뺀 약 58분 안에 시험이 안 끝나면) 그 칸은 빨강이 되고 병합 가지 검사도 빨강이라 병합이 막힌다(한 커밋이라 빨간 칸만 다시 돌릴 수 없다, 4절). 자동 PR 기다림(60분)과의 관계는 14절이다.

## 13. 돌 때 조건과 진단 가지에서 바꿀 한 줄(결정 D-718, 운영자 확인 042 ① 승인 — 이슈 #277)

`ci.yml` 의 `qt` 잡에 작업 수준 `if` 한 줄이 있다: `github.ref` 가 `refs/heads/main` 이거나 `refs/heads/ai/claude/M` 로 시작하면 돈다(`startsWith`). 그러므로 병합 가지(`ai/claude/M번호-이름`)와 main 푸시에서 돌고, 작업 중 가지(`ai/claude/NO-MERGE-…`·`desktop/…` 등)와 태그에서는 건너뛴다. 수동 실행(`workflow_dispatch`)은 main 을 골라 돌릴 때 이 조건을 만족해 이 칸도 돈다(다른 가지를 고르면 건너뛴다). `test` 잡(열두 칸)은 `if` 가 없어 모든 가지에서 돈다. 이 한 줄은 줄 끝 주석·뒤 공백 없이 줄 전체가 글자 그대로여야 한다(독립 검증 Q 권고-5 — 네 시험 묶음이 같은 잣대를 쓴다).

- **왜 작업 중 가지에서는 안 도나.** 이 칸은 러너 약 3.3시간(표 합계 10,956초 = 3.0시간에 조각마다 설치 1.5분씩을 더한 값)을 쓰고 동시 작업 20개 한도의 자리를 차지해 다른 검사를 늦춘다. 작업 중 가지는 푸시마다 열두 칸이 돌면 충분하고, 화면 시험은 병합 가지가 만들어질 때 한 번 도는 것으로 병합 문턱 구실을 한다. 병합 가지 검사 시간은 약 19분에서 약 30분대 이상으로 는다(운영자 확인 042 ① 이 받아들였다 — 4차 진단에서 가장 느린 화면 조각이 설치까지 약 33분).
- **건너뛴 잡은 초록 취급이다.** GitHub 는 `if` 가 거짓이라 건너뛴 잡을 실패로 치지 않고, 그 실행의 결론은 나머지 잡이 정한다. `auto-pr.yml` 은 병합 가지(`ai/claude/M번호-…`)에서만 시작하고 그 커밋의 `ci.yml` 실행이 `completed:success` 인지만 본다 — 병합 가지에서는 `qt` 도 돌므로 `test` 와 `qt` 모두가 문턱이다. 작업 중 가지에서는 `auto-pr.yml` 이 시작하지 않고 검사는 `test` 칸만으로 끝난다. `scripts/release_check.py` 는 CI 실행 결과를 읽지 않는다.
- **시험이 이 줄을 글자 그대로 못박는다**: `tests/workflow_golden.py` 의 `QT_IF`(골든 표)·`tests/test_ci_workflow_qt.py`·`tests/test_ci_shard.py`·`tests/test_repo_layout.py`. 없애거나 `true`·`always()`·다른 가지 패턴·진단 가지 이름으로 바꾼 사본, `test` 잡이나 단계에 `if` 를 끼운 사본, `if` 를 두 번 쓴 사본, **줄 끝에 주석이나 공백을 단 사본**을 모두 거절한다(옛날에는 골든과 `test_ci_workflow_qt` 가 줄 끝 주석을 값이 아니라며 통과시켰지만 이 줄은 Qt 칸이 도는 가지를 정하므로 가장 엄격한 쪽으로 맞췄다). 파일 전체에서 `if:` 는 이 한 줄뿐이다(옛 '`if:` 는 어디에도 없다' 를 '정해진 한 줄만' 으로 좁힌 것이지 푼 것이 아니다).
- **가지 이름 비교는 대소문자를 가리지 않는다.** GitHub 식의 문자열 비교(`==`·`startsWith`)는 대소문자를 가리지 않는다(GitHub 문서 기준) — 그래서 소문자 `ai/claude/m…` 가지(와 `MAIN` 같은 표기)도 이 칸이 돈다. 병합 가지의 이름 규칙(대문자 `M` + 번호)은 이 식이 아니라 사람과 `auto-pr.yml` 의 규칙이 정하므로 규칙을 어긴 소문자 가지가 생기면 화면 칸이 도는 것까지는 막지 못한다. 지금 가지 중 영향받는 것은 0 이고 권한·비밀에 닿지 않는다(러너 줄 서기만 늘 수 있다). 시험의 평가기(`test_ci_workflow_qt.runs_on`·`test_workflow_golden.runs_on`)도 대소문자를 가리지 않고 소문자 사례를 참으로 못박는다(독립 검증 S 권고-3, D-718 ⑥).
- **진단 가지에서 바꿀 줄(이 한 줄뿐이어야 한다).** 병합 금지 가지에서 새 모양의 조각 시간을 재려면 그 가지의 `.github/workflows/ci.yml` 에서 아래 한 줄을, 같은 줄에 `|| github.ref == 'refs/heads/ai/claude/NO-MERGE-진단가지이름'` 만 덧붙인 것으로 바꾼다.

  `    if: github.ref == 'refs/heads/main' || startsWith(github.ref, 'refs/heads/ai/claude/M')`

  그 가지에서는 위 시험들이 빨개지는 것이 맞다(그 한 줄이 승인값과 다르므로). 병합 가지에는 이 변경을 섞지 않는다 — 섞이면 같은 시험이 막는다.

## 14. 자동 PR 의 기다림 숫자(결정 D-719 — 승인된 T3 의 '숫자만')

(D-719 당시의 계산이다 — 그때 화면 칸의 시간 한도는 40분이었다. 지금은 아래 '화면 칸 한도를 60분으로 올린 뒤'.) 병합 가지에 Qt 칸 열두 조각이 더해지면 동시 작업 한도 때문에 일부 조각이 줄을 서서 늦게 시작한다(12절). `auto-pr.yml` 이 검사가 끝나기를 기다리는 시간이 작업 시간 한도(40분)와 같은 40분이면 늦게 시작한 조각이 끝나기 전에 PR 을 만들지 않고 끝낼 수 있다(모의: 다른 가지가 한 건 겹치면 54%). 그래서 숫자 둘만 올렸다 — 기다림 최대 40분 → 60분(`AUTOPR_MAX_WAIT_SECONDS` 2400 → 3600 과 기본값 둘, 경고 문구의 분), 그 작업의 시간 한도 45분 → 65분(기다림 + 마지막 걸음 몫 5분). 60분은 작업 시간 한도 40분에 줄 서는 시간 20분을 더한 값이다. 이 값에서는 다른 가지가 두 건 겹쳐도(중앙 46분) 모의 실험에서 60분을 넘긴 일이 없었다(이 절의 모의 숫자는 2차 진단 표 기준의 옛 값이다 — 3차 진단 뒤 조각이 짧아져(7절·12절 끝) 여유가 더 크지만 자동 PR 숫자 3600초·65분은 그대로 둔다).

**화면 칸 한도를 60분으로 올린 뒤(재작업 2, 운영자 확인 046 ① — 이슈 #284).** D-719 때 60분은 '작업 시간 한도 40분에 줄 서는 시간 20분을 더한 값' 이었다. 화면 칸 한도가 60분이 되자 대기 60분은 한도와 **같아졌다**(줄 서기 여유 20분은 한도 인상이 가져갔다). `auto-pr.yml` 의 숫자(기다림 3600초·작업 65분)는 그대로 두었고(이 재작업의 범위가 아니다), 그 위에서 화면 칸이 한도까지 가도 자동 PR 의 기다림 안에 끝나는지 계산하면 이렇다. 끝까지 시간 = 줄 서기(0–20분) + 설치 1.5분 + 시험 단계이고, 자동 PR 의 대기는 푸시와 거의 같은 때부터 60분이다.

| 상황 | 줄 서기 | 설치 | 시험 단계 | 끝까지 | 대기 60분 안인가 |
|---|---|---|---|---|---|
| 4차 진단에서 가장 느린 조각 | 0–20분 | 1.5분 | 31.3분 | 32.8–52.8분 | 예 |
| 교차 평가의 최악(N=12) | 0–20분 | 1.5분 | 38.7분 | 40.2–60.2분 | 줄 서기가 20분이면 경계(넘길 수 있다) |
| 한도에 닿은 칸 | 0 이상 | 1.5분 | 약 58.5분에서 잘림 | 60분 한도에서 칸이 빨강 | 해당 없음 — 칸이 빨강이라 PR 이 어차피 필요 없다 |

해석: 시험 단계가 약 38분(60분 − 설치 1.5분 − 줄 서기 20분) 안이면 줄 서기가 최대여도 대기 60분 안에 끝난다. 38분에서 58분 사이에 끝나는 칸(관측된 적 없다 — 4차 진단 31분, 최악 평가 39분)은 줄을 오래 섰을 때만 대기를 넘길 수 있고, 그러면 자동 PR 은 PR 을 만들지 않고 경고와 함께 성공으로 끝난다(노란 배너로 만든다 — 실패 아님). 한도 60분에 닿아 잘리는 칸은 칸이 빨강이라 검사가 빨강이고 PR 이 필요 없다. 그러니 한도 인상으로 생기는 것은 '기다림이 모자라 PR 이 안 만들어지는 경우가 드물게 있을 수 있다' 는 것뿐이고 병합이 잘못 열리는 일은 없다.

이 변경은 `auto-pr.yml` 의 숫자(와 그 숫자를 설명하는 머리 주석 한 문단)뿐이고 단계·권한·`gh` 호출·가지 필터·비밀은 그대로다(`tests/test_auto_pr_workflow.py` 가 줄마다 고정한다). 시험은 숫자를 새 값으로 고쳤다 — `tests/test_ci_workflow_qt.py` 는 옛 '대기 = 작업 한도' 를 '대기 = 작업 한도 + 줄 서는 20분, 자동 PR 작업 한도 = 대기 + 5분' 으로(더 엄격하게) 못박는다. 옛 서술 '최대 40분'(D-175·D-176·D-716 과 `auto-pr.yml` 머리 주석의 옛 판)은 이 절이 대체한다. 이 절의 숫자 변경만 따로 빼도 앞의 절은 성립한다(그때는 기다림이 짧아 겹침이 있으면 PR 을 노란 배너로 만든다). **재작업 2 는 `auto-pr.yml` 을 한 줄도 바꾸지 않았다.** `tests/test_ci_workflow_qt.py` 의 `test_the_job_time_limit_is_exactly_the_max_wait_of_the_auto_pr_workflow` 는 이제 '대기 3600초 = 화면 칸 한도 60분, 열두 칸(`test`) 한도 40분, 자동 PR 작업 한도 = 대기 + 5분' 을 글자 그대로 못박는다(옛 '대기 = 한도 + 줄 서는 20분' 대신 — 같은 엄격함). `auto-pr.yml` 머리 주석 19째 줄('`ci.yml` 은 한 칸이 최대 40분 … 줄 서는 20분 … 합쳐 60분')은 화면 칸 한도가 60분이 된 지금 낡았다 — 숫자를 안 바꾸는 범위라 고치지 않았고 병합 때 총괄이 주석 한 줄을 고칠지 정한다(`tests/test_auto_pr_workflow.py` 는 그 주석에서 '최대 60분' 낱말만 본다).

# 글자 읽기 추가 도구 — 만들기·받기·점검 (운영자·개발자용)

**개인 PC 제한 시험용, 미서명 추가 도구 — 공개 배포용이 아닙니다**

사진 속 글자를 **이 PC 안에서만** 읽는 선택 기능의 작업자 프로그램(`ocr_worker.exe`)을 앱 본체와 **따로** 압축 파일 하나로 만드는 방법과 점검을 적는다(운영자 확인 026 ②·028 ②, 결정 D-527 에서 D-533). 본체 Package([`PACKAGE.md`](PACKAGE.md))는 그대로이고 이 도구가 들어가지 않는다 — 글자 읽기를 안 쓰는 사람은 아무것도 더 받지 않는다. 앱은 소스 상수 `LOCAL_OCR`(기본 꺼짐)이 꺼져 있는 동안 이 도구가 있어도 작업자를 띄우지 않는다. 빌드 흐름 파일(`.github/workflows/package-ocr.yml`)은 `.github` 변경이라 T3 였고, **병합은 운영자만** 한다 — 운영자가 병합해(M101, 2026-11-22) 이 흐름은 main 에 있고 Actions 목록에 `Package OCR` 로 보인다. 이 문서는 그 흐름을 **준비한 사실**과 쓰는 법이며, 흐름이 GitHub 러너에서 실제로 도는지는 아직 아무도 보지 못했다(10절).

## 1. 무엇이고 무엇이 아닌가

- **선택 기능의 별도 설치물**이다: 압축을 풀어 본체 옆 `ocr` 폴더에 두면 앱이 알아본다(PATH 검색·사용자가 정한 경로·환경 변수로 위치를 바꾸는 길은 없다). 지우려면 `ocr` 폴더만 지운다(§3의 8).
- **네트워크 0**이 목표다: 작업자는 첫 줄에서 소켓 가드를 켜고(안 켜지면 시작하지 않는다), 묶음에는 OpenSSL·진짜 `requests`·`urllib3`·`certifi`·영상용 FFmpeg DLL·인증서 파일이 없다(빌드 점검 §4). 증거의 한계는 `SECURITY.md` 의 글자 읽기 절에 있다.
- 비밀·토큰·서명이 없다. 서명하지 않은 새 실행 파일이라 스마트 앱 컨트롤·백신이 막을 수 있다(§3의 7).
- 모델 2개와 글자 사전은 **앱 소스에 박은 해시**와 같을 때만 쓴다(앱이 띄우기 전에 확인). 모델은 이 저장소에 싣지 않고 빌드가 받는다(§4).

## 2. 산출물

올라가는 것은 **세 개뿐**이다(보존 14일, 이름 `ChanceBlogDesktop-OCR-preview`):

| 파일 | 뜻 |
|---|---|
| `ChanceBlogDesktop-OCR-<버전>-win64.zip` | 추가 도구 본체. 안에 맨 위 폴더 `ocr` 하나(`ocr_worker.exe`·`_internal`·`models`·`data`·`licenses`·`THIRD_PARTY_NOTICES.txt`·`OCR_INFO.json`). 시각·순서·압축 수준을 고정한 결정적 zip |
| `SHA256SUMS` | 위 압축 파일의 SHA-256 한 줄(`sha256sum -c` 모양, 두 칸 띄움) |
| `PACKAGE_INFO.json` | 압축 파일 안 `OCR_INFO.json`(패키지 21개의 판·해시·업로드일, 파일 목록과 해시, 점검 결과, 커밋)에 압축 파일 이름·해시·크기를 더한 사본 |

정보 파일을 `OCR_INFO.json` 이름 그대로 올리지 않은 까닭: 본체의 산출물 허용 목록(`tests/test_workflow_artifacts.py` 의 허용 모양 — 지금은 여섯 — 과 결정 D-344)에 `PACKAGE_INFO.json` 은 있고 `OCR_INFO.json` 은 없다 — 안전 목록을 넓히지 않으려고 허용된 이름으로 올린다(D-527). 압축 파일 안의 `OCR_INFO.json` 은 앱이 읽는 정보 파일이다(앱이 요구하는 이름·약속 번호·파일 목록 모양을 시험이 앱의 확인 함수로 직접 읽어 본다).

크기(이 PC 시제품 실측, 합친 빌드 — 라이선스 고지 만들기를 합친 뒤의 스크립트, 2026-11-23, 가상환경·같은 핀): 풀린 크기 약 207MB(정보 파일 `OCR_INFO.json` 을 뺀 파일 144개 — `licenses/` 37개 파일과 `THIRD_PARTY_NOTICES.txt` 포함, 압축 파일의 항목은 정보 파일까지 145개), 압축 파일 약 85MB — 본체 Package(43.2MB)의 약 2배다. 정확한 값은 만들 때마다 조금씩 다르다(부품·커밋이 바뀌면 달라진다). 합치기 전(a 단계 시제품·D 갈래 단독 빌드)의 값은 풀린 크기 205.7MB(파일 106개)·압축 파일 84.6MB 였다 — 합치면서 라이선스 고지 파일 38개(고지문 1개 + `licenses/` 37개)가 더해졌다. 러너에서 만든 값은 첫 실행 뒤에 이 줄을 고친다.

## 3. 운영자가 수동으로 만들고 쓰는 방법 (1–2 단계는 휴대폰의 PC 버전 GitHub 에서도 됩니다 · 3–7 단계는 개인 PC 에서)

화면 글자는 GitHub 가 바꿀 수 있으니 같은 뜻의 단추를 고르세요. **이 흐름은 이미 병합되어 main 에 있습니다**(운영자 병합 M101, 2026-11-22 — 병합은 운영자 몫이고 AI 는 하지 않습니다). Actions 탭 왼쪽 목록에 `Package OCR` 로 시작하는 항목이 보입니다 — 보이지 않으면 알려 주세요. **어디서 하나**: 1–2 단계는 휴대폰에서도 할 수 있습니다. 3–7 단계(내려받은 파일 풀기·PowerShell·명령 프롬프트)는 **개인 PC(윈도)에서** 합니다. **병합 순서**(지나간 일): 이 흐름은 B1 갈래(라이선스 고지 파일을 만드는 코드가 든 앞선 변경)의 최종 위에 얹어 합쳤고 둘 다 병합되었습니다(10절). 산출물 점검이 요구하는 라이선스 고지 파일(`licenses/`·`THIRD_PARTY_NOTICES.txt`)은 빌드 스크립트의 `notices` 단계가 점검 앞에서 만듭니다(8절).

1. 이 저장소의 `Actions` 탭 → 왼쪽 목록에서 `Package OCR — 글자 읽기 추가 도구 빌드(수동, 개인 PC 제한 시험용)` 를 엽니다 → 오른쪽 `Run workflow` → 초록색 `Run workflow` 를 **한 번** 누릅니다(`Branch: main` 그대로, 입력 칸은 없습니다). 목록에 비슷한 이름이 둘 있습니다 — `Package OCR — …` 가 이 도구이고, 그냥 `Package — …` 는 앱 본체입니다. `Package OCR` 쪽을 고르세요.
2. 끝날 때까지 기다립니다. **걸리는 시간은 아직 모르지만 보통 10–20분을 예상합니다**(AI 추정이며 측정이 아닙니다 — 합치기 전 D 갈래 빌드(CPU 가 바쁜 PC)의 만들기 단계는 147–199초였고, 합친 뒤 이 PC 실측(2026-11-23)은 전체 약 1분(59–71초)이었습니다. 러너에서는 거기에 설치·받기·올리기가 더해집니다. 첫 실행 뒤에 이 줄을 실제 값으로 고칩니다). 45분이 지나도 끝나지 않으면 GitHub 가 알아서 멈춥니다(빨간 X). 초록으로 끝났어도 첫 실행은 첫 관측이니, 실행 화면의 단계별 걸린 시간(단계 이름 옆의 시간)과 `추가 도구 만들기` 단계 로그의 `[build` 로 시작하는 줄(버전·점검 통과·자가 점검 시간·끝 시간)을 복사해 알려 주시면 이 문서에 적습니다.
3. **여기부터(3–7 단계)는 개인 PC 에서 합니다.** **초록 체크** 실행을 열어 맨 아래 `Artifacts` 아래 `ChanceBlogDesktop-OCR-preview` 를 내려받습니다.
4. **압축 속 압축을 조심하세요.** 받은 `ChanceBlogDesktop-OCR-preview.zip` 은 GitHub 가 묶은 겉 꾸러미입니다. `모두 압축 풀기` 로 **한 번만** 풀면 `ChanceBlogDesktop-OCR-<버전>-win64.zip`·`SHA256SUMS`·`PACKAGE_INFO.json` 이 나옵니다. 안쪽 `win64.zip` 은 아래 5 에서 해시를 확인하기 전에는 풀지 않습니다.
5. **해시 확인**: 압축 파일이 있는 폴더의 탐색기 주소 표시줄에 `powershell` 을 쓰고 Enter(관리자 권한 아님) → `Get-FileHash .\ChanceBlogDesktop-OCR-<버전>-win64.zip -Algorithm SHA256`(이름을 다 치지 말고 `Get-FileHash .\ChanceBlogDesktop-OCR-` 까지 쓴 뒤 Tab 키를 누르면 파일 이름이 완성됩니다 — 지금 이름은 `ChanceBlogDesktop-OCR-0.1.0-preview.1-win64.zip` 입니다) → `SHA256SUMS` 첫 줄 앞 64글자와 `Hash` 칸이 한 글자도 다르지 않으면 통과(대소문자 차이는 같은 값). 다르면 풀지 말고 알려 주세요.
6. **본체 옆 `ocr` 폴더에 풀기**: 본체 압축을 푼 폴더(`ChanceBlogDesktop.exe` 가 있는 폴더) 안에 안쪽 압축 파일의 `ocr` 폴더가 오게 풉니다 — 풀 위치를 그 폴더로 고르면 됩니다. **함정**: `모두 압축 풀기` 창의 대상 칸 끝에는 `ChanceBlogDesktop-OCR-…-win64` 같은 폴더 이름이 미리 적혀 있습니다. 그대로 누르면 `ocr` 폴더가 한 겹 더 깊이 풀려 앱이 찾지 못합니다 — 그 폴더 이름을 지우고 `ChanceBlogDesktop.exe` 가 있는 폴더 경로만 남기세요. `ocr` 폴더는 짧은 경로(예: 본체 폴더 바로 아래)에 두세요 — 경로가 길거나 한글이 섞였을 때 압축 풀기·작업자 실행을 시험한 기록이 아직 없습니다. 끝나면 `ChanceBlogDesktop.exe` 옆에 `ocr` 폴더가 있고 그 안에 `ocr_worker.exe`·`OCR_INFO.json` 이 보입니다. 앱은 이 폴더의 파일을 하나하나 정보 파일의 해시와 견주고, 모르는 파일이 하나라도 섞여 있으면 쓰지 않습니다. **지금 main 의 앱은 글자 읽기 스위치(`LOCAL_OCR`)가 꺼져 있어 `ocr` 폴더를 두어도 앱 화면에는 아무 변화가 없습니다. 그것이 정상이고, 이 도구만 따로 확인하는 것은 5·7 단계입니다.**
7. **스마트 앱 컨트롤·백신 확인(시험지 한 줄)**: 받은 압축 파일을 푼 `ocr` 폴더에서 명령 프롬프트를 열어 `ocr_worker.exe --selftest` 를 실행하고 **마지막 줄(한 줄로 이어진 긴 글) 안에 `"ok": true` 가 있고 줄이 `"ok": true}` 로 끝나면 통과**입니다(닫는 중괄호가 붙는 것이 맞습니다. `"ok": false` 가 있거나 오류 글이 나오면 실패). 막히거나 경고가 뜨면 화면에 뜬 문구 한 줄만 알려 주세요(사진·글은 필요 없습니다 — 이 실행은 네트워크 없이 합성 글자 그림 한 장만 읽습니다). SmartScreen 경고에서 `실행` 을 누를지는 운영자가 정합니다(이 도구는 서명·보안 설정을 건드리지 않습니다). **이어서 같은 `ocr` 폴더 안에 `licenses` 폴더와 `THIRD_PARTY_NOTICES.txt` 파일이 있는지 눈으로 확인합니다**(운영자 확인 030 ② — 라이선스 고지 파일입니다. 없거나 비어 있으면 알려 주세요).
8. **끄는 방법**: `ocr` 폴더를 지웁니다. 데이터 폴더·사진·초안은 건드리지 않습니다.
- **빨간 X 로 끝난 실행이면**: 시작하지 말고 빨간 X 가 붙은 단계를 펼쳐 맨 아래의 `빌드를 멈췄다` 로 시작하는 줄과 `[모델]` 로 시작하는 줄, 그리고 `★` 가 들어 있는 줄(`★` 줄은 `[build 시각]` 뒤에 붙으므로 줄 맨 앞이 아닙니다)을 그대로 복사해 알려 주세요(키·비밀은 그 줄에 들어 있지 않습니다). 설치·`pip check` 단계가 빨갛게 끝났을 때는 이 낱말들이 없으니 단계 이름만 알려 주셔도 됩니다.
- **보관 기간**: 올려 둔 파일은 14일만 보관됩니다. 지나면 새로 만듭니다.

## 4. 빌드가 하는 일과 점검(`ocr_addon/`)

| 파일 | 하는 일 |
|---|---|
| `build_ocr_addon.py` | 동결(PyInstaller 한 폴더) → 모델·사전 얹기(잠금 크기·해시 대조) → 쓰지 않는 기본 모델 3개·FFmpeg DLL·인증서 파일 빼기 → 라이선스 전문·고지문 만들기(`notices`, 점검 앞 — 고지문에는 모델 2개·글자 사전의 이름·출처·라이선스 표기 절이 든다) → 점검 → 정보 파일 → 결정적 zip·`SHA256SUMS`·`PACKAGE_INFO.json`. 점검을 끄는 옵션은 없다 |

| `verify_release.py` | 올리기 전 **산출물 점검** — 압축 파일·`SHA256SUMS`·`PACKAGE_INFO.json` 을 빌드 스크립트의 말이 아니라 파일 자체에서 다시 읽어 해시·크기·파일 목록과 모델 잠금 값, 그리고 라이선스 고지 파일이 압축 파일 안에 있는지 확인한다 |

| `requirements-ocr.meta.json` | 21개 핀의 PyPI 업로드 날짜(a 단계가 대조한 값) — 14일 규칙의 근거 |
| `data/` | 글자 사전 11,945줄(47,451바이트)과 정보 파일 — 줄바꿈 변환을 하지 않는다(`.gitattributes`) |

**흐름의 단계**(`package-ocr.yml`, 단계마다 명령 하나): 가상환경 만들기 → 잠금 파일 `--require-hashes --only-binary=:all:` 로 설치(패키지 21개, 이어서 빌드 도구 7개) → `pip check` → 모델 받기 → 빌드(`all --require-clean`) → **산출물 점검(`verify_release.py`)** → SHA-256 보기 → 올리기. 밖으로 나가는 곳은 둘: 파이썬 패키지 저장소(PyPI)와 모델을 받는 Hugging Face(커밋 고정 주소·크기·SHA-256 대조, 허용 호스트는 `huggingface.co`·`hf.co` 와 그 하위뿐 — 리디렉션도 같은 규칙).

**점검 규칙**(하나라도 걸리면 빌드가 실패하고 정보 파일·zip 을 만들지 않는다):

- **R1 가져오기 표**: 묶음의 모든 exe·DLL·pyd 의 가져오기 표(정적·지연·묶음)에 네트워크 DLL(WS2_32·WinINet·WinHTTP·mswsock·iphlpapi·dnsapi 등 19개)이 있는 파일은 `_internal` 의 `python312.dll`·`_socket.pyd`·`select.pyd` 셋뿐(CPython 표준 구성요소 — 총괄 결정). 위치와 이름이 정확히 맞아야 하고, 이 셋도 `ws2_32`·`iphlpapi` 밖의 네트워크 DLL 은 못 가져온다. 점검 대상에 `ocr_worker.exe`·`python312.dll` 이 없으면(점검이 묶음을 못 훑은 것) 실패한다.
- **R2 묶음 파일**: `opencv_videoio_ffmpeg*.dll`·`*.pem`·`*.crt`·`*.key`·기본 모델(`*.onnx` 중 우리 모델 2개 밖)이 없고, 모델 2개와 사전의 크기·SHA-256 이 잠금 값과 같다.
- **R3 부품**: `ssl`·`_ssl`·`_hashlib`·`libcrypto`·`libssl`·`_overlapped`·`_multiprocessing`·`urllib3`·`certifi` 가 없고, `requests` 는 가짜 껍데기(`0+offline-stub`)이며, 동결본이 `ssl`·`urllib3`·`certifi`·`asyncio`·`multiprocessing` 을 실제로 가져오지 못한다고 스스로 적는다(`--selftest` 의 시도 기록).
- **R4 자가 점검**: 동결본 `--selftest` 가 소켓 가드 음성 대조 5/5 차단·정상 읽기 소켓 시도 0·점검 그림이 같은 글로 읽힘·모델·사전 해시 일치를 모두 보이고, 실행하는 동안 묶음 폴더에도 임시 폴더에도 파일을 쓰지 않는다(전후를 견준다).
- 그 밖에: 묶음 안 글 파일의 키 모양 훑기, 본체의 비밀·사용자 데이터 파일 이름 목록, **DLL 출처 허용 뿌리**(가상환경·기본 파이썬·Windows 폴더 밖의 DLL 이 묶음에 들어오면 거절 — 러너 PATH 의 자바 DLL 사건, D-468), 설치된 판이 잠금 파일과 같은지, PyPI 업로드가 14일 이상인지 — **둘 다 런타임 핀 21개만 기계로 점검한다.** 빌드 도구 7개는 `--require-hashes` 로 내용만 고정되고(정보 파일에 설치된 판이 적힌다) 판 일치·14일 규칙은 기계로 점검하지 않는다. 실제 업로드 나이는 런타임 핀과 겹치는 `packaging` 을 뺀 여섯 모두 a 단계 PyPI 대조 기록(2026-11-17 기준)에서 48일 이상이었다: pyinstaller-hooks-contrib 48·pyinstaller 66·setuptools 101·altgraph 361·pefile 813·pywin32-ctypes 825.
- **산출물 점검**(올리기 직전의 별도 단계 `verify_release.py`, 어긋나면 흐름이 빨갛게 끝나 아무것도 올리지 않는다): 올리는 폴더에 정해진 셋뿐인지 · 압축 파일의 해시·크기가 `SHA256SUMS`·`PACKAGE_INFO.json` 과 같은지 · 압축 파일의 항목이 모두 맨 위 폴더 `ocr` 아래의 안전한 이름이고 안의 `OCR_INFO.json` 의 파일 목록과 한 줄씩(이름·크기·해시) 같은지 · 모델 2개·사전이 잠금 값과 같은지 · **라이선스 고지 파일(`licenses/` 에 파일이 있고 — 그중 GEOS 라이선스 전문 `licenses/shapely/LICENSE_GEOS` 가 꼭 있고 — `THIRD_PARTY_NOTICES.txt` 가 비어 있지 않으며 GEOS·LGPL 을 말하고, GEOS 가 `_internal` 아래 별도 DLL 파일로 있다)이 압축 파일 안에 있는지**. **'없어야 할 것'도 압축 파일 쪽에서 다시 판정한다**(독립 검증 S 의 SP-1): FFmpeg DLL·pem·crt·key·기본 모델·알 수 없는 모델(R2 규칙 함수 그대로)과 OpenSSL·`_hashlib`·`_overlapped`·`_multiprocessing`·진짜 `urllib3`·`certifi`(R3 이름 규칙 — 맨 위·`_internal` 직속 이름과 모든 `.pyd`·`.dll` 이름)가 압축 파일 안에 있으면 빌드가 먼저 막았어야 해도 여기서 한 번 더 실패하고, 정보 파일에 적힌 빌드 점검 기록(`checks.ok`·문제 목록 비어 있음·자가 점검 통과·종료 코드 0)이 통과가 아니어도 실패하고, 압축 파일 안 정보 파일이 JSON 객체가 아니어도(`[]`·`null`·글) 실패한다(그렇지 않으면 정보 파일 검사 전체가 조용히 건너뛰어진다 — 독립 검증 S 의 SP-7). 빌드가 점검에 실패하고도 산출물을 만들거나 점검이 건너뛰어지는 길이 합치는 과정에서 다시 열려도 금지 부품이 든 압축 파일은 올라가지 못한다 — 빌드 쪽 문(점검 실패면 종료 코드 1·정보 파일·zip 없음)과 이 문은 서로 독립이다. 고지 파일을 묶음 폴더에 만드는 코드(`notices` 단계)와 이 점검은 짝이다 — 빌드는 그 파일이 없으면 점검(`check`)에서 이미 멈추고(`R2 라이선스 고지 산출물이 없다`), 그 방어선이 없었던 산출물도 이 점검이 한 번 더 거른다.

**본체 빌드에서 가져다 쓰는 것**(읽기 전용, 본체 코드는 고치지 않는다): 출력 폴더 안전 점검(`safe_out_dir`)·PyInstaller 환경(`pyinstaller_env` — 좁힌 PATH `narrow-v1`·해시 씨앗 0·고정 시각)·DLL 출처 점검(`check_binary_origins`)·금지 파일 이름 목록. 본체에서 이름이 바뀌면 `tests/test_ocr_addon_build_flow.py` 가 알린다.

## 5. 재현 빌드와 해시

- 시각은 환경 변수 `SOURCE_DATE_EPOCH`(없으면 이 저장소 HEAD 의 커밋 시각)이고, 정보 파일에는 빌드한 PC 의 시계가 들어가지 않는다(커밋·커밋 시각·핀 나이만). 같은 커밋·같은 잠금 파일·같은 파이썬이고 DLL 이 같은 곳에서 오면 같은 압축 파일이 나오도록 만들었다.
- (합치기 전 — 라이선스 고지 만들기를 합치기 전의 D 갈래 단독 빌드) 이 PC(Windows 11, 파이썬 3.12.0)에서 같은 입력(같은 커밋·같은 `SOURCE_DATE_EPOCH`)으로 두 번 빌드한 결과는 **압축 파일·`SHA256SUMS`·`PACKAGE_INFO.json`·묶음 파일 107개가 바이트까지 같았다**(압축 파일 SHA-256 `eed3750c…`). **다른 가상환경(다른 위치·다른 PC·러너)에서 설치해 만들면 같지 않을 수 있다**: `numpy`·`tqdm` 의 pip 설치 기록(`RECORD`)에 pip 가 만든 실행 래퍼의 해시가 들어 있어 가상환경 위치마다 다르고, 러너의 파이썬 3.12.x 패치 판이 다르면 `python312.dll`·VC++ 런타임이 달라 해시도 다르다 — 그때는 해시를 견주지 말고 점검 규칙과 `--selftest` 로 판정한다.
- (합치기 전 기준) a 단계 시제품(압축 파일 SHA-256 `197deea1…`)과 그때의 압축 파일은 바이트가 다르다: 맨 위 폴더 이름(`ocr_addon` → 앱이 찾는 `ocr`)과 정보 파일이 바뀌었기 때문이다. 묶음 안 파일 107개를 견주면 **101개는 한 바이트도 다르지 않고**, 다른 여섯의 이유는 이렇다 — 정보 파일(시계 칸 대신 커밋 칸 등) · `ocr_worker.exe`(안의 파이썬 모듈 602개 중 `protocol` 하나만 다르다 — 앞선 단계에서 물결표 글자 둘을 줄표(en dash)로 바꾼 고침이고, 빌드한 폴더 경로가 달라도 나머지 모듈의 바이트는 같았다) · `vcruntime140.dll`·`vcruntime140_1.dll`(PATH 를 좁혀 PyInstaller 가 파이썬 폴더의 것을 먼저 찾는다 — a 단계는 System32 것이었고 둘 다 허용 뿌리 안이다) · `numpy`·`tqdm` 의 `RECORD` 둘(위).
- **합친 빌드**(라이선스 고지 만들기 `notices` 단계를 합친 뒤의 스크립트)를 이 PC 에서 같은 가상환경으로 다시 재어 보았다(2026-11-23): 병합된 main 의 코드 그대로 한 번(기준선), 고지문에 모델·글자 사전 절을 더한 코드로 같은 커밋을 위치가 다른 출력 폴더 둘에 두 번. 뒤의 두 번은 **압축 파일·`SHA256SUMS`·`PACKAGE_INFO.json`·묶음 파일 145개(정보 파일 포함)가 바이트까지 같았다**(세 번 모두 점검 문제 0건). 기준선을 합친 직후의 D2 갈래 기록(2026-11-22, 다른 커밋)과 견주면 정보 파일을 뺀 묶음 파일 144개 중 143개가 한 바이트도 다르지 않았고 다른 하나는 `ocr_worker.exe` 였는데, 달랐던 바이트 8개는 모두 PE 머리의 시각 칸 둘(빌드한 때가 아니라 커밋 시각을 쓰는 `SOURCE_DATE_EPOCH`)과 그에 딸린 검사합이었고 그 exe 안에 묶인 항목 10개는 모두 같았다(정보 파일은 커밋·커밋 시각 칸만 달랐다). 고지문에 절을 더한 코드를 기준선과 견주면 달라진 묶음 파일은 고지문과 `ocr_worker.exe`(같은 이유) 둘뿐이었다. 그래서 **커밋이 바뀌면 압축 파일 해시가 바뀌는 것이 정상**이고, 정확한 값은 이 문서에 적지 않는다(만들 때마다 다르다).
- **2차 라운드의 빌드 둘**(값 모양 문 D-577 을 더한 최종 코드, 2026-11-23, 이 PC, 같은 입력 — 2026-11-23 감사 후속으로 위 열거에 덧붙였다): 새 커밋에서 한 번, 앞 최종 빌드의 커밋 시각을 `SOURCE_DATE_EPOCH` 로 고정해 한 번 더 돌렸다 — 둘 다 점검 문제 0건·파일 144개·산출물 점검 통과·앱의 추가 도구 확인 ok 였다. 새 커밋에서 돌린 쪽은 앞 최종 빌드와 고지문이 바이트까지 같았고 묶음 파일 144개 중 143개가 같았으며 `ocr_worker.exe` 하나만 달랐다(PE 머리의 시각 칸과 검사합 — 커밋 시각이 달라서). 시각을 고정한 쪽은 144개 모두 바이트까지 같았다(정보 파일은 `source.commit` 칸과 시각 근거 칸만 다르다). 위 합친 빌드의 세 번에 더한 두 번이며, 정확한 해시와 바이트 수는 이 문서에 적지 않는다.

## 6. 개발자가 이 PC 에서 돌려 보는 법

러너와 같은 순서이고 네트워크는 쓰지 않아도 된다(휠 폴더와 받아 둔 모델이 있으면):

```text
python -m venv ..\ocr-build-venv
..\ocr-build-venv\Scripts\python -m pip install --require-hashes --only-binary=:all: -r ocr_addon/requirements-ocr.lock
..\ocr-build-venv\Scripts\python -m pip install --require-hashes --only-binary=:all: -r ocr_addon/requirements-build.txt
python ocr_addon/fetch_models.py --dest ..\ocr-models
..\ocr-build-venv\Scripts\python ocr_addon/build_ocr_addon.py all --out-dir ..\ocr-out --models-dir ..\ocr-models --require-clean
python ocr_addon/verify_release.py --release ..\ocr-out\release
```

- 휠을 미리 받아 둔 폴더가 있으면 첫 두 줄에 `--no-index --find-links <폴더>` 를 더한다(해시 검사는 그대로 한다). 이것은 시험·재현용이고 흐름은 온라인 설치다.
- `--out-dir` 는 비었거나 이 도구가 만든 폴더(표지 파일 `.chanceblog-ocr-out`)여야 한다(아니면 아무것도 지우지 않고 거절).
- 앱 없이 단위 시험: `python -m unittest test_ocr_addon_build_rules test_ocr_addon_fetch test_ocr_addon_build_flow test_ocr_addon_verify_release test_package_ocr_workflow test_workflow_yaml_support test_ocr_addon_merged_flow test_ocr_addon_notices test_ocr_addon_build_check`(tests 폴더에서). pefile 이 있는 환경에서만 도는 시험은 없으면 건너뛴다.

## 7. 핀 갱신 정책

- **언제**: 분기마다, 또는 쓰는 패키지에 보안 공지가 있을 때.
- **어떻게**: 새 판 후보는 **PyPI 업로드 14일 뒤에** 받는다(갓 나온 판은 쓰지 않는다 — 이 규칙은 `requirements-ocr.meta.json` 의 업로드 날짜와 시험이 지킨다). 후보로 합성 사진 27장을 읽어 줄·글자·확신도·상자가 지금과 같은지 견주고(a 단계 도구 `compare_dumps.py`, 운영자 PC 의 시제품 폴더에 있다 — 저장소에는 없다), 다르면 채점기로 글자 오류율과 줄 재현율을 재서 정한다. 같은 일을 `rapidocr` 를 올릴 때는 `--selftest` 의 `requests` 표기와 같은 글 시험을 다시 한다(가짜 `requests` 가 `rapidocr` 가 가져오기만 하고 부르지 않는다는 사실에 기대므로).
- **고칠 곳**: `requirements-ocr.lock`(해시 포함)·`requirements-ocr.meta.json`(날짜·휠 이름·크기)·필요하면 `models.lock.json` 과 앱 `service/ocr_addon.py` 의 박은 값 — 시험이 이 값들이 서로 같은지 본다. 핀을 올리면 `tests/test_ocr_addon_build_rules.py` 의 잠금 시험이 박아 둔 현재 판(numpy 2.5.4·rapidocr 3.10.0·onnxruntime 1.31.1·requests 2.34.2)과 가장 어린 핀의 나이도 일부러 빨개지므로 **같이 고친다**(첫 갱신 때 놀라지 않게 적어 둔다).

## 8. 라이선스 고지 — 정해짐(운영자 확인 030 ②, 2026-11-22) · 법률 자문이 아니다

- 휠 메타데이터 기준 표기는 Apache-2.0·MIT·BSD 계열·MPL-2.0(`tqdm`)이다. 메타데이터 밖의 사실: `shapely` 휠에 GEOS(LGPL-2.1 — 별도 DLL)가 들어 있어 최종 묶음에도 있다. opencv 휠의 FFmpeg 는 묶음에서 뺐다(재배포 의무 대상에서 뺌).
- 모델 2개·사전은 저장소 카드의 태그가 Apache-2.0 이고 카드 본문은 사실상 비어 있다(원본 PaddleOCR 의 라이선스 본문은 확인하지 못했다).
- **글자 사전의 출처**: `ocr_addon/data/ppocrv5_korean_dict.txt`(11,945줄·47,451바이트·SHA-256 `a88071c6…`)는 모델 저장소가 아니라 원본 Paddle 저장소 `PaddlePaddle/korean_PP-OCRv5_mobile_rec` 커밋 `c02ecaf1…` 의 `inference.yml`(96,039바이트, git blob `ba8f60f3…`)에서 `character_dict` 목록을 PyYAML 로 읽어 한 줄에 한 글자씩 적은 것이다(순서·내용 그대로 — 받아 둔 원본과 직접 견주어 확인했다). 라이선스 근거는 그 저장소 카드의 태그(apache-2.0)뿐이다. 이 기록은 `ocr_addon/data/ppocrv5_korean_dict.provenance.json` 에 있고(저장소에만 있고 묶음에는 들어가지 않는다) 시험이 모양과 잠금 값과의 일치를 지킨다. 고지문(`THIRD_PARTY_NOTICES.txt`)의 [5] 절이 사전의 출처(저장소·커밋·파일)를 적는다(아래). 상류 사전에는 사설 영역 글자 U+F8FF 가 한 개 있다(모델 출력 클래스와 한 칸이라 그대로 둔다).
- **정해진 방식(운영자 확인 030 ②, 2026-11-22)**: GEOS(LGPL-2.1)의 의무는 **고지문과 소스 안내문을 추가 도구 폴더에 넣는 방식**으로 지킨다. **원본 소스 압축 파일은 넣지 않는다**(새로 내려받지 않는다).
  쉬운 말로: `ocr` 폴더 안에 ① `licenses` 폴더(라이선스 전문)와 ② `THIRD_PARTY_NOTICES.txt`(어떤 부품이 들어 있고, 각각 어떤 라이선스이며, 소스는 어디서 받을 수 있는지)가 **같이 들어 있다**. GEOS 는 `_internal` 안 `Shapely.libs` 에 **따로 있는 DLL 파일**이다(다른 부품과 하나로 합쳐 굳히지 않았다) — 그래서 같은 버전의 GEOS 파일로 바꿔 끼울 수 있다.
  이 두 가지는 빌드 스크립트가 묶음 폴더에 만들고(빌드 스크립트의 `notices` 단계 — B1 갈래의 만들기 코드를 이 가지에 합치면서 **점검 앞**으로 옮겼다: 점검의 금지 이름·키 모양 훑기가 이 파일들도 보고(`licenses/` 아래는 확장자가 없어도 훑는다) 정보 파일의 파일 목록에 들어간다. GEOS 기록은 묶음 밖 `geos.json` 으로 남겨 정보 파일 단계가 읽는다), 정보 파일의 파일 목록과 압축 파일에 그대로 실리며(앱의 폴더 확인도 모르는 파일이 아니라고 읽는다), 빌드 흐름의 **산출물 점검**(4절)이 압축 파일 안에 실제로 있는지 확인한다.
  **정정**: 이 문서의 앞선 판은 '병합 전에 운영자께 따로 여쭙는다·지금 묶음에는 고지 폴더가 없다' 고 적었다 — 확인 030 ② 로 방식이 정해졌으므로 위와 같이 바로잡는다(방식 말고 구성요소별 고지 문구의 내용은 고지 파일을 만드는 쪽이 적는다).
- **고지문의 모델·글자 사전 절([5])과 GEOS 바꿔 끼운 뒤 주의**(2026-11-23, 독립 점검 W1 의 R5·R6): 고지문 `THIRD_PARTY_NOTICES.txt` 의 [5] 절은 검출 모델·한국어 인식 모델·글자 사전마다 파일·크기·SHA-256·출처(Hugging Face 저장소·커밋·파일)·라이선스 표기(저장소 카드의 license 태그 — 지금은 셋 다 `apache-2.0`. 철자는 카드 태그 원문 그대로 소문자이고, 이 문서의 `Apache-2.0` 도 같은 라이선스 Apache License 2.0 을 가리킨다)를 적고, 근거가 그 태그뿐이며 원본 PaddleOCR 라이선스 본문은 확인하지 못했다는 사실과 `licenses` 폴더에 이 모델·사전 전용 전문이 없다는 사실을 함께 적는다. 값은 빌드가 `models.lock.json` 과 사전 출처 기록(`ocr_addon/data/ppocrv5_korean_dict.provenance.json` — 읽기만 하고 묶음에 복사하지 않는다)에서 그대로 옮기고, 빠졌거나 모양이 다르면 — 사전 출처 기록이 잠금 파일의 사전과 다른 파일의 기록이어도 — 점검 앞에서 빌드가 멈춘다(조용히 건너뛰지 않는다). 시각이 없고 차례가 고정이라 같은 입력은 같은 글이다. [2] 절에는 GEOS 파일을 바꿔 끼우면 `OCR_INFO.json` 의 `files` 목록에서 그 파일의 항목(`bytes`·`sha256`)도 새 파일에 맞게 고쳐야 앱이 받아들인다는 한 줄을 더했다(앱은 정보 파일과 크기·SHA-256 이 다른 파일이 하나라도 있으면 추가 도구를 쓰지 않는다 — 시험이 앱 쪽 확인으로 이 말이 사실임을 본다).

## 9. 본체 점검과의 부딪침 (사실표)

본체 묶음 점검(`packaging/build_package.py` 의 `bundle_problems` 등)은 **본체 묶음 폴더에만** 돌고 이 빌드는 돌리지 않는다. 같은 점검을 이 묶음에 일부러 돌려 본 결과(합치기 전 a 단계 묶음 106개 파일):

| 본체 점검 | 이 묶음에 걸리는가 | 어떻게 다루었나 |
|---|---|---|
| 필수 파일(`ChanceBlogDesktop.exe`·`VERSION`·`vendor`·Qt 파일 4개) | 8건 — 다른 묶음이라 당연하다 | 별개(이 묶음용 규칙은 `build_rules.py`) |

| 금지 이름·확장자(`.pem` 등) | 0건 — 가짜 `requests` 방식이라 `certifi` 가 묶음에 없다 | 이름 목록을 읽기 전용으로 가져다 쓴다 |

| OpenSSL·QtNetwork 금지 | 해당 없음 | 이 묶음의 R3 가 OpenSSL 계열을 따로 막는다 |

해결 제안(별도 변경, 이번 일 밖): 없다 — 두 점검이 서로 방해하지 않는다. 다만 **본체가 이 빌드에 빌려 준 함수의 이름·동작이 바뀌면** 이 빌드가 멈추므로(시험이 알린다) 본체 `packaging/` 를 고칠 때 이 문서 4절의 목록을 같이 본다.

- **PyInstaller 호출 방식**(S 의 SN-5): a 단계·B1 의 `-I`(격리) 대신 본체 빌드와 같은 `-s` 에 환경 정리(`PYTHONPATH`·`PYTHONHOME`·`PYTHONSTARTUP`·`PYTHONINSPECT`·`PYTHONOPTIMIZE` 삭제, 좁힌 PATH)로 부른다 — 한 도구에서 두 방식이 갈라지지 않게 본체와 같은 함수를 쓴 것이다(D-530).
- **비용·한도**(S 의 SN-8): Windows 러너 사용 시간(제한 45분, 본체 Package 는 30분)과 아티팩트 약 85MB 를 14일 보관한다 — 개인 저장소면 사용 시간·저장 용량 한도에 닿을 수 있다. 수동 실행만이라 폭주 위험은 없다.
- **워크플로 규칙 검사의 작은 YAML 읽개**(독립 검증 S 의 SP-6·SN-16·SN-17, Q 의 ΔQ-1): `tests/workflow_yaml_support.py` 는 표준 라이브러리만 쓰고(앱 CI 에 PyYAML 이 없다) **쓰는 표기만 읽는다** — 흐름식·앵커·별칭·태그·병합 키·여러 문서·탭·겹친 키·접은 글은 거절하므로 `package-ocr.yml` 하나에만 쓴다(`ci.yml` 의 `[…]` 같은 표기는 읽지 못해 거절한다 — 다른 워크플로에 쓰려면 읽개를 넓히거나 표기를 바꾼다). 줄 나눔처럼 읽힐 수 있거나 보이지 않는 글자(`U+000B`·`U+000C`·`U+001C`에서 `U+001F`·`U+0085`·`U+2028`·`U+2029` 와 유니코드 범주 제어·서식(제로폭·방향 제어)·줄/문단 구분·사설 영역)는 **주석·`name:` 값·키·따옴표 글·블록 글 어디에 있든 거절한다** — YAML 1.1 계열 파서는 `U+0085`·`U+2028`·`U+2029` 를 줄 나눔으로 읽어서, 주석 안의 그 글자 뒤에 숨긴 단계를 PyYAML 은 단계 12개(기준선 11)로 읽는데 이전 검사기는 못 봤다. GitHub 서버의 실제 파서가 같은 줄 나눔을 하는지는 네트워크 금지로 확인하지 못했다 — 추측이지만 안전한 쪽으로 막았다. 입력 상한: 글 전체 10만 글자·한 줄 1000글자·중첩 깊이 24(진짜 파일은 약 3,700글자·가장 긴 줄 221글자·깊이 7 안팎) — 긴 공백 줄의 제곱 시간과 깊은 중첩의 `RecursionError` 를 빠른 거절로 바꾼다. 주석과 `name:` 값은 이 글자 규칙 밖에서는 자유 글이다(구조 규칙은 단계의 키·명령·`with` 를 정해진 글과 견주고 `name` 은 비어 있지 않은지만 본다).
- **두 번째 문(산출물 점검)의 이름 기반 판정의 한계**(S 의 SN-18): 빌드와 같은 범위라 한 단계 더 깊은 곳의 순수 파이썬 폴더(`_internal/pkg/urllib3/`)·이름을 바꾼 OpenSSL(`crypto3.bin`)·이름을 바꾼 기본 모델(`det.bin`)·확장자를 바꾼 깊은 `dll`·중첩 압축 안의 금지 파일·PYZ 안에 묶인 순수 파이썬 모듈은 못 본다(마지막 것은 빌드의 PYZ 목록과 R4 기록 몫). MZ 머리로 실행 파일을 고르기·중첩 압축의 안쪽 이름 훑기는 선택 강화로 남겼다.

## 11. 켜기 전에 정할 일 — 사실과 질문 후보 (운영자에게 보내는 일은 총괄 몫)

AI 독립 점검(OCR-W1, 2026-11-23)이 모은 사실을 정리한 것이고 **법률 자문이 아닙니다.** 아래 질문은 운영자에게 물을 **후보**이며, 질문을 운영자에게 보내는 일은 총괄 몫입니다(이 문서를 고친 구현자는 보내지 않습니다). 글자 읽기는 아직 꺼져 있고(`LOCAL_OCR`), 아래는 모두 **켜기 전에** 정할 일입니다.

1. **GEOS 소스 제공 방식** — 사실: 고지문 [2] 절의 소스 안내는 GEOS 프로젝트 공식 사이트의 호스트 이름과 '같은 버전 소스를 받으세요' 뿐이고, 판 별 주소·배포자가 직접 소스를 주겠다는 서면 제안(기간·비용 문구)은 없다. 원본 소스 압축 파일은 확인 030 ② 에 따라 넣지 않았다. 질문 후보: 호스트 이름 안내로 충분하다고 보는가, 판 별 주소나 서면 제안 문구를 더할까.
2. **바꿔 끼우기와 앱의 파일 확인** — 사실: 고지문은 GEOS 가 별도 파일이라 같은 이름의 호환 판으로 바꿔 끼울 수 있다고 하지만, 앱은 정보 파일과 크기·SHA-256 이 다른 파일이 있으면 추가 도구를 쓰지 않는다. 그래서 바꾸는 사람은 `OCR_INFO.json` 의 그 항목도 고쳐야 하고, 그 방법을 고지문 [2] 절에 한 줄 더했다. 질문 후보: 안내문 한 줄로 충분한가, 아니면 앱 쪽 방식을 바꿀까(앱 소스 변경이라 승인이 필요한 일).
3. **앱 약관·라이선스 문구** — 사실: LGPL-2.1 이 요구한다고 이 저장소 문서(`ocr_addon/README.md`)가 적은 '앱 약관이 디버깅용 리버스 엔지니어링을 막지 않기' 는 앱 약관 문구의 몫인데, 이 앱에는 자체 약관·라이선스 문구가 없고 앱 자체 라이선스도 정해지지 않았다(`ocr_addon/README.md`·`PACKAGE.md` 8절). 질문 후보: 언제 정할까(추가 도구를 처음 켜기 전에 정한다고 적혀 있다).
4. **공개 저장소의 산출물 14일 보관과 '개인 PC 제한'** — 사실: 이 저장소는 공개이고(`SECURITY.md` 첫머리) 올린 산출물은 14일 보관된다. 공개 저장소의 Actions 산출물은 로그인한 다른 GitHub 사용자도 받을 수 있는 구조가 일반적이다(AI 가 확인하지 못했다 — 운영자가 저장소 설정으로 확인할 일). '개인 PC 제한 시험용' 은 약속이지 접근 통제로 확인된 것이 아니다(10절의 비용·한도 문장은 개인 저장소 기준이다). 질문 후보: 이 약속으로 충분한가, 산출물을 운영자만 받도록 막거나 보관 기간을 줄일까(저장소 설정 변경이라 승인이 필요한 일).
5. **모델 고지** — 사실: 고지문의 [5] 절이 모델 2개·글자 사전의 이름·출처·라이선스 표기(저장소 카드 `apache-2.0`)와 '원본 PaddleOCR 라이선스 본문은 확인하지 못했다' 를 적는다(8절). 묶음의 `licenses/rapidocr/MODEL_LICENSES.md` 는 rapidocr 가 기본으로 싣는 모델(PP-OCRv6 small 검출·인식과 옛 방향 분류 모델)에 관한 글인데 그 세 파일은 이 묶음에서 뺀 것이고, 이 묶음에 든 PP-OCRv5 모델 2개에 관한 글이 아니다(2026-11-23, 이 PC 의 가상환경에 설치된 rapidocr 3.10.0 의 파일을 읽어 확인). 질문 후보: 지금 표기로 충분한가, 원본 PaddleOCR 라이선스 본문(Apache-2.0 사본과 NOTICE 유무)을 확인해 고지문에 더할까.
